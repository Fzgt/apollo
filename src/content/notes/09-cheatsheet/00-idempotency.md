# 幂等在四个场景里的四种实现

> Day 7 当日附加，**Day 14 Round 3 必考**。四个场景来自四个不同项目——这题答好了能一次证明「**我理解的不是某个库，是这个问题本身**」。

## 先立住一句话

> ⭐ **exactly-once 在跨系统场景下不存在。能做到的是 at-least-once 加上幂等消费。**
>
> 所以真正的问题从来不是「怎么做到恰好一次」，而是「**重复来自哪里，以及这个业务宁可重复还是宁可丢失**」。

## 四个场景对照

| 场景 | 重复来自哪 | 怎么做到幂等 | 在哪一层 | 局限 |
|---|---|---|---|---|
| **Beyz 重叠生成** | 语音 UtteranceEnd 自动触发 + 用户手动点击，**两条路径互不知情** | 四态机 + `statusRef.current === Generating` **直接丢弃** | **客户端状态机** | 只挡本地；刷新、另开标签页都挡不住 |
| **Stripe webhook** | Stripe 的**至少一次投递** + 网络重试 | **写绝对值而非增量**（`set({subscribedPlan: plan})`），重复投递结果一样；发邮件另用 `emailTracking` 表显式去重 | **应用逻辑 + 一张去重表** | ⚠️ **没有 event id 去重表**，重复投递会重复执行，只是结果收敛。**照实说** |
| **百度提现** | 用户连点、网络超时重试、**刷新后再点** | 前端：请求锁 + **幂等 key 提前生成存 sessionStorage**；后端：**幂等 key 建唯一索引** | **数据库约束** | 前端那层能被绕过，**真正的保证只在唯一索引** |
| **Beyz 邮件 cron** | 每分钟跑一次，**崩在发信和记账之间会重发** | `leftJoin` + `isNull` 的 **anti-join**：只挑「还没有提醒记录」的用户 | **一张状态表** | ⚠️ `select` 和 `insert` 之间没锁，**两个实例并发会各发一封** |
| **Periplus resume** | 崩溃后从上一个 gate 重跑 | replay 边界是**通过了 gate 的产物**；没过 gate 的留着供检查但**永远不是合法边界** | **产物 + 阶段契约** | 一个 gate 都没过就死掉的 run 无从恢复 |

## 归纳成三层（这才是答案的骨架）

**被问到时不要逐个场景背，先给这三层，再举例子。**

| 层 | 手段 | 强度 | 例子 |
|---|---|---|---|
| **1. 客户端** | 状态机丢弃、请求锁、Promise 去重 | 最弱——**只减少无效请求，不提供保证** | Beyz 四态机、提现请求锁 |
| **2. 应用逻辑** | **写绝对值而不是增量**、anti-join 挑未处理项 | 中等——**重复执行但结果收敛** | Stripe webhook、邮件 cron |
| **3. 数据层约束** | **唯一索引**、`WHERE` 里的业务不变量 | 最强——**并发和乱序都挡得住** | 提现幂等键、`ne(Lifetime)`、`balance >= ?` |

> ⭐ **贯穿三个项目的同一个模式：把不变量放在数据层，不放在应用层的 if 里。**
>
> ```sql
> ne(users.subscribedPlan, Lifetime)      -- Stripe：终身档不可被降级
> WHERE balance >= ?                       -- 百度提现：余额不会被扣成负
> UNIQUE(idempotency_key)                  -- 幂等键：并发插入只有一个能成功
> ```
> **它们跟「谁调用的、并发几次、事件什么顺序到」完全无关**——这是应用层的 if 永远做不到的。

## 「宁可重复」还是「宁可丢失」

**跨系统操作没有原子性，只能二选一。选哪个由业务决定：**

| 业务 | 选择 | 理由 |
|---|---|---|
| 营销/提醒邮件 | **宁可重复** | 多收一封是骚扰；收不到是丢一次转化 |
| 付款通知、密码重置 | **宁可丢失** | 重复发付款成功会让用户以为被扣两次 |
| 资金扣减 | **都不能** | 所以必须上第 3 层——数据库约束 + 事后对账 |

## 最后一层：对账

**前三层是「让它不发生」，对账是「发生了也能发现并补回来」。**

> **真正的零资损靠的是对账兜底，不是前三层做到完美**——网络会抖、渠道会超时、人会写 bug。详见 [#8 · 零资损](/docs?section=baidu&item=withdrawal)。

## 一句话答法

> 幂等这件事我在四个地方处理过，但手段分三层：**客户端的状态机和请求锁最弱，只减少无效请求；应用层靠写绝对值或者 anti-join，重复执行但结果收敛；最强的是数据层约束——唯一索引、`WHERE balance >= ?`、`ne(Lifetime)` 这类写在 SQL 里的不变量，它跟谁调用、并发几次、事件什么顺序到完全无关。** 而 exactly-once 跨系统本来就不存在，能做到的是 at-least-once 加幂等消费，**所以真正要判断的是这个业务宁可重复还是宁可丢失**——营销邮件宁可重复，付款通知反过来，涉及钱的两个都不能选，那就必须上数据库约束再加事后对账。

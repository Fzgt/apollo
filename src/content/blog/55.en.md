---
title: SSE (Server-Sent Events) — an HTTP Response That Never Ends
---

> SSE always felt mysterious to me. It is actually the crudest of the real-time options: **an HTTP response that never ends.** Absorb that sentence and everything else is detail.

## 1. What it actually is

An ordinary HTTP request looks like this:

```
Browser: give me /api/data
Server:  here is the content… (done writing) … end
         ↑ the response is over and the connection can close
```

SSE changes only the last step:

```
Browser: give me /api/stream
Server:  here is the first chunk…
         (does not end; holds it open)
         here is the second chunk…
         (still does not end)
         here is the third chunk…
```

⭐ **The server writes half a response body, stops there without closing, and writes some more a while later.** The browser hands each piece to you as it arrives, without waiting for the response to finish.

**No new protocol, no handshake upgrade, no binary frames.** You can watch it with `curl`, and any ordinary HTTP server can implement it.

#### How is that different from downloading a large file?

Mechanically it is not — both are chunked transfer. **The difference is the convention.** SSE specifies the response header `text/event-stream` and a minimal format for splitting the body into messages, so the browser knows to notify JavaScript on each piece rather than accumulating it as a download.

## 2. What the raw response looks like

This is the thing worth seeing once; after that there is no mystery left:

```
HTTP/1.1 200 OK
Content-Type: text/event-stream
Cache-Control: no-cache
Connection: keep-alive

data: first message

data: second message

data: this message
data: spans two lines

: this line is a comment, used as a heartbeat; the client ignores it

```

⭐ **Three rules**: every line is `field: value`; **a blank line ends a message** (so `\n\n`); a line starting with `:` is a comment.

**That is all.** Writing an SSE server by hand in Node takes under ten lines.

#### The four fields

| Field | What it does |
|---|---|
| `data:` | The message body. **One message can span several lines; the client joins them with `\n`** |
| `event:` | The message type. Without it, the type is `message` |
| `id:` | This message's number — ⭐ **used on reconnect; see section 4** |
| `retry:` | Tells the browser how many milliseconds to wait before reconnecting |

**Note that `data:` can only be text.** To send an object you `JSON.stringify` it and `JSON.parse` on receipt. **Binary is impossible** — which matters later.

## 3. The browser side

```js
const es = new EventSource('/api/stream');

es.onmessage = (e) => console.log(e.data);   // a data: line arrived
es.onerror = () => { /* the browser reconnects on its own; this is usually just a notice */ };

// if the server sent event: progress
es.addEventListener('progress', (e) => console.log(e.data));

es.close();   // close deliberately; after this it will not reconnect
```

**Five lines and you are done.** But `EventSource` has three hard limits, and **these three are why many projects end up not using it**:

1. ⭐ **GET only** — you cannot POST a request body
2. ⭐ **No custom headers** — meaning **no `Authorization: Bearer xxx`**. You are left with cookies, or putting the token in the query string (poor: it ends up in logs)
3. **Text only**

**The way around it**: skip `EventSource`, use `fetch` to get the response body as a stream, and parse the format yourself. That gives you POST, headers, and binary — at the cost of **writing your own reconnection** (see the next section). `@microsoft/fetch-event-source` exists to do exactly this.

## 4. The one thing SSE really adds over a raw stream

If all you want is "the server keeps pushing data", `fetch` plus a stream reader does it. **So what does SSE actually give you?**

⭐ **Automatic reconnection with resumption.**

```
The server puts an id on each message:

    id: 1042
    data: message 1042

the network drops
  → the browser waits 3 seconds (or whatever retry: specified) and reconnects
  → ⭐ the reconnect request automatically carries a header: Last-Event-ID: 1042
  → the server reads it and knows to resume from 1043
```

⭐ **All of that is built into the browser and costs you no code at all** — whereas reading a stream with `fetch` means implementing reconnection, backoff, and resumption yourself.

**This is SSE's reason to exist.** Without needing it, SSE is barely different from a `fetch` that never finishes.

## 5. Compared with the alternatives

| | Direction | Connection | Auto-reconnect | Binary | Complexity |
|---|---|---|---|---|---|
| **Polling** | Request/response | A new request each time | — | ✅ | Lowest |
| **Long polling** | Request/response (the server just holds the answer) | A new request each time | — | ✅ | Low |
| **SSE** | ⭐ **Server → client only** | One long connection | ⭐ **Built in** | ❌ | Low |
| **WebSocket** | ⭐ **Both ways** | One long connection | ❌ write it yourself | ✅ | Medium |

#### Choosing comes down to two questions

**① Does the client need to keep sending data upward?**
Yes → **WebSocket**. SSE is one-directional; anything going up needs a separate HTTP request, which means **two mechanisms maintaining one logical data flow**.

**② Do you need binary?**
Yes → **WebSocket**. SSE is text only.

**Neither, and SSE is the answer** — simpler, less to worry about (free reconnection), and it **passes through proxies and firewalls naturally** because it is just HTTP. WebSocket's `Upgrade` handshake gets blocked on some corporate networks.

## 6. The four things that bite in practice

**① Proxy and gateway buffering, so nothing actually streams**

⭐ **The most common way this goes wrong**: fine in development, then in production every message **arrives at once at the end**. Reverse proxies like Nginx buffer a response before forwarding by default.

```
add_header X-Accel-Buffering no;   # tell Nginx not to buffer this response
proxy_buffering off;
```

**② Compression also buffers**

gzip has to accumulate a batch before it can compress. So SSE responses usually **turn compression off**, or make sure every write is flushed.

**③ HTTP/1.1 allows only six connections per domain**

⭐ **One SSE stream occupies one of them for as long as it lives.** Open three tabs and three are gone, leaving three for every other request — and the page mysteriously stalls. **HTTP/2 does not have this problem** (multiplexing), so using SSE today essentially requires HTTP/2.

**④ Middleboxes cut connections that look idle**

After a quiet spell, a proxy or load balancer may decide the connection is dead and close it. **The fix is a periodic comment line as a heartbeat:**

```
: ping
```

⭐ **The client ignores comment lines, but the bytes really did cross the wire, so the connection is not idle.** Same idea as a WebSocket keep-alive frame.

## 7. Two cases from my own projects, one each way

#### The Beyz real-time interview assistant: **not** SSE; WebSocket

That path is: the browser **sends a chunk of audio every 250 milliseconds** while receiving the recognised text.

⭐ **It hits both of SSE's dead ends at once**: audio has to go **upward continuously** (SSE is one-way and cannot), and audio is **binary** (SSE is text only). It had to be WebSocket.

#### Streaming a model's answer: **looks like SSE, but there are two hops**

⭐ **OpenAI's HTTP endpoint is SSE** — capture the traffic and the format is identical:

```
data: {"choices":[{"delta":{"content":"He"}}]}

data: {"choices":[{"delta":{"content":"llo"}}]}

data: [DONE]
```

(Note that `[DONE]` is OpenAI's own end-of-stream convention, **not part of the SSE spec**.)

**But what our front end receives is not SSE.** We use the Vercel AI SDK's streaming response: the front end sends a **POST** (it has to carry the conversation history, which will not fit in a GET), the response body is a stream, and the front end consumes it with `for await...of`.

⭐ **So the accurate statement is: the model provider's hop is SSE; ours is a POST with a streaming response body.** Asked "is your answer streaming SSE?", the answer is "upstream yes, our hop no, because we need POST to carry the history" — **that distinction shows you have actually looked at the transport rather than heard a word.**

## 8. In one sentence

⭐ **SSE = an HTTP response that never ends, plus the convention that a blank line separates messages, plus free automatic reconnection and resumption from the browser.**

**It is one-way and text-only, and what you get in return is simplicity.** If you need to send upward or send binary, use WebSocket rather than forcing it.

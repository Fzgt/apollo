# Daily output standard

Every bullet needs at least four things:

1. **A 30-second plain version** — a non-technical recruiter can follow it. Lead with the user's problem and the result; do not pile up API names.
2. **A 2–3 minute STAR / technical version**
3. **A list of follow-up questions** — every one needs an answer, and anything unanswered gets marked on the spot
4. **At least one "why not the other approach"**

## The shape of the story

> Context → what I did → why I did it that way → how it works → trade-off → how the result was measured → what I would change if I did it again

## Before you start, from Day 8 on

Open the files on that day's "must read" list and finish reading them **before writing a word of the answer**. Every class name, enum value and file location in the answer has to match the code.

## Done means

- Any bullet can be told in plain language in 30 seconds
- An S-grade bullet runs 3–5 minutes without a script
- Every architectural choice has an alternative and a trade-off
- Every failure case has handling and a recovery path
- Every number has a source, a way it was measured, and a scope it can be attributed to
- **When talking about my own code, class names, enum values and file locations match the repository**
- From any sentence on the resume, I can go two levels deeper

## How the status field works

Each note has a `status` line in its frontmatter. Change it and the board on the overview page updates itself:

- `todo` — not started
- `doing` — working on it today
- `done` — all four outputs exist and the follow-up questions are answered

# 定时任务这条怎么答赢

> 🔴 **必看**。**按面试官会问什么组织**，每问：**事实（简短）→ 原理 → 生产级会怎么做**。第三段是赢的地方。

## 先定尺度：主动说小

**真实体量：402 行 TypeScript，16 个文件，三周，22 个提交全是你。**

**开场就说出来。** 你不说他迟早看出来（那时是被戳破），你先说，接下来每个技术判断都在可信区间里。

> 「这是个很小的服务，四百来行，三周做完，就我一个人。做的事很窄——每分钟扫一次库，给注册超过 24 小时还没付费的用户发一封升级提醒。**它的价值不在代码量，在于我一个人把它从零带到了线上**：容器化、定时任务、EC2 部署、CI/CD 全走了一遍。」

> `Sole author` 是字面真实的——22/22 提交都是你。

## Q：为什么单独一个服务

**事实**：主应用是 Next.js，部署在无状态平台上。**定时任务需要常驻进程**——一个自己醒来的东西，而 serverless 函数是被请求唤醒的。

**原理**：这是**按运行模型拆服务**，不是按业务域拆。收益是独立发版/重启/扩容（它的负载曲线和主站完全不同）；代价是多一套部署监控、**两边 schema 要同步**。

**生产级**：402 行的规模下自己养个 NestJS 合理，但这类任务变多我会换成——**云原生调度**（EventBridge Scheduler / Cloud Scheduler 触发函数，不养常驻进程）、**任务队列**（BullMQ / Temporal，有重试退避死信队列，这些我现在全是手写或没有）、以及最关键的**从轮询改成事件驱动**：注册那一刻就排一个 24 小时后的延时任务，根本不用扫库。

## Q：怎么保证同一封邮件不发两遍（最值钱的一问）

**事实**：幂等靠**一张表**，不靠调度频率。

```ts
// email.job.ts:24-37
.leftJoin(upgradeReminders, eq(users.id, upgradeReminders.userId))
.where(and(
  eq(users.subscribedPlan, 'Free'),
  lt(users.createdAt, twentyFourHoursAgo),
  isNull(upgradeReminders.id)        // ⭐ 只挑「还没发过」的
))
```

`leftJoin` + `isNull` 是 SQL 的 **anti-join**。发完写一条记录。

> **「已发过」是数据库里的一行，不是内存标志位、不是「上次跑到哪」的游标——所以重启、换机器、跑几次都不影响正确性。**

**原理：at-least-once vs at-most-once**（**这一问必须上到这个层次**）

发邮件跨**两个系统**（邮件服务商 + 数据库），**跨系统没有原子性**，只有两种排法：

| 排法 | 崩在中间 | 语义 |
|---|---|---|
| **先发后记**（我当时这样） | 邮件发了记录没写 → **重发** | **at-least-once** |
| 先记后发 | 记了已发送但邮件失败 → **永远收不到** | at-most-once |

> ⭐ **「exactly-once 在跨系统场景下不存在，能做到的是 at-least-once 加上幂等消费。」** 说出这句这一问就满分了。
>
> 所以真正的问题不是「怎么做到恰好一次」，是**「这个业务宁可重复还是宁可丢失」**——营销邮件宁可重复（多收一封是骚扰，收不到是丢一次转化）；付款通知反过来。

**生产级**：当时有两个洞——`select` 和 `insert` 之间**没有锁**（两个实例并发会各发一封）、崩在发信和记账之间会重发。四层做法：

| 做法 | 解决 |
|---|---|
| ⭐ **`userId` 建唯一索引** | 第二次 insert 违反唯一约束，**数据库层面挡住并发重复**。最便宜最可靠 |
| 先插「处理中」再发信 | 插入成功才拿到发送权（抢锁），**把二选一变成三态**，可重试可对账 |
| 给服务商传 `Idempotency-Key` | 把去重推到最后一层 |
| 调度层保证单实例 | 分布式锁或 singleton 调度器 |

> **唯一索引兜底这一招和 [Stripe webhook](/docs?section=beyz&item=n02-stripe-events)、[百度提现](/docs?section=baidu&item=n07-qps) 是完全同一个模式：把不变量放在数据层，不放在应用层的 if 里。** 三个项目串起来讲，是 Day 14 跨项目题的现成答案。

## Q：为什么 cron 定成每分钟

```ts
// @Cron(CronExpression.EVERY_DAY_AT_9AM)     ← 注释掉的
// @Cron(CronExpression.EVERY_10_MINUTES)     ← 注释掉的
@Cron(CronExpression.EVERY_MINUTE)
```

**幂等靠表不靠频率，所以频率不影响正确性，只影响触达延迟**——注册满 24 小时后最多一分钟收到。

**诚实的另一半**：对一个「24 小时后才发」的提醒，每分钟是**过剩的**；注释里从每天一路降到每分钟的痕迹，说明是调试时调下来忘了改回去。

**生产级**：**改成事件驱动，根本不轮询**——注册时排一个 24 小时后的延时任务。精确触发、不扫库、**用户量涨了也不会变慢**（轮询代价随用户数线性增长，延时任务 O(1)）。

## Q：为什么 Fastify 不是 Express

**事实**：`new FastifyAdapter()`（`main.ts:3,6`）。**NestJS 把 HTTP 层抽象成可替换的 adapter**，换 Fastify 只改这一行，controller/service/DI 全不动。

**原理**：路由用基数树匹配、序列化走预编译 JSON schema、schema 校验一等公民、插件有显式封装边界。

> ⚠️ **别吹性能。** 这服务的负载是「每分钟查一次库发几封邮件」，**吞吐差异根本体现不出来**。
>
> **赢的答法是主动否认自己本可以吹的点**：「这是选型题不是性能题。adapter 让切换成本几乎为零，Fastify 在 schema 和 swagger 上更顺手。**这个量级完全用不到它的吞吐优势，说它解决了性能瓶颈是不诚实的。**」

**NestJS DI 顺带**：`MailerService` 是**按类型**注入（Nest 从 TS 元数据读参数类型）；`@Inject('DATABASE_CONNECTION')` 是**按 token**——因为数据库连接不是类、是工厂造出来的对象，**没有类型可以匹配**。

## 一个该主动交代的疤

`app.controller.ts:17-28` 的 `@Get('trigger-cron')`：**它并不真的触发 cron**（只给写死的邮箱发测试邮件）、**没有鉴权**、**用 GET 做有副作用的操作**（浏览器预取、链接预览都可能意外触发）。

> 「这是当时留的调试口子，名字起得比它做的事大。上生产前应该删掉，或至少加鉴权并改成 POST。」
>
> **主动指出自己代码里的疤，收益比看起来大**：它证明你现在的标准高于当时的产出——**而面试官招的是现在的你。**

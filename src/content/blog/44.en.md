# Core concepts in agent engineering

## Hallucination

A model producing text that reads smoothly and sounds confident but is not grounded in any fact or source. It is not lying — when filling a gap, the model habitually picks the words that look statistically most like an answer rather than the words it has verified.

Summarising a document, a model will often fuse two sentences into one, change a digit in a number, or invent a detail the source never mentioned — and then put it in quotation marks as though it were verbatim. That is what makes hallucination dangerous: it does not write "I am not sure", it writes with more conviction than the truth.

This is exactly the value of Periplus's design: do not take the model's word that something is from the source. Force it to produce an evidence substring that can be compared character by character, and reject anything that does not match. This is the most practical engineering answer to hallucination available, and far more effective than asking the model "are you sure?" a second time.

## Structured output

**Structured output = the LLM no longer returns just a string; it returns an object conforming to a specified schema or `interface`.**

- Programs can parse and handle it reliably
- It can be validated against a schema
- Domain models like `Claim` and `Evidence` can be the LLM's output shape

---

## Tool calling

**Tool calling = the LLM does not only generate text; it can decide to call external tools for the task.**

For example:

- Web search
- Fetch page
- Weather API
- Route calculator
- Database

**Structured output decides *how* the AI outputs. Tool calling decides *what it can do*.**

---

## RAG

**RAG = retrieval-augmented generation.**

The flow:

user question → retrieve material → give the material to the LLM → the LLM generates from it

**RAG solves "get the relevant material in front of the AI".**

RAG is not the same thing as a vector database. Web search, database queries, and vector search can all be the retrieval step.

---

## Grounding

**Grounding = the AI's conclusions must trace back to real sources and evidence.**

For example:

Claim:
> The Prado Museum closes at 20:00 on Saturdays.

Evidence:
> "Monday to Saturday: 10:00–20:00"

Source:
> The Prado Museum's official website

**RAG solves "get the material to the AI".**

**Grounding solves "is the AI's conclusion actually built on that material".**

Never let the LLM be its own proof.

---

## Prompt injection

**Prompt injection = malicious instructions inside external content changing the agent's behaviour.**

When an agent reads web pages, emails, or documents, the text inside them must not be treated automatically as trusted instructions.

The risk is much higher once the agent can call tools.

---

## Guardrails

**Guardrails = putting rails around the agent.**

Guardrails are a whole category of mechanisms, not a particular library. For example:

- Restrict which tools the agent may use
- Cap the number of tool calls
- Restrict read and write permissions
- Schema validation
- Evidence validation
- Output validation

**Do not hand an LLM unlimited permissions just because it is clever.**

**The principle of least privilege matters a great deal in agent systems.**

It is also why multi-agent systems so often split the work:

Research agent → only research tools

Planner agent → only planning tools

Content agent → only content generation tools

---

## Eval

Ordinary code can usually be judged: input → a fixed output.

An LLM or agent's output is probabilistic and is not identical every time.

So: **use unit tests for the deterministic parts, and evals for probabilistic things like model quality.**

Unit tests can cover:

- URL normalisation
- Caching
- Schema validation
- Whether the evidence really appears in the source document

Evals can cover:

- Factual accuracy
- Evidence accuracy
- Hallucination rate
- Claim coverage
- Whether an itinerary makes sense
- Content quality

**Agent engineering = tests + evals.**

---

## Tokens

**A token is the LLM's basic unit for measuring text, and the key figure behind both cost and context capacity.**

More input and more output means:

→ more tokens
→ higher cost
→ usually higher latency too

So you cannot mindlessly stuff whole web pages into the model.

---

## Latency

**Latency = how long the user waits for the agent to finish.**

Serial multi-agent calls stack their latency up. Anything that can run in parallel should:

```
Research A ─┐
Research B ─┼→ Verification → Planner
Research C ─┘
```

---

## Cost

An agent system's cost comes mainly from:

- LLM tokens
- Search APIs
- Third-party APIs
- Compute and storage

Common optimisations:

- Caching
- Fewer pointless LLM calls
- Less context
- Parallel execution
- A cheaper model for the simple work

---

## Model selection

**Not every task should go to the strongest model.**

Different tasks can use different models:

Simple classification → a small model

Schema repair → a small model

Claim extraction → a mid-sized model

Complex planning → a strong model

Complex content generation → a strong model

This is usually called **model routing** or a **model strategy**, and the goal is a balance between **quality, cost, and latency**.

---

# How it all fits together

Tool calling → what the agent can do

RAG → find the agent its material

Grounding → make sure the conclusions rest on something real

Structured output → make the results safe for programs to handle

Guardrails → limit what the agent may and may not do

Prompt injection defence → stop external content from steering the agent

Eval → measure whether the agent is any good

Tokens / cost / latency → control the engineering cost

Model selection → the right model for each task

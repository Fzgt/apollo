title: 'Blobs, Binary Transfer, and Base64: When Do You Need to Encode?'
---

## The conclusion first

`Blob` and Base64 are not two file formats. They are concepts at two different levels:

- **Blob**: an object holding binary data in the browser's memory
- **Base64**: an encoding that turns binary data into ordinary text characters

The rule for choosing is one sentence:

> If the channel supports binary, send the Blob, ArrayBuffer, or bytes directly. Only consider Base64 when the channel accepts text alone.

Base64 is not compression and not encryption. It typically adds about a third to the size, so it should never be the default way to move data.

---

## 1. What does MediaRecorder produce every 250ms?

```ts
const recorder = new MediaRecorder(stream);

recorder.ondataavailable = (event) => {
  const audioBlob = event.data;

  if (audioBlob.size > 0) {
    socket.send(audioBlob);
  }
};

recorder.start(250);
```

The `250` in `start(250)` is the **timeslice**: the browser fires `dataavailable` roughly every 250ms, and `event.data` is a Blob.

Note:

- `250ms` is the time slice, not the Blob's size
- `blob.size` is the size, in bytes
- `blob.type` is the MIME type, e.g. `audio/webm;codecs=opus`
- The event loop and the encoder's buffering introduce error; there is no guarantee each chunk covers exactly 250ms

Several Blobs may each correspond to roughly 250ms of audio without containing the same number of bytes. The encoding format, bitrate, variable bitrate, and scheduling delay all contribute.

### How to think about a Blob

Blob stands for **binary large object**. Read it as:

> An immutable stretch of raw binary content in the browser's memory, plus a size and a MIME type.

Blob is not an audio-specific type. Images, video, PDFs, and any binary file can go in one.

```ts
console.log(audioBlob.size); // bytes
console.log(audioBlob.type); // audio/webm;codecs=opus
```

A `File` is a Blob with extra information — a filename, a modification time. In the browser's type hierarchy, `File` extends `Blob`.

The Blob MediaRecorder produces is usually not raw PCM samples but audio the browser has encoded and containerised:

```text
MediaStreamTrack
  → encoded by MediaRecorder
  → WebM / Opus or similar
  → Blob
```

## 2. Why can WebSocket send a Blob directly?

WebSocket supports both text and binary frames:

```ts
socket.send("hello");       // text frame
socket.send(blob);          // binary frame
socket.send(arrayBuffer);   // binary frame
```

Given a Blob, the browser reads its bytes and sends a binary frame. What travels over the network is not a JavaScript Blob object but the binary data the Blob contains.

So for real-time audio you can simply write:

```ts
socket.send(event.data);
```

There is no need to convert to Base64 first. That would turn the path into:

```text
Blob → read bytes → Base64 string → send as text
     → receiver Base64-decodes → bytes again
```

More bytes, more CPU, more memory, more latency.

---

## 3. What is Base64?

Base64 represents arbitrary binary bytes as a string of safe ASCII characters, drawn mainly from:

```text
A-Z  a-z  0-9  +  /
```

Each Base64 character has 64 possible values, so it carries 6 bits:

```text
2⁶ = 64
```

The input is grouped 3 bytes at a time:

```text
3 bytes = 24 bits
24 bits ÷ 6 bits = 4 Base64 characters
```

So:

```text
3 original bytes → 4 Base64 characters
```

Base64 typically adds about 33% to the size. The trailing `=` is padding to fill out the last group; it is not part of the content.

For example:

```text
Man → TWFu
Ma  → TWE=
M   → TQ==
```

### What Base64 is not

```text
Base64 ≠ encryption
Base64 ≠ hashing
Base64 ≠ compression
```

Anyone can decode it, so it cannot protect a password or an API key, and it is no substitute for HTTPS.

## 4. Which channels take binary directly?

Strictly speaking a channel does not "transfer a Blob object". The API accepts a Blob, reads it, and transfers its bytes.

| Channel / API | Binary? | How |
|---|---:|---|
| WebSocket binary frame | ✅ | `socket.send(blob)` |
| A raw HTTP request body | ✅ | `fetch(url, { body: blob })` |
| `multipart/form-data` | ✅ | `form.append("file", blob)` |
| XMLHttpRequest | ✅ | `xhr.send(blob)` |
| WebRTC DataChannel | ✅ | Send a Blob or ArrayBuffer |
| Object storage (S3, R2) | ✅ | Upload a Blob or stream |
| IndexedDB | ✅ | Store the Blob directly |
| `postMessage` | ✅ | Structured clone carries the Blob |

### HTTP is not text-only

An HTTP body can be arbitrary bytes. Whether Base64 is needed depends on the application-level format:

```text
application/json          → JSON has no binary type
multipart/form-data       → can contain file bytes directly
audio/webm                → the body can simply be the audio
application/octet-stream  → generic binary
```

Uploading a single Blob:

```ts
await fetch("/upload", {
  method: "POST",
  headers: { "Content-Type": blob.type },
  body: blob,
});
```

Uploading a file alongside fields:

```ts
const form = new FormData();
form.append("audio", blob, "interview.webm");
form.append("userId", "123");

await fetch("/upload", {
  method: "POST",
  body: form,
});
```

With FormData, do not set `Content-Type` by hand — the browser has to add the multipart boundary itself.

## 5. Which places accept text only?

| Channel / place | The limit | The usual choice |
|---|---|---|
| A JSON field | JSON has no binary type | Base64, or send a file URL instead |
| A URL query | A URL is text | Not for files; send an ID or URL |
| localStorage / sessionStorage | Strings only | Base64 for small data; IndexedDB for large |
| Cookies | Text, and very small | Not for files |
| HTML/CSS data URLs | Attributes and styles are text | Base64 for small assets |
| Native SSE `data:` | UTF-8 text events | Base64 for small data; change channel for large |
| A third-party API that only accepts strings | The schema | Base64, as the API requires |

### Why can't JSON hold a Blob?

JSON supports strings, numbers, booleans, null, arrays, and objects. There is no binary type:

```ts
JSON.stringify({ audio: blob });
```

The Blob's bytes are not serialised, and you usually get:

```json
{ "audio": {} }
```

If the API has to be JSON, it might be designed as:

```json
{
  "mimeType": "audio/webm",
  "audioBase64": "GkXfo59ChoEBQveBA..."
}
```

But a large file is better uploaded separately to object storage, with the JSON carrying the object key or URL.

### Why is localStorage unsuitable for a Blob?

localStorage stores strings only:

```ts
localStorage.setItem("audio", blob as unknown as string);
```

That does not store the Blob's contents; you get something like `[object Blob]`. When the browser needs to store binary locally, reach for IndexedDB.

### Why is SSE usually text only?

Native `EventSource` consumes UTF-8 text events:

```text
data: hello
```

A small amount of binary can be Base64-encoded first, but continuous audio or large files should not go this way — use WebSocket, an HTTP binary stream, or object storage.

---

## 6. When should you actually use Base64?

The typical cases:

1. An external API explicitly requires binary inside a JSON string
2. Embedding a very small image, font, or icon in HTML or CSS
3. An older text protocol that has to carry binary, such as some email attachment encodings
4. A storage location that only accepts strings, with data small enough not to matter

Do not reach for Base64 automatically just because something is an image or audio.

For large files or continuous streams:

```text
the client uploads to object storage directly
  → gets an object key / URL
  → the JSON carries only the reference
```

This is generally better than stuffing an entire file into Base64 JSON.

---

## 7. What Base64 costs

### 1. About 33% more bytes

```text
3 bytes → 4 Base64 characters
```

A 3 MB file becomes roughly 4 MB, before counting the JSON or data-URL prefix.

### 2. Extra CPU and memory

The sender encodes and the receiver decodes. On a large file the browser may hold the Blob, the ArrayBuffer, and the Base64 string at the same time, which raises the memory peak.

### 3. Streaming gets awkward

Base64 groups bytes in threes. Encoding several chunks independently produces padding and boundary problems, and the receiver has to know whether the chunks are independent or one continuous encoded stream.

### 4. It provides no security

Base64 is a reversible representation and hides nothing.

---

## 8. Quick reference

| Situation | Use |
|---|---|
| Real-time audio over WebSocket | Blob or ArrayBuffer directly |
| Uploading a single file over HTTP | The Blob as the raw body |
| Uploading a file with fields | FormData |
| A JSON API that must carry small binary | Base64 |
| Uploading a large image, audio, or video | Object storage; the JSON carries the URL or key |
| Storing a file in the browser | A Blob in IndexedDB |
| A little binary in localStorage | Base64, but prefer IndexedDB |
| A small icon embedded in HTML | A Base64 data URL |
| Continuous large binary over SSE | Don't; use WebSocket or a binary stream |

Three questions to settle it:

1. Does the API accept a Blob, ArrayBuffer, Uint8Array, or stream? If so, send it directly.
2. Is the message specified as JSON or a string? Only then consider Base64 — or switch to a file URL.
3. Is the data large or continuously produced? Then avoid Base64.

In one sentence:

> Base64 is a compatibility layer for when binary has no choice but to travel through a text channel. It is not the default way to move binary data.

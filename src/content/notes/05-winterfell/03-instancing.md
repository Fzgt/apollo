# ③ 合批渲染与它的代价

> **简历原句**
>
> **Cut draw calls from 129 to 76** by collapsing each obstacle field into **two instanced meshes**, **measured frame by frame in a headless Chromium harness**: **the cost is that off-screen obstacles can no longer be skipped one by one**.
>
> ---
>
> 把每一段障碍阵合并成两个实例化 mesh，draw call 从 129 降到 76 —— 由一个无头 Chromium 测量装置逐帧测得；代价是屏幕外的障碍不能再逐个跳过。

「提交的三角形涨了 2.6 倍」这个数不在简历上，代价那半句写成了大白话。但 2.6 倍仍要会答——它是「为什么绘制命令少了反而要交代代价」的关键一环。

## 先把词说清

**draw call（绘制调用 / 绘制命令）**：CPU 对 GPU 说一次「画这个东西」。**成本主要在 CPU 那一侧**，不在 GPU。

**CPU-bound / GPU-bound（受 CPU 限制 / 受 GPU 限制）**：瓶颈在哪一侧。**draw-call bound** 是 CPU-bound 的一种具体形态。

**instancing（实例化）**：同一个几何体、同一个材质的 N 个物体，只传一次几何体、把 N 个变换矩阵打包传过去，发**一次** draw call 画 N 遍。three.js 里的类是 `THREE.InstancedMesh`。

**frustum（视锥）**：相机能看到的那个截头金字塔形空间，近平面到远平面之间。

**frustum culling（视锥剔除）**：渲染前先判断物体在不在视锥里，不在就跳过，连提交都不提交。

**bounding volume（包围体）**：一个能装下物体的球或盒子，用来做廉价的粗略判断。**这条 bullet 的代价全出在这个词上。**

**vertex shader（顶点着色器）**：GPU 上对每个顶点跑一遍的程序。**极度并行。**

**headroom（富余产能）**：某个资源还没用满的那部分。

**headless（无头）**：没有界面窗口的浏览器，用脚本驱动，用来自动化测量。

## 这条要讲清什么

整份简历二十个数字，十九个是变好了，**这条里有一个是变差了**——而它恰恰最能加分，因为它证明你在报代价，不只是报收益。

这条 bullet 自己就把取舍写在句子里了。面试官读到这一句会认真起来，因为绝大多数简历只报收益。

## 为什么 draw call 是瓶颈

每发一次 draw call，图形驱动要做状态校验、可能要切换着色器和贴图和顶点缓冲、把命令打包送进队列。**这些全是 CPU 的活。**

典型的瓶颈长这样：场景里五百个方块，每个一次 draw call，每帧五百次 CPU 到 GPU 的提交，**CPU 忙不过来，GPU 反而在等**，帧率被 CPU 卡住而 GPU 占用率很低。

这种情况叫 **draw-call bound**。它的特征很好认：**你把模型面数砍一半，帧率纹丝不动**——因为瓶颈根本不在 GPU 算不算得过来。

## 实例化：一次命令画一万个

如果五百个方块用的是同一个几何体和同一个材质，只是位置、旋转、缩放不同，那完全没必要发五百次命令。把几何体传一次，把五百个**变换矩阵（transform matrix）**打包成数组传过去，发一次命令告诉 GPU 用这个几何体画五百遍，第几遍用数组里第几个矩阵。

three.js 里这个东西叫 **`InstancedMesh`**。

简历那句「合并成两个 instanced mesh」的意思是：每个区段原本几十个独立物体，合并成两个。**为什么是两个不是一个——因为实例化要求同几何体、同材质**，两个大概对应两类外观，面试时要能说出这两类分别是什么。两个网格共用同一份变换数据，同一批障碍物的位置只算一次、只上传一次。

## 测量的坑：两个后端的计数字段含义不一样

**这是这条最有含金量的地方。**

WebGL 渲染器里 `info.render.calls` 是「**这一帧**的绘制命令数」。而 WebGPU 渲染器里同名的 `info.render.calls` 却是「**从启动到现在**渲染函数被调用了多少次」——一个单调递增的累计值；它的每帧 draw call 在 `info.render.drawCalls` 里。而且 WebGPU 是异步渲染的，它自动的每帧清零不一定在你读取之前完成。

**三个坑叠在一起。**解法是三步：

```tsx
info.autoReset = false;                                   // ① 关掉自动清零

bench.push({
    drawCalls: render.drawCalls ?? render.calls ?? 0,     // ② 优先 WebGPU 字段，回退 WebGL
    triangles: render.triangles ?? 0,
    // ...
});

info.reset?.();                                           // ③ 采样完自己手动清零
```

这样每次读到的都恰好是一帧的量，**两个后端才可比**。

不知道这个坑的话，你在 WebGPU 下量出来的 draw call 会是一个从零一路涨到几万的数字，**而且你可能还会信它**。

能讲出「我发现两个后端的同名字段含义不同」，是**「真的量过」和「抄了段代码」的分水岭**。这句话本身就值得在面试里说出来。

同一个探针里还有一条值得说的：**帧时长超过 250 毫秒的帧单独记成 stall，不丢掉。**曾经把长帧静默过滤，结果一次软件渲染、每帧几秒的运行报出了稳定 120fps——因为只有那少数几个快帧活过了过滤器。

## 实验是怎么设计的

一共四个场景，是个**二乘二的受控实验（controlled experiment）**：渲染后端 × 实例化开关。WebGPU 开实例化、WebGPU 关、WebGL 开、WebGL 关。

三个 URL 开关各有用途：`?perf=1` 挂载性能探针，**只在带这个参数时挂载，正常访问零开销**；不死开关让飞行器不会撞毁；`?renderer=webgl` 关掉 WebGPU 走对照组。

**不死那个开关是关键设计**：它把**采样窗口（sampling window）**这个变量固定住了。没有它，采样会因为撞毁而中断，两组数据采集的赛道段落都不一样，比出来的差异就混进了场景差异。

采样方式是用 **Playwright** 启动一个无头浏览器，每个场景采样固定秒数，探针每帧记一条，最后取统计量。**129 → 76 报的是每帧 draw call 在采样窗口内的平均值。**

## 为什么报 draw call 而不是 FPS

测量脚本里有一个判断：如果一个场景的**帧率中位数超过 115**，就在报告里加一条警告，说这些场景顶在了**显示合成器（compositor）**大约 120 帧的上限上，帧率区分不了它们，请改看 draw call 和三角形数。

这不是在过滤数据，是在给报告加警告。逻辑是：**帧率这个指标已经饱和（saturated）了**，优化前后都是 120，看不出任何差别；但这不代表没有差别，只代表 GPU 还有富余、瓶颈还没到。

被问「为什么不报帧率提升」，答案就在这里——**报一个已经饱和的指标是自欺欺人。**

还有一条相关的警告：**无头浏览器里 WebGL 常常退化成软件光栅化（software rasterisation）**，也就是用 CPU 模拟 GPU。所以在这个环境里，**draw call 和三角形数是可信的**，因为它们是 CPU 侧的计数，渲染器记录自己提交了多少，跟有没有真 GPU 无关；而**帧时间和帧率是不可信的**。

主动说出这一条非常加分：它说明你清楚自己的测量环境边界在哪，只在有效范围内下结论。

## 按「审什么」逐条

探针是自己写的组件，每帧采样一次，只在 `?perf=1` 时挂载。同一台机器、同一个无头浏览器、同一分辨率，不死开关固定采样窗口，四个场景只差开关。报的是采样窗口内的每帧平均值。复现方式是起开发服务器再跑 `bench/` 下的脚本，需要 Playwright。归因是自己写的探针、自己搭的实验、自己跑的。

跑之前把具体命令、分辨率、采样秒数记下来——**这三个参数会影响结果**，尤其是分辨率，它决定 GPU 是不是真的被压满。

## 实例化为什么会杀掉视锥剔除

**这就是那个取舍的核心。**

优化前，场景里是 N 个独立物体，剔除是逐个判断的，视野外的一个都不提交。优化后，场景里只有两个 `InstancedMesh`，**整个区段共用一个包围体**，只要有一个实例在视野里，整批全部提交。

**关键一句话：剔除是按场景对象（scene object）做的，而实例化把 N 个对象合成了一个。**

于是一个区段里八十个方块、玩家只看得到最前面十个的时候，优化前剔掉七十个只提交十个的三角形，优化后包围体和视锥相交，**八十个全部提交**。GPU 会为那七十个不可见的实例跑完顶点着色器，然后在**裁剪阶段（clipping）**把它们丢掉——工作做了，画面上什么都没多。

这就是**提交的三角形涨到 2.6 倍**的原因，绝对数是从 **26,000 多涨到 69,000 多**。报比值的时候要能一并报出绝对值，被问「涨到多少」答不上来会显得只背了个倍数。

注意「**提交**」这个词用得很准：涨的是**提交给 GPU** 的三角形数，不是画面上多了三角形，**画面完全一样**。面试时要强调这一点，否则听起来像是画质变了。

## 那为什么这笔交易还是划算

**这是必答题**：draw call 降了四成，三角形涨了一倍半，凭什么说这是优化？

答案在于**两种成本的性质完全不同**：

**draw call 的成本花在 CPU 上**——驱动状态校验、命令打包、提交，基本串行，受驱动开销限制，成为瓶颈时的表现是 CPU 满 GPU 闲。

**顶点处理的成本花在 GPU 上**——顶点着色器，极度并行，几千个核同时算，成为瓶颈时的表现是 GPU 满 CPU 闲。

如果瓶颈在 CPU，那么少发 53 次 draw call 是**直接省下 CPU 时间**，多提交 1.6 倍三角形花的是 **GPU 的富余产能**。

**用一个瓶颈资源换一个非瓶颈资源——这就是这笔交易划算的全部理由。**而前面那条帧率饱和的提示正好佐证了 GPU 有富余：四个场景的帧率都顶在合成器上限上，测量脚本自己就说了在这个分辨率下 GPU 还有余量。

## 但这个结论有前提，必须主动说

如果换个场景——更高分辨率、更复杂的着色器、更重的后处理——**GPU 变成瓶颈，这笔交易就反过来亏了**。

那时候正确的做法是**分块实例化（chunked instancing）**：不是整个区段一个 `InstancedMesh`，而是按空间切成若干块、每块一个，换回一部分**剔除粒度（culling granularity）**。

**能说出「什么情况下我这个优化是错的」，比说出它为什么对更有说服力。**这句话适用于任何一条性能优化的 bullet。

## 实际帧率影响：诚实答案

**在这次测量里看不出来，因为帧率饱和了。**四个场景的帧率中位数都超过 115、顶在合成器约 120 的上限。

正确的说法是：这次测量没能显示帧率提升，因为那个分辨率下四个场景都顶在合成器帧率上限。要看到 draw call 下降转化成帧率，得把分辨率调高、把 GPU 压到成为瓶颈之前；测量脚本里那条提示也建议了用更大的窗口重跑。

**别硬说帧率提升了。**数据不支持，而且测量脚本自己把这件事写在报告里了——面试官只要打开代码就能看到那行提示。

## 这条 bullet 最大的价值

收益是 draw call 从 129 降到 76，代价是提交的三角形涨了 2.6 倍，**机制是每个网格只有一个包围体**，代价来自失去逐实例的视锥剔除。

讲的时候可以直接点出来：**这条我特意把代价也写上了，因为只报 draw call 下降是不完整的——它是用三角形数换来的。**

## 英文怎么说

**三句最容易说错的。**「用瓶颈资源换非瓶颈资源」说 **we spent GPU headroom to buy back CPU time**，这是这笔交易划算的全部理由。「提交的三角形涨了」一定要用 **submitted**，并补一句 **the image is identical**，否则听起来像画质变了。「帧率区分不了这四个场景」说 **FPS is saturated at the compositor cap, so it can't separate them**。

**术语对照**：绘制命令 draw call ／ 受绘制命令限制 draw-call bound ／ 受 GPU/CPU 限制 GPU-bound / CPU-bound ／ 实例化 instancing ／ 变换矩阵 transform matrix ／ 合批 batching ／ 视锥 frustum ／ 视锥剔除 frustum culling ／ 包围体 bounding volume ／ 剔除粒度 culling granularity ／ 顶点着色器 vertex shader ／ 裁剪阶段 clipping ／ 富余产能 headroom ／ 帧率上限 frame cap ／ 饱和 saturated ／ 软件光栅化 software rasterisation ／ 无头测量装置 headless harness ／ 受控实验 controlled experiment ／ 采样窗口 sampling window ／ 分块实例化 chunked instancing ／ 长帧 stall。

# 四个状态，和它挡住的三件事

> 🔴 **必看**。简历用的动词是 **`drops`（丢弃）**，不是排队、不是取消 —— **这个词选得很准**，第三节讲为什么。

## 一、先说清「状态机」在这里指什么

**这个组件在任何时刻都处于四种情形之一**，用一个枚举变量记录：

```js
// CopilotSection.tsx:42-47
enum CopilotStatus {
  Ready,       // 还没开始，等用户点「开始面试」
  Listening,   // 正在听，转录在滚动
  Generating,  // 正在生成答案
  Done,        // 这一轮答案出完了，等下一个问题
}
```

**「状态机」就是「这四种情形 + 它们之间允许怎么跳」这一整套规则。**

## 二、四个状态怎么跳

```
                     初始 :146
                        │
                        ▼
    ┌──────────────► Ready ───点「开始面试」，且连接和麦克风都就绪──┐
    │                  ▲                                        │
    │                  │                                        ▼
    │          点「停止面试」:218                            Listening
    │                  │                                        │
    │                  │                    静默 2 秒 / 手动点「要答案」:239
    │                  │                                        ▼
    │                  │                                   Generating ◄──┐
    │                  │                                        │        │
    │                  │                        答案流结束 :267-269      │
    │                  │                  （且中途没被停止）             │
    │                  │                                        ▼        │
    └──────────────────┴─────────────────────────────────── Done ────────┘
                                                    下一个问题 → Generating
```

**代码里的五处转移，一个不多一个不少：**

| 行号 | 从哪到哪 | 什么时候 |
|---|---|---|
| `:146` | → `Ready` | 组件的初始值 |
| `:189` | → `Listening` | 连接打开且麦克风启动了 |
| `:239` | → `Generating` | 提交问题时（且通过了守卫） |
| `:267-269` | → `Done` | 答案流结束时，**且中途没被停止** |
| `:218` | → `Ready` | 用户点了「停止面试」 |

> **一个值得讲的设计观察**：`Listening` 和 `Done` **其实都是「等下一个问题」**，区别只在屏幕上有没有上一条答案。
>
> 理论上可以合成一个状态加一个「有没有答案」的标志。**但分开之后，界面那段按状态渲染的代码可以直接一一对应**，不用在一个分支里再判断有没有答案。**这是「状态该切多细」的一个真实取舍：多一个状态，换掉一个条件判断。**

## 三、为什么不用几个布尔变量

**最有说服力的答法是算一下组合数。**

假设改用四个布尔变量：

```js
const [isReady, setIsReady] = useState(true);
const [isListening, setIsListening] = useState(false);
const [isGenerating, setIsGenerating] = useState(false);
const [isDone, setIsDone] = useState(false);
```

**4 个布尔 = 2⁴ = 16 种组合，而合法的只有 4 种。剩下 12 种全是 bug，而且没有任何东西拦着它们发生。**

**三个具体的非法组合：**

| 组合 | 现实里怎么发生 | 后果 |
|---|---|---|
| `isListening` 和 `isGenerating` 同时为真 | 上一条还在生成，用户又说了一句 | **界面不知道该显示「正在听」还是「正在生成」**，两个转圈同时转 |
| `isGenerating` 和 `isDone` 同时为真 | 流结束时忘了把前一个置回 false | **「要答案」按钮永远不出现**，用户卡死 |
| **四个全是 false** | 某个异常路径漏了一次赋值 | **未定义状态** —— 界面什么都不渲染，用户以为页面挂了 |

> ⭐ **根本问题是：这四个变量之间「只能有一个为真」这条规则，只存在于开发者脑子里，代码里没有任何东西强制它。** 每加一个布尔变量，你要手动维护的不变量就翻一倍。
>
> **换成枚举之后，一个变量只能持有一个值 —— 非法组合在类型层面就不存在。这不是代码风格问题，是把运行时 bug 变成了编译期错误。**

## 四、怎么保证两次生成不重叠

### 重叠是怎么来的 —— 两条互不知情的路径

```
路径 A：面试官说完话，静默 2 秒 → 自动提交
路径 B：用户觉得答案不够，手动点「要答案」→ 提交
```

**这两条路径互相不知道对方存在。** 面试官问完一句触发了 A，用户同时点了按钮触发 B —— 两次提交撞在一起。

**而且 A 自己也会连续触发**：面试官说完停两秒（触发一次），又补了一句再停两秒（又触发一次）—— **第一条还在生成，第二条就来了**。

### 守卫

```js
// CopilotSection.tsx:228-232
const submitQuestion = useCallback(async () => {
  if (statusRef.current === CopilotStatus.Generating) {
    return;                    // ← 直接返回，不排队、不取消
  }
  ...
}, []);
```

### ⭐ 为什么必须用 `statusRef` 而不是 `status`

**先说清楚 `useCallback` 干什么**：它把一个函数「记住」，避免每次渲染都造一个新的。第二个参数是**依赖数组** —— 数组里的东西变了，才重新造这个函数。

**这里的依赖数组是空的 `[]`**（`:270`），意思是「**这个函数只在首次渲染时创建一次，之后永远是同一个**」。

**问题就在这**：这个函数被创建的那一刻，`status` 的值是 `Ready`。**函数把那一刻的 `Ready` 记在了自己身上**（JavaScript 里这叫闭包捕获）。之后 `status` 变成 `Generating`，**这个函数里读到的还是 `Ready`**。

```js
if (status === CopilotStatus.Generating) return;   // ❌ 永远读到 Ready，守卫永不命中
```

**`statusRef` 解决这个问题**：ref 是一个**固定的盒子**，函数记住的是「这个盒子」，而读 `.current` 时拿到的是**盒子里当前装的东西**。

```js
// :148-149
const statusRef = useRef(status);
statusRef.current = status;      // 每次渲染都把最新值放进盒子
```

> **和 [① 转录](/docs?section=beyz&item=d2-transcript) 里那个 ref 是同一类问题，但成因不同：**
> - **那里**：WebSocket 回调触发得比 React 重新渲染快，用 state 会读到上一次渲染的值
> - **这里**：函数只创建一次，闭包永远停在初始值
>
> **两个场景都指向同一句话：需要读「此刻最新的值」时，用 ref，不用 state。** 面试里把这两个例子并起来讲，说明你是真理解 React 闭包，不是背了条规则。

**顺带**：`:149` 那行赋值是在**渲染过程中直接执行**的，不是放在 `useEffect` 里。这是「保存最新值」的常见写法 —— 渲染时同步写入，所以下一次事件回调读到的一定是最新的；放进 `useEffect` 反而会晚一拍。

## 五、为什么是「丢弃」而不是排队或取消

**这一问是这条 bullet 的题眼，`drops` 那个词就是为它准备的。**

| 策略 | 在这个场景下会怎样 |
|---|---|
| **排队** | 面试官已经问了第二个问题，你还在生成第一个的答案。等第一个完了再生成第二个 —— **用户看到的是一个已经过时的问题的答案**，而他现在需要的是第二个 |
| **取消上一个，改做新的** | 第一条生成到一半被打断。**如果第二次触发只是用户手抖或者一句无意义的补充，就把一个本来有用的答案毁了** |
| **丢弃新的** ✅ | 保住正在生成的那条，新的这次不做 |

> ⭐ **核心理由：面试是实时的，过期的答案没有价值。**

### ⚠️ 但「丢弃」丢的是动作，不是内容

**这是最常被追问的一处，也是最容易答错的。**

```js
if (statusRef.current === Generating) return;   // ← 守卫在前
...
resetTranscript();                               // ← 清空暂存区在后
```

**注意顺序**：被丢弃的那次触发，**在清空暂存区之前就返回了** —— 所以**那句话的文字还留在暂存区里，会和后面的话攒在一起，等生成完之后一起发出去**。

**完整时间线在 [① 转录与触发](/docs?section=beyz&item=d2-transcript) 第五节。**

## 六、取消之后才到达的响应怎么处理

**这一问看着像在问 `AbortController`（一个用来取消进行中的请求的浏览器 API）。代码里没有它 —— 但有一个更轻的处理，而且位置很准。**

```js
// CopilotSection.tsx:267-269
setStatus((prev) => prev === CopilotStatus.Generating ? CopilotStatus.Done : prev);
```

**先解释这个写法**：`setStatus` 可以传一个函数，React 会把「当前的值」传给它，用它的返回值作为新值。**这样你能在设置之前先看一眼现在是什么。**

**它在防什么：**

```
t0  提交问题 → 状态变成 Generating，开始接收答案
t1  用户点了「停止面试」→ 状态变成 Ready
t2  答案的流终于结束了
```

**如果第 t2 步无条件写 `Done`**：用户明明已经停止了面试，**界面却自己跳回「已生成」状态**。

**加了 `prev === Generating` 这个检查之后**：t2 时 `prev` 已经是 `Ready` 了，条件不成立，函数返回 `prev` 原值 —— **迟到的响应写不进去，用户的意图被保住了。**

> ⭐ **这是「迟到的异步响应」的标准处理方式：不阻止它到达，而是让它到达之后写不进去。** 判据是「我离开的时候，状态还是不是我离开时那个」。

### ⚠️ 但它只挡住了状态，没挡住内容

```js
// :257-266  流的循环体里，没有任何检查
for await (const delta of readStreamableValue(suggestion)) {
  suggestionContent += delta;
  startTransition(() => setMessages(...));   // ← 还在往屏幕上写字
}
```

**用户点了停止之后，这个循环还在跑，字还在往屏幕上出。** 只有最后那一次状态设置被挡住了。

**该怎么补：**

| 做法 | 说明 |
|---|---|
| **`AbortController`** | 把取消信号传给请求，用户停止时调 `abort()`，**从源头掐掉这个流**，顺带省掉后续的 token 费用 |
| **请求版本号** | 每次提交时把一个数字加一，循环体里检查「我这次的编号还是最新的吗」，不是就 `break`。**改动小，不依赖底层支持** |

> **主动交代这个缺口，比含糊说「我们用了 AbortController」强得多** —— 后者一查代码就露馅。

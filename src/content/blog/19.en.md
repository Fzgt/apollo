## Bullet 1: the Xiaodu App's H5 smart home module — jsBridge and a hybrid app

> Delivered the Xiaodu App's embedded H5 smart home module (Vue 2 + Webpack 3), implementing native sharing via jsBridge for iOS/Android, device detail pages, and analytics tracking via Baidu Statistics API.

### jsBridge

- How H5 talks to native
1. **URL scheme** (the old way): H5 sets `location.href = 'xiaodu://share?title=xxx'`, native watches for URL changes, matches the scheme, intercepts it, parses it, and runs it. The downsides: it is asynchronous with no return value, and only one call at a time.
2. **Injecting a native object** (what everyone does now)

```js
Android: webView.addJavascriptInterface(new NativeBridge(), 'AndroidBridge'), then call window.AndroidBridge.share(...) straight from H5
iOS (WKWebView): WKUserContentController.add(handler, name: 'iosBridge'), then call window.webkit.messageHandlers.iosBridge.postMessage({...}) from H5; the callback comes back through evaluateJavaScript
```

- **One jsBridge wrapper**

The standard approach: wrap it in a layer so the front end never sees the iOS/Android difference and just calls `bridge.call('share', {...})`.

### An H5 page is slow inside a native app — what do you do?

① Offline packages (native ships the H5 assets, so nothing goes over the network). ② Pre-warm the WebView when the app launches. ③ SSR/SSG for the first screen. ④ Inline critical assets, to cut request count. ⑤ Trim dependencies.

## Bullet 2: withdrawals at 2,000+ QPS — front-end defence under high concurrency

> Delivered the cash withdrawal feature for a commercial campaign page. Handled peak QPS of 2,000+ with button debounce, request locking, and error fallbacks, ensuring zero financial loss during the campaign.

#### ① Debounce vs throttle — easy to mix up

- **Debounce**: fire repeatedly, and the callback runs **n milliseconds after the last one**. If the user hammers the button, the call only happens once they stop for 300ms.
  - Where it fits: search inputs, `resize`, a first pass at click protection.
- **Throttle**: fire repeatedly, and the callback runs **at most once every n milliseconds**. Constant triggering gives you an even rate.
  - Where it fits: `scroll`, `mousemove`.
- **Which one for a withdrawal button?**
  - Debounce has a problem: "only the last one counts" means that if the user clicks 100 times, the request fires 300ms after click 100. In the meantime it looks like nothing is happening, so they click more.
  - **Better**: **run immediately on the first click, then lock** (② below). That is leading-edge debounce plus a request lock.

#### ② The request lock

```js
let inFlight = false;

async function withdraw() {
  if (inFlight) return; // locked — ignore
  inFlight = true;
  try {
    const res = await api.withdraw();
    handleSuccess(res);
  } catch (err) {
    handleError(err);
  } finally {
    inFlight = false; // unlock
  }
}
```

A fuller version deduplicates by key, so the same withdrawal is locked but different ones can run in parallel:

```js
const inFlightMap = new Map();

async function withdraw(orderId) {
  if (inFlightMap.has(orderId)) return inFlightMap.get(orderId);
  const promise = api.withdraw(orderId);
  inFlightMap.set(orderId, promise);
  try {
    return await promise;
  } finally {
    inFlightMap.delete(orderId);
  }
}
```

This pattern is called promise deduplication. React Query and SWR do exactly this internally.

#### ③ Idempotency — this is what actually gives you zero financial loss

- A front-end lock only stops fast clicking in one tab. It cannot stop:
  - a front-end retry after a network timeout
  - the user acting from two devices or tabs at once
  - a click after a page refresh
- Zero loss has to come from an idempotent backend:
  - every withdrawal request carries an idempotency key — a UUID the front end generates, or the order ID
  - the backend stores the keys it has already processed; a repeat of the same key returns the previous result instead of running again
- What the front end can do: generate the idempotency key up front and keep it in `sessionStorage` so it survives a refresh, then send it on every call. It is only a complete solution together with the backend.

#### ④ Error fallbacks

The rule for anything touching money: assume failure, and only show success when success is explicit.

#### ⑤ What "2,000+ QPS" means from the front end

QPS is queries per second.
2,000 QPS is usually a backend number, not a front-end one. The front end does not *absorb* QPS, it *contributes* to it — every user click adds 1.
What the front end can do:

- send fewer requests (debounce plus lock)
- queue and rate-limit, so 100,000 people do not all click at the instant the campaign opens
- cache static assets on a CDN, so fewer requests need to be dynamic

> Rate limiting and queueing on the front end brings in status code 429, Too Many Requests, which stops the backend being hit with everything at once.

> A static request returns the same thing to everyone. A dynamic one has to compute — a user's balance, for instance.

> On SSE: the client opens an ordinary HTTP GET with `EventSource` — no special headers needed. The server must answer with `Content-Type: text/event-stream` (usually alongside `Cache-Control: no-cache` and `Connection: keep-alive`), keep the connection open, and keep writing to it. The data has to follow the `data: xxx\n\n` convention, ending with a blank line, optionally with `event:` for a custom event type and `id:` for a message number. `EventSource` parses that format and fires `onmessage` or the custom event handler. If the connection drops, the browser reconnects automatically and sends `Last-Event-ID` — the last `id:` the server sent — so the server knows where to resume and no messages are lost.

### The withdrawal flow

1. Disable the button in `onClick` — disabled the moment it is clicked, re-enabled when the response arrives. That is the visual lock.
2. The logical lock: an in-memory `inFlightMap` or `Set` that blocks a repeat of the same `orderId`.
3. Generate an idempotency key (UUID) on the front end and keep it in `sessionStorage`.
4. Inject the idempotency key into the header or body in one place, in the API layer.
5. Error fallbacks: one shared error handler — "check back shortly" on a timeout or network error, the business error on a 4xx.
6. A global loading state, so the user never thinks nothing happened.

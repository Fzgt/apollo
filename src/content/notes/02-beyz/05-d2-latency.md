> ⚪ **速查**。被问到「延迟多少」时翻。一句话记住就够：**用户感知里有个 2 秒的固定底座，那是设计不是性能。**
# Day 2 · 端到端延迟从哪一刻算到哪一刻

> 回答 **Q5**。这一问的价值不在于报一个数字——**代码里没有任何延迟埋点**——而在于能不能把这条链路拆成可测的段。

## 一、先定义「端到端」的两端

**这是这一问的核心：起点和终点各有两种合理选法，选不同答案完全不同。**

| | 候选起点 | 候选终点 |
|---|---|---|
| A | 面试官**说完最后一个字**的那一刻 | 屏幕上出现**第一个** token |
| B | `UtteranceEnd` **事件到达**的那一刻 | 答案**完整**渲染完 |

**四种组合，量的是完全不同的东西：**

| 组合 | 量的是什么 | 合不合理 |
|---|---|---|
| A起点 → A终点 | **用户真实感受到的等待** | ✅ **产品意义上唯一正确的口径** |
| B起点 → A终点 | 系统内部处理耗时 | ✅ 工程调优用 |
| A起点 → B终点 | 含了整段答案的生成时间 | ⚠️ 会被答案长度左右，没什么用 |

> **关键陷阱**：A 起点到 B 起点之间**天然隔着 `utterance_end_ms` 的 2000 毫秒**。
>
> 也就是说，**用户感知的延迟里有一个 2 秒的固定底座，而且它是设计出来的，不是性能问题。**
>
> **面试官如果问「你们端到端延迟多少」，先反问清楚是哪个口径**——报「1.5 秒」（B→A）和报「3.5 秒」（A→A）说的是同一个系统。**答不清口径的数字，和 [Day 1](/docs?section=numbers&item=day01) 那二十条一个毛病。**

## 二、把链路拆成可测的段

```
面试官说完最后一个字
   │
   │  ① 静默检测窗口 —— 固定 2000 ms（utterance_end_ms）
   │     ⚠️ 设计决定，不是性能问题
   ▼
Deepgram 判定 utterance end，发出事件
   │
   │  ② 事件下行网络传输 —— 几十 ms
   ▼
onUtteranceEnd() → submitQuestion()          useAudioToText.ts:129
   │
   │  ③ 客户端处理 + Server Action 调用往返
   ▼
generateCopilotSuggestion 进入服务端           copilot.ts:88
   │
   │  ④ 鉴权 + 查套餐 + 组装 history          copilot.ts:94-106
   ▼
streamText 发出请求
   │
   │  ⑤ ⭐ GPT-4o 的首 token 时间（TTFT）—— 通常是最大的一段
   ▼
第一个 delta 回到服务端
   │
   │  ⑥ StreamableValue 传回浏览器
   ▼
readStreamableValue 收到第一个 delta          CopilotSection.tsx:257
   │
   │  ⑦ startTransition → React 提交 → 绘制
   ▼
屏幕上出现第一个字
```

**还有一段在图外、但同样真实的延迟**：音频本身的 **250 ms 切片延迟**（`MediaRecorder.start(250)`）。它影响的是**转录出现在屏幕上的时间**，不影响上面这条触发链路——因为触发是由 Deepgram 侧的静默判定发起的。

## 三、七段里哪几段能优化

| 段 | 量级 | 能不能动 |
|---|---|---|
| ① 静默窗口 | **2000 ms** | ⚠️ **能动但有代价**——调小会把句中停顿误判成说完 |
| ② 事件下行 | 几十 ms | ❌ 网络 |
| ③ Server Action 往返 | 几十~百 ms | 🔸 有限：可以考虑走 edge runtime |
| ④ 鉴权 + 组装 | 几~几十 ms | 🔸 有限：`getAuthUser` 有 `cache()` 包着 |
| ⑤ **GPT-4o TTFT** | **几百 ms ~ 1s+** | ✅ **最大的一段**：换更快的模型、缩短 system prompt、减少历史条数 |
| ⑥ 流回传 | 几十 ms | ❌ |
| ⑦ React 提交绘制 | 几 ms | ❌ 已经用 `startTransition` 优化过 |

> **两个最大项是 ① 和 ⑤，而它们的性质完全不同**：
> - **① 是产品决策**——2 秒静默换的是「不误判」，缩短它是在拿准确性换延迟
> - **⑤ 是工程/成本决策**——换模型、砍 prompt、减历史都能压，但换的是答案质量
>
> **能把「延迟的两个大头分别是设计决策和模型选择，都不是代码写得慢」讲出来，这一问就答满了。**
>
> 顺带：`MaxHistoryLength = 4`（`copilot.ts:86`）这个截断**同时在优化成本和 TTFT**——prompt 越短，首 token 越快。

## 四、⚠️ 诚实交代：代码里没有埋点

**全仓库没有任何延迟测量。** 没有 `performance.mark`，没有把 `UtteranceEnd` 到首 delta 的时间记下来，`copilot.ts` 的 `onFinish` 里只记了 token 用量（`:107-117`），没记耗时。

**所以现在能说的是「链路是流式的、每一段都不攒批」，说不出 P50/P95。**

**被问到时的正确答法：**

> 「这条链路我能把每一段拆开讲，但**当时没有埋端到端延迟的点**，所以我给不了 P95，只能说体感是对方说完一两秒内开始出字。要真正回答这个问题，我会在四个位置打点。」

**然后给出方案——这比含糊报一个数字强得多：**

```js
// 1. UtteranceEnd 到达
const t0 = performance.now()

// 2. Server Action 返回（首 delta 之前）
const t1 = performance.now()

// 3. 第一个 delta 到达 ← 这个是关键指标
const t2 = performance.now()

// 4. 流结束
const t3 = performance.now()
```

**上报三个区间：`t2 - t0`（用户等待首字）、`t1 - t0`（网络+鉴权开销）、`t2 - t1`（模型 TTFT）。**

**再加上服务端在 `onFinish` 里记录 `streamText` 的耗时**，就能把「慢」归因到具体某一段，而不是笼统地说"有时候有点慢"。

> **和 [Day 1 那二十条](/docs?section=numbers&item=day01) 是同一个道理**：报数字之前先有口径，有口径之前先有埋点。**没埋点就老实说没埋点。**

## 五、一句话答法

> 得先说清算哪一段。用户感知的是「面试官说完最后一个字」到「屏幕出现第一个字」，而这里面有个 **2 秒的固定底座**——`utterance_end_ms` 要用两秒静默来判定这轮说完了，这是设计决策不是性能问题。系统内部的处理是从 UtteranceEnd 事件到达算起，那一段主要是事件下行、Server Action 往返、鉴权组装，然后**最大的一块是 GPT-4o 的首 token 时间**。所以延迟的两个大头一个是产品决策、一个是模型选择，都不在代码快慢上。**要说明的是当时没有埋端到端的点，所以我给不出 P95**——真要测的话我会在 UtteranceEnd 到达、Server Action 返回、首 delta 到达、流结束这四个位置打点，把用户等待时间和模型 TTFT 分开上报。

# ⑤ P2 白屏事故

> **简历原句**
>
> **First to diagnose a P2 white screen** on Haokan Video's search page (**30M+ DAU**): **mismatched Node versions regenerated package-lock.json**, pulling a **breaking minor bump** — **version locks and release checks followed**.
>
> ---
>
> 第一个定位出好看视频搜索页（3000 万+ DAU）P2 白屏事故的根因：Node 版本不一致导致 package-lock.json 被重新生成，放进来一个带破坏性改动的小版本升级 —— 随后落地了版本锁定与发布前检查。

## 这条 bullet 在讲什么

⭐ **它讲的不是「我修了一个 bug」，是「我把一个 bug 变成了一类 bug 的终结」。**

**这条 bullet 的价值全在最后那半句 `version locks and release checks followed`。** 只讲排查过程会浪费掉它 —— **表面看是「某个库出了问题」，实际是「我们的锁文件根本没锁住」，而后者会以任何一个依赖的形式再来一次。**

## 30 秒口播稿

> 好看视频的搜索页在一次发布后白屏，是个 P2 事故，那个产品是亿级 DAU 的量级。
>
> **根因链条是四层**：有人本地的 Node 版本和团队不一致 → 他的 npm 版本跟着不同 → 装依赖时 ⭐ **`package-lock.json` 被重新生成了** → 锁文件里某个依赖的版本被放行到了一个带破坏性改动的新版本，上线就炸。
>
> ⭐ **表面看是「某个库出了问题」，实际是「我们的锁文件根本没锁住」。** 所以修完之后做的不是改那一个依赖，是**锁 Node 版本、CI 里改用 `npm ci`、加发布前的预发布验证** —— **因为同样的机制会以任何一个依赖的形式再来一次。**

## 一、⭐ 四个术语，讲这条之前必须先说清

### ① semver（语义化版本）和那两个符号

版本号 `4.17.21` 读作 `主版本.次版本.修订号`：⭐ **主版本变 = 有破坏性改动，次版本变 = 加了功能但兼容，修订号变 = 只修 bug。**

`package.json` 里写的**不是一个版本，是一个允许范围**：

| 写法 | 允许装 | 说明 |
|---|---|---|
| `4.17.21` | 只有 4.17.21 | 锁死 |
| `~4.17.21` | `>=4.17.21 <4.18.0` | 只放行修订号 |
| ⭐ `^4.17.21` | `>=4.17.21 <5.0.0` | **放行次版本** —— `npm 默认给你写的就是这个` |

⭐ **`^` 是这次事故的起点：它赌的是「次版本一定兼容」。而这个赌注每年都有人输** —— 库作者认为是「加功能」的改动，在你的用法下就是破坏性的。

### ② `package-lock.json`（锁文件）是干什么的

`package.json` 写的是**范围**，⭐ **锁文件写的是「上次实际装的那一个确切版本」**，连它的依赖的依赖也一起钉死。

⭐ **它存在的全部意义就是：让每个人、每台 CI 装出完全一样的 `node_modules`。**

### ③ ⭐ 为什么 Node 版本不一致会把锁文件搞坏（这是整条链的关键一环）

**锁文件有个 `lockfileVersion` 字段，它的格式随 npm 大版本变**（npm 6 是 v1，npm 7+ 是 v2/v3）。⭐ **而 npm 版本是跟着 Node 版本走的** —— 装 Node 就带一个 npm。

**于是：**

```
某人的 Node 版本高/低一截
  → 他的 npm 看到一个「格式不对」的锁文件
    → ⭐ 它会按自己的规则重新生成一份
      → 重新生成时去 registry 拿「符合 ^ 范围的最新版本」
        → 那个最新版本带了破坏性改动
```

⭐ **整条链的关键一环是「重新生成」：锁文件不是被人手动改的，是被工具在他毫不知情的情况下重写的。**

⭐ **这也是为什么修法的第一条是「锁 Node 版本」—— 不锁住 Node，就锁不住 npm，就锁不住锁文件。**

### ④ `npm ci` vs `npm install`

| | 行为 |
|---|---|
| `npm install` | ⚠️ **可以修改锁文件** —— 发现 `package.json` 和锁文件对不上时，它会更新锁文件 |
| ⭐ `npm ci` | **只读锁文件**；对不上就直接报错退出；而且先删掉整个 `node_modules` 从头装 |

⭐ **CI 里必须用 `npm ci`**（名字里的 ci 就是 continuous integration）。**用 `npm install` 等于允许 CI 悄悄改变依赖版本。**

## 二、排查过程怎么组织

⭐ **用 observe → hypothesize → verify → fix → prevent 五步讲，重点在最后两步的分离。**

| 步 | 这次做了什么 |
|---|---|
| **Observe** | 搜索页白屏，控制台报错指向某个第三方库的一个方法不存在 |
| **Hypothesize** | 表层假设：那个库有 bug / 我们用错了 API。⭐ **但发布内容里没人动过它** —— 这一步的关键是**注意到「症状和这次改动对不上」** |
| **Verify** | 对比发布前后的 `node_modules` 实际装的版本，**发现它悄悄涨了一个次版本**；再往上追，`package-lock.json` 在那次提交里被整体重写了 |
| **Fix** | 回滚锁文件、锁死那个依赖的版本 —— ⭐ **让这次好** |
| ⭐ **Prevent** | 锁 Node 版本（`.nvmrc` + `engines` 字段）、CI 改用 `npm ci`、加发布前的预发布验证 —— ⭐ **让这类不再来** |

⭐ **fix 和 prevent 的分离是这条 bullet 的骨架。** 面试里讲完 fix 一定要继续讲 prevent，**否则这就只是一个「我会看报错」的故事。**

## 三、「第一个定位到」怎么讲才不虚

⚠️ **`First to diagnose` 是个强声明，会被追。**

> ⭐ **答法**：「当时还有别人在查，**我是最先把根因指到锁文件被重新生成这一层的**。」

⭐ **说清「第一个」指的是定位到根因，不是第一个发现故障** —— 这个区分能挡住大多数追问，而且它是诚实的：发现白屏的通常是监控或客服，不是开发。

## 四、预期追问

**Q：为什么本地和测试环境没发现？**

⭐ **因为出问题的人本地 `node_modules` 里装的就是那个新版本，而它在他的环境下恰好没走到那条崩溃路径**（或者他根本没跑到那个页面）。**其他人拉代码之后重新装依赖，才把这个新版本扩散开。**

⭐ **更本质的答案是：测试环境和生产环境如果不是用同一份锁文件、同一个 Node 版本装出来的，那测试就不构成保证。** 这正是 prevent 里那三条要解决的。

**Q：怎么防止下次再发生？（这一问就是简历后半句）**

| 措施 | 挡住什么 |
|---|---|
| ⭐ **锁 Node 版本** | `.nvmrc` + `package.json` 的 `engines` 字段 + CI 里校验 —— **不锁 Node 就锁不住 npm** |
| ⭐ **CI 用 `npm ci`** | 锁文件和 `package.json` 对不上直接报错，**而不是默默改掉** |
| **锁文件进 code review** | ⭐ **`package-lock.json` 的大规模改动必须被人看见** —— 它平时不该整体重写 |
| **发布前预发布验证** | 用**和生产完全一样的构建产物**在预发布环境跑一遍冒烟 |
| **依赖版本收紧** | 关键依赖从 `^` 改成精确版本或 `~`，**升级走单独的 PR** |

**Q：为什么不干脆全部锁死精确版本？**

⭐ **代价是安全补丁也进不来了。** 常见的折中是：**关键依赖锁死，其余用 `~` 只放行修订号，再配一个自动升级机器人（Renovate/Dependabot）把升级变成一个个可审查的 PR** —— **让升级发生在你看得见的地方，而不是某个人装依赖的时候。**

## 五、`30M+ DAU` 这个数字怎么说

⭐ **它和[虚拟列表那条的 5M PV](/docs?section=baidu&item=virtual-list) 一样，是环境不是成果** —— 但它在这里的作用更明确：**它解释了为什么这是 P2 而不是 P3。**

**答法**：「好看视频是亿级 DAU 量级的产品，搜索页白屏影响面很大，所以定级是 P2。**这个数字我是从产品侧公开口径知道的，不是我测的。**」

⚠️ **注意 DAU 是产品级指标，和你负责的模块不是一回事** —— 别让它听起来像「我的页面有 3000 万 DAU」。

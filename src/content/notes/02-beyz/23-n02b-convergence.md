# 两个写入赛跑，为什么都不会出错

> ⚪ **速查**。这是 `none of which can downgrade a lifetime purchase` 最强的答法 —— 主线在 [③ Stripe 与权益](/docs?section=beyz&item=d4-stripe) 第七节。

## 一、先看买断时代码干了什么

用户买终身版，结账完成的事件到达，处理函数做了**两件事，有先后**（`route.ts:92-109`）：

```js
if (containsLifetimePlan) {
  // 第一件：取消该用户所有现存的订阅
  const subscriptions = await stripe.subscriptions.list({ customer: customerId });
  for (const sub of subscriptions.data) {
    await stripe.subscriptions.cancel(sub.id);        // :99
  }
  // 第二件：把用户的套餐写成终身版
  await db.update(users).set({ subscribedPlan: Lifetime, ... })   // :102-108
    .where(eq(users.stripeCustomerId, customerId));   // ⭐ 注意这里没有「不是终身版」的条件
}
```

**为什么要先取消订阅**：用户原来可能正按月付着 Standard。既然买断了，**就不该再继续扣他钱**。

## 二、⚠️ 但这一步会捅出一个副作用

**取消订阅会让 Stripe 再发一个「订阅已删除」的事件回来。** 而那个事件的处理逻辑是 —— **把套餐写成免费**。

**于是就有了两个写入在赛跑：**

| | 是什么 | 在哪 |
|---|---|---|
| **甲** | 把套餐写成**终身版** | `route.ts:102-108`，**就在当前这个处理函数里** |
| **乙** | 把套餐写成**免费** | 由「订阅已删除」事件触发的另一个处理函数 |

> ⭐ **关键是要意识到：乙是一个全新的 HTTP 请求，Stripe 从外面重新打进来的**，跟甲不在同一个执行流里，甚至可能落在另一台服务器上。**两者谁先完成不由你决定。**

```
当前处理函数里：
  :99   取消订阅  ──────► Stripe 那边准备发「订阅已删除」事件
  :102  写入终身版  = 甲

Stripe 发回来（时间不确定）：
  订阅已删除事件 ──────► 写入免费  = 乙
```

## 三、两条时间线，都是对的

**乙晚于甲：**

```
:99   取消订阅
:102  数据库 → 终身版                      ← 甲先完成
        乙到达：想写「免费」
              但它的 SQL 带着「不是终身版才更新」这个条件
              当前正是终身版 → 匹配到 0 行 → 什么都没改
最终：终身版 ✅
```

**乙早于甲：**

```
:99   取消订阅
        乙到达：想写「免费」
              此时数据库里还是 Standard，条件成立 → 真的写成了免费
:102  数据库 → 终身版                      ← 甲后完成，无条件写，直接盖掉
最终：终身版 ✅
```

## 四、⭐ 为什么两种顺序都收敛

**靠的是两个不同的机制各管一边：**

| 顺序 | 靠什么兜住 |
|---|---|
| **乙晚到** | WHERE 里那个「不是终身版才更新」的条件挡住了降级 |
| **乙早到** | 甲那次写入**故意不带这个条件**，无条件覆盖 |

> ⭐ **所以之前说的「甲那次写入故意没有守卫」不只是「入口不能挡自己」—— 它同时还是「乙早到」那条路径的兜底。**
>
> **少了它，乙早到时用户就卡在免费档了：付了买断的钱，拿不到权限。**

## 五、这说明了什么

**`none of which can downgrade a lifetime purchase` 不是靠事件顺序保证的。**

**顺序你根本控制不了** —— webhook 什么时候到、走哪台服务器、会不会重投，全在 Stripe 那边。**你能控制的只有「不管什么顺序，最终状态都对」。**

**这个性质有个名字叫收敛（convergence）**：系统从任何中间状态出发，都会落到同一个正确的终态。

> ⭐ **一句话答法**
>
> 「买断时会先取消旧订阅，而那个取消又会触发一个『订阅已删除』的 webhook 回来试图降级。这两次写入谁先谁后不确定，**但两种顺序都收敛到终身版**：晚到的被 SQL 里那个『不是终身版才更新』的条件挡住，早到的被随后那次无条件写入盖掉。**所以这半句话保证的不是顺序，是终态。**」

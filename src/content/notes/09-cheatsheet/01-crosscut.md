# 跨项目追问

> Day 14 Round 3 的原题。每题的价值在于**用两个不同项目的实例回答同一个抽象问题**。

## 1. 虚拟列表和 GPU instancing 各自减少了哪一类工作？

**表面上都是「少做事」，但性质完全不同——这是这一问的题眼。**

| | 减少了什么 | 代价 |
|---|---|---|
| **虚拟列表** | **浏览器主线程**的 style / layout / paint。DOM 节点数从 **O(n)（随已加载条数）变成 O(1)（只随视口高度）** | 几乎没有——那些节点本来就看不见 |
| **GPU instancing** | **CPU→GPU 的 draw call 提交**（驱动状态校验、命令打包），129 → 76 | ⭐ **提交的三角形涨 2.6 倍**（26,230 → 69,112），因为剔除粒度从「每个方块」退化成「整个区段」 |

> ⭐ **关键区分**：**虚拟列表是真的少做了工作**——那些 DOM 节点根本不存在。**instancing 是把工作从 CPU 挪到了 GPU，总工作量反而增加了。**
>
> 后者划算的前提是**当时的瓶颈在 CPU 而 GPU 有富余**——harness 里那句「四个场景都顶在合成器 120 帧上限」就是证据。**换成高分辨率或重后处理，这笔交易就该反过来，改成按空间分块 instancing 换回一部分剔除粒度。**

> 提示：一个减少的是浏览器主线程的 style/layout/paint，一个减少的是 GPU 的 draw call 提交；而 instancing 还**增加**了三角形数。两者都是「用一种成本换另一种成本」。

## 2. 哪些保证来自确定性代码，哪些只能靠 eval 衡量？

**判据一句话：能写成断言的就该写成代码；只能「比较好坏」的才需要 eval。**

| 确定性代码保证的 | 在哪 |
|---|---|
| 引用完整性 | Periplus：模型引的 evidence ID 必须在证据组里——**集合成员检查** |
| 新鲜度 | Periplus：`as_of` 减发布日期，和 `FRESHNESS_DAYS` 比——**日期减法** |
| 幂等 | 提现的幂等键唯一索引、Beyz cron 的 anti-join |
| 状态合法性 | Beyz 四态机、Periplus 的 `STAGE_ORDER` 只跑连续前缀 |
| 业务不变量 | `WHERE balance >= ?`、`ne(subscribedPlan, Lifetime)` |

| 只能靠 eval 衡量的 | 为什么 |
|---|---|
| 生成内容的质量 | 没有「正确答案」可以断言 |
| prompt 改动的效果 | 只能比较前后，不能判定对错 |
| 检索的召回率 | 取决于语料，是分布问题不是逻辑问题 |

> ⚠️ **而且要补一句**：Periplus 的离线评测**恰恰把模型判断钉死了**（oracle 读 case 标签不读证据），所以**它测的也是确定性那部分**——流水线、gate、预算、引用完整性。**真正评价「这个 prompt 让模型变成了更好的审核员吗」，需要真实 provider 跑同一批语料，那是另一套模式。**

> 提示：Periplus 的 freshness / 引用归属是代码强制的；生成质量只能靠 golden set 断言范围。这题答好了直接证明你懂 LLM 系统的边界在哪。

## 3. 哪些状态必须持久化，哪些可以只活在客户端？

**判据两句话：跨进程、跨设备、崩溃之后还要成立的，必须持久化；丢了只影响这一次会话体验的，可以只在客户端。**

| 必须持久化 | 为什么 |
|---|---|
| **entitlement**（Stripe 的 `subscribedPlan`） | 用户换设备、清缓存之后权限还得在 |
| **run state + 阶段产物**（Periplus） | 进程会挂，续跑要知道上次到哪 |
| **「已发过提醒」**（Beyz cron 的 `upgradeReminders`） | 服务重启、换机器都不能重发 |
| **幂等 key 的处理记录**（提现） | 跨请求、跨设备去重的唯一依据 |

| 可以只在客户端 | 为什么 |
|---|---|
| 四态机的当前状态 | 刷新就重来，不影响正确性 |
| `confirmedTranscript` | 断线重连后重新拼即可 |
| hover prefetch 的缓存 | 丢了最多多发一次请求 |

> ⚠️ **一个反例要主动交代**：Beyz 的**提问配额判定只在客户端**（服务端只拦 Free 档）。**按上面的判据它本该在服务端——这是我知道要补的地方**（[② 用量与配额](/docs?section=beyz&item=d3-quota)）。

> 提示：Beyz 的四态状态机 vs Periplus 的 run state；entitlement 为什么只能由 webhook 写。

## 4. 实时性、正确性、成本、复杂度之间你怎么取舍？

**别泛泛而谈，用四个具体决策各举一例，最后归纳出判据。**

| 优先了什么 | 具体决策 | 付出的代价 | 怎么补的 |
|---|---|---|---|
| **实时性** | Beyz 浏览器**直连** Deepgram，不走服务端转发 | 浏览器必须持有凭证 | 60 秒 TTL + 单一 scope 的临时凭证 |
| **正确性** | 提现「**不确定即失败**」；Periplus「**没有支持性引用就不推进**」 | 会误报失败、会少给内容 | 提示引导用户查记录；缺口显式上报为 `gap` |
| **成本** | Beyz 只带 4 条历史；Periplus 的 token / 时间 / 查询 / 抓取四维预算 | 长会话丢早期上下文 | 预算是整个 run 的天花板，**续跑不重置** |
| **拒绝复杂度** | Stripe **不建 event id 去重表**，靠「写绝对值」天然收敛 | 重复投递会重复执行 | 只有发邮件这种有外部副作用的才显式去重 |

> ⭐ **归纳成一句话**：**先问「这里错了，代价有多大」。**
>
> - **金融和事实性内容里，错误的代价高于慢和贵**——所以宁可拒绝、宁可标记缺口、宁可让用户重试
> - **实时交互里，过期的代价高于丢失**——所以面试 copilot 宁可丢弃重叠请求，也不排队生成一个已经过时的问题的答案
>
> **同一个人在两类系统里做出相反的取舍，不是不一致，是因为错误的代价不一样。**

> 提示：Beyz 的 250 ms chunk 与 `utterance_end_ms: 2000`；Periplus 的六阶段 vs 一个大 prompt；WinterFell 的 instancing 取舍。

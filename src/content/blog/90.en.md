title: "Handed a slow project — where to start: a project-level framework for performance work, and an index of 15 posts"
---

[#73](https://github.com/Fzgt/Blog/issues/73) is about the order of work at the **code level** — loading, requests, node count, where state lives, re-renders. But when you are handed a project where "the page is slow", the first step is not to open the editor.

This post sits one level up, at the project, and fills in the entrance. The whole flow is:

```
baseline → hygiene checklist → diagnose → route to a layer → fix → verify → lock in
```

Which post on this site covers each step is listed at the end.

---

## First, separate two things: steps and scopes

Most "performance checklists" mix "what to check" and "where to change code" into one table, and the result is code-level tactics applied to delivery-level problems. This post keeps them apart: **the flow above is the steps; the three layers below are the places you fix things.**

| Scope | What it owns | Typical problems |
|---|---|---|
| **Delivery layer** | How the build is packaged, how assets are served, how the browser fetches them | Large first-load JS, no compression, wrong cache headers, LCP image discovered late, third-party scripts, fonts |
| **Server layer** | When the first byte and the data arrive | High TTFB, slow APIs, whether to SSR / go to the edge |
| **Code layer** | How components are written | Request waterfalls, too many nodes, state in the wrong place, needless re-renders |

**All five layers of #73 live in the code layer.** Its first layer, "don't load so much", spills over into the delivery layer, but only covers the bundle; deployment, CDN, cache strategy and third-party scripts are not in that post.

Diagnosis is not a layer. It is an action, and its job is to tell you which layer to enter.

## Step 0: take a baseline and turn on RUM

**Before you change anything, write the numbers down.** Without a baseline, three weeks later nobody can prove the optimisation worked — including you.

**Lab baseline**: fix one Lighthouse throttling profile, run it 5 times, take the median; record LCP / TBT / CLS / TTFB plus the gzip size of the first-load JS. Ten minutes.

**Field baseline**: wire up `web-vitals/attribution` reporting on day one, even if it only goes to whatever analytics platform you already have. The reason is CrUX's 28-day rolling window ([#64](https://github.com/Fzgt/Blog/issues/64)) — if you do not start collecting today, there is nothing to compare against when you want to verify in week three.

### What if there is no field data

This is the most common real situation when you are "handed a slow project": internal B2B tools, brand-new products, sites whose traffic is mostly iOS — none of them get CrUX (it has a traffic threshold and is Chrome-only, [#64](https://github.com/Fzgt/Blog/issues/64)).

The substitute is not "just look at the default Lighthouse score". It is **configuring the lab environment to look like your p75 user**: pull the device and network distribution from your business analytics, then run the Performance panel and Lighthouse at that tier — a mid-range Android on 4G with 4x CPU throttling, say. Once your own RUM has two weeks of data, come back and recalibrate the tier.

This site is on that branch: its traffic never reaches the CrUX threshold, and the Lighthouse run in [#62](https://github.com/Fzgt/Blog/issues/62) used the mobile simulated profile.

## Step 1: the hygiene checklist — no measurement needed

One criterion: **doable with a single config line or a one-off script, no business code touched, no trade-off.** Done right it costs nothing; done wrong it gains nothing — it is pure debt, and you fix it as soon as you see it.

- [ ] Static assets are gzip / Brotli compressed (most servers do not compress `.glb` `.gltf` `.wasm` by default)
- [ ] Hashed filenames + `max-age=31536000, immutable`; HTML is `no-cache` → [#69](https://github.com/Fzgt/Blog/issues/69)
- [ ] The right asset directory: `assets` goes through `import` and gets a hash, `public` only holds files whose URL is assembled at runtime → [#69](https://github.com/Fzgt/Blog/issues/69)
- [ ] Production is running a production build (a red React DevTools icon means a development build shipped)
- [ ] Source maps are not shipped to production, or only uploaded to the error platform
- [ ] No full-import moment, lodash, or component library — run a bundle analyzer once, ten minutes
- [ ] The LCP image has no `loading="lazy"`, and every image has `width` / `height` → the checklist in [#67](https://github.com/Fzgt/Blog/issues/67)
- [ ] Third-party origins get `preconnect`
- [ ] You are on HTTP/2 or later — under HTTP/1.1 many of the conclusions about splitting have to be read the other way round
- [ ] Images are not served as originals — at minimum sized to fit and lossy-compressed (the decision order is in [#67](https://github.com/Fzgt/Blog/issues/67))

**This step is an audit, not an optimisation.**

### Two things people put on this list that do not belong here

**Splitting** and **route-level lazy loading** look like "just do it" items too, but both carry trade-offs, and step 3's diagnosis decides them.

First, a conclusion that gets overstated — "SplitChunks does nothing for a single entry". The real situation is in section 4 of [#81](https://github.com/Fzgt/Blog/issues/81): a module that already lives in the main chunk is not extracted again into an async chunk, which is **de-duplication**, not a failure — the async chunk can already reach it through its parent. Meanwhile **extracting `node_modules` into a vendor chunk by `test` regex works with a single entry and always has**: webpack's default `defaultVendors` group kicks in once you set `chunks: 'all'`, and Vite has `manualChunks`. This site is a single-entry SPA whose build has `vendor-react` and `vendor-framer-motion` as separate chunks; the three first-load JS files are 32 / 50 / 40 KB gzipped.

So the question about splitting is not "can it" but "is it worth it":

- **The point of splitting is cache stability and parallel download, not a smaller total.** Dependencies sit still for months while business code ships daily; split them apart and each release only re-downloads the business half.
- If the output is already small, do not split — an extra request is pure loss; the range [#81](https://github.com/Fzgt/Blog/issues/81) gives is 30–120 KB gzipped.
- Route-level lazy loading saves first-load bytes at the cost of **one extra round trip on navigation**, which is why hover prefetching exists to cover it ([#82](https://github.com/Fzgt/Blog/issues/82)).

Putting these two on the "do it without measuring" list contradicts the argument of this post.

## Step 2: diagnose — field first, lab second

**The order is not negotiable.**

**Field first** — your own RUM or CrUX. It answers "**how many users, which page, which segment**":

- p75, not the average → [#64](https://github.com/Fzgt/Blog/issues/64)
- Break the distribution down by route, device and network instead of one site-wide number; `route` must be the route pattern, not `pathname`, or dynamic routes explode into tens of thousands of keys → [#70](https://github.com/Fzgt/Blog/issues/70)

**And RUM with attribution already answers "which segment is stuck"** ([#66](https://github.com/Fzgt/Blog/issues/66), [#63](https://github.com/Fzgt/Blog/issues/63)): LCP splits into TTFB / resource load delay / resource load duration / element render delay, INP into input delay / processing / presentation, with `interactionTarget` and `longestScript` attached. Only CrUX is "the result without the cause". Very often, once the field data has been read, the lab step is reduced to reproducing and finding the exact line.

**Lab second** — Lighthouse, the Performance panel, the Profiler. They answer "**which resource, which function**", in the tool order from [#62](https://github.com/Fzgt/Blog/issues/62): Lighthouse → flame chart → long tasks → the Layout shifts track → React Profiler → Coverage.

**The classic lab-first failure**: you compress every image the way Lighthouse suggested, the score goes from 62 to 78, and the production LCP p75 does not move — because the test environment's APIs were mocked and the real bottleneck was the API.

Companion reading: what the metrics are → [#63](https://github.com/Fzgt/Blog/issues/63); which tactic for which bad metric → [#13](https://github.com/Fzgt/Blog/issues/13) (FID and TTI are both retired; that post explains); how to use the tools → [#62](https://github.com/Fzgt/Blog/issues/62).

**The output of diagnosis is one sentence with four parts: page, segment, metric, and which stage.** For example: "For mobile users on the product list page, LCP p75 is 4.2s, and resource load delay accounts for 2.8s of it." If you cannot produce that sentence, keep measuring; do not start changing things.

Run this site through it: the run in [#62](https://github.com/Fzgt/Blog/issues/62) came back with LCP 6.8s but CLS 0.001 and TBT 30ms. Those three numbers together *are* the diagnosis — **runtime is fine and the layout does not jump; the whole problem is the first-load chain**, and Lighthouse's top suggestion was render-blocking resources, estimated saving 470ms. That sentence decides that the next step is the delivery layer, and has nothing to do with components.

## Step 3: route by the diagnosis

This is the key step of the whole framework. Different conclusions have their fixes in completely different layers:

| Diagnosis | Which layer | See |
|---|---|---|
| First-load JS too big, long loading chain | Delivery | [#81](https://github.com/Fzgt/Blog/issues/81) splitting, [#69](https://github.com/Fzgt/Blog/issues/69) cache strategy, Coverage in [#62](https://github.com/Fzgt/Blog/issues/62) |
| LCP is an image, resource load delay is large | Delivery | The checklist in [#67](https://github.com/Fzgt/Blog/issues/67): `<img>` not CSS background, `fetchpriority`, preload, no lazy |
| LCP is an image, resource load duration is large | Delivery | [#67](https://github.com/Fzgt/Blog/issues/67) → [#68](https://github.com/Fzgt/Blog/issues/68) → [#65](https://github.com/Fzgt/Blog/issues/65) |
| LCP is text, blocked by a font | Delivery | `font-display`, preload the font file, `size-adjust` on the fallback |
| FCP and LCP both slow | Shared chain | Split front end from back end with TTFB first → [#63](https://github.com/Fzgt/Blog/issues/63); render-blocking resources → [#36](https://github.com/Fzgt/Blog/issues/36) |
| High TTFB | Server | Add `Server-Timing` before arguing about whose fault it is ([#63](https://github.com/Fzgt/Blog/issues/63)); redirect chains, CDN; [#79](https://github.com/Fzgt/Blog/issues/79) edge, [#77](https://github.com/Fzgt/Blog/issues/77) the SSR trade-off |
| LCP looks fine, users are still waiting | Server + business marks | The skeleton got counted as LCP and the bottleneck is the API → business-ready time in [#70](https://github.com/Fzgt/Blog/issues/70) |
| Bad INP, janky interaction | Code | Layers three to five of [#73](https://github.com/Fzgt/Blog/issues/73), the INP section of [#13](https://github.com/Fzgt/Blog/issues/13), the Interactions track in [#62](https://github.com/Fzgt/Blog/issues/62) |
| Bad INP, but `longestScript` is third-party | Delivery | Defer or move the analytics / support / ad SDK into a worker; start with Lighthouse's third-party audit |
| Bad CLS | Delivery / Code | Unsized images, font swap, content injected at the top → the Layout shifts track in [#62](https://github.com/Fzgt/Blog/issues/62) |
| Long blank first screen | Delivery | CSS/JS order and `defer` / `async` in [#36](https://github.com/Fzgt/Blog/issues/36); one level up, SSR in [#77](https://github.com/Fzgt/Blog/issues/77) |
| Long list drops frames on scroll | Code | [The virtualised list (main write-up)](https://apollo-five-omega.vercel.app/library?section=baidu&item=virtual-list), [#21 addenda](https://github.com/Fzgt/Blog/issues/21) |
| High-frequency events fire too often | Code | [#52 Debounce](https://github.com/Fzgt/Blog/issues/52) |
| Data arrives late (request waterfall) | Code | Layer two of [#73](https://github.com/Fzgt/Blog/issues/73) |
| Gets slower the longer it is used | Code | Subscriptions / timers not cleaned up; compare heap snapshots in the Memory panel; StrictMode's double run exists to surface exactly this ([#82](https://github.com/Fzgt/Blog/issues/82)) |

**The most common mismatch**: compressing images when INP is bad, wrapping things in `memo` when LCP is bad. Skip the diagnosis and everything after it is luck.

### When more than one page is slow

Real projects usually have several pages out of bounds, and you fix one at a time. Rank them with a product:

```
priority = share of users out of bounds × page traffic × business value ÷ cost of the change
```

The first two come straight from the route dimension in RUM ([#70](https://github.com/Fzgt/Blog/issues/70)); the last two are product's call and yours. A product list page 1 second over p75 matters far more than an admin settings page 3 seconds over.

## Step 4: fix — now the code layer, and now #73

Once you are in the code layer, follow the [five-layer order of #73](https://github.com/Fzgt/Blog/issues/73):

```
loading → requests → node count → where state lives → render cost
```

One qualification: **that ordering by payoff is about the loading path.** "Loading 300KB less JS saves hundreds of milliseconds; cutting one redundant render saves a few" holds for LCP-class problems. For INP-class problems the order flips — a single re-render of 3000 nodes taking 400ms (the example in [#63](https://github.com/Fzgt/Blog/issues/63)) *is* the main cause, and layers four and five come first. Which class you are in was settled in step 3.

#73's own "layer zero" is localisation inside the code layer (which component in the Profiler, which script in Performance), not this post's diagnosis — this post decides whether to enter the code layer at all; that one decides which layer to look at once inside.

Background concept: [#10 Pixels and the viewport](https://github.com/Fzgt/Blog/issues/10) (the prerequisite for DPR and anything to do with images or canvas).

**Change one thing at a time, and compare against the baseline after each.** Ship two changes together and the effect cannot be attributed, and you do not know which one to roll back.

## Step 5: verify, then lock it in

**Verification** has two layers with different rhythms:

- Lab: re-run the same profile, results the same day — but it only proves "the change took effect"
- Field: wait for the 28-day window to roll over ([#64](https://github.com/Fzgt/Blog/issues/64)); if you cannot wait, compare old vs new by the `release` / rollout-batch dimension in RUM ([#70](https://github.com/Fzgt/Blog/issues/70)) — CrUX cannot separate A/B groups, only your own RUM can

**Locking in** is about not sliding back. Change things without monitoring and in three months they are back where they were:

- Thresholds in CI: `size-limit` gates first-load bundle size, Lighthouse CI assertions gate LCP / TBT, and the PR fails when they are crossed
- RUM alerts: notify when p75 crosses the line, instead of finding out at the quarterly review

The monitoring chain only makes sense read in order:

```
#64 how CrUX counts   →  #66 the edge of web-vitals   →  #70 why still build an SDK  →  #16 bundling and engineering
  reading field data       it owns the calculation;         those four gaps + the context     no Webpack, multi-format
                           transport / sampling / SPA        layer are the reason to build     output, size budget
                           routing / errors are left open
```

**The [#66](https://github.com/Fzgt/Blog/issues/66) → [#70](https://github.com/Fzgt/Blog/issues/70) hand-off is the important one**: read #70 alone and you think "isn't there a library for this?"; read #66 first and you see what the library leaves out.

## The one-minute version

When an interviewer asks "how would you take on a slow project", say it in this order:

> Take a baseline first and wire up RUM. Do the hygiene checklist unconditionally. Diagnose field first, then lab, and produce one sentence naming the page, the segment, the metric and the stage. Route by that sentence: delivery layer, server layer or code layer. Inside the code layer, work in the order loading, requests, node count, where state lives, rendering — one change at a time. Finally, gate it in CI and alert on RUM so it does not slide back.

One line per dimension: do you have a method (the routing table), do you know the metrics (p75, the four-stage split), can you localise (attribution in the field, the tool order in the lab), have you done it (#62 and #65 on this site).

## Summary

> The order of performance work is not "which layer to start from"; it is "first know which layer the problem is in".
>
> Take a baseline; do the hygiene checklist unconditionally; diagnose field first, then lab, and produce one sentence naming the page, the segment, the metric and the stage; route by it to the delivery, server or code layer; change one thing at a time and verify; finally pin the result down with CI and RUM.
>
> Skip the diagnosis and the best case is that you happened to fix the right thing. Skip the baseline and the lock-in, and the best case is that you fixed it this once.

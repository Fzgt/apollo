# #4 · `5M+ daily page views`

> **材料说明**：百度的代码不在本机，这条没有行号可指，材料是 `LEARNING_NOTES_BAIDU.md` + 回忆。所以这一篇的重点不是「代码怎么写的」，而是**这个数字是从哪个系统、用什么手段统计出来的**——答不出口径，这个数就是编的。

## 对应简历原句

Baidu 第 2 条 bullet（v40）：

> Built a virtualized React feed **serving 5M+ daily page views** on a custom useVirtualList hook over IntersectionObserver: live DOM nodes stay near 100 at any scroll depth, scroll from 30 to a stable 60 FPS.

同一条 bullet 里有三个数字，但它们**性质完全不同**：

| 数字 | 性质 | 谁测的 |
|---|---|---|
| **5M+ daily PV** | 规模背书 | 埋点系统，你只是读报表 |
| DOM 节点恒定 ~100 | 优化成果 | 你自己用 DevTools 测的 |
| 30 → 60 FPS | 优化成果 | 你自己用 DevTools 测的 |

**这一篇只管第一个。** 后两个是审计表第 5、6 项，工具和方法完全是另一套。

---

## 一、这个数字在简历里扮演什么角色

**它不是你的成果，是你的工作环境。**

同样一个虚拟列表，写在个人博客上和写在日均 500 万 PV 的信息流上，工程含义完全不一样。后者意味着：一次掉帧影响的是百万量级用户、改动不能直接全量上、必须有性能监控和灰度。

**所以这个数字的作用是给后面的技术选择提供理由**——它解释了「为什么值得自己写一个 hook 而不是随便引个库」。

**`serving` 这个词用对了。** 它描述的是「承载」，不声称「带来」。如果写成 `drove` / `grew 5M+ daily page views`，那就是冒领增长，性质完全变了。**口头讲的时候也别把它讲成 brought 或 grew。**

---

## 二、PV 到底是什么口径

先把几个容易混的量分清楚：

| 指标 | 含义 | 同一个人刷 10 次算几次 |
|---|---|---|
| **PV**（Page View） | 页面浏览量 | **10 次** |
| **UV**（Unique Visitor） | 独立访客，按 cookie / 设备 ID 去重 | 1 次 |
| **DAU** | 日活跃用户，产品级指标 | 1 次 |
| **曝光量**（impression） | 内容被看见的次数 | 一次页面加载可能产生几十次 |

### 坑一：信息流里 PV 和曝光量差一个数量级

信息流的特点是**一次页面加载会滚动出几十条内容**。所以同一个 feed：

- PV 500 万
- 曝光量可能是 **5000 万甚至上亿**

**如果你记忆里那个数其实是曝光量，那 `page views` 这个词就用错了口径，数字还虚高十倍。** 这是这条最容易被问穿的地方——面试官只要问一句「你们信息流一次加载出多少条？曝光是分开统计的吗？」就能试出来。

### 坑二：SPA 里 PV 怎么算

这个坑很实际，而且直接影响数字大小：

- **传统多页应用**：一次 HTTP 页面加载 = 一次 PV，统计 SDK 自动上报，不用管
- **SPA（这个 feed 就是 React）**：路由切换**不重新加载页面**，统计 SDK 默认**不会**再报一次 PV，必须手动调 `_hmt.push(['_trackPageview', '/new-path'])`

所以同一个产品，埋点方式不同，PV 能差好几倍。**被问到「5M 怎么来的」，你得知道你们是不是在路由切换时手动补报的**——这是个只有真接过埋点的人才答得上的细节。

## 三、这个数是怎么测出来的（这一节是重点）

**先说结论：PV 不是「测」出来的，是「埋」出来的。**

前端没有任何 API 能告诉你「这个页面今天被打开了多少次」。唯一的办法是**每次被打开时往服务器发一条记录，后端累加**。

### 完整链路

```
用户打开页面
  → 埋点 SDK 触发上报
    → 一条 HTTP 请求打到日志服务器
      → 日志落盘 → 数仓 / 流处理聚合
        → BI 报表按天出 PV 数
```

**你（前端）只负责第一段。** 5M 这个数是从报表里读的，不是你算的。**这一点必须说清楚，因为它直接决定归因怎么写。**

### 工具：对外那套 —— 百度统计

笔记里记了它的机制（`LEARNING_NOTES_BAIDU.md` Bullet 1 第 ⑤ 点）：

- 页面里嵌一段**异步加载**的 SDK 脚本
- 页面浏览**自动上报**；自定义事件用 `_hmt.push(['_trackEvent', category, action, label, value])`
- **上报走 1×1 的 `hm.gif` 图片请求，不用 XHR**

**为什么用图片不用 XHR？** 两个原因，这是个高频冷问：

1. **图片请求不受同源策略限制**——`<img src="https://hm.baidu.com/hm.gif?...">` 天然跨域，不需要服务端配 CORS
2. **页面卸载时更容易发出去**——用户点了关闭/跳走，XHR 大概率被浏览器掐掉，图片请求存活率更高

（现代更好的做法是 `navigator.sendBeacon`，它就是浏览器专门为「卸载时可靠上报」提供的 API，还不阻塞卸载。能主动提这个是加分项。）

### 工具：内部那套（这部分是推测，讲的时候要标明）

好看视频、小度这类自家产品，日志一般**不走对外的百度统计**，而是走公司内部那套：内部埋点 SDK → 日志采集 → 数仓 → 内部 BI 看板。前端调的是内部封装好的上报方法，看数是在内部报表系统里。

**面试时怎么说**：如果记不清内部平台叫什么，就说**「走的是内部埋点和 BI 看板，不是对外的百度统计」**——这句话既准确又安全。**千万别硬编一个内部系统的名字**，编错了比说不知道难看得多。

### 行业里的同类工具（面试官可能拿来对比）

神策 Sensors Data、GrowingIO、Google Analytics 4、或者自建 Kafka + ClickHouse / Druid 那一套。原理都一样：客户端上报 → 日志聚合 → 报表。

### 为什么 PV 天然被低估

- 广告拦截 / 隐私插件会拦掉统计域名
- 用户秒退，SDK 还没加载完人就走了
- 网络失败、页面被系统直接杀掉

所以**真实访问量一般 ≥ 报表里的 PV**。这也说明**简历写 `5M+` 带个加号是合理的**，而不是含糊其辞。

## 四、按「审什么」逐条过

### ① 日均 PV 还是别的口径

必须说清三件事：

1. **是 PV**，不是 UV、不是 DAU、不是曝光量（见上面坑一）
2. **是「日均」**（一段时间的平均）还是**某个峰值日**
3. **统计周期**——你在百度是 2021 年 7 月到 2022 年 4 月，这个数是哪几个月的平均？

**推荐答法：给区间不给点。**

> 「在职后期这个 feed 的日均 PV 在 500 万量级，节假日和热点事件时峰值更高。」

给量级 + 说明有波动，比咬死一个精确数字可信得多。

### ② 平台数据还是页面数据

**这是这条最危险的一问。**

简历原句在语法上把 5M 归给了 feed 本身：`a virtualized React feed serving 5M+ daily page views`。所以它**必须是这个页面/模块的 PV**。

如果记忆里那个数其实是**整个 App 的 DAU** 或**全站 PV**，那这句话就是超售，必须改措辞。

**自查方法（今天可以自己算一遍）**：500 万日均 PV 的模块，按人均每天打开 3–5 次反推，对应 DAU 大概在**百万量级**。这个量级和好看视频那类产品的体量对不对得上？对得上就说得通；如果你记得产品 DAU 是几千万，那 5M 大概率是模块级的、没问题；如果产品本身就只有几十万 DAU，那 5M 一定是拿错口径了。

### ③ 个人贡献如何表述

**三句话记牢：**

- ✅ 「我负责的这个 feed 承载 5M+ 日均 PV」—— 描述工作的影响面
- ❌ 「我带来了 5M+ PV」—— 冒领增长
- ❌ 任何让面试官以为流量是你做出来的说法

**更进一步的答法**——把规模翻译成工程约束：

> 「这个量级意味着一次掉帧影响的是百万级用户，所以改动必须灰度、必须有性能监控。这也是为什么我们没有直接引一个第三方虚拟列表库，而是自己写了个可控的 hook。」

这样这个数字就从「吹牛」变成了「技术决策的依据」，是这条 bullet 最好的用法。

## 五、现在还能拿出证据吗

**不能，也不该。** 公司内部数据不能外带，面试官也知道你带不出来。

**所以这类数字，面试官考的不是证据，是口径。** 你说得出 PV 的定义、说得出它从哪个系统来、说得出统计周期和归属范围——这个数就可信；说不出，就是编的。

**一句话答法**

> 5M+ 是这个 feed 的日均 PV，从内部埋点上报到 BI 看板里读到的，不是我测的，也不是我带来的——它描述的是这个模块的体量。写在简历上是为了说明约束：这个量级下一次掉帧影响百万级用户，所以才值得自己写虚拟列表，而不是随便引一个库。

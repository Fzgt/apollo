---
title: Debounce in Depth — leading / trailing / cancel
---

Earlier I only wrote the most basic form: run n milliseconds after the last trigger. Real situations usually need a more flexible combination — should it run immediately on the first trigger, should it run again after things stop, and can a queued call be cancelled from outside.

#### ① What each of the three is for

- **leading**: run immediately on the first trigger, no waiting. Click protection needs the first press to give feedback at once.
- **trailing**: run once, some time after the triggers stop. A search box needs to wait until the user has finished typing.
- **cancel**: abandon a queued call from outside. On unmount or a route change, so a callback does not fire after the page is gone.

#### ② A correct implementation (every trap is in here)

```js
function debounce(fn, wait, immediate = false) {
  let timer = null;

  function debounced(...args) {
    const callNow = immediate && !timer; // is this the first call of a new round?

    clearTimeout(timer);
    timer = setTimeout(() => {
      timer = null; // crucial: reset so the next round can decide afresh
      if (!immediate) fn.apply(this, args); // in immediate mode, do not run again here
    }, wait);

    if (callNow) fn.apply(this, args); // run this one right away
  }

  debounced.cancel = function () {
    clearTimeout(timer);
    timer = null;
  };

  return debounced;
}
```

#### ③ Two easy mistakes

- **`timer` must be reset to `null` when it fires.** Without the reset, `immediate && !timer` is only ever true once in the function's whole life — once `timer` has been assigned, it never goes back to `null` unless you clear it. Leading behaviour would work on the very first call and never again, no matter how long you wait between triggers. This is a real bug and easy to miss.
- **Leading and trailing must not both run for the same trigger.** Without the `if (!immediate)` check inside the `setTimeout` callback, a single trigger in `immediate: true` mode runs twice — once immediately, once `wait` milliseconds later. `!immediate` makes the two paths exclusive: in immediate mode, `setTimeout` only counts down and resets the timer, it does not call `fn`.

#### ④ Why cancel needs both `clearTimeout` and `timer = null`

`timer` is just a JavaScript variable holding the numeric ID `setTimeout` returned. Setting it to `null` only throws away your receipt; the timer the browser registered is untouched and will still fire. The call that actually cancels it is `clearTimeout(timer)`. You need both: `clearTimeout` to cancel the browser's timer, and `timer = null` to keep the internal state consistent so the next `immediate && !timer` check is correct.

`clearTimeout` can only cancel a timer that has not fired yet and has not been pushed into the macrotask queue — once the callback is in the task queue it is too late. In practice, though, `cancel()` fires on unmount or a route change, which is comfortably inside the safe window, so this edge is not worth worrying about.

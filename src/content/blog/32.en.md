---
title: Hooks Can't Go in Conditionals, Loops, or Nested Functions — So What if the Business Logic Needs an if?
---

## Why not inside an `if` — the real issue is order

React keeps a component's state and effects in a singly linked list, and on each render it runs the hooks in the order they were declared. **As long as the order and the number of hook calls are identical on every render, there is plenty of room to decide whether the business logic runs.** The rule is not "this hook must never be triggered conditionally".

---

## Solution 1 (the usual one): move the `if` from "should I call the hook" to "should the hook's body do the work"

```javascript
// ❌ wrong: the hook itself is wrapped in an if, so the call count and order change
function MyComponent({ shouldFetch }) {
  if (shouldFetch) {
    useEffect(() => { fetchData(); }, []); // breaks the rule
  }
}

// ✅ right: call useEffect unconditionally, and move the if inside the callback
function MyComponent({ shouldFetch }) {
  useEffect(() => {
    if (shouldFetch) {   // the condition lives here
      fetchData();
    }
  }, [shouldFetch]);
}
```

This covers most cases where the business logic "needs an if": **always call the hook unconditionally, and put the real decision inside its callback.**

---

## Solution 2: if the whole block of logic is conditional, extract a child component

```javascript
// ❌ wrong: trying to decide conditionally whether to use a hook
function Parent({ showDetail }) {
  if (showDetail) {
    const [detail, setDetail] = useState(null); // breaks the rule
  }
}

// ✅ right: extract the block into a child; the parent only decides whether to render it
function Parent({ showDetail }) {
  return showDetail ? <DetailSection /> : null;
}
function DetailSection() {
  const [detail, setDetail] = useState(null); // inside the child, the hook is unconditional
}
```

**Conditionally rendering a whole child component is entirely legal.** Once `DetailSection` renders, the hook order inside it is fixed forever; when it does not render, the component does not exist and there is no order to change. This is the pattern the docs recommend.

---

## Solution 3 (niche, narrower): state outside the component (Zustand and friends)

This answers a **different** question from the first two. It solves "I do not want this state's lifetime tied to a component that may be mounted and unmounted conditionally" — you want the state remembered after the component unmounts, or shared across several conditionally rendered components.

**Note**: reaching for Zustand is not about the "no `useState` inside an `if`" rule. It is about the state not belonging to a conditionally rendered component in the first place. That is an architectural decision, not a general fix for the hook-order constraint.

---

## Choosing between them

| Situation | Solution |
|---|---|
| Whether the logic runs depends on a condition, but the hook is needed either way | 1: move the `if` inside the hook's callback |
| Whether a whole block of UI and logic exists depends on a condition | 2: extract a child component |
| The state has to outlive the component and persist across components | 3: an external state library |

**In short**: when the business logic seems to demand a hook inside an `if`, reach for solution 1 or 2 — those are the standard answers to the ordering constraint. Only when the real requirement is "this state should not be tied to a component's lifetime" do you need something like Zustand.

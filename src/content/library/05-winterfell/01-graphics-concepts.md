## 1. 渲染管线与 draw call:为什么"合并"是第一优化手段

**定义。** 一次 draw call = CPU 通过图形 API 让 GPU 画一批几何体。每次调用都要设置管线状态(着色器、材质、绑定资源),这部分开销在 CPU 侧。

**为什么它是瓶颈。** GPU 画三角形很快,**换状态很慢**。1000 个各自独立的小物体,GPU 干的活不多,但 CPU 要提交 1000 次状态切换,主线程先撑不住。所以浏览器 3D 的第一优化通常不是"减面",是"减提交次数"。

**三种合并手段与代价:**

| 手段 | 做法 | 代价 |
|---|---|---|
| **Instancing** | 同几何体+同材质的 N 个副本,一次提交,靠 per-instance 矩阵区分 | **一个包围体,逐实例视锥剔除消失** |
| **静态合并(merge)** | 编译期/加载期把多个静态网格焊成一个 | 失去单独变换、单独剔除、单独隐藏的能力 |
| **图集/材质合并** | 贴图合成图集以复用材质 | 打包复杂度、mipmap 边缘渗色 |

**WinterFell 里的例子。** 障碍用 instancing(每段两个 `InstancedMesh`),场景装饰用静态 merge(每公里瓦片合成少数几个 draw call),只有会动的(鱼、飞艇、涡轮、灯塔光束)保留独立动画实例。

**面试追问:**
- "instancing 一定更快吗?" → 不一定。密集近景更快;稀疏大范围场景里,失去剔除会让提交的几何体反而更多,**要量**。
- "剔除有哪几种?" → 视锥剔除(frustum,在相机可视体外)、遮挡剔除(occlusion,被别的东西挡住)、背面剔除(backface,GPU 免费给)。浏览器里 three 默认只做视锥剔除。

## 2. WebGPU vs WebGL2,以及 TSL 是什么

**WebGL2** 是 OpenGL ES 3.0 的浏览器绑定,状态机模型:全局状态一路 set,再 draw。**WebGPU** 对齐现代原生 API(Vulkan/Metal/D3D12):显式的**管线状态对象**、**绑定组**、**命令编码器**,提前把状态固化下来,提交时驱动几乎不用做验证。附带的大事是**原生 compute shader**。

**实际差异在哪:** 提交密集(很多 draw call、很多状态切换)的场景,WebGPU 的 CPU 侧开销显著更低;纯像素填充受限的场景,两者差别不大。**不要背"WebGPU 快多少"这种数字。**

**着色器语言不同:** WebGL 用 GLSL,WebGPU 用 **WGSL**。这就是 TSL 存在的原因。

**TSL(Three.js Shading Language)** 是 three 提供的**节点式着色器描述**:用 JS 组合节点搭出材质/后处理逻辑,three 在运行时把节点图编译成 WGSL 或 GLSL。价值是**一份描述,两个后端**。代价是它绑定 `three/webgpu` 这条新入口,传统 `WebGLRenderer` 执行不了节点管线——WinterFell 统一用 `WebGPURenderer` + `forceWebGL` 正是因为这个。

**面试追问:**
- "WebGPU 现在能用吗?" → Chrome/Edge 桌面端已默认开启,Safari/Firefox 与移动端参差,**所以 fallback 不是可选项**。
- "compute shader 你用了吗?" → 没用。老实说,并说明这个项目的瓶颈在提交次数和着色器编译,不在并行计算。

## 3. 着色器编译与 program key:一次卡顿的真正来源

**问题的形状。** 着色器不是运行时解释执行的,是**编译**成 GPU 程序的。编译发生在主线程/渲染线程上,一份复杂材质可能几毫秒到几十毫秒。一帧只有 16.7ms——**同一帧里编译一批材质,必然掉帧**。

**three 怎么管:** 它按材质的**特性组合**做缓存键(俗称 program key / program cache key),同样组合复用同一份编译产物。进这把钥匙的典型有:
- 场景是否有 **fog**、fog 的类型
- 灯光的数量与类型
- 是否 skinning / morph targets
- 启用了哪些贴图槽(map / normalMap / emissiveMap ...)
- 是否 instancing、是否顶点色、是否 shadow

**关键区分(必答):**
> **uniform 变了不用重编,program key 变了才要重编。**
> 颜色、强度、位置这类是 uniform,运行时上传;**"有没有雾""有几盏灯""开不开 instancing"是编译期分支**,一变就换一份程序。

**由此推出的两条实践:**
1. **别在运行时新建/替换会进 key 的对象**——比如每次换色就重建 `Fog`。改 uniform,别换身份。
2. **首次进入的卡顿**用预热解决:`renderer.compileAsync(scene, camera)` 或在加载页把材质各变体先渲染一次。但预热治不了"每次都重编",那是设计问题。

**怎么确认卡顿是编译引起的:** 统计**每帧新建的管线数**,和帧时长对齐。数量暴涨的那一帧就是编译帧。WinterFell 的 `bench/pipelines.mjs` 就是干这个的。

## 4. React Three Fiber:声明式壳子包命令式 WebGL

**它是什么。** r3f 是 three 的 React 渲染器:JSX 里写 `<mesh>`、`<instancedMesh>`,r3f 维护一棵与 three 场景图对应的树。`useFrame` 给你每帧回调,`useThree` 拿 renderer/scene/camera。

**必须记住的两条机制:**

1. **`args` 是构造函数参数,一变就重建实例。** 这是 r3f 的核心规则,也是 fog 那个 bug 的来源。可变的东西应该走 prop/mutation,不该走 `args`。
2. **`useFrame` 里不要 `setState`。** 每帧 setState = 每帧 React 重渲染。动画应该直接 mutate three 对象(`ref.current.position.x = ...`),让 React 只负责结构,不负责逐帧数值。

**r3f v9 的一个坑(这个项目踩过):** v9 不再在组件卸载时自动 dispose 几何体/材质。自建几何体多的项目会累积 GPU 资源。要么自己在 cleanup 里 dispose,要么复用而不是新建。

**面试追问:**
- "为什么用 r3f 而不是裸 three?" → 组件化的生命周期与状态复用(hooks 复用控制/渲染器逻辑),以及和 React 生态(状态管理、UI 层)天然接得上。代价是多一层抽象,出问题要能穿透它看到 three 本身——fog 那个 bug 就是必须穿透才能找到。
- "状态管理怎么分层?" → UI/游戏状态(分数、关卡、暂停)进 Zustand;逐帧的位置/矩阵不进任何 store,直接 mutate。**这条界线画错就是性能灾难。**

## 5. 浏览器里的性能测量:什么信号可信

**先说一个反直觉的结论:** **FPS 常常测不出东西。** 浏览器的帧呈现被**合成器**按显示器刷新率节流(常见 60/120Hz)。桌面 GPU 上,优化前后可能都顶格在 120 —— FPS 曲线一模一样,而 CPU 提交开销差了几倍。

**该看什么:**
- **draw call 数、三角形数**(three 里是 `renderer.info.render`)——直接反映提交成本。
- **每帧新建管线数**——反映着色器编译。
- **帧时长分布的尾部(p95/p99、最差帧)**,不是平均值。卡顿是尾部现象,平均值会把它抹平。
- **GPU 资源存活数**(buffer/texture 计数)——反映泄漏。

**无头浏览器的陷阱:** headless Chromium 里 WebGL 常退化成**软件光栅**,一帧几秒。所以**无头环境适合测"逻辑属性"(布局是否可通过、统计计数),不适合测"渲染速度"**。WinterFell 的公平性检验就是据此设计的:不试玩,直接对生成器做步进判定。

**面试追问:**
- "你怎么保证探针本身不影响结果?" → 单独测一遍探针开销(`bench/probecost.mjs` 就是问这个)。这个反问会让面试官注意到你懂测量污染。

## 6. 程序化生成:可玩性怎么做成可验证的属性

**核心思路。** 随机生成的关卡,"能不能通过"不能靠人试玩保证——试玩覆盖率极低,且一改参数全作废。正确做法是把可玩性**表述成一个可判定的性质**,然后对大量样本自动检验。

**判据设计的要点:** 判据必须用**玩家的实际能力**做尺子,不是几何上的"有没有缝"。WinterFell 用的是**该关卡速度下飞行器的横向可达距离**——够不够得着那条缝。

**必须有对照组。** 全部通过可能说明判据太松。拿随机撒布的布局跑同一套判据,它应该**失败**;失败了才证明判据有分辨力。这个思路和"测试必须能失败"是同一回事。

**参数化的一般原则(可迁移到任何随机内容):**
- 按**时间预算**而不是按距离约束密度——速度会变,距离不会告诉你玩家有多少反应时间。
- 难度维度之间要**互相买单**(高度用宽度换),否则多个维度同时取极值就会生成不可能的组合。
- 约束要对着**玩家感知到的量**解(可视距离),不是对着实现的分段解。

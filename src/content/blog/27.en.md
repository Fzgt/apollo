## 1. createContext + useContext + useReducer ≈ hand-rolled Redux

### 1. What createContext and useContext solve

**Prop drilling.** Instead of forwarding a value by hand through every level, skip them all and let a deep component read it directly.

```javascript
const ThemeContext = createContext('light'); // ① create the channel

function App() {
  return (
    <ThemeContext.Provider value="dark">  {/* ② start broadcasting */}
      <Toolbar />
    </ThemeContext.Provider>
  );
}
function Toolbar() {
  return <Button />; // ③ the middle layer does not care
}
function Button() {
  const theme = useContext(ThemeContext); // ④ tune in directly
  return <button>{theme}</button>;
}
```

### 2. Why these three add up to Redux

Redux is two things: **① a global store any component can read; ② one consistent set of rules for updating it.**

- `createContext` + `Provider` → ①: a global channel
- `useReducer` (`dispatch({type:'xxx'})` plus a reducer) → ②: exactly Redux's "dispatch an action, the reducer computes the new state"

```javascript
const StoreContext = createContext();

function App() {
  const [state, dispatch] = useReducer(reducer, initialState);
  return (
    <StoreContext.Provider value={{ state, dispatch }}>
      <DeepChild />
    </StoreContext.Provider>
  );
}
function DeepChild() {
  const { state, dispatch } = useContext(StoreContext); // any component at any depth gets state and dispatch
  return <button onClick={() => dispatch({type: 'increment'})}>{state.count}</button>;
}
```

No Redux dependency needed — three built-in React APIs give you the same thing in miniature.

### 3. That "≈" is not modesty — the gap is real

The code above has a fatal flaw: `value={{ state, dispatch }}` creates a **brand-new object** on every render of `App`. Context decides whether to notify its consumers with an `Object.is` comparison, and a new object is never equal to the old one, so:

**any change to `state` re-renders every component that calls `useContext(StoreContext)`** — including a component that only reads `state.theme` when all you changed was `state.count`. `React.memo` cannot stop it either: memo compares props, and context bypasses props entirely.

react-redux does not work this way. `useSelector` subscribes to an external store through `useSyncExternalStore`; each component subscribes only to the slice it selected, and **only a change to that slice re-renders it.** That is the real reason it is "≈" and not "=", and it is the first thing an interviewer asks next.

Two mitigations for the hand-rolled version:

**1. Wrap `value` in `useMemo`.** This only fixes half the problem — the half where the parent re-renders for some unrelated reason and hands down a fresh object. When `state` genuinely changes, everyone still re-renders.

**2. Split `state` and `dispatch` into two contexts.** This one is worth doing:

```javascript
const StateContext = createContext(null);
const DispatchContext = createContext(null);

function App() {
  const [state, dispatch] = useReducer(reducer, initialState);
  return (
    <StateContext.Provider value={state}>
      <DispatchContext.Provider value={dispatch}>
        <DeepChild />
      </DispatchContext.Provider>
    </StateContext.Provider>
  );
}
```

`dispatch` has a stable identity (`useReducer` guarantees it does not change across renders), so once they are split, a component that only dispatches and never reads `state` — a plain action button, say — stops re-rendering on state changes entirely.

If you genuinely need selector-level subscriptions, stop hand-rolling and reach for Redux Toolkit, Zustand, or Jotai.

## 2. Event delegation

### 1. Handlers and delegation

- **An event handler** is the function called when the user acts: `onClick={() => {...}}`.
- **The naive approach**: bind a listener to every element. A thousand buttons means a thousand listeners, which costs resources.
- **Delegation**: bind **one** listener on an ancestor. The browser's native bubbling carries a click on any descendant up to that ancestor, where the single listener catches it and uses `e.target` to work out what was actually clicked.

### 2. How React uses it

Every `onClick={...}` you write does **not** attach a native listener to that DOM node. React attaches **one** listener in a single place; every event bubbles up to it, and React works out which component's callback should fire and calls it.

**There is an exception list, though.** React's source keeps a `nonDelegatedEvents` set (`DOMPluginEventSystem.js`) whose events are still attached **directly to the element itself**, with no delegation:

```javascript
export const nonDelegatedEvents = new Set([
  'beforetoggle', 'cancel', 'close', 'invalid',
  'load', 'scroll', 'scrollend', 'toggle',
  ...mediaEventTypes,   // play/pause/ended/error/loadeddata… every media event
]);
```

The comment right above it says why:

> We should not delegate these events to the container, but rather set them on the actual target element itself. This is primarily because **these events do not consistently bubble in the DOM.**

Delegation rests entirely on bubbling. `scroll`, `load`, `error` and the media events either do not bubble natively or do so inconsistently, so a listener on the root container would never hear them; they have to go on the element. So "React delegates all its events" is wrong — **almost all of them, with one explicit exception list.**

### 3. `document` (old) vs the root container (new)

- **React 16 and earlier**: however many independent React trees were on the page (`#app`, `#header`, `#footer`, each with its own `ReactDOM.render`), all of them attached their listener to **`document`** and shared one listening point.
- **React 17 onwards**: each `ReactDOM.render()` attaches its listener to **its own root container** (the `#app` div, say). No more shared document.

### 4. Why sharing `document` broke `e.stopPropagation()`

The situation: your site has its own React rendering `#app`, and embedded inside it is a third-party widget with **its own separate React** rendering `#widget`.

- A click inside the widget calls `stopPropagation()`, meaning "do not let this affect the site outside".
- But **both Reacts attach independently to the same `document`.** The `stopPropagation()` the widget's React calls is just a note to itself; the site's React is a completely separate copy of the code, knows nothing about that note, receives the same bubbled native event, and handles it as usual — ignoring the widget's intent entirely.

**"The inner tree stopped propagation and the outer tree still received it"** is exactly this: two independent Reacts sharing one listening point, each talking only to itself.

### 5. How React 17 fixed it

By moving the listener from the shared `document` to each tree's own root container. Now when the widget calls `stopPropagation()`, the **browser's own bubbling** stops the event before it reaches the site's `#app` listener, physically, because the two listening points now have a real parent-child relationship in the DOM instead of both sitting at the same endpoint.

## Worth remembering

> **Context + useReducer**: Context handles the global broadcast, `useReducer` handles the rules for changing the data. Together they are Redux in miniature — but the price of "in miniature" is that any change to state re-renders every consumer indiscriminately, with no `useSelector`-style slice subscription. What you can do is split state and dispatch into two contexts.
> **Event delegation**: do not bind a listener per element; let bubbling bring everything to one node. React 17 moved that node from the shared `document` to each tree's own root container, which fixed `stopPropagation` when several Reacts coexist. Mind the `nonDelegatedEvents` exception list — `scroll`, `load`, `error` and media events do not bubble, so they are still attached directly to the element.

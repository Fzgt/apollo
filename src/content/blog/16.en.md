---
title: "Bundling a performance monitoring SDK — why not Webpack, output formats, size budget"
---

> Following on from [#70](https://github.com/Fzgt/Blog/issues/70): once you have decided to build your own, this is how that layer gets bundled. The conclusions come from the actual configuration of [Performance-SDK](https://github.com/Fzgt/Performance-SDK).

Bundling a monitoring SDK is not the same problem as bundling an application. An application needs to run; an SDK needs to **work however someone imports it, and stay as small as possible** — because it sits on the first-paint blocking path. That is exactly the "the monitoring drags down the metric it is monitoring" point from [#70](https://github.com/Fzgt/Blog/issues/70).

---

## 1. Why not Webpack

Webpack's value is its **loader and plugin ecosystem** — CSS, images, fonts, every kind of non-JS asset.

A monitoring SDK is **pure TS/JS** with no non-JS assets at all. Using Webpack means paying for the configuration complexity without buying its core strength, and the output carries Webpack's runtime glue on top.

The right tools are the ones built for **bundling libraries**:

| Tool | Notes |
|---|---|
| **Rollup** | The de facto standard for libraries; the best **multi-format output**, and the cleanest tree-shaken result |
| **esbuild** (Go) | An order of magnitude faster, but less precise on output formats and tree-shaking |
| **swc** (Rust) | A Babel-class transpiler with esbuild-class speed; usually sits underneath other tools |
| **microbundle** | A zero-config wrapper around Rollup, aimed at small libraries |

**Performance-SDK uses microbundle** — `"build": "microbundle"` and nothing else. It derives the outputs from `package.json` fields. For a library this small, zero config beats a hand-written Rollup setup.

---

## 2. Which output formats to cover

Consumers may be in any environment, so multi-format output is a hard requirement:

| Format | Who needs it |
|---|---|
| **ESM** | Modern bundlers (Vite / Rollup / Webpack 5); tree-shakeable |
| **CJS** | Node, and older Webpack setups |
| **UMD / IIFE** | **A plain `<script>` tag** — monitoring SDKs particularly need this; plenty of teams just want one line in their HTML |

> ⚠️ Correcting an error in the earlier version of this note: **CMD does not need supporting.** CMD is Sea.js's module format and has long been obsolete; neither Rollup nor microbundle emits it. The three to cover are ESM / CJS / UMD, with AMD only mattering for projects still on RequireJS.

`package.json` points the way:

```json
{
  "main": "dist/index.js",              // CJS entry
  "module": "dist/index.module.js",     // ESM entry, preferred by bundlers
  "types": "dist/typings/index.d.ts",   // type declarations
  "files": ["dist", "src"]              // what gets published
}
```

Shipping `src` lets consumers step into the source while debugging.

## 3. Size is a hard constraint

The SDK sits on the blocking path, so its own weight eats the metric it reports. Three rules:

1. **No polyfills.** The target is browsers that support `PerformanceObserver`; a polyfill is pure overhead.
2. **No heavy dependencies.** If ten lines will do, do not add a package.
3. **Set `sideEffects: false`** so consumers' bundlers can tree-shake the collectors they do not use.

For reference: `web-vitals` is around **3 KB** brotli'd in its standard build, noticeably more with attribution (see [#66](https://github.com/Fzgt/Blog/issues/66)). If your own collection layer is an order of magnitude past that, something is being bundled that should not be.

**Splitting the build is common**: core metrics on one entry, optional features — error capture, resource timing — behind subpath exports, so consumers who skip them never download them.

## 4. Types and documentation

For a TypeScript library the declarations are part of the product. Two tools earn their place:

- **`@microsoft/api-extractor`** — rolls scattered `.d.ts` files into one and emits an **API report file**. Commit that report, and **every change to the public API shows up in the diff** — effectively a lock on breaking changes.
  ```
  api:run → api-extractor run --local --verbose
  ```
- **`typedoc`** — generates an API documentation site straight from the comments.

For an SDK several teams integrate with, "the API changed and nobody noticed" is the most expensive kind of incident. api-extractor exists to prevent it.

## 5. Test environment

The SDK is nothing but browser APIs — `PerformanceObserver`, `navigator.sendBeacon`, `visibilitychange` — none of which exist under Node.

So Jest needs **`jest-environment-jsdom`**, plus mocks for the APIs in use, set up in `setupFilesAfterEnv`:

```js
// jsdom has no PerformanceObserver, so supply one
global.PerformanceObserver = class {
  observe() {}
  disconnect() {}
};
navigator.sendBeacon = jest.fn(() => true);
```

Utility libraries want coverage close to 100%: a bug hits every consumer at once.

---

## 6. Verifying locally

Unit tests are not enough. Much of an SDK's behaviour — reporting on `visibilitychange`, bfcache restores, long-task capture — **can only be verified in a real browser**.

Keep an `examples/` directory, serve it, and check by hand:

- [ ] Switch tabs — does a beacon actually leave, per the Network panel?
- [ ] Navigate back (bfcache) — do the metrics recompute?
- [ ] Throw an error — does it take the URGENT path via `fetch` + `keepalive`?
- [ ] Load the built bundle through a plain `<script>` — does it run?

---

## Summary

| Decision | Reason |
|---|---|
| Not Webpack | An SDK is pure JS; no loaders needed, and it adds a runtime layer |
| Rollup family (microbundle) | Multi-format output plus clean tree-shaking |
| ESM / CJS / UMD | Covers bundlers, Node, and plain `<script>` |
| No polyfills, no heavy deps | It is on the first-paint blocking path |
| api-extractor | Public API changes become visible in the diff |
| jsdom plus manual mocks | Browser APIs do not exist under Node |
| Keep `examples/` | Reporting timing and bfcache can only be checked in a real browser |

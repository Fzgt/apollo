> This is the pocket version of [#90](https://github.com/Fzgt/Blog/issues/90): the thing to read the night before an interview — conclusions only, no reasoning. The number after each line is where to read more.

## The 30-second version

> Take a baseline first and wire up RUM. Do the hygiene checklist unconditionally. Diagnose field first, then lab, and produce one sentence: "which page, which users, which metric, stuck at which stage". Route by that sentence — delivery layer, server layer or code layer. Inside the code layer, work in the order loading, requests, node count, where state lives, rendering, one change at a time. Finally, gate it in CI and alert on RUM so it does not slide back.

The closing line: **the order of performance work is not "which layer to start from"; it is "first know which layer the problem is in".**

## Numbers to memorise

| Metric | Good / poor | Notes |
|---|---|---|
| LCP | ≤ 2.5s / > 4s | Four stages: TTFB → resource load delay → resource load duration → element render delay; **the second stage is where things most often go wrong** |
| INP | ≤ 200ms / > 500ms | Three segments: input delay → processing → presentation; close to the worst interaction, not the average |
| CLS | ≤ 0.1 / > 0.25 | The largest session window, not a running total |
| TTFB | ≤ 800ms | Includes redirects, DNS, TLS; slow ≠ slow backend — split it with `Server-Timing` |
| Long task | > 50ms | Main thread held for more than 50ms |
| CrUX | p75, 28-day rolling, Chrome only, traffic threshold | After a change ships, 2–4 weeks before it shows |
| Lighthouse weights | TBT 30%, LCP 25%, CLS 25% | FID retired 2024-03, TTI retired in Lighthouse 10 |
| First-load JS | 30–120 KB gzipped is acceptable | This site's three chunks: 32 / 50 / 40 KB |

## Follow-up prep

- **"Lighthouse went up but production didn't move?"** — Lab is one simulated run, field is a distribution. The classic failure: the test environment's APIs were mocked and the bottleneck was the API.
- **"Why does `memo` come last?"** — Loading 300KB less saves hundreds of milliseconds; cutting one render saves a few. But that is an LCP statement; in an INP problem a single re-render of 3000 nodes taking 400ms *is* the cause, and the order flips.
- **"How do you debug bad INP?"** — In production, `web-vitals/attribution` gives `interactionTarget`, the three-segment split and `longestScript`; locally, the Interactions track in the Performance panel with 4x CPU throttling to reproduce. TBT is only a load-time proxy and cannot see post-load interactions.
- **"What if LCP is an image?"** — Discovery timing before size: `<img>` not a CSS background, `fetchpriority="high"`, `preload`, and never `loading="lazy"`. Compression is third; sizing to fit and going lossy are the big wins.
- **"Does splitting help a single-entry app?"** — Yes, but the goal is cache stability and parallel download, not de-duplication or a smaller total. webpack needs `chunks: 'all'`; Vite uses `manualChunks`. If the output is already small, don't split.
- **"Does route-level lazy loading have a cost?"** — One extra round trip on navigation, covered by hover prefetching: `onMouseEnter={() => import(...)}`.
- **"How do you prove the optimisation worked?"** — Baseline before, same-profile re-run after; in production wait out the 28-day window, or compare by the release / rollout-batch dimension in RUM. CrUX cannot separate A/B groups.
- **"Why build an SDK when web-vitals exists?"** — web-vitals is the metric-calculation layer; transport, sampling, SPA route attribution and error correlation are left open. The reason to build is context: business line, route pattern, rollout batch, and "business-ready ≠ LCP". In one line: what you buy does not know your business.
- **"What does SSR improve?"** — FCP / LCP, the bundle (RSC), request waterfalls. TTFB and server cost get worse; INP is unchanged. Do not say SSR improves TTI.

## Five wrong answers to avoid

1. Compressing images for bad INP, wrapping in `memo` for bad LCP.
2. Lab before field; reporting a Lighthouse 90.
3. Putting splitting and route-level lazy loading on the "unconditional" list.
4. Saying useEffect always runs after paint, or that a click's setState goes through the Scheduler.
5. Calling FID or TTI core metrics.

## The "have you done it" dimension

- This site's Lighthouse run: LCP 6.8s but CLS 0.001 and TBT 30ms → the whole problem was the first-load chain; the top suggestion was render-blocking resources, estimated saving 470ms. → #62
- 58 screenshots, 23.7 MB, converted to lossy WebP at 2.4 MB, 9.8x — the bulk of it from going lossy, not from the format. → #65
- Virtualised list: DOM from 500+ to a constant dozen or so, 30 → 60 FPS. → the library write-up, #21

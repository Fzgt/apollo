## INP (Interaction to Next Paint)

**INP replaced FID as a Core Web Vital in March 2024.** The techniques below used to be filed under FID, but FID only measured the first of the three segments (input delay), which is why its numbers were universally too flattering.

Thresholds: **≤200ms good / 200–500ms needs improvement / >500ms poor**.

### Break up long tasks

Most bad INP comes down to the main thread being occupied, leaving the click event queued behind it.

Common sources: parsing large JSON, complex DOM work, bulk data processing, third-party library initialisation, image and video processing.

The fix is **interruption, not speed**:

- `scheduler.yield()` or `setTimeout` to hand the main thread back
- Move heavy computation into a **Web Worker**
- Split the bundle so initialisation cost is spread out (with `lazy` in React; a plain `import()` is already lazy)

### Code splitting

Route-level splitting is the highest-value single change:

```js
const Home = lazy(() => import('./Home'));
```

Webpack emits an async chunk automatically and the first-load bundle drops immediately.

> Since HTTP/2 there is no need to fight the old "six connections per origin" limit — multiplexing carries many files in parallel. **But do not over-split either**: every file still costs a request.

### React's concurrency

⚠️ **Wording matters**: there has been no "concurrent mode" since React 18 — that was the React 17 experimental framing. What exists now are concurrent **features**, on by default, but **only updates marked with `startTransition` / `useDeferredValue` enter the interruptible lane**.

So what it improves is **INP, not FID** — it lets rendering be interrupted so user input can jump the queue, which is precisely the "input delay" and "processing time" segments of INP. See the causality section in [#73](https://github.com/Fzgt/Blog/issues/73) and [#82](https://github.com/Fzgt/Blog/issues/82).

## LCP (Largest Contentful Paint)

Target **2.5s**. Pulling this in is what makes a page *feel* fast.

Per the four-part breakdown in [#63](https://github.com/Fzgt/Blog/issues/63), **the segment that goes wrong most often is the second — how early the resource is discovered**, not its size:

```
① TTFB → ② resource load delay → ③ resource load duration → ④ element render delay
                 ↑ the one that gets overlooked
```

- **`fetchpriority="high"`** — tell the browser this image comes first

  <img width="400" height="200" alt="Image" src="https://github.com/user-attachments/assets/6dc61195-7f45-4c5c-8ae3-e52bbbc3020b" />

- **`<link rel="preload" as="image">`** — for images that would otherwise only be discovered after JS renders the DOM
- **`dns-prefetch` / `preconnect`** — when the image is on a third-party origin. Note `dns-prefetch` only resolves DNS; use `preconnect` to get the TCP and TLS handshakes out of the way too

- **Never put `loading="lazy"` on the LCP image** — the classic self-inflicted wound; see the checklist in [#67](https://github.com/Fzgt/Blog/issues/67)

## FCP (First Contentful Paint)

The typical SPA problem: the page renders through a single `<div id="app">`, whose contents only appear after the data request, the diff and the append — and only then does FCP fire. **While the JS is downloading and executing, the page is blank.**

So the fixes all live on the loading path:

- Fewer render-blocking resources (CSS and synchronous JS) — see [#36](https://github.com/Fzgt/Blog/issues/36)
- First-load JS size — see [#81](https://github.com/Fzgt/Blog/issues/81)
- Server rendering, so the first screen's content arrives inside the HTML

**FCP and LCP share the same prefix of the chain**: both slow means the problem is in the shared part (TTFB or render-blocking resources); FCP fast and LCP slow means the problem is the LCP element itself.

## TTFB

**A slow TTFB does not mean a slow backend.** It spans redirects → DNS → TCP → TLS → server processing → first byte, and only the last part is the backend. Splitting responsibility precisely requires a `Server-Timing` response header. Expanded in [#63](https://github.com/Fzgt/Blog/issues/63).

## On TTI: it has been retired

**TTI was removed from Lighthouse 10 and no longer contributes to the score.**

It was too sensitive to a single long task, too noisy, and impossible to collect from real users. What took over:

| | Now use |
|---|---|
| Lab measure of "how busy is the main thread" | **TBT** (30% of the Lighthouse performance score) |
| Real-user interaction responsiveness | **INP** |

The old advice "use SSR to improve TTI" pointed in a reasonable direction — SSR does get content on screen earlier — but note that **SSR does not reduce JS size and hydration still costs the same**. TTI/TBT stay where they were; what SSR improves is mainly FCP and LCP.

## Long tasks

**Any task occupying the main thread for more than 50ms without yielding.**

Why 50ms: 60fps allows 16.7ms per frame, and human tolerance for "instant" is around 100ms. After leaving the browser some room to render and schedule, a single task past 50ms risks pushing interaction response outside that 100ms comfort zone.

How to find them, and the relationship with Fiber's time slicing, is in [#36](https://github.com/Fzgt/Blog/issues/36) and the long-task section of [#62](https://github.com/Fzgt/Blog/issues/62).

## Pre-rendering and SSR

**Skeleton screens versus pre-rendering**: a skeleton has no value to the user, it is a placeholder. Fill it with real content and it becomes pre-rendering.

Pre-rendering works through a headless browser: at build time each route is run once and the rendered result saved as a static page.

> The mechanism is crude — **it simply waits**, as long as it reasonably can, and saves whatever the DOM looks like when it gives up. If the data has not arrived by then, the "pre-rendered" page is saved incomplete.

<img width="450" height="300" alt="Image" src="https://github.com/user-attachments/assets/6cc8640c-2ce9-4f09-a902-34645f93a81c" />

So its range is narrow: fairly static pages only, prone to failing for incidental reasons, and weaker for SEO than SSR.

### Isomorphic rendering

Isomorphic rendering removes the need for those workarounds: **the first load behaves like an MPA (HTML from the server), subsequent navigation like an SPA.**

| | Upside | Downside |
|---|---|---|
| **SPA navigation** | Minimal content transferred | The first screen waits for JS |
| **MPA** | Skips a pile of client-side requests | Re-loads assets between routes |
| **Isomorphic** (Next.js / Nuxt.js) | Both upsides | Complexity and server cost |

> One practical difference: **sharing client state costs more under SSR** — on the server a store only covers a single request's full-page render, whereas in pure CSR it lives across the whole site session.

The full trade-off analysis is in [#77](https://github.com/Fzgt/Blog/issues/77).

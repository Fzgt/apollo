---
title: Cookies, Sessions, and Tokens
---

- A cookie holds things like the session ID, `httpOnly`, and `secure`. It keeps the user logged in so they do not have to sign in again on every visit. The account and password are never stored in it. The browser handles both sending and storing: every HTTP request carries the cookie automatically, and when a response sets `Set-Cookie` the browser writes it back on its own.
  The session ID is the server's ticket for finding the session data. It *is* the login state — as long as it has not expired or been revoked, the user stays signed in.
  A token is what you reach for on clients that have no cookie mechanism at all, like a mobile app or a mini program: it carries the session and tells you whether the login has expired.
- A token has three parts. The header carries the signing algorithm (for example `HS256` = HMAC-SHA256) and the token type (JWT). The payload carries the data. Header and payload are **Base64URL-encoded, not encrypted** — anyone can decode and read them, so the payload must not carry secrets. The third part, the signature, is an HMAC-SHA256 (or an RSA / ECDSA signature) over the first two segments **using the server's secret key**. The key is the whole point: with a bare SHA-256 hash the front end could forge the signature and the scheme would collapse.

- Tokens exist because cookie behaviour runs into limits.
  Apps and mini programs are not browsers and have no cookie mechanism.
  When the backend is a cluster — several servers, with the session sitting in the database of only one of them — or when you are running at the edge, session data cannot be shared. A token is stateless: any server can decode it, verify it, and check the expiry. Nothing has to be stored.
  And when the front end spans several sites, cross-site requests only carry cookies with `SameSite=None; Secure` plus `credentials: 'include'`; on other platforms (apps, mini programs) there is no cookie mechanism at all.
- The front end only has to Base64-decode the second segment to read the data. The backend verifies the signature in the third segment on every request to decide whether to let it through. JWT needs no storage on either side — it is just an encoded string.

### Tokens are stateless authentication

- JWT and similar token schemes
- The session data is encoded straight into the token (username, role, and so on)
- The server stores no session — the token itself is the identity
- The client sends the token with each request, usually as `Authorization: Bearer xxx`

When the server receives the request it:

- verifies the signature, to confirm the token was not forged;
- checks whether the token has expired;
- reads the identity (`userId`, for example) straight out of the payload.

### Why web front ends still keep the token in a cookie

- Browsers send cookies automatically across requests within the same site and its subdomains, which is less work than `localStorage`.
- If the web app calls several subdomain APIs (`api.example.com`, `static.example.com`), the cookie rides along on its own.
- On mobile — apps and mini programs — there is no cookie mechanism, so you have to put the token in the request header yourself.

# 这个数字不是性能指标，是证据

> ⚪ **速查**。⭐ **看懂这一点，这条 bullet 就从「我们测试跑得快」变成「我们的依赖隔离做对了」。**

## 对应简历原句

> ...so the whole system runs with no API keys and no network: 406 server tests, **about a second end to end**.

（seam 的技术细节见 [④ 406 server tests](/docs?section=periplus&item=n14-server-tests)，这一篇只管这个时间数字。）

## 一、先定掉一个歧义：`end to end` 指什么

| 读法 | 指什么 |
|---|---|
| ✅ **A** | **整个测试套件**从头跑到尾约一秒 |
| ❌ **B** | 一次六阶段流水线**跑完**约一秒 |

**正确的是 A。** 从语法看它跟在 `406 server tests` 后面，修饰的是那 406 个测试。

> ⚠️ **但 `end to end`（端到端）这个词在工程语境里通常指「端到端流程」，很容易被听成 B。** 面试官如果按 B 理解，会问「一秒就跑完六个阶段？那模型调用呢？」—— **你得能立刻分辨他问的是哪个。**
>
> **想更清楚可以改成 `406 server tests in about a second`** —— 把 `end to end` 换成 `in`，歧义就没了。

## 二、实测数据（已核准）

```bash
cd server && uv run pytest
```

```
403 passed, 3 skipped in 1.38s
```

**用 `time` 包住整条命令：**

```
1.26s user  0.21s system  82% cpu  1.768s total
```

**两个数字都对，但含义不同 —— 这正是审计要问的。**

## 三、按「审什么」逐条

### ① 什么命令

`cd server && uv run pytest`。项目配置里已经设好了默认参数，不用带任何选项。

### ② 串行还是并行

**串行，单进程。**

**证据**：开发依赖里只有 `pytest` 和 `pytest-asyncio`（异步测试支持），**没有装 `pytest-xdist`**（那是并行插件）。

> ⭐ **这一点反而是加分的**：**1.38 秒是单进程串行跑完 403 个用例，不是靠开 8 个进程堆出来的。**
>
> **没有并行还这么快，说明快的原因是「没有 IO 等待」，不是「有并发」。**

### ③ 含不含收集用例的时间

**这是两个数字的差别所在：**

| 数字 | 含什么 | 不含什么 |
|---|---|---|
| **1.38s**（pytest 自己报的） | **含**收集用例 + 执行 | 不含 Python 解释器启动、模块导入、`uv` 自身开销 |
| **1.77s**（`time` 量的） | 含**全部** —— 从敲回车到回到提示符 | — |

> **报哪个都说得通**（1.38 和 1.77 都能叫「约一秒」），**但被问到时要能说清报的是哪个**。
>
> **推荐报 pytest 自己那个 1.38 秒**，因为它是**可比的** —— 换台机器 `uv` 的启动开销不一样，但套件本身的执行时间可比。

### ④ 哪台机器

这台 MacBook Pro（16 GB 内存）。

**并且要主动补一句**：这个数字**对机器不敏感** —— 因为它是**纯 CPU 计算、没有任何 IO 等待**。换台机器可能变成 0.9 秒或 2 秒，**但不会变成 30 秒**。

> ⭐ **这个「不敏感」本身就是论点**：如果套件里还残留任何一个真实网络调用，**机器和网络环境一变，时间会跳一个数量级**。**稳定在秒级，说明 IO 真的清干净了。**

## 四、为什么能这么快

**逐条拆开，每一条都对应 [④ 406 tests](/docs?section=periplus&item=n14-server-tests) 里的一个 seam：**

| 省掉了什么 | 靠哪个 seam | 如果没有会慢多少 |
|---|---|---|
| **网络往返** | 假的 HTTP 传输层 | 每次抓页几百毫秒，几十个页面就是十几秒 |
| **真实等待** | 假时钟 | 抓取模块里每个域名之间要等 1 秒，**光这一项就够喝一壶**；超时用例更是要等满 |
| **模型调用** | 脚本化的模型客户端 | 一次模型调用几秒起 —— ⭐ **这一项就能把套件拖到分钟级** |
| **向量模型加载** | 哈希技巧做的假向量 | 加载一个真的向量模型权重要几秒到几十秒 |
| **数据库往返** | 3 个用例被跳过 | 连接 + 建表 + 清理 |

> **最后那个假向量特别值得注意**：它用「**把词哈希到固定的桶里再归一化**」造出确定性向量，**整个测试过程根本不导入那个重量级的向量模型库**。**这不只是快，也让测试不依赖模型权重文件的存在。**

## 五、⭐ 这个数字真正的意义

**它不是在说「我们测试跑得快」，而是在说「我们的依赖隔离是完整的」。**

**理由很简单：这四类 IO，只要漏掉任何一个，时间就会立刻跳一个数量级。**

- 漏一个网络调用 → 几秒到几十秒
- 漏一个真实等待 → 按秒累加
- 漏一个模型调用 → 分钟级

> ⭐ **所以「一秒」是个证明，不是个成绩。它证明的是：没有任何一条测试路径偷偷溜出了进程。**
>
> **这是把 [④ 406 tests](/docs?section=periplus&item=n14-server-tests) 和这一条串成一个论点的方式**：那一条说结构（四个 seam），**这一条说这个结构真的没漏。**

## 六、⭐ 这是唯一一个能被当场验证的数字

**其他数字要么在公司内网、要么需要特定环境、要么是别人系统里的口径。**

**这一条不一样：面试官 clone 仓库、装依赖、跑一条命令，一秒后就能自己看到结果。不需要 API key，不需要网络。**

**主动提出这一点，效果比数字本身大得多：**

> 「这个仓库是公开的，`cd server && python -m pytest` 就能跑，**不需要任何 key 也不需要联网 —— 您现在就能验证。**」

> ⭐ **一个能被当场验证的数字，会让面试官对你其他所有数字的信任度一起上升。**

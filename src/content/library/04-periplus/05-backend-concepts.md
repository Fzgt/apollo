## 1. 后端框架的两种模型:同步 vs 异步(Node.js/NestJS、FastAPI、Django)

**是什么:** 一个 HTTP 请求进来后,服务器怎么"同时"处理很多个请求,大体分两条路。同步阻塞模型下,每个请求占一个线程/进程,线程在等 IO(数据库、外部 API)时被挂起,靠多线程/多进程堆并发;异步事件循环模型下,单线程里所有 IO 等待都注册成回调/`await`,线程从不真正阻塞,靠"在等待的间隙切去处理别的请求"堆并发。

**为什么存在这个区分:** 大部分后端请求的耗时主要花在等 IO(等数据库、等下游服务),而不是纯 CPU 计算。为一个"主要在等"的任务分配一整个操作系统线程是浪费的,异步模型用更少的系统资源撑更高的并发量。但异步模型对写代码的人要求更高——一旦某处不小心跑了一段同步阻塞的 CPU 密集代码,会卡住整个事件循环,拖慢所有并发请求,这是同步模型不会有的坑。

**框架对应关系与权衡:**
- **Node.js / NestJS**:Node 本身就是单线程事件循环,`async/await` 是语言原生的;NestJS 是在此之上加了一层 Angular 风格的模块化架构(`Module`/`Controller`/`Provider`/依赖注入容器),解决的是"Express 太自由、大型项目缺乏统一结构"的问题,代价是概念多、装饰器多,学习曲线比裸 Express 陡。
- **FastAPI**:Python 里的异步选择,基于 ASGI + `asyncio`,靠 Pydantic 做类型标注和自动 OpenAPI 生成,是三者里"类型提示驱动开发体验"最好的。
- **Django**:传统上是同步、多线程/多进程(WSGI)模型,近几年加了 `async def` 视图支持,但生态里大量三方库(尤其是 ORM 相关)仍然是同步的,异步化是"半吊子"状态,真正发挥异步优势要格外小心。Django 的核心卖点从来不是异步性能,而是"电池齐全"(ORM、admin 后台、认证、表单一整套开箱即用)。

**Periplus 例子:** 后端选的是 FastAPI 全异步路线——路由函数是 `async def`,Postgres 用异步连接池,长跑的 AI 流水线丢进 `asyncio.create_task` 后立刻返回,不阻塞事件循环。

**可能被追问:**
- 异步模型下,如果某个第三方库只有同步接口(比如某些老的 SDK),怎么在不阻塞事件循环的前提下调用它?(答案方向:丢进线程池,`run_in_executor` / `asyncio.to_thread`。)
- 为什么说异步模型对"CPU 密集型任务"没有帮助,甚至更差?
- NestJS 的依赖注入解决了什么实际问题,和"手动传参数"比好在哪、代价是什么?

## 2. REST API 设计 与 schema-first vs code-first

**是什么:** REST 是一套围绕"资源 + HTTP 动词 + 状态码"的 API 设计风格约定(不是协议,是一组惯例)。而 API 的 schema(接口契约)可以有两种生成顺序:**code-first** 是先写业务代码,框架在运行时反射出接口描述(比如 FastAPI 从 Pydantic model 自动生成 `/openapi.json`);**schema-first** 是先手写一份接口描述文件(YAML/JSON),再用工具从描述文件生成服务端骨架和客户端代码。

**为什么存在这个区分:** 团队协作时,前后端、或者服务间调用,需要一份"谁都认的接口真相"。Code-first 的优点是契约和实现天然同步(改了代码签名,契约立刻跟着变,不会手滑写错);缺点是契约依赖于具体实现语言的反射能力,而且理论上可能设计出不符合 REST 惯例的接口(因为没有一份独立的契约先"审"一遍)。Schema-first 反过来:契约先于代码存在,可以先评审、先冻结,多个团队可以并行按同一份契约开发,但契约和实现容易"说的和做的不一样"(除非有 lint/CI 校验)。

**Periplus 例子:** FastAPI 走的是 code-first——路由的 `response_model` 和请求体 Pydantic model 本身就是唯一真相源,框架在运行时反射出 OpenAPI JSON,没有单独手写一份 schema 文件。

**可能被追问:**
- 什么场景下 schema-first 明显更合适?(多语言微服务、外部第三方要先对接你的 API 再等你实现完、gRPC/Protobuf 这类强制契约先行的体系。)
- REST 之外还有哪些 API 风格,各自适合什么场景?(GraphQL 解决"一次请求拿多资源、避免 over/under-fetching";gRPC 解决"服务间高性能二进制通信、强类型契约"。)
- 一个"符合 RESTful"的 API 和一个"只是用了 HTTP 动词"的 API 有什么本质区别?

## 3. 为什么要从 OpenAPI 生成类型化客户端

**是什么:** 后端产出一份 OpenAPI 契约后,用工具(如 `openapi-typescript`、`openapi-generator`)把这份契约"翻译"成前端语言的类型定义,前端调用 API 时能拿到编译期类型检查,而不是把返回值当 `any`。

**为什么存在:** 前后端是两个独立演化的代码库(尤其当语言不同,比如 Python 后端 + TypeScript 前端,没法直接共享类型),接口字段改名、类型改变这类变更很容易在运行时才暴露成一个难排查的 bug。生成类型客户端把这类错误尽量前移到编译期。

**权衡与替代方案:**
- **和 tRPC 对比**(常见追问):tRPC 是运行时级别共享类型——要求前后端同一个 TypeScript monorepo,client 直接 import server 的类型,零额外生成步骤,类型永远同步,但天然绑死 TS 技术栈,跨语言场景用不了。OpenAPI 生成路线适用面更广(任意后端语言 + 任意前端语言),代价是**契约和实现之间有一个"生成"的中间步骤**,后端改了 schema 忘记重新生成,前端类型就会过期而不自知——需要在 CI 里加一步"重新生成后 diff 是否为空"来防漂移,否则这道防线形同虚设。
- 也可以完全不生成类型,前端手写接口类型或者干脆用 `any`,这是最省事但最脆弱的选择。

**Periplus 例子:** `npm run generate:api` 跑 `openapi-typescript` 拉取本地跑起来的 FastAPI 服务的 `/openapi.json`,生成的 `.ts` 类型文件提交进仓库;这一步目前是手动跑的,没有 CI 校验是否过期。

**可能被追问:**
- 生成的类型文件过期了会发生什么?怎么在工程上防止?
- 这套方案本质上防住的是哪类 bug、防不住哪类 bug?(能防字段改名/类型不匹配,防不住语义变化,比如某个字段含义变了但类型没变。)

## 4. ORM vs 裸 SQL:为什么"不用 ORM"可以是合法选择

**是什么:** ORM(对象关系映射,如 SQLAlchemy、Prisma、TypeORM)把数据库表映射成编程语言里的对象/类,读写数据库变成操作对象,由 ORM 在背后翻译成 SQL。裸 SQL(如直接用 `psycopg`)则是应用代码自己写 SQL 语句。

**为什么存在 ORM:** 解决两类问题——一是"用宿主语言的对象模型描述数据"比手写 SQL 字符串更贴近应用逻辑,减少样板代码,尤其表多、关系复杂时;二是通常搭配 migration 工具(如 Alembic、Prisma Migrate)管理 schema 版本演进,团队协作下"谁的本地 schema 和谁的不一致"这类问题被规范化解决。

**权衡:** ORM 的代价是——多一层抽象,复杂查询(多表 join、窗口函数、递归 CTE)用 ORM 表达往往比原生 SQL 更别扭,甚至逼你逃出 ORM 写"raw query";ORM 生成的 SQL 有时不是最优的(N+1 查询是经典坑);团队要多学一套 ORM 自己的 API 语义。裸 SQL 的代价对称:样板代码更多、没有自动的类型映射、schema 演进要么手写 migration 脚本要么(像小项目那样)干脆用 `CREATE TABLE IF NOT EXISTS` 幂等建表,放弃版本化迁移的能力。**该不该用 ORM 本质是一个规模权衡**:表少、查询模式简单、团队小,裸 SQL 的心智负担可能反而更低;表多、关系复杂、团队大,ORM 的规范化收益会明显超过它的抽象成本。

**Periplus 例子:** 用的是 `psycopg3` 直接写 SQL,没有 SQLAlchemy,理由是表结构简单(只有几张表,且多是 JSONB 宽表),ORM 的映射层和 migration 工具带来的复杂度收益不明显。

**可能被追问:**
- N+1 查询问题是什么,ORM 场景下怎么发现和解决?(`select_related`/`joinedload` 这类预加载机制。)
- 什么规模/复杂度的项目你会切换到 ORM?判断标准是什么?
- 裸 SQL 怎么防 SQL 注入?(参数化查询/prepared statement,而不是字符串拼接。)

## 5. 连接池(Connection Pooling)

**是什么:** 数据库连接的建立(TCP 握手 + 认证 + 可能的 TLS)有实打实的开销,连接池是预先建立一批连接放在池子里,请求来时借一个用完还回去,而不是每次请求都新建/关闭连接。

**为什么存在:** 如果每个请求都现建连接,在高并发下这部分开销会成为明显瓶颈,而且数据库对"同时打开的连接数"本身有上限(Postgres 默认通常是三位数量级),裸开连接容易把数据库打垮。连接池把"应用层的并发请求数"和"实际打给数据库的连接数"解耦,用一个可控的连接数支撑远大于这个数字的并发请求。

**关键权衡与坑:** 池子大小要调——太小会让请求排队等连接,太大会让数据库端承压;更隐蔽的坑是"连接在池子里看着活着,但服务端已经把它悄悄断了"(比如网络中断,或者一些 serverless/自动休眠的数据库在空闲后回收计算实例),这种失效连接如果被池子直接借出去,业务查询会直接报错。成熟方案通常在"借出连接前先做一次健康检查(ping)"或者用带自动重连能力的池实现。

**Periplus 例子:** 用 `psycopg_pool` 的 `AsyncConnectionPool`,并显式配置了借出前的连接健康检查,应对 serverless Postgres(如 Neon)空闲后休眠导致连接失效的情况。

**可能被追问:**
- 连接池大小怎么定?和数据库最大连接数、应用实例数之间是什么关系?
- 遇到"连接池借出的连接实际已断开"这种问题,除了健康检查还有什么处理方式?(重试机制、更短的连接存活时间。)

## 6. 请求校验(Request Validation)

**是什么:** 对进入系统的外部输入(HTTP 请求体、query 参数)在业务逻辑执行前做类型、格式、边界的检查,不合法的请求在最外层就被拒绝。

**为什么存在:** 这是防御性编程的第一道墙——不校验的输入可能直接导致程序崩溃(类型不对)、逻辑错误(必填字段缺失却被当默认值处理)、甚至安全问题(注入类攻击的很大一部分前提就是后端对输入毫无假设地信任)。把校验放在框架层集中做,比业务代码里到处手写 `if` 判断更不容易漏。

**常见实现方式:** Python 生态常用 Pydantic(FastAPI 深度绑定)、TypeScript 生态常用 Zod/class-validator(NestJS 深度绑定 class-validator),都是"用声明式的 schema/类型描述代替命令式的校验代码"。校验失败通常统一返回 `400`/`422`,而不是让请求带着脏数据往下游流。

**一个容易被问到的细节:** 对未定义字段是"直接报错拒绝"还是"静默丢弃",是两种不同的防御强度——前者(如 Pydantic 的 `extra="forbid"`)能在客户端拼错字段名或者传了不该传的字段时立刻暴露问题;后者更宽松但也更容易掩盖调用方的错误。

**Periplus 例子:** 请求体模型用 `ConfigDict(extra="forbid")`,多传的字段直接 422 而不是被静默丢弃;还有跨字段的 `@model_validator`(比如结束日期不能早于开始日期)。

**可能被追问:**
- 校验应该放在哪一层?只在最外层 API 边界够吗,业务逻辑内部还要不要防御性检查?
- 校验失败时,返回给客户端的错误信息应该包含多少细节?(太少不好排查,太多可能泄露内部实现。)

## 7. PostgreSQL vs MongoDB:关系型 vs 文档型

**是什么:** PostgreSQL 是关系型数据库(RDBMS),数据组织成有固定 schema 的表,行之间靠外键关联,强调 ACID 事务和 SQL 查询能力。MongoDB 是文档型数据库,数据组织成 BSON/JSON 风格的文档,schema 灵活(同一个 collection 里的文档字段可以不完全一样),原生贴近"对象"这种嵌套结构。

**为什么会有两种范式并存:** 关系模型的强项是**数据一致性和复杂查询**——多表 join、聚合、事务保证多条写入要么全成功要么全回滚,适合"数据之间关系复杂、正确性要求高"的场景(订单、账务、库存)。文档模型的强项是**schema 灵活性和贴近应用对象的存储**——不需要提前想清楚所有字段、不用为了存一个嵌套结构去拆多张表再 join 回来,适合"数据结构本身经常变、或者天然是一整块嵌套 JSON"的场景。

**关键权衡:**
- 关系型数据库现在也能存 JSON(Postgres 的 `JSONB` 类型),某种程度上"蚕食"了文档数据库的部分场景——如果你的核心数据大部分字段稳定、只有少部分是灵活的附属信息,完全可以在关系表里开一列 `JSONB` 存那部分,不必上一整个 MongoDB。
- 文档数据库的事务和跨文档一致性能力通常比关系型数据库弱(虽然近年 MongoDB 也加了多文档事务支持,但不是它的设计初衷强项)。
- 选型本质是问:数据之间的关系复杂吗?正确性要求有多强?schema 演进频率如何?查询模式是"按主键/单文档取"为主还是"跨实体聚合"为主?

**Periplus 例子:** 用的是 Postgres,但表设计上大量用了 `JSONB` 宽表(比如把整个业务对象序列化后整列存进去),这是"关系型数据库里借用文档型思路"的典型做法——好处是模型加字段不用写 migration,代价是没法对内部字段做 SQL 层面的索引/查询,除非额外加冗余列。

**可能被追问:**
- 什么情况下你会选 MongoDB 而不是 Postgres 的 JSONB?(真正需要文档级别的灵活 schema、大规模水平分片、查询模式主要是单文档存取而不是跨实体 join。)
- Postgres 的 `JSONB` 列能不能建索引、怎么建?(能,GIN 索引支持对 JSONB 内部字段做查询加速。)

## 8. pgvector:给 Postgres 加向量能力,什么时候要专用向量数据库

**是什么:** `pgvector` 是 PostgreSQL 的一个扩展,给 Postgres 加了一个 `vector` 数据类型和向量距离/相似度的查询能力(比如余弦相似度、近似最近邻索引),让你可以在关系表里直接存 embedding 向量,并对它做相似度检索。

**为什么存在:** 语义搜索/RAG 这类场景需要"给一段文本算出一个 embedding 向量,存起来,之后按向量相似度检索"。在 `pgvector` 出现前,这类需求通常要单独引入一个专用向量数据库(Pinecone、Weaviate、Milvus、Qdrant)。`pgvector` 的价值在于:如果你的数据本来就在 Postgres 里,不需要为了"顺带需要一点向量检索能力"而额外运维一整套新的数据库系统,把向量列和其他关系数据放在同一张表、同一个事务里,查询时甚至能把向量相似度和普通 SQL 过滤条件混在一起写。

**什么时候仍然要上专用向量数据库:** 当向量检索是系统的**核心、大规模、高 QPS** 需求时——比如千万级以上向量、需要非常高的检索吞吐和低延迟、需要专用向量数据库那些更精细的索引算法和分布式扩展能力,专用方案通常在这个规模下更有优势。简单说:`pgvector` 适合"向量检索是众多能力之一、数据规模中等、想少一个系统运维"的场景;专用向量数据库适合"向量检索就是主战场、规模巨大"的场景。

**Periplus 例子:** 用 `pgvector` 做了一个语义缓存(embedding cache),复用跨 run 已经抓取/处理过的相似网页内容,这是一个性能优化型的旁路组件——它的定位和"必须强一致的核心数据"不同,失败时应该优雅降级(当作没缓存命中),而不能让向量检索失败连累主流程报错。

**可能被追问:**
- `pgvector` 的近似最近邻索引(如 IVFFlat/HNSW)和暴力全表扫描相比,牺牲了什么换取速度?(牺牲了检索的绝对准确率,是近似解而不是精确解。)
- 向量检索失败时,系统应该怎么处理?这类"检索增强"型组件在可靠性设计上应该归到哪一类?

## 9. 幂等性与长任务的崩溃恢复 / 检查点(Checkpointing)模式

**是什么:** 幂等性(idempotency)指"同一个操作执行一次和执行多次,产生的结果是一样的"——重复调用不会造成重复副作用。检查点/checkpointing 指长任务把自己的执行进度分阶段持久化下来,这样任务中途失败或进程重启后,能从上一个已知完好的检查点继续,而不是从头重来。

**为什么存在:** 长时间运行的后端任务(调用外部 LLM、跑一条多步流水线、批量数据处理)天然有一个现实问题——进程随时可能因为部署、崩溃、资源限制被中断,而这类任务往往涉及**不可重复的真实成本**(调用付费 API、抓取外部资源),从头重跑意味着真金白银和时间的浪费。同时,如果恢复逻辑写得不够小心,很容易在重放时对同一份数据做了两次副作用(比如同一条记录被处理两遍),这就是为什么"检查点"和"幂等"必须一起讨论——检查点解决"从哪继续",幂等性保证"就算意外重复执行了某一步,也不会产生错误的重复效果"。

**常见模式:**
- **状态机 + 持久化状态转移**:把任务拆成明确的阶段(pending → running → succeeded/failed),每次状态转移前先持久化,重启后通过"卡在某个中间状态但没有对应的终态记录"这个信号识别出哪些任务是"上次跑到一半就死了的"。
- **按阶段边界做检查点**,而不是任意粒度:阶段粒度太细,持久化开销大;太粗,一次失败要重跑的工作量大。选择在哪些点做检查点,本质是在"恢复精度"和"持久化开销"之间取舍。
- **写入语义的取舍**:强一致地同步写入检查点(每一步都等落盘完成再继续)更安全但更慢;异步"回声"写入(先更新内存态、异步补写持久化)更快但要接受一个"进程恰好死在内存已更新、持久化还没完成"的窄窗口——设计上必须明确这个窗口最坏情况下的后果是"最多重跑一步",而不是"污染已经确认完成的历史数据"。

**这类机制能提供的保证通常是 at-least-once(至少一次),而不是 exactly-once(恰好一次)**——工程上一般不追求真正的 exactly-once(代价极高),而是retreat 到"at-least-once + 幂等"的组合:允许某一步在极端情况下被重放,但重放的代价可控、且不破坏已确认的结果。

**Periplus 例子:** 用"阶段 + 门禁(gate)"的检查点方案:一张表记录 run 是否跑完,另一张表按 `(run_id, stage, attempt)` 记录每个阶段的产出和是否通过门禁;重启时找到"最远一个已通过门禁的阶段",从下一个未完成阶段继续,而不是整条流水线重跑。这是应用层设计出来的检查点机制,不是数据库自带的"crash recovery"能力。

**可能被追问:**
- exactly-once 语义为什么在分布式/多进程场景下几乎做不到,通常怎么退而求其次?
- 如果检查点粒度太粗(比如整个任务只有一个检查点),会有什么问题?怎么权衡检查点的粒度?
- 幂等性在 API 设计层面怎么落地?(比如客户端传一个 idempotency key,服务端记录已处理过的 key,重复请求直接返回上次的结果而不重新执行。)

## 10. CI/CD 与容器化:成熟设置长什么样(即便当前项目还没有)

**是什么:** 容器化(Docker)把应用连同它的运行时依赖打包成一个可移植、环境一致的镜像,"在我机器上能跑"和"在服务器上能跑"之间的落差被大幅压缩。CI/CD(持续集成/持续交付)是一套自动化流水线:代码提交后自动跑测试、lint、构建镜像,通过后自动(或人工确认后)部署。

**为什么存在:** 手动部署容易出两类问题——环境不一致导致的"本地好好的、线上炸了",以及人为操作失误(忘了跑测试、漏了一步)。CI/CD 把这些步骤固化成自动化流程,每次变更都跑一遍同样的检查,减少"这次是不是又忘了做什么"的不确定性。容器化进一步把"应用需要什么系统依赖、什么版本"这件事从"写在 README 里靠人记"变成"写进 Dockerfile 里靠工具保证"。

**一个成熟设置大致包含:**
- **Dockerfile**:定义镜像怎么构建,通常用多阶段构建(build 阶段装依赖编译,最终阶段只拷贝产物,镜像更小更安全)。
- **CI 流水线**(如 GitHub Actions):PR/push 触发,跑 `pytest`/`ruff` 这类测试和 lint,失败就挡住合并;有的团队还会在这一步顺带跑"OpenAPI 契约是否漂移"这类专属校验。
- **CD 流水线**:测试通过后构建镜像、推到镜像仓库,再触发部署(蓝绿部署/滚动更新,尽量做到零停机);数据库 migration 通常作为部署流程里单独的一步,而不是应用启动时顺手执行(避免多实例同时抢着跑 migration)。
- **环境分层**:至少 dev/staging/prod 分开,prod 的部署通常需要额外的人工确认或者更严格的检查门槛。

**Periplus 现状(诚实说明,不回避):** 目前没有 Dockerfile,本地跑法是虚拟环境 + 直接跑 `uvicorn`;仓库里唯一的 CI workflow 只做了把前端构建成静态 demo 页面发布到 GitHub Pages,没有针对后端跑测试/lint 的 CI,也没有自动化部署流程。这是一个规模较小、单人开发的项目里可以接受的现状,但如果继续往前推进到多人协作或者真实上线,这块是明确要补的。

**可能被追问:**
- 为什么数据库 migration 通常不建议放在应用启动时自动跑?(多实例并发启动会导致同一个 migration 被并发执行,存在竞态和加锁复杂度。)
- 多阶段 Docker 构建解决了什么问题?
- 蓝绿部署和滚动更新分别是什么,各自的权衡是什么?

# 让「用错」变得做不到

> 🔴 **必看**。覆盖简历第 ② 条（React 架构 + ESLint 边界）和第 ④ 条（设计系统 + MSW）。
>
> **这两条表面上没关系，其实是同一个思想的两次应用** —— 合起来讲比分开讲各强一倍。

## ⭐ 统领这一天的一句话

> **「文档是约定，ESLint 是约束。」**
>
> **约定靠人记得住，约束靠工具挡得住。** 团队一大、人一换，约定就会漂 —— **唯一不会漂的是「做不到」。**

| | 约定（会漂） | 约束（挡得住） |
|---|---|---|
| **架构边界** | README 里画一张依赖方向图 | **一条 ESLint 规则 —— 违规直接编译报错** |
| **前后端解耦** | 「接口先约定好，后端慢慢写」 | **MSW 拦在网络层** —— 前端跑的是真实的请求路径 |

> **面试里先抛这句话，再用两个例子落地。** 这比逐条介绍 ESLint 规则高一个层次 —— **展示的是判断力，不是工具熟练度。**

## 一、ESLint 怎么强制依赖方向

### 先说清要解决什么

**大项目里最常见的腐化叫「大泥球」**：模块之间随便互相引用，最后谁也删不掉、谁也读不懂。

**解法是规定「依赖只能往一个方向流」**（`.eslintrc.cjs:116-124` 的注释里画了这张图）：

```
app/ ──→ features/ ──→ components/ hooks/ lib/ types/ utils/

箭头方向是允许的依赖方向，反向一律禁止。
```

- **`app/`** 是页面和路由的组装层
- **`features/`** 是一个个业务功能（blog、comments、theme……）
- **底下那一排**是通用的东西：组件、工具函数、类型

### 用什么规则强制

**`import/no-restricted-paths` 这条 ESLint 规则**的作用是：**「在某个目录里，不许 import 另一个目录的东西」**。代码里定了五条（`:126-172`）：

| 规则 | 挡住什么 |
|---|---|
| **1–3** | `features/blog` 不能引用 `features/` 下的其他功能（除了它自己）—— **功能之间互相引用** |
| **4** | `features/` 不能引用 `app/` —— **下层反向依赖上层** |
| **5** | 通用层不能引用 `features/` 和 `app/` —— **通用层被业务污染** |

**外加一条 `import/no-cycle`（禁止循环引用）。**

### 为什么这三条值钱

**功能隔离防的是「焊死」：**

```
blog 引了 comments 的一个工具函数
  → comments 又引了 blog 的一个类型
    → 两个功能焊死了
      → 想删掉 comments？删不掉
      → 想让新人只改 blog？他得先读懂 comments
```

**要通信只能通过上层组装，或者把公共部分下沉到通用层。** 这样每个功能才是**可以独立删除、可以独立理解**的单元。

**通用层不能反向引用**：`components/Button` 一旦引了 `features/blog` 的东西，**它就不再通用了** —— 别的项目、别的功能都用不了它。

**禁止循环引用防的是真实的运行时 bug**（注释里写了三条）：模块初始化顺序变得不确定、**可能拿到 `undefined`（因为那个模块还没初始化完）**、难以维护。**第二条是真的会炸的。**

### 生产级怎么做

| 做法 | 说明 |
|---|---|
| ⭐ **规则必须进 CI** | 规则不进持续集成等于没有 —— 和 [Beyz 的 CI gate](/docs?section=beyz&item=d4-deploy) 是同一个道理 |
| **规模大了上专门的工具** | `dependency-cruiser` 能生成依赖图、定义更复杂的架构规则、输出可视化 |
| **规则要和目录结构一起演进** | 加了新功能就要加规则，**否则它会慢慢变成摆设** |

## 二、⭐ 为什么 MSW 优于假的 fetch（题眼：拦截位置决定你在测什么）

### 先说 MSW 是什么

**MSW（Mock Service Worker）是一个假接口工具**，但它和常见的做法有个根本区别：**它不替换你的代码，它拦在网络这一层。**

- 在浏览器里，它注册一个 **Service Worker**（浏览器提供的一种在网页和网络之间的代理），**请求发出去之后被它截住，返回你写好的假数据**
- 在测试环境（Node）里，它直接接管底层的 HTTP 模块

**关键是：你的代码完全不知道它存在** —— 该发的请求照发，只是最后一跳没出去。

### 拦截位置决定测什么

```
组件 → 自定义 hook → API 函数 → axios/fetch → ❶ 网络层 → 服务器
      ↑ mock 这里    ↑ 这里      ↑ 这里         ↑ MSW 拦这里
```

| Mock 的位置 | 下面这些还是不是真的 |
|---|---|
| **把 hook 换成假的** | ❌ API 函数、请求组装、拦截器、序列化 —— **全跳过了** |
| **把 API 函数换成假的** | ❌ axios 实例、基础地址、请求头、拦截器、错误映射 —— **全跳过** |
| **把 axios 整个替换掉** | ⚠️ 请求配置和拦截器逻辑**还是没跑到** |
| **MSW（网络层）** | ✅ **上面全部真实执行**，只有最后一跳没出去 |

> ⭐ **一句话：MSW 拦在网络层，所以你测的是真实的请求路径。**
>
> **这和 [Periplus 的 scripted seam](/docs?section=periplus&item=n14-server-tests) 是完全同一个原则** —— 那边替换模型调用时只覆写了「把请求发出去」那一个方法，**prompt 组装、格式校验、重试全都还在真跑**；抓网页那边换的是 HTTP 客户端的传输层，**robots 解析、限流、重定向跟随全是真测的**。
>
> **两个项目串起来讲：「替换点要放在最接近进程边界的位置，越靠外，被测的真实代码越多。」**

### 三条 MSW 独有的收益

| 收益 | 说明 |
|---|---|
| **同一套假接口，浏览器和测试通用** | 开发时和 Storybook 用浏览器那套，测试用 Node 那套，**假接口的逻辑只写一份** |
| **前端能完全独立跑起来** | 后端接口还没写，前端已经能开发、能演示、能截图 —— **这就是简历里「让前端交付不依赖后端进度」的字面意思** |
| ⭐ **假数据是有状态的** | 用的是一个内存数据库，不是写死的 JSON。**POST 一条评论，GET 就能查到它** —— 能测完整的交互流程，而不只是渲染 |

### 一个已经做对的配置

```js
// setup-tests.ts:37
server.listen({ onUnhandledRequest: 'error' })
```

**「没有匹配到任何假接口的请求，直接报错」。**

> **没这一条的话，漏配的接口会静默地打到真实网络上** —— 测试结果就变成不确定的了（网络好的时候过，网络差的时候挂）。

### ⚠️ 必须主动交代的风险

> **MSW 的假接口会和真实接口漂移。**
>
> **后端改了一个字段名，你的测试全绿、线上全炸。**

**生产级的补法**：让假接口从后端的 OpenAPI 描述**自动生成**（保证形状一致），再配**契约测试** —— **MSW 保证前端「按约定跑得通」，契约测试保证「约定没被后端偷偷改掉」。**

> **说出这一点，比只讲 MSW 的好处更能证明你真用过。**

## 三、设计系统（面试价值低于前两块，知道怎么讲清楚就够）

| 工具 | 一句话 |
|---|---|
| **Radix UI** | ⭐ **只给行为，不给样式**（这类库叫 headless）—— 键盘导航、焦点管理、无障碍属性、点外面关闭，**这些是最容易做错、也最不该重复造的部分**。样式全是你自己的 |
| **CVA** | 把「尺寸 × 变体 × 状态」的组合写成一份配置，**类型自动导出** —— 不用手拼样式类名字符串 |
| **design tokens** | 颜色、间距、圆角定义一次，**主题切换只换这一份定义** |
| **Storybook** | 组件的独立开发环境和文档，**配合 MSW 就能脱离后端做交互演示** |

**`asChild` 这个模式值得单独提**：它让你把样式「套」到子元素上，所以 `<Button asChild><Link/></Button>` **渲染出来是一个 `<a>` 标签，而不是一个 `<button>` 里套一个 `<a>`** —— 语义正确，无障碍也正确（后者是无效的 HTML）。

> **整套的目的是让「用错」变难 —— 和 ESLint 边界是同一个思路。**

The approach that generalises well: separate container components from UI components.

Extract only the genuinely reusable part into a UI component, and control the different looks through props.

All the logic lives in the container, which nests the UI component inside it. Keep business logic out of the reusable component — it will change sooner or later.

Something like this: one prop decides whether the button reads "Add product" or "Save changes".

Then the container that handles adding and the container that handles editing both call the same UI component.

One more note: in a modern React codebase the container layer usually ends up in a custom hook rather than an actual container component. The separation is the same idea either way.

## Forwarding refs: handing a child's DOM node to the parent

A recurring problem when wrapping components: the parent wants to call `inputRef.current.focus()`, but the `input` is hidden inside the wrapper. `ref` **is not an ordinary prop** — putting it on a custom component gives you nothing by default.

### React 19 onwards: ref is just a prop

```jsx
function MyInput({ ref, ...props }) {   // destructure it straight out of props
  return <input ref={ref} {...props} />;
}

// parent
const inputRef = useRef(null);
<MyInput ref={inputRef} />
inputRef.current.focus();   // this is the real <input> inside
```

The docs now mark `forwardRef` as deprecated: **"In React 19, `forwardRef` is no longer necessary. Pass `ref` as a prop instead."** The `forwardRef((props, ref) => ...)` you see in older code was the only option up to React 18 — worth being able to read, not worth writing.

### useImperativeHandle: expose methods, not the DOM node

Hand over the real DOM node and the parent can do anything to it — restyle it, rewrite its contents, remove it — and the encapsulation was pointless. `useImperativeHandle` lets you **decide what sits on the ref**:

```jsx
function MyInput({ ref }) {
  const innerRef = useRef(null);

  useImperativeHandle(ref, () => ({
    focus: () => innerRef.current.focus(),
    clear: () => { innerRef.current.value = ''; },
  }), []);

  return <input ref={innerRef} />;
}

// the parent gets these two methods and no access to the node itself
inputRef.current.focus();
inputRef.current.clear();
```

Its range is narrow — **only for imperative actions that genuinely cannot be expressed as props**: focusing, scrolling somewhere, play/pause, opening or closing a dialog. Anything describable as state belongs in props or state, not on a ref.

### How it works underneath

- **`ref` takes no part in rendering.** Mutating `ref.current` does **not** trigger a re-render — that is the fundamental difference from state, and the reason you must not read or write it during render.
- **Assignment happens in the commit phase**, after the DOM is attached, so it is always populated inside `useEffect` / `useLayoutEffect`, and still `null` the first time the component body runs.
- **React resets `ref.current` to `null` on unmount.** From React 19, a callback ref (`ref={node => ...}`) can **return a cleanup function**, matching the shape of `useEffect`.

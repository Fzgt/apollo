## 2. Three things that genuinely changed

### 1. The React Compiler retires useMemo and useCallback

- **v1.0 shipped 2025-10-07**
- Next.js 16 supports it out of the box: `reactCompiler: true` in the config
- Vite has a plugin
- How it works: it analyses component dependencies at build time and inserts memoisation for you

**In a new project, stop hand-writing `useMemo` and `useCallback` for performance.**

They are not deprecated, but they have been demoted to a niche tool for **dealing with reference equality in third-party libraries**. The typical case: older versions of TanStack Table compare internally on the assumption of stable references, and need a `"use no memo"` directive to opt out of the compiler.

> **For interviews**: asked "when do you use `useMemo`", the 2026 answer is no longer a recitation of dependency-array rules. It is: leave it to the compiler by default, and step in by hand only when a library requires a stable reference.

### 2. RSC went from silver bullet to conditional tool

**(a) Security — this one needs handling today, not discussing as best practice**

| Date | Issue | Fixed in |
|---|---|---|
| 2025-12-03 | RSC **unauthenticated remote code execution (RCE)** | 19.0.1 / 19.1.2 / 19.2.1 |
| 2025-12-11 | RSC denial of service and source disclosure | 19.0.2 / 19.1.3 / 19.2.2; a follow-up CVE for the incomplete fix landed, and the complete fix is **19.0.3 / 19.1.4 / 19.2.3** |

> ⚠️ **If you have an RSC project running below 19.2.3 (or below 19.0.3 / 19.1.4 on those branches), upgrade now.** 19.2.1 only fixed the RCE; the two later issues are unpatched there.

**(b) The architectural backlash**

The current consensus: sprinkling `"use client"` everywhere cancels out every server-first advantage and leaves only the mental cost of the server/client boundary — ending up **harder to reason about** than plain client-side React.

RSC's benefits — around 40% smaller bundles, secrets that never leave the server — **only exist if the boundary is genuinely held**. Plenty of teams turned RSC on expecting it to be automatically faster and hit the architectural constraints instead.

### 3. State management has converged

| Kind of state | Answer |
|---|---|
| Server data (API responses) | **TanStack Query** — the de facto standard |
| Global client state | **Zustand** — the community's de facto standard |
| Shareable UI state (filters, pagination, tabs) | **URL search params**, not `useState` |
| Local component state | `useState` / `useReducer` |
| Large enterprise codebases | Redux Toolkit is still reasonable |
| Slow-changing config (theme, locale) | React Context |

**The core principle: server state and client state must stay separate.**

Stuffing API data into Zustand or Redux and hand-writing cache invalidation is the anti-pattern most likely to be flagged in code review and in interviews right now.

**How to decide where state belongs**: local by default; promote it to global only when several unrelated components genuinely need the same data.

## 4. Code-level practices that keep coming up

Nothing new here, but these are still frequent review comments in 2026:

- Do not use the array index as a `key`
- Avoid anonymous functions, object literals, and array literals in JSX props
- **Handle all three of loading, error, and empty** — not just the happy path
- Use the React Compiler; do not pre-emptively memoise by hand
- Avoid `dangerouslySetInnerHTML` (XSS)
- Server components can safely touch secrets, environment variables, and the database — that code never reaches the client

## 5. Where to spend the effort (my own judgement)

In order of return:

1. **Being able to explain the boundary between server state and client state.**
   Right now this is the fastest way to tell "can use React" from "understands React architecture", and you can practise it without starting a new project.

2. **A mental model of the React Compiler.**
   Cheap — an hour will do it — and it makes your answers sound like 2026 immediately.

3. **Go deep on RSC only if you are actually using the Next.js App Router.**
   Otherwise the return is poor, and the industry's attitude is visibly more cautious than it was a year ago.

**Do not rewrite an existing project just to keep up.** Nothing above says "the old way stops working". They are all changes to **the defaults for new projects**.

title: "Three.js performance — 39 tips across monitoring, scene, assets, renderer and shaders"
---

> Compiled from course notes and the performance chapter of [Three.js Journey](https://threejs-journey.com/), with reference to [discoverthreejs.com](https://discoverthreejs.com/tips-and-tricks/). The original notes targeted an older three.js; several APIs have changed since, and the corrections are listed at the end.

Target **60fps**. Gamers may expect more. There are only two limits: the **CPU** and the **GPU**.

Two prerequisites:

1. **Do the ordinary frontend optimizations before touching 3D.** DNS prefetching, lazy loading, asset compression — that is the foundation, and 3D work on a bad foundation is wasted. (3D projects usually need neither SSR nor SSG.)
2. **Test on real devices**, especially mobile. Your M-series Mac running smoothly says nothing about your users.

---

## 1. Monitoring

### 1 — Monitor FPS

Use three.js's own `stats.js`, wrapping the whole frame in `tick`:

```js
const tick = () => {
  stats.begin();
  // ...
  stats.end();
};
```

DevTools also works: **More tools → Rendering → Frame rendering stats**.

### 2 — Unlock the frame rate limit

Chrome caps rendering at the display refresh rate. Without unlocking it, a steady 60fps on a good machine is misleading — the site may only reach 70fps there and drop below 60 elsewhere. Unlocked, you should see 150–200fps on a strong machine to feel safe.

> Unlocking is done via launch flags, **but it can crash the browser — use it only for local profiling.**

### 3 — Monitor draw calls

A draw call is the GPU drawing triangles. More objects, geometries and materials means more draw calls. **Fewer is better.**

Use the **Spector.js** Chrome extension (built by the Babylon.js team, but coupled to neither Babylon nor three.js): click the icon to activate, click the red circle to record a frame, then read the **Commands** tab. Blue steps are draw calls; the rest is data sent to the GPU — matrices, attributes, uniforms.

**Note: Spector.js only works with WebGL, not WebGPU.**

### 4 — Renderer information

The cheapest check there is:

```js
console.log(renderer.info);
```

You get geometry and texture counts plus this frame's draw calls and triangles.

## 2. General

### 5 — Performant JavaScript

`tick` runs every frame, so the code inside it directly determines frame rate. Keep ESLint on it; avoid allocations and `new` in there.

In react-three-fiber there is no `tick` — the equivalent is the `useFrame` hook.

### 6 — Dispose of things

Free resources as soon as you are sure you no longer need them. In a level-based game, dispose of the previous level on transition:

```js
scene.remove(cube);
cube.geometry.dispose();
cube.material.dispose();
```

## 3. Lights

### 7 — Avoid them

Lights are simple to use and **steadily drain performance** — materials that support lighting are expensive to compute. Five or six lights in one scene is a disaster.

If you must, pick the cheap ones: `AmbientLight`, `DirectionalLight`. **Emissive materials** can sometimes stand in for a light at a fraction of the cost.

### 8 — Avoid adding or removing lights

Adding or removing a light forces **every light-supporting material to recompile**. In a complex scene that freezes the frame. Once the scene is set up, leave the lights alone.

## 4. Shadows

### 9 — Avoid them

Same reasoning as lights. Prefer alternatives — **baked shadows**, where the shadow is painted into the texture, look better and cost nothing in a static scene.

### 10 — Optimize shadow maps

Use `CameraHelper` to see what the shadow camera actually renders, then shrink it to the minimum:

```js
directionalLight.shadow.camera.top = 3;
directionalLight.shadow.camera.right = 6;
directionalLight.shadow.camera.left = -6;
directionalLight.shadow.camera.bottom = -3;
directionalLight.shadow.camera.far = 10;

scene.add(new THREE.CameraHelper(directionalLight.shadow.camera));
```

Drop the resolution as far as the result allows:

```js
directionalLight.shadow.mapSize.set(1024, 1024);
```

### 11 — Use castShadow and receiveShadow deliberately

Some objects only cast, some only receive, few need both. **Enable each on as few objects as possible:**

```js
cube.castShadow = true;
cube.receiveShadow = false;

floor.castShadow = false;
floor.receiveShadow = true;
```

### 12 — Deactivate shadow auto-update

By default the shadow map is recomputed before every render. A static scene does not need that:

```js
renderer.shadowMap.autoUpdate = false;
renderer.shadowMap.needsUpdate = true;   // trigger manually when needed
```

The rule is simple: **if the object does not move, its shadow does not need to either.**

## 5. Textures

### 13 — Resize textures

Textures take a lot of GPU memory, and mipmaps make it worse. **Resolution is what matters, not file size** — a 100KB 4096×4096 JPEG costs the same in VRAM as a 5MB PNG of the same dimensions.

Reduce resolution as far as the visual result permits.

### 14 — Keep power-of-two resolutions

This matters for mipmaps. It need not be square — width and height can differ — but both should be powers of two. "Otherwise three.js resizes to a power of two" is WebGL1-era behaviour — since r163 three.js is WebGL2-only and non-power-of-two textures are no longer resampled. The reason to keep powers of two now is a clean mip chain and compressed textures (KTX2 wants dimensions that are multiples of 4).

### 15 — Use the right format

- Run jpg/png through TinyPNG or similar
- **Prefer KTX2** (`.ktx2`, Khronos's supercompressed GPU texture format) — small files, and crucially **it stays compressed in GPU memory**

Measured example: switching a texture set to KTX2 barely changed file size, but **removed the quality loss and cut GPU memory to 21.43MB**. Compared to game bundles measured in tens of gigabytes, file size matters less than VRAM.

## 6. Geometries

### 16 — Everything is a BufferGeometry

**This is no longer something to worry about.** Before **r125**, three.js had non-buffer `Geometry` objects that stored vertices, faces and colours directly — convenient but slow, and converted to `BufferGeometry` at render time anyway.

**`THREE.Geometry` was removed in r125.** All geometries are buffer geometries now. Any tutorial telling you to "use plain Geometry when there aren't many objects" predates 2021.

### 17 — Do not update vertices

Updating a geometry's vertices is terrible for performance. Doing it once at creation is fine; **never do it in `tick`.**

To animate vertices, use a **vertex shader**.

### 18 — Mutualize geometries

When several meshes share a shape, create the geometry once:

```js
const geometry = new THREE.BoxGeometry(0.5, 0.5, 0.5);
const material = new THREE.MeshNormalMaterial();

for (let i = 0; i < 50; i++) {
  const mesh = new THREE.Mesh(geometry, material);   // same geometry reused
  mesh.position.set(
    (Math.random() - 0.5) * 10,
    (Math.random() - 0.5) * 10,
    (Math.random() - 0.5) * 10
  );
  scene.add(mesh);
}
```

### 19 — Merge geometries

If those objects never need to move independently, merge them into one geometry with one mesh — 50 draw calls become 1:

```js
import * as BufferGeometryUtils from 'three/addons/utils/BufferGeometryUtils.js';

const geometries = [];
for (let i = 0; i < 50; i++) {
  const geometry = new THREE.BoxGeometry(0.5, 0.5, 0.5);
  geometry.rotateX((Math.random() - 0.5) * Math.PI * 2);
  geometry.translate(
    (Math.random() - 0.5) * 10,
    (Math.random() - 0.5) * 10,
    (Math.random() - 0.5) * 10
  );
  geometries.push(geometry);
}

const merged = BufferGeometryUtils.mergeGeometries(geometries);
scene.add(new THREE.Mesh(merged, new THREE.MeshNormalMaterial()));
```

⚠️ **The API was renamed.** `mergeBufferGeometries` from older tutorials has been **removed**; it is now **`mergeGeometries`**. Copying old code gives you an undefined error.

The precondition is that relative positions are fixed — after merging there is a single mesh, so individual objects can no longer be moved. Very useful in WebGIS-style scenes.

## 7. Materials

### 20 — Mutualize materials

Same as geometries: create one material of a given kind and share it.

### 21 — Use cheap materials

Roughly, from most to least expensive:

```
MeshPhysicalMaterial > MeshStandardMaterial > MeshPhongMaterial > MeshLambertMaterial > MeshBasicMaterial
```

`MeshStandardMaterial` and `MeshPhysicalMaterial` are physically based (PBR) — good looking and costly. Pick the cheapest material that gives the look you need.

## 8. Meshes

### 22 — Use InstancedMesh

For many objects with **the same geometry and material differing only in transform** (bridge railings, a forest, a field of cubes), use `InstancedMesh` — one draw call for all instances.

```js
const mesh = new THREE.InstancedMesh(geometry, material, 50);
scene.add(mesh);

for (let i = 0; i < 50; i++) {
  const position = new THREE.Vector3(
    (Math.random() - 0.5) * 10,
    (Math.random() - 0.5) * 10,
    (Math.random() - 0.5) * 10
  );
  const quaternion = new THREE.Quaternion().setFromEuler(
    new THREE.Euler((Math.random() - 0.5) * Math.PI * 2, (Math.random() - 0.5) * Math.PI * 2, 0)
  );

  const matrix = new THREE.Matrix4();
  matrix.makeRotationFromQuaternion(quaternion);
  matrix.setPosition(position);
  mesh.setMatrixAt(i, matrix);
}
```

Nearly as good as merging geometries, **but each instance can still be transformed individually** — that is its advantage over tip 19.

If you will change matrices inside `tick`, declare the usage:

```js
mesh.instanceMatrix.setUsage(THREE.DynamicDrawUsage);
```

## 9. Models

### 23 — Low poly

Fewer polygons, better frame rate. Where detail is needed, use **normal maps** — they buy a lot of apparent geometry at texture cost, which is a very good trade.

### 24 — Draco compression

Compress geometry-heavy models with Draco; the size reduction is substantial.

**Three limits worth remembering:**

1. **Draco compresses geometry, not textures.** If the weight comes from large PBR textures, Draco will not help — go compress the textures instead.
2. **Decompression has a cost**: a possible freeze while decoding, plus the Draco decoder library to load.
3. **It does not combine with server-side compression.** Gzipping already-Draco data gains almost nothing and the configurations tend to interfere.

The rule: **Draco pays off when there are no large PBR textures.**

### 25 — Server-side compression

Gzip / Brotli, configured on the server (Nginx, Apache, Node). **Most servers do not compress `.glb` / `.gltf` / `.obj` by default** — add those MIME types explicitly.

⚠️ **Mutually exclusive with incremental loading (tip 27)** and with progress bars — see below.

### 26 — LOD

Distant objects do not need full detail. Prepare a few levels and switch by distance — the same idea as `<img srcset>`.

```js
const lod = new THREE.LOD();
lod.addLevel(highDetailMesh, 0);
lod.addLevel(lowDetailMesh, 50);
scene.add(lod);
```

Essential in large-world projects — GTA, PUBG, WebGIS. In the react-three-fiber ecosystem, **drei** provides `<Detailed>` for this.

Other fallbacks: update distant animations every 2–3 frames, or replace far objects with billboards.

### 27 — Incremental loading

Render part of a model while the rest is still downloading.

State of support: **three.js does not support it**; Babylon.js manages via the `.incremental.babylon` format (Blender needs a plugin to export it); UE and Unity support it. Doing this with glTF requires converting to a binary stream and is considerably more work.

⚠️ **Gzip disables incremental loading**, because compressed responses cannot be fetched with HTTP Range requests. For the same reason, **a progress bar also rules out gzip** — progress is computed from `Content-Length`, which no longer reflects the original size.

## 10. Cameras

### 28 — Field of view

Objects outside the field of view are not rendered — **frustum culling**. A narrower FOV means fewer objects on screen and fewer triangles.

### 29 — Near and far

Likewise, tighten `near` and `far`. In a vast world of mountains, trees and buildings, the user cannot see the small houses behind the mountains — lower `far` and they will not even be considered.

## 11. Renderer

### 30 — Pixel ratio

Some devices have very high pixel ratios (recent iPhones are 3:1). More pixels to render, worse frame rate. Cap it at 2 when performance suffers:

```js
renderer.setPixelRatio(Math.min(window.devicePixelRatio, 2));
```

This is a **quality/performance trade-off** — decide per project.

> Related: models looking blurry on a Mac is usually an unhandled DPR issue.

### 31 — Power preference

Some devices switch between GPUs (integrated vs discrete) or power modes. Hint at instantiation:

```js
const renderer = new THREE.WebGLRenderer({
  canvas,
  powerPreference: 'high-performance',
});
```

Desktop: `high-performance`. Mobile: weigh it against battery. **If you have no performance issue, use `'default'`.**

⚠️ Spelling matters. `powerPreference` is a WebIDL enum: a misspelled value such as `'high-performatnce'` throws a `TypeError` from `getContext`, the renderer fails to construct and the page goes blank — it does not fall back silently.

### 32 — Antialias

The default antialiasing is reasonably fast, but **still slower than none**. Enable it only when aliasing is visible and performance allows.

### 33 — Offscreen rendering / Web Worker

Move rendering into a Web Worker with `OffscreenCanvas` so the main thread is not blocked.

**The environment must be headless (no DOM).** three.js and Babylon.js support this, and so does PixiJS (v7+ ships a `WebWorkerAdapter`, documented under "Web Worker environment"; only accessibility and DOM events are unavailable). DOM-dependent libraries such as Phaser do not.

The same idea applies to **physics**: the physics world and the 3D world are already separate, so running the physics engine (cannon, for instance) on its own thread is a clear win. Communicate with `postMessage` or `SharedArrayBuffer`.

> Aside: with `headless-gl` and `node-canvas`, three.js and Babylon.js also run under Node — they do not strictly require a browser host.

## 12. Postprocessing

### 34 — Limit passes

**Every postprocessing pass repaints the full screen at render resolution, pixel ratio included.**

The arithmetic makes the cost obvious. At 1920×1080, pixel ratio 2, four passes:

```
1920 × 2 × 1080 × 2 × 4 = 33,177,600 pixels
```

Group your custom passes into one where possible.

## 13. Shaders

### 35 — Specify the precision

```js
const shaderMaterial = new THREE.ShaderMaterial({
  precision: 'lowp',
  // ...
});
```

Check for quality loss or banding afterwards. `RawShaderMaterial` ignores this property — declare `precision` in the shader source yourself.

### 36 — Keep the code simple

**Avoid `if` statements.** Make good use of swizzles and built-in functions. Use `clamp` instead of a branch:

```glsl
modelPosition.y += clamp(elevation, 0.5, 1.0) * uDisplacementStrength;
```

And `mix` instead of hand-rolled colour formulas in the fragment shader:

```glsl
vec3 finalColor = mix(depthColor, surfaceColor, elevation);
```

### 37 — Use textures instead of noise functions

Perlin noise is elegant but expensive. **`texture2D()` is far cheaper**, and noise textures are easy to author in tools like Photoshop.

### 38 — Use defines instead of uniforms

Uniforms are convenient — tweakable and animatable from JavaScript — but they have a cost. **If the value never changes, use a define:**

```glsl
#define uDisplacementStrength 1.5
```

With `ShaderMaterial`, entries in `defines` are injected into the GLSL automatically.

### 39 — Do calculations in the vertex shader

There are far fewer vertices than fragments. Anything that can be computed per-vertex and passed down should not be computed per-fragment.

## Appendix: two bundling notes

**Three.js and Babylon.js are large, and still large after gzip.** Two mitigations:

1. **Import only what you use.** Importing Babylon.js globally costs 5MB and defeats tree-shaking.
2. **CDN + externals.** Configure it as a Webpack external and load from a CDN — assuming that CDN is reliable.

If production needs shader compilation (writing WebGL shaders inside React via something like `gl-react`), Webpack's ecosystem is more complete than Vite's here.

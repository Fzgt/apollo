# #6 · `scroll from 30 to a stable 60 FPS`

> **材料说明**：百度代码不在本机，材料是 `LEARNING_NOTES_BAIDU.md` + 回忆。和 [#5](/docs?section=baidu&item=n05-dom-nodes) 一样是**你自己量出来的数**，所以审的是工具和条件。
>
> 但它比 #5 难答得多：**DOM 节点数是个客观计数，帧率不是。** 帧率极度依赖设备、依赖你怎么滚、依赖滚到第几屏——不把这些条件说清楚，「60 FPS」就是个没有意义的数。

## 对应简历原句

Baidu 第 2 条 bullet（v40）：

> ...over IntersectionObserver: live DOM nodes stay near 100 at any scroll depth, **scroll from 30 to a stable 60 FPS**.

注意 `stable` 这个词——**它是个比 60 更强的声明**，下面第五节专门讲它。

---

## 一、60 FPS 到底意味着什么

```
60 FPS  =  1000ms / 60  =  每帧 16.67ms
```

**这 16.67ms 里要跑完整条渲染流水线**：

```
JS → Style(样式计算) → Layout(布局) → Paint(绘制) → Composite(合成)
```

留给你 JS 的实际只有 **~10ms**，剩下的要给浏览器自己。**超过 16.67ms 就掉帧。**

顺带记住 RAIL 模型（笔记第 ⑥ 点），面试官爱问：

| | 目标 |
|---|---|
| **R**esponse | 用户交互 100ms 内响应 |
| **A**nimation | 每帧 16ms |
| **I**dle | 主线程留出空闲 |
| **L**oad | 首屏 1s 内可交互 |

---

## 二、为什么恰好是「30」——这个数不是随机的

**这一点讲出来会显著提高可信度。**

显示器按固定节奏刷新（vsync，60Hz 就是每 16.67ms 一次）。浏览器必须**赶在 vsync 之前**把这一帧交出去。

**一旦某帧超时，它不会「晚一点点交」，而是直接等下一个 vsync。** 于是实际帧间隔从 16.67ms 跳到 **33.3ms**——正好是 **30 FPS**。

```
每帧耗时 < 16.67ms          → 60 FPS
每帧耗时 16.67 ~ 33.3ms     → 掉到 30 FPS（不是 45，也不是 50）
每帧耗时 33.3 ~ 50ms        → 掉到 20 FPS
```

**所以「30 FPS」是 60 的谐波，是掉帧时的典型稳态值，不是一个随手写的数。** 它说明当时每帧耗时落在 16.67–33.3ms 之间——超了预算，但没超太多。

> 这也顺带回答了「为什么优化后正好回到 60」：**因为把每帧压回 16.67ms 以内，就自动回到 60，没有中间态。**

## 三、怎么测（这一节是重点）

### 工具一：Frame Rendering Stats —— 最快的定性验证

`Cmd+Shift+P` → `Show Rendering` → 勾上 **Frame Rendering Stats**。

页面左上角出现一个实时浮层，直接显示当前 FPS 和 GPU 内存。**滚动的时候盯着那个数字看**——这是三十秒就能做完的验证，适合自己反复调参时用。

### 工具二：Performance 面板录制 —— 最有说服力的证据

录一段滚动，然后看三个地方：

| 看哪里 | 能得到什么 |
|---|---|
| 顶部 **FPS 条带** | 绿色是正常，**红色标记就是掉帧**。优化前后对比截图放一起，一目了然 |
| **Frames 轨道** | 每一帧的实际时长，鼠标悬停能看到具体多少 ms——这是「16.67ms 预算」的直接证据 |
| **Main 轨道** | 掉帧那几帧里，主线程到底在干什么。展开火焰图能定位到具体函数 |

**这也是和 [#5](/docs?section=baidu&item=n05-dom-nodes) 共用的那份录制**——同一段录制里，DOM 节点数、Layout 耗时、帧率能对上，**这才是完整的因果链条，而不是三个孤立数字**。

### 工具三：Performance Monitor —— 看流水线哪一段被打爆

`Cmd+Shift+P` → `Show Performance Monitor`。除了 #5 用的 DOM Nodes，这里还有三条直接相关的：

- **CPU usage**
- **Layouts / sec**
- **Style recalcs / sec**

优化前后对比这三条，能直接证明**是布局阶段被打爆了**，而不是别的原因。

### 工具四：`requestAnimationFrame` 自己数帧

```js
let last = performance.now(), frames = 0;
function tick(now) {
  frames++;
  if (now - last >= 1000) {
    console.log(frames, 'fps');
    frames = 0;
    last = now;
  }
  requestAnimationFrame(tick);
}
requestAnimationFrame(tick);
```

**优点**：能在**真机、真实网络、真实用户环境**下跑，DevTools 做不到这一点。

**必须主动说的局限**：`rAF` 自己也跑在主线程上。主线程被打爆时，**它自己也会被推迟**，所以重负载下这个数偏乐观。**知道这个局限比会写这段代码更重要。**

### 工具五：`PerformanceObserver` 监听 long task

```js
new PerformanceObserver((list) => {
  for (const entry of list.getEntries()) {
    console.log('long task', entry.duration, 'ms');
  }
}).observe({ entryTypes: ['longtask'] });
```

**long task = 主线程被单个任务占用超过 50ms。** 一个 50ms 的 long task 就意味着**连掉 3 帧**。

**这个视角比 FPS 更有用**，因为它直接指出「是哪一段代码卡住了」，而不只是「卡了」。

### 工具六：线上 field 数据

上面五个全是 **lab（实验室）** 手段。真实用户的卡顿要靠 **field** 数据：上报 long task、上报 **INP**（Interaction to Next Paint，已经取代 FID 成为 Core Web Vitals 的交互指标）。

**lab 和 field 的区别，和 [#3](/docs?section=biomap&item=n03-lcp) 是同一套话术**，答的时候可以呼应。

## 四、按「审什么」逐条过

### ① 工具

见上一节。**准备一个主答案**：

> 主要是 DevTools Performance 面板录滚动，看 FPS 条带和 Frames 轨道的帧时长；快速验证用 Rendering 里的 Frame Rendering Stats 实时浮层。

### ② 设备 —— 这条最容易被问死

**FPS 极度依赖设备。** 同一个页面，旗舰机稳 60，千元机可能连 30 都够呛。而这是个**移动端 H5 feed**，用户设备分布极广。

所以必须交代：**在什么机器上测的？**

- 如果是**桌面 Chrome 上量的**，那这个数偏乐观，得说明
- 如果用了 **DevTools 的 CPU throttling**（Performance 面板里的 `4x slowdown` / `6x slowdown`）来模拟低端机，**一定要说**——这是 lab 里模拟真实设备的标准手段，说出来直接加分
- 如果是**真机**测的，说清机型

**没有设备信息的 FPS 数字等于没有数字。**

### ③ 交互场景

同样必须限定：

- **匀速慢滚** 还是 **快速甩动（fling）**？——快速滚动才是压力测试，慢滚可能根本不掉帧
- **滚到第几屏时测的？**

第二点特别重要：**优化前那个 30 FPS，一定是在列表已经累积到几百条之后测的。** 刚打开页面时只有二三十条，全量渲染也不卡。

**所以「30 FPS」必须绑定「滚了 N 屏、DOM 里已经堆了五百多个节点」这个前提**——这也正好把 [#5](/docs?section=baidu&item=n05-dom-nodes) 那条串进来。

### ④ 是否稳定值

见下一节。

---

## 五、`stable` 这个词要怎么撑住

**`a stable 60 FPS` 是个比「60 FPS」更强的声明**，它承诺的是「没有波动」。

而这里有个坑：**FPS 是个不能简单取平均的指标。**

「平均 30 FPS」可能是两种完全不同的情况：

| | 用户感知 |
|---|---|
| 稳定在 30 | 有点钝，但**均匀** |
| 在 10 和 60 之间反复跳，平均 30 | **明显卡顿** |

**用户感知到的「卡」来自帧时间的方差，不是平均帧率。** 所以现代性能工作已经不太看平均 FPS 了，改看：

- **帧时长的分位数**（p95 / p99 frame time）
- **long task 的数量和时长**
- **掉帧数（dropped frames）**
- 线上看 **INP**

**所以 `stable` 该怎么答？**

> 「stable 的意思是滚动过程中 Performance 录制里没有出现红色掉帧标记，Frames 轨道里没有超过 16.67ms 的长帧——不是指平均值到了 60。」

**把 `stable` 定义成「没有长帧」而不是「平均值高」，这个答法既准确又显得专业。**

## 六、量化归因：具体是哪一步让 FPS 上去的

面试官很可能追这一句。笔记里第 341–347 行给了四条，**每条都能在 DevTools 里找到对应证据**——这是这条 bullet 最硬的部分：

| # | 做了什么 | 为什么快了 | 在 DevTools 里看哪 |
|---|---|---|---|
| 1 | **DOM 节点五百多 → 恒定一百上下** | layout 时间从 ~10ms 降到 ~0.5ms，单帧的 Layout 阶段被释放出来 | Performance Monitor 的 `Layouts/sec`；录制里 Layout 的耗时 |
| 2 | **`transform: translateY` 替代 `top`** | `top` 触发 Layout + Paint + Composite；`transform` **只走 Composite**，GPU 做，主线程无压力 | 录制里 Paint 事件明显减少；Layers 面板能看到合成层 |
| 3 | **scroll 加 `passive: true`** | 告诉浏览器「我不会 `preventDefault()`」，浏览器可以**立即开始滚动**而不等 JS 跑完 | 录制里 scroll handler 不再阻塞合成 |
| 4 | **IntersectionObserver 替代 scroll + `getBoundingClientRect()`** | 后者每次滚动都**强制同步布局（forced reflow）**，是典型的性能杀手 | **DevTools 会直接标出来**——Main 轨道上黄色三角 + `Forced reflow is a likely performance bottleneck` 警告 |

**第 4 条那个警告特别值得说**：它不是你推断出来的，是**浏览器自己报的**。「优化前 DevTools 一直在报 forced reflow，改用 IntersectionObserver 之后警告消失了」——这是能拿出来的具体证据。

---

## 七、一句话答法

> 60 FPS 就是每帧 16.67ms 的预算。优化前每帧超预算，因为 DOM 里累积了五百多条，单次 layout 就要十毫秒量级；而 vsync 机制下一帧超时就得等下一个刷新周期，所以直接掉到 33.3ms 一帧、也就是 30 FPS——这个 30 是 60 的谐波，不是随手写的数。做了虚拟列表把 DOM 压到一百上下、而且不再随数据量增长，再加上 transform 替代 top、scroll 用 passive、IntersectionObserver 替掉 getBoundingClientRect 消除强制重排，每帧回到预算内就自动回到 60。测的方法是 DevTools Performance 录一段滚动看 FPS 条带和 Frames 轨道的帧时长；这里说的 stable 指的是录制里没有超过 16.67ms 的长帧，不是平均值到了 60。

### FID (First Input Delay)

- Block the main thread less. This is why React 18's concurrent mode helps FID.
- Split the bundle. Avoid one huge file.
  - Split at the route level with `lazy(() => import('./Home'))`. Webpack splits the async chunk for you, and lazy loading makes the first payload much smaller. (HTTP/2 is the norm now, so you no longer need to over-split to work around HTTP/1.1's six connections per domain — multiplexing sends many files in parallel.)
- Avoid long tasks: parsing large JSON, heavy DOM work, processing large data sets, initialising third-party libraries, image and video processing.
  - The fixes: dynamic `import()` for lazy loading (paired with `lazy` in React; plain JS `import()` is already lazy), and web workers.

### FCP (First Contentful Paint)

- A SPA renders everything into one `div#app`. Nothing shows until the data request comes back, the diff runs, and the result is appended — that is the moment FCP fires.
- Loading the JavaScript takes a while, and the page is blank for all of it.

### What is a long task

- Any task that runs more than **50 ms** on the main thread is a long task by the browser's definition. Why 50 ms? To keep things smooth — 60fps animation, say — the browser has to finish a frame every 16.7 ms (1000 / 60). One task holding the thread for over 50 ms blocks rendering, drops frames, and stutters.
- Why 50 ms specifically:
  - 100 ms — the upper limit of what users perceive as an instant response
  - 50 ms — the budget left for JavaScript once you account for the browser's own rendering work
  - Past 50 ms, users start to feel the jank

### Pre-rendering: fixing SEO and the blank first page

A skeleton screen is useless to the user. Fill the same space with real content and you have pre-rendering.
The idea is to render your Vue or React project ahead of time.
How it works: a headless browser.

> How does it turn your routes into static pages? It runs them in a headless browser. But the mechanism is dumb — it just waits, as long as it can, and executes when it decides it has waited long enough. If the content arrived, you get a pre-rendered page. If it did not, the pre-rendered page is missing that content.

Pre-rendering is not flexible enough, though. It only works for fairly static pages, unexpected conditions can make it fail, and it is worse for SEO than SSR. SSR is the better answer.

### On isomorphic rendering

Isomorphic rendering saves you all of the above.
It is MPA on a full page load and SPA when you navigate between pages.
SPA navigation wins on payload: it transfers the minimum.
MPA wins by skipping all the extra requests. It loses by re-loading the same assets when you go from route A to route B.
Next.js and Nuxt.js are what you get when you combine the strengths of both.
(Sharing data on the client is more expensive under SSR because Vuex only covers a full page there, while under CSR it covers the whole site.)

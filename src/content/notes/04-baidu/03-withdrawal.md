# ③ 提现客户端

> **简历原句**
>
> Built the **withdrawal client** on a path **peaking above 2,000 QPS**: **request locking** drops in-flight duplicates, **client-generated idempotency keys survive reloads**, and **uncertain outcomes surface as failures, never successes**.
>
> ---
>
> 在峰值超过 2,000 QPS 的链路上实现提现客户端：请求锁丢弃在途的重复请求，前端生成的幂等键在页面刷新后依然有效，结果不确定时一律按失败提示，绝不显示成功。

## 这条 bullet 在讲什么

⭐ **一句话：前端在金融链路里能保证什么，不能保证什么。**

**这条 bullet 最容易翻车的方式，是把它讲成「我用前端的锁扛住了 2000 QPS」。** 那句话经不起一层追问 —— F12 直接调接口就绕过去了。

⭐ **它真正的价值在于你能主动划清界限：前端减少无效负载，后端提供正确性。** 说不出这句，这条 bullet 就是负资产。

## 30 秒口播稿

> 这是个活动期间的提现入口，峰值时整条链路到过两千多 QPS。**前端在这里的职责很窄但很明确：把无效的重复请求挡在发出之前，并且在结果不确定时永远往「失败」那边说。**
>
> 具体三件事：**请求发出到响应回来这段窗口里锁住同一笔提现**，不让用户狂点产生第二个请求；**幂等 key 在前端生成并存进 sessionStorage**，这样用户刷新页面重试，后端还能认出这是同一笔；**超时和网络中断一律按失败提示**、引导去查提现记录，绝不显示成功。
>
> ⭐ **但我很清楚前端锁挡不住跨设备、跨标签页和刷新重试 —— 真正的正确性来自后端的幂等键和数据库约束。前端减少的是无效负载，不是提供保证。**

## 一、先定义「幂等」，这个词后面到处要用

⭐ **幂等（idempotent）= 同一个操作执行一次和执行 N 次，系统最终状态一样。**

- `把余额设为 100` → **幂等**（做几次都是 100）
- `余额减 50` → ⚠️ **不幂等**（做两次就扣了 100）

**提现天然属于第二种。** 所以必须在外面套一层机制，⭐ **让「重复执行」变成「识别出是重复、不再执行」。**

## 二、防抖 vs 节流 vs 请求锁（常混，要分清）

| | 行为 | 场景 |
|---|---|---|
| **Debounce（防抖）** | 多次触发，**停下来之后 n 毫秒才执行一次** | 搜索框输入、resize |
| **Throttle（节流）** | **每 n 毫秒最多执行一次**，匀速 | scroll、mousemove |
| ⭐ **请求锁** | **第一次立即执行，之后到响应回来为止全部拦掉** | 提交类操作 |

⭐ **提现按钮为什么不能用 debounce**：「停下来才生效」意味着用户点了 100 次，只有最后一次在 300ms 后发请求。**用户点第一下时什么都没发生，他会觉得「没反应」，于是点更多次** —— 体验和意图完全相反。

> **提交类操作要的是「首次立即执行 + 锁住后续」（leading edge + lock），不是防抖的「最后一次才执行」（trailing edge）。**

## 三、请求锁的两个版本，逐行读

**朴素版：**

```js
let inFlight = false;                    // 「有没有一个请求正在飞」
async function withdraw() {
  if (inFlight) return;                  // 正在飞 → 直接不做事
  inFlight = true;                       // 上锁
  try { ... } finally { inFlight = false; }   // ⭐ finally：成功失败都要解锁
}
```

⭐ **`finally` 那一句是重点**：如果只在成功分支里解锁，**一次失败之后按钮就永久锁死了**，用户再也提不了现。

**按参数去重版**（同一笔锁住，不同笔可以并发）：

```js
const inFlightMap = new Map();           // key = 这一笔的单号，value = 正在飞的那个 Promise
async function withdraw(orderId) {
  if (inFlightMap.has(orderId))
    return inFlightMap.get(orderId);     // ⭐ 不是「拒绝」，是把同一个 Promise 还给他
  const promise = api.withdraw(orderId);
  inFlightMap.set(orderId, promise);
  try { return await promise; }
  finally { inFlightMap.delete(orderId); }
}
```

**逐行说明：**

- 用 `Map` 而不是布尔量 → ⭐ **锁的粒度从「整个按钮」细化到「每一笔单」**，用户同时提两笔不同的不会互相挡
- ⭐ `return inFlightMap.get(orderId)` → 第二次调用**拿到的是第一次那个 Promise**。调用方 `await` 之后照样拿到结果，**它不知道自己被去重了**，代码不用写任何特判
- `finally { delete }` → 请求结束就把锁拿掉，下次点击是一次全新请求

⭐ **这个模式叫「请求去重」（request deduplication），React Query / SWR 内部就是这么做的。** 能点出这一句，说明你知道自己在复现一个通用模式，而不是随手写的。

## 四、幂等 key：前端能做的最有价值的一件事

**前端锁挡不住三件事**（因为那个 `Map` 只活在当前页面的内存里）：

1. 网络超时后的**自动重试**
2. 用户在**不同设备 / 不同标签页**同时操作
3. ⭐ **页面刷新后再点** —— 刷新等于整块内存清零，锁没了

**所以真正的保证必须来自后端幂等**：每个提现请求带一个**幂等 key**（这笔操作专属的随机串），后端把处理过的 key 存下来，**同 key 再来就直接返回上次的结果，不再执行扣款**。

**前端的配合是关键的一半：**

| 做法 | 为什么 |
|---|---|
| **提前生成 key**（进页面就生成，不是点击时） | 点击时生成的话，**用户点两次就是两个不同的 key，后端看到的是两笔不同的提现** |
| ⭐ **存 sessionStorage** | **刷新页面后还是同一个 key** —— 否则刷新重试在后端看来是一笔新提现。**简历里 `survive reloads` 就是这个** |
| 每次调用都带上它 | |

## 五、defensive fallback：金融场景的错误处理原则

⭐ **默认失败，只有明确成功才展示成功。**

| 结果 | 怎么处理 |
|---|---|
| **明确失败**（4xx/5xx、业务错误码） | 显示错误 + 可重试 |
| ⭐ **不确定**（超时、网络中断、发出去没响应） | **按失败处理**，但措辞是「网络异常，请稍后查看提现记录」—— ⚠️ **不要直接说「失败了」**（后端可能已经处理了） |
| **明确成功**（2xx + 业务成功码） | 展示成功 |

⭐ **为什么「不确定」要往失败那边倒 —— 因为两种错法的代价不对称：**

- **错误地显示失败** → 用户去重试 → **重试有幂等 key 兜底，不会真的扣两次** → 代价只是一次白跑
- **错误地显示成功** → 实际没到账 → **用户以为提了但钱没来** → 客诉、投诉、事故

⭐ **「代价不对称」是这一节的题眼，也是所有金融前端错误处理的通用原则。**

## 六、⭐ 2,000 QPS 是什么、谁测的（这一节必须自己先想清楚）

### 归属：这个数字不属于前端

⭐ **QPS 是后端指标。前端不「扛」QPS，前端「贡献」QPS** —— 每个用户点一下就贡献 1 QPS。**前端拿不到全站每秒请求数，那是网关和后端监控里的东西。**

**从后端同事那里知道这个数完全合理**，这是团队里正常的信息流动。⭐ **但你必须能说清楚你知道的是什么、你做的是什么，这两件事不能混。**

> **简历现在的写法是安全的**：`on a path peaking above 2,000 QPS` 只说**链路的量级**，锁和幂等 key 各自写成自己的动作 —— **规模还在，但不声称是你的锁扛住的。**（原句是 `sustained 2,000+ peak QPS through request locking and defensive fallbacks`，语法上把「扛住」归因给了前端的两样东西，已经改掉。）

### QPS 是算出来的，不是测出来的

⭐ **监控系统实际存的是一个只增不减的计数器，QPS 是「计数器在一个时间窗口上的斜率」：**

```
QPS = (窗口结束时的计数 - 窗口开始时的计数) / 窗口长度
```

⭐ **于是窗口大小直接决定了你看到的数字：**

| 统计窗口 | 同一段流量算出来的「峰值 QPS」 |
|---|---|
| 1 秒 | 可能 2000 |
| 1 分钟 | 可能只有 600 |
| 5 分钟 | 可能只有 300 |

⭐ **窗口越大，峰值被抹得越平。所以「峰值 2000 QPS」不说窗口，等于没说。**

**`peak` 和 `sustained` 差很远**：峰值 2000 持续 3 秒，和持续 2000 跑 30 分钟，**对数据库的压力完全不是一回事**。⭐ **你得知道自己说的是哪个** —— 简历现在明确只说峰值。

### 监控还是压测：两条来源，含义天差地别

| | **监控** | **压测** |
|---|---|---|
| 含义 | ⭐ **真实发生过** | ⭐ **验证过能承受** |
| 怎么来的 | 网关记日志 → 采集 → 时序库 → 看板画曲线 | 用工具造流量打系统，梯度加压 |
| 正确表述 | 「活动峰值时段监控看到 2000+」 | 「压测验证能扛 2000+」 |

⚠️ **绝对不能混说** —— 说成监控但其实是压测，是在虚报业务体量；反过来则是低估了自己的工作。

**压测的几个概念，能说出来就说明你真见过：**

- **梯度加压**：从低 QPS 一档档往上加，不是一上来就打满
- ⭐ **拐点 / 容量水位**：QPS 还在涨、但 **P99 延迟开始飙升、错误率开始上升**的那个点才是真实容量。**容量不是「打得进去多少」，是「打进去还不崩的最大值」**
- ⭐ **完整的压测结论长什么样**：不是「能扛 2000 QPS」，而是「压到 2000 时 P99 延迟 120ms、错误率 0，继续加到 2600 时 P99 涨到 800ms」
- **影子库 / 压测标记**：线上压测必须把压测流量写进影子表。⭐ **金融场景尤其不能污染真实资金数据**

> ⚠️ **记不清就用安全说法**：「这是后端给的口径，我记得是活动期间的峰值量级，具体是监控还是压测报告我需要确认。」—— ⭐ **「我需要确认」永远比编一个答案安全。**

## 七、后端做了什么才扛得住（讲这段能从「听说」升级成「理解」）

| 层 | 做了什么 |
|---|---|
| **接入层** | **限流**（令牌桶/漏桶，宁可拒绝一部分也不能全崩）、**排队/验证码削峰**、**熔断降级** |
| **应用层** | 无状态 → **加机器就能线性扩容**。⭐ **QPS 是集群指标不是单机指标** —— 20 台机器分摊 2000 QPS，单机只有 100 |
| ⭐ **数据层（真正的瓶颈）** | **提现是写操作，缓存救不了写**。分库分表按用户 ID 哈希打散、读写分离；⭐ **热点账户问题** —— 如果所有提现都从同一个资金池账户扣钱，**所有事务都在抢同一行的行锁，分库分表也救不了**，要把账户拆成多个分桶 |
| **一致性** | 幂等键**建唯一索引**；余额不变量**写进 SQL 的 WHERE** |
| ⭐ **异步化** | 提现通常不是同步完成的 —— 校验后落一条「处理中」订单就返回，**真正打款走异步队列**。**所以那个 2000 QPS 是「提交申请」的量，不是「实际打款」的量，这两个数可以差很远** |

### 两个数据层的写法值得单独背

```sql
-- ① 幂等 key 建唯一索引，重复请求直接违反约束
INSERT INTO withdraw_order (idempotency_key, user_id, amount, ...) VALUES (...);

-- ② 余额不变量写进 WHERE，靠「影响了几行」判断成败
UPDATE account SET balance = balance - ?
WHERE user_id = ? AND balance >= ?;
```

⭐ **为什么不能「先查再写」**：查和写之间有时间窗口，**2000 QPS 下两个并发请求可能同时查到「不存在」然后都写进去**。数据库的唯一索引和单条 UPDATE 是原子的，**没有这个窗口**。

> ⭐ **这和 [Stripe 的终身档保护](/docs?section=beyz&item=stripe-billing)、[Beyz 邮件的唯一索引](/docs?section=beyz&item=service-cicd)、[BioMap 的类型约束](/docs?section=biomap&item=tanstack-query) 是同一个模式：把不变量放在数据层，不放在应用层的 if 判断里。** 四个例子来自三个项目，**串起来就是[跨项目追问](/docs?section=cheatsheet&item=crosscut)的现成答案。**

## 八、「零资损」被问到怎么答（这句已从简历删掉，但话题会自己撞上来）

**原句里有 `without a single dollar of financial loss`，已经删了。** 删的原因值得知道：

⭐ **它是个否定性断言 —— 证明「从来没有发生过任何一次资金损失」。你没法穷举所有「没发生的事」。**

⭐ **唯一能支撑它的是对账，而对账在财务侧，不在任何技术监控看板里：**

```
业务库的提现流水  ↕ 按渠道流水号逐笔比对  支付渠道的对账文件（T+1 下发）
                → 差异进差错处理流程：补单、退款、追回
```

**所以「零资损」的准确含义是：对账差异全部平掉、最终没有净损失。**

### ⭐ 资损防线是分层的（讲出来很加分）

| 层 | 做什么 | 性质 |
|---|---|---|
| 1. **前端** | 请求锁、幂等 key、错误兜底 | 减少无效重复 |
| 2. 网关 / 应用 | 限流、参数校验、风控 | 挡住异常流量 |
| 3. **数据库** | 幂等键唯一索引、余额不变量、事务 | ⭐ **正确性的真正来源** |
| 4. 异步状态机 | 订单只允许合法的状态转移 | 防乱序和重放 |
| 5. ⭐ **对账** | T+1 逐笔核对，差异进差错流程 | **发现并修补** |

⭐ **关键洞察：前四层是「让它不发生」，第五层是「发生了也能发现并补回来」。真正的零资损靠的是第五层兜底，不是前四层做到完美** —— 任何做支付的人都知道前四层不可能完美：网络会抖、渠道会超时、人会写 bug。

> ⭐ **承认自己只是第一层，反而比声称做到了第五层更可信。**

## 九、被追问时的分工表（一口气说清）

| 问题 | 答法 |
|---|---|
| **用户绕过前端锁会怎样？** | ⭐ **能绕，而且很容易** —— F12 直接调接口。所以前端锁只减少无效请求，**正确性靠后端幂等键 + 唯一索引 + 数据库事务 + 余额不变量** |
| **2000 QPS 是你测的吗？** | 不是，后端监控里整条链路的量级。**前端不扛 QPS，前端贡献 QPS** |
| **零资损怎么保证的？** | **对账的结论，不是我测的。** 防线分五层，前端只在第一层 |
| **前端还能做什么？** | 限流（没配额时按钮 disabled）、活动开始瞬间排队/验证码削峰 —— ⚠️ **但这些都是体验优化，不是正确性保证** |

⭐ **一句话收尾：前端减少无效负载，后端提供正确性。**

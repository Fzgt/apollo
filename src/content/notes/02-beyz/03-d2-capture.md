# 采集层：怎么拿到面试官的声音

> ⚪ **速查**。被追问 `video: true` 或 250 毫秒时翻这里。

## 一、两个接口，方向完全相反

浏览器里拿音频有两个接口，**这个项目两个都用了，但用途不同**：

| 接口 | 拿到的是 | 用在哪 |
|---|---|---|
| **`getDisplayMedia`** | **另一个标签页 / 整个系统**播出来的声音 | ⭐ 主路径——听**面试官** |
| **`getUserMedia`** | **麦克风**收到的声音 | 另一个模式——听**自己** |

**为什么主路径必须是前者**：面试官的声音是从 Zoom / Teams 里**播放出来**的，属于另一个应用的音频输出。麦克风只能收到房间里的空气振动 —— **你自己说话它听得最清楚，那正好是我们不需要的。**

**顺带一个能加分的观察**：`getUserMedia` 那条路开了 `echoCancellation`（回声消除）和 `noiseSuppression`（降噪）—— **这两个参数只对麦克风有意义**，因为麦克风会把扬声器放出来的声音又录回去。而 `getDisplayMedia` 拿到的是**系统内部直接给的数字信号，没经过空气**，所以不需要这些处理，**信噪比也高得多**。

## 二、为什么必须 `video: true`

```js
navigator.mediaDevices.getDisplayMedia({ video: true, audio: true })
```

**规范层面**：这个接口的定义是「**共享一个画面**」，音频是挂在画面上的可选附加项。**必须至少请求一条画面轨**，写 `{ video: false, audio: true }` 会直接抛错。

**为什么规范要这么定**（这一层是加分的）：

**因为音频没有可视化的授权载体。**

用户点「共享」时，浏览器弹出的窗口里展示的是**一个个可选的窗口/标签页缩略图** —— **用户是在选一个画面**。「顺带分享它的声音」是挂在这个画面上的一个勾选框。

**如果允许只要音频不要画面**，弹窗要怎么展示？「请选择一个你要被窃听的应用」—— **用户没有任何视觉锚点来判断自己授权了什么。**

> **一句话答法**：`getDisplayMedia` 的授权模型是围绕「一个可见的画面」建立的，音频是挂在画面上的附属权限。**没有画面就没有东西可以让用户确认自己在共享什么**，所以规范要求必须请求 video。

## 三、拿到之后为什么立刻关掉画面

```js
// useAudioStream.ts:38-43
const videoTrack = stream.getVideoTracks()[0];
if (videoTrack) {
  videoTrack.stop();              // ① 停止采集
  stream.removeTrack(videoTrack); // ② 从流里摘掉
}
```

**先解释这两个调用的区别 —— 它们是两件事，都要做：**

| 调用 | 做什么 | 不做会怎样 |
|---|---|---|
| **`stop()`** | **真正停止采集**，释放屏幕捕获资源 | 浏览器**还在持续编码屏幕画面**，CPU 和内存一直在烧 |
| **`removeTrack()`** | 把这条轨**从这个流对象里摘掉** | 后面的 `MediaRecorder` 还能看到它，**会把视频也录进去发给 Deepgram** |

> ⚠️ **只 `removeTrack` 不 `stop` 是个常见的漏** —— 流里看不见它了，但采集还在跑。

**四个理由，前两个是硬的：**

1. **省资源** —— 我们一帧画面都不用，没必要让浏览器一直编码屏幕
2. **隐私** —— **不留一条能读到用户屏幕内容的流**。这条讲出来很加分：**拿到了不需要的权限就立刻交还，是最小权限原则在客户端的体现**
3. **`MediaRecorder` 的行为** —— 它会录流里的所有轨
4. **共享指示条** —— 浏览器在共享画面时会显示醒目提示条，停掉后行为更干净

**还有一处**：用户可以中途换共享源，所以设新流之前要**先停掉旧的音频轨**（`:33-36`）—— 不停的话旧轨一直活着采集，是典型的资源泄漏，而且用户会看到两条共享指示条。

## 四、250 毫秒这个切片

```js
new MediaRecorder(mediaStream).start(250)
```

**`MediaRecorder` 是浏览器内置的录音器。** `start(timeslice)` 里的参数含义是：**每隔 timeslice 毫秒，把这段时间录到的音频打包成一块（Blob）交给你**。

> ⚠️ **不传这个参数会怎样**：它会一直录，**直到调 `stop()` 才一次性把全部数据给你**。对实时转写来说等于没有流 —— **所以这个参数就是「流式」和「批式」的开关。**

**调大调小的取舍：**

| | 太小（50ms） | 太大（1000ms） |
|---|---|---|
| **延迟** | ✅ 音频更快到达 | ❌ **每块音频天然自带最多 1 秒延迟**（要攒满才发） |
| **开销** | ❌ 每秒 20 次发送，**每个包的固定开销占比上升** | ✅ 低 |
| **编码** | ❌ 太短的片段可能形不成有效的音频帧 | — |
| **体验** | — | ❌ 屏幕上的字一顿一顿地出 |

**250 为什么合理：**

1. **切片延迟压在了「感知不到」的量级** —— 而这是整条链路里**你唯一能自由选择**的延迟项（识别和生成的耗时你控制不了）
2. **每秒 4 个包** —— WebSocket 上非常轻松的频率
3. **它比「判断说完了」的 2 秒窗口小 8 倍** —— 切片粒度远小于静默判定的粒度，不会互相干扰

> **诚实的基线**：250 也是 Deepgram 官方示例里的默认值。**但「是默认值」和「它合理」不冲突** —— 面试官问的是你能不能讲清它合理在哪。

## 五、这一层的失败分支

| 情况 | 代码 | 处理 |
|---|---|---|
| **用户点了取消** | `:57-58` | 抛 `NotAllowedError` → 走「拒绝」分支，**和真错误分开**（拒绝是正常选择，不该弹「出错了」） |
| **选了屏幕但没勾「分享音频」** | `:46-51` | `getAudioTracks()[0]` 是空的 → 报错并清空流 |
| **其他异常** | `:59-60` | 统一走错误回调 |
| **无论成败** | `:62-64` | `finally` 里关掉 loading 状态 |

> ⚠️ **第二条是这个接口最常见的用户失误**：弹窗里「分享音频」的勾选框**默认不勾**，而且选「整个屏幕」时部分平台根本不提供系统音频。**代码显式检查了音频轨是否存在，没有假设它一定在** —— 被问「用户没勾会怎样」时能指着这几行说话。

# 崩在半路，怎么接着跑

> 🔴 **必看**。⚠️ **④ scripted seam 那半边在另外两篇**：[④ 406 server tests](/docs?section=periplus&item=n14-server-tests)（四个替换点、三种注入手法、为什么注入时钟）和 [④ 约一秒跑完](/docs?section=periplus&item=n15-end-to-end)。**这一篇只讲 ③。**

## 对应简历原句

> **Persisted run state, stage artifacts and a pgvector evidence cache in PostgreSQL under per-run token and time budgets. A run that dies mid-pipeline resumes from the last completed stage.**

## 一、要解决什么

**这个流水线跑一次要几分钟、要花钱**（每个阶段都在调模型、抓网页）。

**如果进程挂在第四阶段，重跑意味着前三阶段的钱和时间全部白花。**

**所以：run 的状态、每个阶段的产物、还有检索到的证据全部存进 PostgreSQL。进程重启时把没跑完的捡起来接着跑。**

## 二、30 秒口播稿（改一改就能用）

> 这个流水线跑一次要几分钟、要花钱。**进程挂在第四阶段，重跑意味着前三阶段全部白花。**
>
> 所以 run 的状态、每个阶段的产物、还有检索到的证据全部落在 PostgreSQL 里。**进程重启时会扫出所有还标着「运行中」的 run，从它「最后一个通过了关卡的阶段」之后接着跑。**
>
> **关键在「通过了关卡」这个限定**：失败的产物我们也留着 —— 供事后检查 —— **但它永远不是合法的续跑边界**。另外预算是整个 run 的天花板，**续跑时不会重置，而是把已经花掉的量带进来** —— 否则**反复重启就能一次一个阶段地把配额刷穿**。

## 三、⭐ 三个能体现深度的设计

### ① 续跑边界必须是「通过了关卡的产物」

**先说「关卡」（gate）是什么**：每个阶段跑完，会有一道检查 —— **产物结构合法吗？内容是不是空的？** 不合格就算这个阶段没过。

`artifacts.py` 文件头原话：

> *"Every stage attempt's produced artifact is retained, **whether or not it passed the stage's gate**... A rejected or superseded attempt stays retrievable for inspection; **it is simply never a valid replay boundary**."*
>
> （每一次阶段尝试产出的东西都保留下来，**不管它有没有通过这个阶段的关卡**……被拒绝或被取代的尝试仍然可以取出来检查；**它只是永远不能作为重放的起点。**）

> ⭐ **保留失败产物是为了排查，允许从它续跑是另一回事。这两件事分开，是这个设计最容易被忽略的一半。**

### ② ⭐ 预算续跑时不重置（这条最值钱）

**先说「预算」是什么**：一次 run 有四个上限 —— **最多发多少次检索、最多抓多少个网页、最多花多少 token、最多跑多少秒**。

`budget.py` 文件头原话：

> *"A budget is a ceiling for the whole Run, **replays included**: a BudgetTracker built for a replay is **seeded with everything the run already spent**, not reset to zero. **Resuming a run repeatedly cannot be used to spend past a configured ceiling one stage at a time.**"*
>
> （预算是整个 run 的天花板，**包括重放在内**：为重放建的计数器**会把这次 run 已经花掉的量作为起点**，而不是清零。**反复续跑一个 run，不能被用来一个阶段一个阶段地突破配额上限。**）

> ⭐ **这是个真正的安全性质**：如果续跑时预算归零，那「反复让它崩」**就变成了绕过配额的手段**。
>
> **能主动指出这一点，说明你想过「这个机制会怎么被滥用」—— 这比讲清楚它怎么工作高一个层次。**

**检查的时机也讲究**（同一段注释）：预算检查发生在**一个阶段跑完之后、下一个阶段开始之前**，**从不在阶段内部打断它** —— 所以它「**不能抢占正在飞的阶段，只能让它不算通过，或者不让下一次尝试开始**」。

### ③ 崩在哪里，决定了怎么恢复

**`runs.py:219-251` 有三个分支：**

| 情况 | 处理 | 为什么 |
|---|---|---|
| **一个关卡都没过就死了** | 标成**失败**，不重跑 | 注释原话：*"a fresh start would **silently pretend this attempt never happened** instead"*（重新开始等于**静默地假装这次尝试从未发生过**） |
| **所有阶段都过了，死在记录成功的路上** | 直接标成**成功** | *"rather than replaying a pipeline that already finished"*（而不是重放一条已经跑完的流水线） |
| **中间某个阶段之后崩的** | 从下一个阶段续跑 | 正常路径 |

> ⭐ **第一种最值得讲**：**「无从恢复」和「重新开始」是两回事。**
>
> 直接重跑会让这次失败的尝试**在记录里凭空消失** —— **而那正是你排查问题时需要的东西。**

## 四、四个必答

### Q：第四阶段挂了怎么从第三阶段之后接着跑

> 「进程启动时扫数据库里所有还标着『运行中』的 run —— **这个状态本身就是信号**，因为正常结束一定会写一次『已完成』。然后沿着阶段顺序走一遍，**找最靠后的、有『通过关卡的产物』的阶段，从它的下一个开始。**」

> ⚠️ **一个位置问题，答错很难看：**
>
> **续跑逻辑不在编排器里，在 API 层的 run 存储里（`api/runs.py`）。**
>
> **编排器只管「在给定的起点上跑流水线」，「上次跑到哪、该不该续」是持久化层的职责。**

### Q：run 状态为什么不能只放在内存

**三条：**

1. **进程会挂** —— 这就是整个机制的前提
2. **要能水平扩容** —— 另一个实例得看得到状态
3. **用户要能刷新页面看进度** —— 前端轮询的是数据库，不是某个进程的内存

### Q：续跑的那个阶段怎么保证幂等

**靠的不是「让阶段本身幂等」，是「让边界干净」：**

- **只从通过关卡的产物续跑**，所以续跑的**输入是确定的**
- 重跑的那个阶段会产生**新的尝试编号**，**不覆盖旧的**

> ⚠️ **有个很细的坑值得讲**（`runs.py:253-262`）：**崩溃可能发生在某个阶段中途**，所以要续跑的那个阶段**可能已经有过没通过关卡的尝试记录了**。
>
> 代码会**先填充占位的历史**，让编排器的尝试计数器接着往下走，**而不是撞上一个产物库里已经存在的编号**。
>
> ⭐ **能讲出这个细节，说明你真的处理过「崩在半路」，而不只是「崩在阶段之间」。**

### Q：向量缓存里存的是什么，怎么失效

**存的是抓取到的证据段落 + 它的向量**，目的是**同一段证据不重复抓、不重复算向量**。

**「向量」是什么**：把一段文字转换成一串数字，**意思相近的文字，数字也相近**。这样就能问「有没有和这段话意思差不多的、我已经抓过的内容」。

**失效靠的是 [② 那套新鲜度窗口](/docs?section=periplus&item=d9-evidence)** —— **缓存本身不设过期时间，是消费它的时候按日期判断过没过期。**

> ⭐ **这个区分值得说**：**缓存不负责判断「新不新鲜」，只负责「别重复干活」。新鲜度是业务语义，归判断过期的那个函数管。**

## 五、pgvector 那几个选择（代码里核过）

```sql
CREATE INDEX evidence_cache_embedding_idx
    ON evidence_cache USING ivfflat (embedding vector_cosine_ops) WITH (lists = 100);
```

**「pgvector」是 PostgreSQL 的一个扩展，让数据库能存向量并做「找最相似的」查询。**

| 问 | 答 |
|---|---|
| **为什么用余弦相似度不用欧氏距离** | 余弦是语义相似度的惯例选择，**而且对向量长度不敏感** —— 两段话意思一样但长短不同时，余弦仍然判它们近 |
| **`lists = 100` 怎么定的** | 这个索引把向量空间**切成 100 个簇**，查询时只扫最近的几个簇。**这是个「查得快」和「找得全」的旋钮**，100 是常见起点。⚠️ **代码里没写调优依据，照实说是默认值** |
| **为什么用 ivfflat 不用 HNSW** | ⚠️ **代码里没有说明理由。** 我的理解：ivfflat **建索引快、占内存小**，适合这种写入频繁、行数中等的缓存；HNSW 查询更快但建索引慢、吃内存。**被问到就说这是权衡不是定论** |

**但有一行注释值得引**（`postgres_evidence.py:71-72`）：

> *"a fresh database just gets a single-list index, which degrades to a full scan until enough rows accumulate. **That is a correct, if slow, index — never a wrong answer.**"*
>
> （空库只会得到一个单簇的索引，在积累够行数之前它退化成全表扫描。**那是一个正确但慢的索引 —— 绝不会给出错的答案。**）

> ⭐ 「**宁可慢也不能错**」 —— 和 [② 那条「宁可没有日期也不要猜一个」](/docs?section=periplus&item=d9-evidence) 是同一个价值观。

**还有一个「失败也不炸」的设计**：算向量失败或数据库出错时，缓存**返回「没找到相似的」而不是抛异常** —— 所以 **PostgreSQL 抖一下只会导致重复抓一次页面，不会让整个 run 挂掉。**

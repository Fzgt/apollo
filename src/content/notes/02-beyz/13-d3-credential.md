## 一、Q1：为什么长期 key 不能下发到浏览器

**Day 1 讲了「怎么做」，这里补「不这么做会怎样」——面试官问的常常是后者。**

### 「浏览器里没有秘密」要讲到位

任何下发到前端的东西都是**明文**：F12 的 Network 面板、`localStorage`、内存里的变量，全都能看。混淆、加密、藏在闭包里——**没用，因为代码最终要用它，用的那一刻它就是明文。**

### 下发长期 key 的实际后果，按严重度排

| 后果 | 说明 |
|---|---|
| **无限期盗用** | 长期 key 没有 TTL。**泄露一次就是永久泄露**，直到有人发现并手动吊销 |
| **账单被打爆** | 拿到 key 的人可以拿你的额度做任意转写，**账单记在你头上** |
| **提权** | 长期 root key 通常带管理权限——**能读项目、读用量、看账单，甚至再铸新 key**。一把钥匙换来整个项目 |
| **吊销代价极高** | 唯一的补救是吊销这把 key，**而所有用户共用它**——一吊销全线服务中断，还得发版换 key |

**最后一条是最能体现理解的**：临时凭证真正买到的不只是「泄露损失小」，而是**「不需要吊销」**——它自己会过期。

### authentication vs authorization（复习重点里列了）

**这两个词面试里经常被混着问，分清很加分：**

| | 问题 | 在这条链路里对应什么 |
|---|---|---|
| **Authentication（认证）** | **你是谁？** | `getAuthUser()` —— next-auth 从 session 认出用户，认不出直接 throw |
| **Authorization（授权）** | **你能干什么？** | `subscribedPlan === Free → 拒绝` —— 认出来了，但这个身份没有这个功能的权限 |

**`route.ts:10-13` 那三行同时做了两件事，顺序不能反**：先认人（不知道你是谁就谈不上你能干什么），再查权限。

**而下发给浏览器的那把临时 key，本身是第三层**：它对 Deepgram 而言是一个 authorization 凭据——`scopes: ["usage:write"]` 精确描述了「持有者能干什么」。**三层各管一段，边界很干净。**

### plan gate 与滥用防护

**`route.ts:10-13` 的套餐门禁挡住的是「谁能拿到凭证」，但挡不住「拿到之后刷多少次」。**

已知缺口（[#1 里也提过](/docs?section=numbers&item=n01-ephemeral-keys)）：**这个路由没有任何限流**，全仓库 grep 不到 `ratelimit`。付费用户可以无限刷 `/api/deepgram` 铸 key。

**缓解它的恰恰是 60 秒 TTL**——铸出来的 key 一分钟后自动消失，堆不起来。**但这是缓解不是防护**，真正该做的是给这个路由加按用户的速率限制。

## 二、Q6：60 秒 TTL 过期时用户正在说话怎么办

**这一问是 [#1](/docs?section=numbers&item=n01-ephemeral-keys) 那句话的直接推论，但换了个问法，要能一秒反应过来。**

**答案：什么都不会发生。**

**因为 TTL 管的是「用这把 key 建立连接」这个动作，不是连接的存活时间。** 握手完成之后，socket 已经立住了，key 过不过期跟这条连接无关。

**一场 40 分钟的面试用一把 60 秒的 key 完全够**——key 在第 60 秒失效时，socket 已经开了 59 分钟还在跑。

**代码内部的自证**（[keepAlive 那篇](/docs?section=numbers&item=n01b-keepalive)讲过）：`useAudioToText.ts:163-167` 每 10 秒发一次 keepAlive 来防止连接被空闲超时断掉。**如果 key 过期会杀连接，这套 keepAlive 根本没有意义**——所有面试都会在第 60 秒整齐地挂掉。

> **必须分清的两条生命周期**：60 秒管**凭证**（能不能建立新连接），10 秒管**连接**（会不会被空闲超时踢掉）。**把 keepAlive 说成「续期 key」就露馅了。**

## 三、TTL / scope / 吊销，三个维度一起看

**复习重点把这三个词并列了，它们其实是同一个设计的三个旋钮：**

| 旋钮 | 控制什么 | 这里的取值 | 调它的代价 |
|---|---|---|---|
| **TTL** | 泄露之后还能用多久 | 60 秒 | 太短会误伤慢网络下的正常握手 |
| **Scope** | 泄露之后能干什么 | `["usage:write"]` 一个 | 太窄会导致功能不可用 |
| **吊销（revocation）** | 出事之后怎么止损 | **不需要**——自己过期 | 长期 key 才需要吊销，代价是全线中断 |

> **三者的关系**：TTL 和 scope 是**事前**把爆炸半径压小，吊销是**事后**止损。**临时凭证的价值在于把问题从「事后」挪到了「事前」——你不需要一套吊销机制，因为不会有需要吊销的东西长期存在。**
>
> **这个框架讲出来，比单独背「TTL 60 秒」高一个层次。**

## 四、这半条的完整说法（Day 3 产出之一）

> 实时识别是浏览器**直连** Deepgram 的——走服务端转发会多一跳延迟，而且服务器要为每个用户长期扛一条音频流，带宽和成本都不划算。但直连意味着凭证必须到前端，**而浏览器里没有秘密**。
>
> 所以长期 key 只留在服务端环境变量里。浏览器请求 `/api/deepgram`，服务端先用 next-auth 认人、再查套餐（Free 直接拒），**通过了才用长期 key 现铸一把临时 key**：只有 `usage:write` 一个 scope、TTL 60 秒。这个响应还配了三层 no-store——路由级、响应头、客户端 fetch——**因为凭证一旦被任何一层缓存住，就等于被多个用户共享，临时凭证的意义当场归零。**
>
> **60 秒管的是握手窗口，不是通话时长。** 握手实际只要几百毫秒，60 秒留了两个数量级的余量兜网络抖动；连接一旦建立就不再依赖这把 key，所以不需要续签——断线重连时重铸一把新的就行。
>
> 连接活着靠的是另一套机制：麦克风暂停期间每 10 秒发一次 keepAlive，防止 Deepgram 的 10 秒空闲超时把连接断掉。**这两个数字管的是两件事，别混。**
>
> 最坏情况：有人在 60 秒内抢到这把 key，能干的极限是替我消耗一点转写额度——**没有数据泄露、没有提权、没有持久化，因为它不带 `keys:write`，用它铸不出新 key。**

# React Query

## The API

```js
const { data, isPending, error } = useQuery({
  queryKey: ['posts'],           // this data's identity / cache key
  queryFn: () => fetch('/api/posts').then(res => res.json()), // how to go and get it
});
```

- `queryKey` decides which slot in the cache this data occupies. Two places using the same `queryKey` share one cache entry.
- `queryFn` is how the request is made. React Query does not care whether you use `fetch` or axios, only that it gets a promise back.
- The returned `isPending` / `error` / `data` map onto the `loading` / `error` / `data` states you would write by hand, and behave the same.

`queryKey` equality is a **deep** comparison of the contents, not a reference comparison. So passing a fresh object literal into the factory on every call is fine — as long as the contents match, it is the same cache entry. You do not have to worry about a new object invalidating the cache.

## Three layers: why split, and what each one is for

```
API function → queryOptions factory → typed hook
```

### Layer 1: the API function (pure)

```js
export const getPosts = (
  options: GetPostsOptions = {},
): Promise<PostsResponse> => {
  return api.get('/api/posts', { params: options });
};
```

No React dependency, so it can be tested and reused outside a component. One caveat: with axios, the type after the response interceptor may not be accurate, so annotate the return type explicitly.

### Layer 2: the queryOptions factory

```js
export const getPostsQueryOptions = (options: GetPostsOptions = {}) => {
  return queryOptions({
    queryKey: ['posts', options],
    queryFn: () => getPosts(options),
  });
};
```

Why this layer exists: **the `queryKey` is defined in exactly one place.** Hand-writing it in several places invites inconsistency — `['posts']` here, a slip of `['post']` there, and the cache that should have been shared is not. The official `queryOptions()` helper changes nothing at runtime; it just lets TypeScript tie the `queryKey` to the type `queryFn` returns, so the same config infers correctly wherever it is reused: `useQuery`, `prefetchQuery`, `ensureQueryData`.

### Layer 3: the typed hook

```js
export const usePosts = ({
  options = {},
  queryConfig,
}: UsePostsOptions = {}) => {
  return useQuery({
    ...getPostsQueryOptions(options),
    ...queryConfig,
  });
};
```

A component calls `usePosts()` and never has to know how the `queryKey` or `queryFn` is written.

`queryConfig` is the dial the caller gets to turn — `enabled` (should it fetch automatically), `staleTime` (how long the cache counts as fresh), and so on. What it **cannot** pass is `queryKey` or `queryFn`; swapping out the underlying logic is blocked by the type system.

## How QueryConfig blocks queryKey and queryFn (the real bulletproof-react code)

```js
export type QueryConfig<T extends (...args: never[]) => unknown> = Omit<
  ReturnType<T>,
  'queryKey' | 'queryFn'
>;
```

Piece by piece:

- `ReturnType<T>` — a built-in utility type that extracts the type of the object the factory returns
- `Omit<Type, 'field'>` — a built-in utility type that removes the named fields
- Together: work out the full shape the queryOptions factory returns, drop `queryKey` and `queryFn` from it, and what remains is `QueryConfig`

The result: a component that tries to pass `{ queryConfig: { queryKey: [...] } }` gets a **compile-time** error. No runtime code is needed to filter out the dangerous field.

Why `never[]` rather than `any[]`: in a contravariant position — function parameters — `never[]` still matches functions with any parameter list, but unlike `any` it does not switch type checking off elsewhere. It is the stricter choice and does not leak.

## useMutation and invalidateQueries: refreshing the cache after a write

```js
function useCreatePost() {
  const queryClient = useQueryClient();

  return useMutation({
    mutationFn: (newPost) => api.post('/posts', newPost),
    onSuccess: () => {
      // mark the cache for this queryKey stale — this does not force a refetch
      queryClient.invalidateQueries({ queryKey: ['posts'] });
    },
  });
}
```

**The thing to understand**: `invalidateQueries` does not fire a new request. It marks the matching `queryKey` as stale. A refetch only happens if a component on the page is actively subscribed to that data; if nothing is using it, the mark just sits there until someone does.

If the `queryKey` you pass does not match the one in the cache, nothing errors — the entry simply is not invalidated. That bug is quiet and does not surface immediately, which is exactly why every `queryKey` should come from the factory.

## Prefetching: prefetchQuery vs ensureQueryData

| | prefetchQuery | ensureQueryData |
|---|---|---|
| Waits for the result? | No — fire and forget, non-blocking | Yes — returns a promise you can await |
| Typical use | Speculative loading on hover | Before a route change, when the data must be ready |
| Cost | A wasted request if you guessed wrong — cheap | The navigation itself is slightly slower |

```js
// prefetch on hover
function handleMouseEnter() {
  queryClient.prefetchQuery(getPostDetailQueryOptions(postId));
}

// make sure the data is there before navigating
async function navigateToDetail(postId) {
  await queryClient.ensureQueryData(getPostDetailQueryOptions(postId));
  setCurrentPage({ name: 'detail', postId });
}
```

# Why LCP cannot measure "SPA route change plus prefetch"

A client-side route change (`router.push`) is not a real document navigation, and `largest-contentful-paint` only ever tracks the page's original load.

**So you measure it yourself: the time from the start of the navigation to the banner and list both being rendered.** Mark each critical block on the detail page (banner, data list) with its own "am I rendered" flag, and only compute the total once all of them are done.

## How native LCP is measured

```js
const observer = new PerformanceObserver((entryList) => {
  const entries = entryList.getEntries();
  const lastEntry = entries[entries.length - 1]; // the last entry = the largest element so far
  console.log(lastEntry.startTime); // render time
});

observer.observe({ type: 'largest-contentful-paint', buffered: true });
```

- The browser keeps tracking the largest visible content element on the page — an image, a block of text — and updates the record whenever a larger one appears
- The moment the user first interacts (a click, a key press), LCP stops and freezes at the current value
- The `web-vitals` library wraps this native API and handles the edge cases: interruption by interaction, the page going to the background, and so on

## Knowing when the banner has rendered (using `img.onload`)

```js
const img = imgRef.current;

function handleLoad() {
  // onload only means the data is downloaded and decoded, not that it is painted
  // a double requestAnimationFrame approximates "the browser has finished this frame"
  requestAnimationFrame(() => {
    requestAnimationFrame(() => {
      onBannerReady();
    });
  });
}

if (img.complete) {
  // the image may already be in the browser cache and load instantly, in which case
  // onload never fires again — handle that case separately
  handleLoad();
} else {
  img.addEventListener('load', handleLoad);
}
```

## Computing the total once both banner and list are ready (state in Jotai)

```js
// keep the start time and each block's readiness in Jotai
const navigationStartAtom = atom(0);
const bannerReadyAtom = atom(false);
const listReadyAtom = atom(false);

// on click: record the start, reset the flags
function handleClick() {
  setNavigationStart(performance.now());
  setBannerReady(false);
  setListReady(false);
  navigate(`/post/${postId}`);
}

// one place watching for both
useEffect(() => {
  if (bannerReady && listReady && navigationStart > 0) {
    const duration = performance.now() - navigationStart;
    sendToAnalytics({ name: 'detail-page-full-load', value: duration });
  }
}, [bannerReady, listReady, navigationStart]);
```

## What Lighthouse cannot do

Lighthouse simulates a full page load from nothing — empty cache, fresh browser instance. That fits "someone opens this URL directly" perfectly, but it cannot reproduce "sit on the list page, trigger a prefetch, then navigate". Lighthouse will not show you the effect of prefetching; that has to be instrumented by hand.

## btw

The Chrome team is experimenting with **soft navigations**, a mechanism for recognising route changes triggered by user interaction inside a SPA and recomputing LCP for them. When this was written it was still experimental and behind a flag; since Chrome 151 it ships for real, and `web-vitals` reports soft-navigation LCP / INP once `reportSoftNavs` is on — details and caveats in [#66](https://github.com/Fzgt/Blog/issues/66). It is **Chromium-only**, though — Safari and Firefox have nothing — so a cross-browser number still needs manual instrumentation.

# 1. Unit testing with Jest

- **The testing pyramid**: unit (70%) > integration (20%) > E2E (10%). Unit tests run fastest and are easiest to maintain.
- **The core API**: `describe` / `it` for structure, `expect().toBe()` for assertions, `beforeEach` / `afterEach` for hooks, `jest.mock()` for module mocks, `jest.fn()` for mock functions, `jest.spyOn()` to watch a function while keeping the original (override it with `.mockReturnValue`).
- **Where test files go**: either a separate `__tests__` folder or next to the source (`Button.jsx` + `Button.test.jsx`). Both work; pick one as a team. `testMatch` / `testRegex` in the Jest config decides what gets picked up.

**What to understand about coverage**:

- Four metrics: line, branch, function, statement
- **Coverage is not a quality metric, it is a gap warning.** 100% coverage can be nothing but `expect(true).toBe(true)`; a high number does not mean the tests verify that the logic is right.
- **60% coverage on the modules that matter (payments, subscriptions) is worth more than 90% on utils.** Spend testing effort where a mistake costs the most.

**What unit tests cannot do**: they can check that the rendered structure is right and that interactions do the right thing (React Testing Library with jsdom). They cannot check what the UI actually *looks* like, pixel by pixel — that needs visual regression testing (Chromatic, Percy) or E2E.

# 2. E2E testing (Playwright)

The critical payment flow: sign up → pick a plan → redirect to Stripe → pay with a test card (4242…) → land back on the success page → assert the UI copy.

- Stripe provides dedicated test card numbers (`4242 4242 4242 4242` and friends). In a test environment they move no real money; Stripe just simulates the outcome.
- Stripe's card inputs live in an `iframe` (a PCI compliance requirement), so Playwright needs `frameLocator` rather than a plain `locator` to reach elements inside it.
- E2E is about whether the final UI the user actually sees is correct, not about checking the database directly. That is the part unit tests cannot cover: verification along the user's whole path.

# 3. Where PostHog ends and Sentry begins

- **PostHog**: product analytics. What the user did. In our project it was not used for errors (PostHog has had its own Error Tracking since 2025; we never wired it up).
- **Sentry**: error monitoring. Where the code broke.
- PostHog's public key (front end, write-only for events) and secret key (backend, can read data) are two deliberately different permission levels. "One-way data flow" means the front end can report events but cannot read back what has been collected.
- Error counts and error-rate spikes after a release are diagnosed with **Sentry**, not PostHog. In the project the two had entirely separate jobs.

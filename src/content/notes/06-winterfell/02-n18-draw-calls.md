# 绘制命令为什么是瓶颈，以及怎么量

> ⚪ **速查**。这条能**当场演示给面试官看**，测量方法很具体。

## 一、什么是 draw call，为什么它是瓶颈

**draw call（绘制调用）= CPU 对 GPU 说一次「画这个东西」。**

**关键在于：它的成本主要在 CPU 那一侧，不在 GPU。** 每发一次绘制命令，图形驱动要做状态校验、可能要切换着色器/贴图/顶点缓冲、把命令打包送进队列。

**典型的瓶颈长这样：**

```
场景里 500 个方块，每个一次绘制命令
  → 每帧 500 次 CPU → GPU 的命令提交
    → CPU 忙不过来，GPU 反而在等
      → 帧率被 CPU 卡住，而 GPU 占用率很低
```

> **这种情况有个名字叫「受绘制命令限制」（draw-call bound）。特征是：你把模型面数砍一半，帧率纹丝不动** —— 因为瓶颈根本不在 GPU 算不算得过来。

## 二、实例化渲染：一次命令画一万个

**如果 500 个方块用的是同一个几何体和同一个材质，只是位置/旋转/缩放不同，那完全没必要发 500 次命令。** 可以：

1. 把几何体传一次给 GPU
2. 把 500 个**变换矩阵**打包成一个数组传过去
3. **发一次**绘制命令，告诉 GPU「用这个几何体画 500 遍，第 i 遍用数组里第 i 个矩阵」

**three.js 里这个东西叫 `InstancedMesh`（实例化网格）。**

**简历那句「把每个障碍区合并成两个实例化网格，共用一套矩阵」的意思是：**

- 每个区段原本几十个独立物体 → 合并成 **2 个**
- **为什么是 2 个不是 1 个**：实例化要求**同几何体、同材质**。两个大概对应两类外观 —— **面试时要能说出这两个分别是什么**
- **共用一套矩阵**：两个网格用同一份变换数据，同一批障碍物的位置**只算一次、只上传一次**

## 三、⚠️ 测量的坑：两个后端的计数含义不一样

**这是这条最有含金量的地方。**

`PerfProbe.tsx:11-21` 的注释：

> - **WebGL 渲染器的 `info.render.calls` 是「这一帧的绘制命令数」**
> - **WebGPU 渲染器的同名字段却是「从启动到现在，渲染函数被调用了多少次」** —— 一个单调递增的累计值；它的每帧绘制命令数在**另一个字段** `drawCalls` 里
> - **而且 WebGPU 是异步渲染的**，它自动的每帧清零**不一定在你读取之前完成**

**三个坑叠在一起。解法（`:37-44` 和 `:74`）：**

```js
info.autoReset = false;                              // ① 关掉自动清零
// ...读取...
drawCalls: render.drawCalls ?? render.calls ?? 0,    // ② 优先读 WebGPU 那个字段
// ...
info.reset?.();                                      // ③ 采样完自己手动清零
```

> ⭐ **关掉自动清零、采样后自己清零** —— 这样每次读到的都恰好是一帧的量，**两个后端才可比**。
>
> **不知道这个坑的话，你在 WebGPU 下量出来的「绘制命令数」会是一个从 0 一路涨到几万的数字，而且你可能还会信它。**
>
> **能讲出「我发现两个后端的同名字段含义不同」，是「真的量过」和「抄了段代码」的分水岭。**

## 四、实验是怎么设计的

`bench/run.mjs:32-40` 定义了**四个场景**：

```js
{ name: 'WebGPU + instancing',    flags: 'perf=1&immortal=1' },
{ name: 'WebGPU, no instancing',  flags: 'perf=1&immortal=1&instancing=off' },
{ name: 'WebGL + instancing',     flags: 'perf=1&immortal=1&renderer=webgl' },
{ name: 'WebGL, no instancing',   flags: 'perf=1&immortal=1&renderer=webgl&instancing=off' },
```

**这是个 2×2 的受控实验**：渲染后端 × 实例化开关。

**三个开关各有用途，都值得讲：**

| 开关 | 作用 |
|---|---|
| `perf=1` | 挂载性能探针。**只在带这个参数时挂载，正常访问零开销** |
| ⭐ `immortal=1` | **飞行器不死** —— 否则采样窗口会因为撞毁而中断，**每次采样的时长和场景都不一样** |
| `instancing=off` | 关掉实例化，走对照组 |

> ⭐ **`immortal=1` 这个设计很关键**：它把「采样窗口」这个变量固定住了。**没有它，两组数据采集的赛道段落都不一样，比出来的差异就混进了场景差异。**

**采样方式**：用 playwright 启动一个无界面的浏览器，每个场景采样固定秒数，探针**每帧**记一条，最后取统计量。

**129 → 76 报的是每帧绘制命令数在采样窗口内的平均值。**

## 五、`fps.p50 > 115` 那个条件是干什么的

```js
// bench/run.mjs:123-131
const capped = ok.filter(r => r.report.fps.p50 > 115);
if (capped.length) {
  console.log(`> Note: ${capped.length}/${ok.length} scenarios sit at the compositor's
    frame cap (~120 fps), so FPS does not separate them — the GPU still has headroom
    at this resolution. Compare draw calls and triangles instead...`);
}
```

**这不是在过滤数据，是在给报告加一条警告。**

**逻辑**：如果一个场景的**帧率中位数超过 115**，说明它**顶在了显示合成器的 120 帧上限**上。**这时候帧率这个指标已经饱和了** —— 优化前后都是 120，看不出任何差别，**但这不代表没有差别，只代表 GPU 还有富余、瓶颈还没到。**

> ⭐ **所以这行代码是在说：「在这个分辨率下帧率已经区分不了这四个场景了，请改看绘制命令数和三角形数。」**
>
> **这正是为什么这条 bullet 报的是绘制命令数而不是帧率。** 被问「为什么不报帧率提升」，答案就在这里 —— **报一个已经饱和的指标是自欺欺人。**

**还有一条相关的警告**（`:146-153`）：无界面浏览器里 WebGL 常常退化成**软件渲染**（用 CPU 模拟 GPU）。这条警告划清了界限：

| 指标 | 在无界面环境里可不可信 |
|---|---|
| **绘制命令数 / 三角形数** | ✅ **可信** —— **它们是 CPU 侧的计数**（渲染器记录自己提交了多少），跟有没有真 GPU 无关 |
| **帧时间 / 帧率** | ❌ **不可信** |

> **这一条能主动说出来非常加分**：它说明你清楚**自己的测量环境边界在哪**，只在有效范围内下结论。

# 端到端延迟：从哪一刻算到哪一刻

> ⚪ **速查**。一句话记住：**用户感知的延迟里有个 2 秒的固定底座，那是设计不是性能。**

## 一、被问到时先反问口径

**「端到端」的起点和终点各有两种合理选法，选不同答案完全不同。**

| 口径 | 从哪到哪 | 量的是什么 |
|---|---|---|
| **A** | 面试官**说完最后一个字** → 屏幕出现**第一个字** | ✅ **用户真实的等待**（含 2 秒静默窗口） |
| **B** | **`UtteranceEnd` 事件到达** → 首个字 | ✅ **系统内部处理耗时**（工程调优用） |

> ⚠️ **A 和 B 之间天然隔着 2000 毫秒** —— 因为要等静默满 2 秒才判定「说完了」。
>
> **所以报「1.5 秒」和报「3.5 秒」说的是同一个系统。** 被问「你们延迟多少」，**先问清楚是哪个口径**，否则这个数字没有意义。

## 二、链路分段

```
面试官说完最后一个字
   │  ① 静默检测窗口 —— 固定 2000 ms      ⚠️ 设计决定，不是性能问题
   ▼
Deepgram 判定说完了，发出 UtteranceEnd 事件
   │  ② 事件从 Deepgram 传回浏览器 —— 几十 ms
   ▼
浏览器决定要提交这个问题
   │  ③ 调用我们自己的服务器，一次网络往返
   ▼
服务端开始处理
   │  ④ 认证 + 查套餐 + 组装历史 —— 几到几十 ms
   ▼
向 GPT-4o 发出请求
   │  ⑤ ⭐ 模型吐出第一个字之前的等待 —— 几百 ms 到 1 秒以上
   ▼
第一个字回到服务端
   │  ⑥ 传回浏览器 —— 几十 ms
   ▼
   │  ⑦ React 更新界面并绘制 —— 几 ms
   ▼
屏幕上出现第一个字
```

> **另外还有一段在图外**：音频本身的 250 毫秒切片延迟。它影响的是**转录出现在屏幕上的时间**，不影响上面这条触发链路 —— 因为触发是 Deepgram 那边根据静默发起的。

## 三、哪几段能优化

| 段 | 量级 | 能不能动 |
|---|---|---|
| ① 静默窗口 | **2000 ms** | ⚠️ **能动但有代价** —— 调小会把句中停顿误判成说完 |
| ② 事件下行 | 几十 ms | ❌ 网络 |
| ③ 服务端往返 | 几十~百 ms | 🔸 有限，可以考虑部署到离用户更近的边缘节点 |
| ④ 认证 + 组装 | 几~几十 ms | 🔸 有限 |
| ⑤ **模型首字时间** | **几百 ms ~ 1s+** | ✅ **最大的一段**：换更快的模型、缩短系统提示词、少带历史 |
| ⑥ 流回传 | 几十 ms | ❌ |
| ⑦ 界面更新 | 几 ms | ❌ 已经优化过 |

> ⭐ **两个大头是 ① 和 ⑤，而它们性质完全不同：**
> - **① 是产品决策** —— 2 秒换来的是「不误判」，缩短它等于拿准确性换延迟
> - **⑤ 是模型/成本决策** —— 换模型、砍提示词、减历史都能压，换的是答案质量
>
> **都不在「代码写得慢」上。** 能讲出这一点，这一问就答满了。

**顺带**：只带 4 条历史（`copilot.ts:86`）这个设计**同时在优化成本和首字时间** —— 提示词越短，模型第一个字出来越快。

## 四、⚠️ 代码里没有任何延迟测量

**先解释什么叫「埋点」**：就是**在代码里打时间戳，把「这一步花了多久」记录下来并上报**。

**全仓库一行都没有。** 生成结束的回调里只记了 token 用量，**没记耗时**。

**所以现在能说的是「链路是流式的、每一段都不攒批」，说不出 P50 / P95。**

### 被问到时的正确答法

> 「这条链路我能把每一段拆开讲，**但当时没有埋端到端延迟的点，所以我给不了 P95**，只能说体感是对方说完一两秒内开始出字。要真正回答这个问题，我会在四个位置打点。」

**然后给方案 —— 这比含糊报一个编的数字强得多：**

```js
const t0 = performance.now()   // UtteranceEnd 事件到达
const t1 = performance.now()   // 服务端返回（首个字之前）
const t2 = performance.now()   // ⭐ 第一个字到屏幕  ← 最关键的指标
const t3 = performance.now()   // 整个答案吐完
```

**上报三个区间：**

| 区间 | 含义 |
|---|---|
| `t2 - t0` | **用户等了多久才看到第一个字** |
| `t1 - t0` | 网络 + 认证的开销 |
| `t2 - t1` | **模型的首字时间** |

**再加上服务端记录一次模型调用的总耗时**，就能把「有时候有点慢」归因到具体某一段，而不是笼统地猜。

> **和[数字口径总表](/docs?section=cheatsheet&item=numbers)里那二十条是同一个道理：报数字之前先有口径，有口径之前先有埋点。没埋点就老实说没埋点。**

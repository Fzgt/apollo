## Vue 2: offline vs online compilation

- Online — runtime + compiler, i.e. `vue/dist/vue.esm.js`
- Offline — runtime only, i.e. `vue/dist/vue.runtime.esm.js`

> If you are optimising, pull the compiler out. It keeps the production bundle smaller.

## What vue-loader does

1. Parses the `.vue` single-file component into JavaScript, splitting `<script>`, `<style>`, and `<template>` apart
2. Handles the template, calling the Vue compiler to turn it into a render function
3. Handles `<style>`, separating scoped CSS from CSS modules
4. Handles `<script>`, passing it to babel-loader or ts-loader
5. Reassembles the three parts into one JavaScript module that Webpack can bundle

## Can `Object.defineProperty` observe arrays?

It can. `Object.defineProperty` observes an object's properties, and an array is an object.

```js
function observe(data) {   // set up the observation
  Object.keys(data).forEach(function(key)){
     defineReactive(data, key, data[key]);
  }
}
```

Observing an array is the same idea: walk every element and call `defineReactive` on it, with the index as the key.
The problem is that adding an element fires the getters and setters of the earlier elements over and over, which can trigger several renders and hurt the page.

## Why Vue 2 rewrote the array methods

1. A new index cannot be observed.
2. Methods like `unshift`, `sort`, and `reverse` move elements around, which fires the setter many times, which calls `__ob__.dep.notify()` many times, which updates the view many times.

(What the rewrite does: patch the prototype chain, intercept the original operation, and call `notify` exactly once.)

## Vue 2 reactivity

<img width="500" height="300" alt="Image" src="https://github.com/user-attachments/assets/c7825498-beb7-4c15-80d5-2bc1ddc460b3" />

Reading that diagram properly: every property on a component's `data` goes through `observe`.

<img width="400" height="100" alt="Image" src="https://github.com/user-attachments/assets/b83fb617-f8b0-43f6-9cdd-4ea6a03ad98a" />

Each property is walked and passed to `defineReactive`, which makes it reactive. Nested objects and arrays are recursed into, so the deep levels become reactive too.

Every reactive object and array then gets an `__ob__` property marking it as reactive. Inside `__ob__` sits a `Dep` instance, and the `Dep` holds a `subs` array of subscribers — every component using that value, i.e. every `Watcher`.

When a property is read, `dep.depend()` adds the current `Watcher` to the `Dep`, and the `Watcher` calls its own `addDep` to add that `Dep` to its `deps` array. The dependency goes both ways so that it can be cleaned up on teardown.

When a property is written, `__ob__.dep.notify()` tells the `Dep`, and the `Dep` calls `update` on every `Watcher` it recorded, so each one updates the value in the template.

The `Watcher` — one per component — turns the directives in the template into a render function. The watcher's callback *is* the compiled render function, and what the render function returns is the virtual DOM used for diffing.

All watchers go into a queue and are flushed in a batch, keeping only the latest of any duplicate; each one is identified by `Watcher.id`. The queue is simulated with `Promise.then` or `setTimeout(0)`, whichever the environment supports.

## How keep-alive works

Caching page state really means keeping the page's virtual DOM around.

> If the cached components' VNodes are large and numerous, that is a lot of memory and it slows JavaScript down. So keep-alive uses an LRU cache. Vue 3's keep-alive works the same way.

## When to use nextTick

When you want to touch the DOM or read from it right after updating data. Vue updates asynchronously, so the DOM is not there yet — put the code in `nextTick` and it runs on the next tick.

```js
// the problem
this.message = 'new content';
console.log(this.$refs.div.textContent); // still the old content!
```

```js
// the fix
this.message = 'new content';
this.$nextTick(() => {
  console.log(this.$refs.div.textContent); // new content
});
```

It uses `with` to extend the scope, where `this` is the current component's Vue instance, so the render function can reach properties on `data` directly. `_c` creates a virtual DOM node, `_m` creates a static node, and the rest are helpers of the same kind — running this render function is what produces the VNodes.

## What Vue 2 optimised

- Marking static nodes at compile time, which makes the diff cheaper (compile-time analysis feeding a runtime optimisation)
- Batching the watcher queue
- Two-way binding: `Dep` maintains the mapping between components and data, so updates are targeted at a specific component

## Why Vue 2 struggles on large applications

- Too much reactive data and too many watchers to maintain. Targeted updates need a watcher each, and that costs both memory and time. `computed` and `watch` are both built on watchers — one cached, one not.
- `with` never releases memory. The more of it there is, the more memory is held.
- The compiler analyses templates with regular expressions, which backtrack, which costs performance.
- Every method is attached to the Vue instance, so using one method still bundles all of the JavaScript.

## What Vue 3 improved

- **Compile-time analysis.** Vue 3 parses templates with an AST plus a state machine, and the output has no `with` in it.

  > It can parse dynamic JavaScript expressions, because it brings in the pieces a real JavaScript compiler needs. The generated render function accesses variables explicitly instead of relying on `with` to look them up — it emits something like `_ctx.name + 'preme'`, where `_ctx` explicitly stands for the component instance.

  > Vue 2's compiler output contains `with` because it cannot analyse dynamic expressions — a ternary, or `{{ name + preme }}`. Doing that would require a full JavaScript parser. Pulling the Vue instance in with `with(this)` means it never has to.

- The Vue 3 reactivity system stores every reactive object's dependencies in a `WeakMap` called `targetMap` — weak keys, so the garbage collector can do its job.
- **PatchFlags.** Dynamic nodes are hoisted into the parent's `dynamicChildren`.

  > At patch time the runtime no longer has to walk every child looking for the dynamic ones; it goes straight to `dynamicChildren`. The point is to cut runtime diff cost, especially on deeply nested DOM.

- **Static hoisting.** Static nodes become constants, so they are not recreated on every render.

  > Vue can do a lot at compile time because it is a template language. And Vue 3, compiled offline, can do more of it than Vue 2 could.

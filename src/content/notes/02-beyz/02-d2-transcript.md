# 转录怎么拼、什么时候问

> 🔴 **必看**。这一篇回答两件事：**识别出来的字怎么显示在屏幕上不出错**，以及**什么时候把问题发给 GPT-4o**。

## 一、先搞清 Deepgram 会推给你什么

开了 `interim_results: true` 之后，**Deepgram 不是等你说完才给结果，而是一边听一边不停地推**。推来的消息分两种：

| 类型 | 消息里的标志 | 含义 |
|---|---|---|
| **interim**（临时） | `is_final: false` | 「我现在**猜**你说的是这个」——**后面还会推新的把它覆盖掉** |
| **final**（定稿） | `is_final: true` | 「**这一小段录音我处理完了**，这几个字不会再改」 |

### ⚠️ final 不等于「这个人说完了」

**这是最容易误解的地方。** final 的意思是「**这一段音频**我处理完了」，而 Deepgram 是**按说话中的停顿**来切段的 —— 人说长句子中间会换气、会想词，**每个明显的停顿都可能切出一个 final**。

所以**一句话经常产生好几个 final**：

```
面试官说：「那你说说，你遇到过难搞的同事吗」

t=1.5s   final「那你说说」          ← 他换了口气
t=3.0s   final「你遇到过难搞的」     ← 又停了一下
t=4.0s   final「同事吗」            ← 真的说完了
```

**一个问题，三个 final。** 这个事实决定了后面所有设计。

## 二、屏幕上的字怎么拼（这一节讲透）

### 天真做法为什么会炸

最直觉的写法是「来一条就接在后面」：

```js
transcript += 新推来的内容      // ❌
```

结果是：`what what's your what's your big ...`

**为什么？因为 interim 每次推来的不是「新增的几个字」，而是「这一段从开头到现在」的完整猜测。**

```
第 1 条 interim：「你遇到过」
第 2 条 interim：「你遇到过难搞的」     ← 不是「难搞的」，是整段重推
```

**第 2 条要把第 1 条盖掉，不是接在后面。** 用 `+=` 就会拼成「你遇到过 你遇到过难搞的」。

### 实际做法：把状态分成两半

**为什么能分成两半？因为 Deepgram 推来的东西天然就是两种性质：**

| | 性质 | 所以 |
|---|---|---|
| 已经收到的所有 **final** | **定稿了，永远不会再变** | 可以放心地累积起来 |
| 当前这一段的 **interim** | **是个会被覆盖的猜测** | 只能整段替换，不能累积 |

**这两种东西的更新规则完全相反，所以必须分开存。** 这就是「劈成两半」的原因。

```js
// useAudioToText.ts:116-127
const onTranscript = (data) => {
  const transcript = data.channel.alternatives[0]?.transcript;   // 这次推来的内容
  if (!transcript) return;                                        // 空的就不管

  const joined = clsx(confirmedTranscriptRef.current, transcript);
  //             ↑ 把「已确认的部分」和「这次推来的这一段」拼成一个字符串
  setTranscript(joined);                    // 屏幕上显示这个拼好的结果

  if (data.is_final) {
    confirmedTranscriptRef.current = joined; // ⭐ 只有定稿时，才把它变成新的「已确认」
  }
};
```

### 逐个变量说清楚

| 名字 | 是什么 | 存什么 | 什么时候变 |
|---|---|---|---|
| `confirmedTranscriptRef.current` | 「**已确认**」 | **到目前为止所有 final 拼起来的那串字** | **只在收到 final 时**，往后加一段 |
| `transcript` | 屏幕上显示的内容 | 已确认 + 这次推来的这一段 | **每条消息都重算** |

> **`clsx` 是什么**：它本来是个拼 CSS class 名的小工具，`clsx("a", "b")` 得到 `"a b"`。它有两个行为正好在这里用得上：**跳过空值**（已确认是空串时不会拼出一个前导空格）、**用空格连接**（两段话之间自动有空格）。
>
> ⚠️ **用一个 className 工具做字符串拼接算是取巧**，被问到可以坦率说：**`[a, b].filter(Boolean).join(" ")` 更直白**，当时是顺手用了项目里已有的依赖。

### 完整走一遍

面试官说：**「那你说说，你遇到过难搞的同事吗」**

| # | 推来 | 类型 | **已确认**变成 | **屏幕** = 已确认 + 这次推来的 |
|---|---|---|---|---|
| 1 | `那` | interim | `（空）` | `那` |
| 2 | `那你说` | interim | `（空）` | `那你说` |
| 3 | `那你说说` | **final** | **`那你说说`** | `那你说说` |
| 4 | `你遇到过` | interim | `那你说说` | `那你说说 你遇到过` |
| 5 | `你遇到过难搞的` | interim | `那你说说` ← **没动** | `那你说说 你遇到过难搞的` |
| 6 | `你遇到过难搞的` | **final** | **`那你说说 你遇到过难搞的`** | 同左 |
| 7 | `同事吗` | interim | `那你说说 你遇到过难搞的` | `那你说说 你遇到过难搞的 同事吗` |
| 8 | `同事吗` | **final** | **`那你说说 你遇到过难搞的 同事吗`** | 同左 |

> ⭐ **看第 4、5 步**：推来 `你遇到过`，再推来 `你遇到过难搞的`。**后者替换了前者**（因为屏幕每次都用「已确认 + 这次推来的」重算），**而「已确认」那部分从头到尾没动过。**
>
> **一句话：临时结果永远是「贴在已确认后面」，不是「累积进已确认」。替换 + 追加，重复就不可能发生。**

## 三、为什么「已确认」要用 ref 不用 state

**先说 ref 和 state 的区别：**

| | 改了之后 | 读的时候 |
|---|---|---|
| **state**（`useState`） | 触发组件重新渲染 | **读到的是「上一次渲染时」的值** |
| **ref**（`useRef`） | **不触发重新渲染** | **读到的永远是最新值** |

**这里必须用 ref，因为 `onTranscript` 是 WebSocket 的回调，一秒可能触发好几次。**

假设用 state：

```
第 1 条消息到达 → setConfirmed("那你说说")     → React 排队，还没重新渲染
第 2 条消息到达 → 读 confirmed → 读到的还是 ""   ← ❌ 丢字
```

**消息来得比 React 重新渲染快，用 state 就会读到旧值。** ref 的 `.current` 是立即可见的，没有这个问题。

> 另外「已确认」本身不需要显示在屏幕上（屏幕显示的是 `transcript`），**它变化时没必要触发重渲染** —— 这也是选 ref 的理由之一。

## 四、什么时候把问题发给 GPT-4o

### 系统里有个「暂存区」

**先建立这个模型**，后面才好讲：

- 识别出来的字都往**暂存区**里放（就是上面那个 `transcript`）
- 每次检测到「说完了」，系统做一个决定：**要不要把暂存区的内容发出去？**
  - **发** → 发给 GPT-4o，**然后清空暂存区**，准备接下一个问题
  - **不发** → 什么都不做，**暂存区原样保留，继续往里加字**

> ⭐ **「发出去」和「清空」是绑在一起的一个动作。不发，就也不清空。**

### 「说完了」怎么判断——不能用 final

**如果每收到一个 final 就发一次**，按上面那个例子会变成：

```
final「那你说说」        → 发出去   ← 半截话，答案毫无意义
final「你遇到过难搞的」   → 发出去   ← 还是半截
final「同事吗」          → 发出去   ← 只有三个字
```

**三次调用、三倍成本**，前两次的答案在屏幕上闪一下就被覆盖，还各自往数据库写了一条记录污染历史。

### 正确的信号：`utterance_end_ms: 2000`

这是**另一个独立的信号**：Deepgram 盯着静默，**连续 2 秒没人说话**才发一个 `UtteranceEnd` 事件，意思是「这个人这一轮说完了，不是中间喘气」。

```js
// useAudioToText.ts:129-131
const onUtteranceEnd = () => { void onSpeechEnd?.() };   // → 一路接到 submitQuestion
```

| | 判断的是 | 依据 |
|---|---|---|
| **final** | 这**一段录音**处理完了 | 声学上的停顿（可能只有零点几秒） |
| **UtteranceEnd** | 这**个人**说完了 | 连续 2 秒静默 |

> ⭐ **一句话答法**：`is_final` 说的是「这一段音频定稿了」，不是「这个人说完了」——长句子中间有停顿就会切出好几个 final，每个都触发就是三倍成本加一堆半截问题的答案在屏幕上闪。`utterance_end_ms` 干的事是**把「转写的分段」和「对话的轮次」分开**——**前者是声学问题，后者是对话问题。**

### 2000 毫秒这个值的取舍

| 太短（500ms） | 太长（4000ms） |
|---|---|
| 说话中间喘口气就被当成说完，**半截问题被提交** | 面试官说完要等四秒才开始生成，**延迟直接吃掉四秒** |

**2 秒大致对应自然对话里一个明显的停顿** —— 比句中换气长，比尴尬沉默短。

**面试场景还有个特殊性**：面试官问完问题**通常会真的停下来等你回答**，所以 2 秒的静默是个可靠信号。**换个场景（比如会议纪要，多人交叉说话）这个值就得重调。**

## 五、生成期间面试官又说话了怎么办

**这是这套设计最常被追问的一处。**

```js
// CopilotSection.tsx:228-238
const submitQuestion = async () => {
  if (statusRef.current === Generating) return;   // ← ⚠️ 守卫在前
  ...
  resetTranscript();                               // ← 清空暂存区在后
  setStatus(Generating);
```

**注意这两行的顺序**：如果上一个答案还在生成，函数在 `resetTranscript()` **之前**就返回了 —— **所以暂存区没被清空，字还在**。

**三句话的完整时间线：**

```
暂存区：（空）

第一句「你最大的弱点是什么」
  → 暂存区：「你最大的弱点是什么」
  → 停 2 秒 → 决定：发
  → 发给 GPT-4o，暂存区清空，开始出答案

第二句「可以举个例子吗」        ← 答案还在生成中
  → 识别没停，暂存区：「可以举个例子吗」
  → 停 2 秒 → 决定：不发（还在生成）
  → 暂存区保持：「可以举个例子吗」    ← 字还在

第三句「比如上一份工作里的」
  → 暂存区：「可以举个例子吗 比如上一份工作里的」   ← 接着攒
  → 停 2 秒，这时答案生成完了 → 决定：发
  → 把这两句一起发出去
```

> ⭐ **所以第二句没丢** —— 它只是等到第三句一起被发出去了。**不发的那次，丢掉的是「再问一次」这个动作，不是那句话的内容。**

**这样好不好，分场景：**

| 场景 | 结果 |
|---|---|
| 面试官在**补充说明**（「可以举个例子吗」） | ✅ **合并是对的**，本来就该连起来理解 |
| 面试官连着问**两个不相干的问题** | ⚠️ **合并就不对了**，模型会被两个问题搞混 |
| 第一个答案**特别长** | ⚠️ 会一直攒，最后提交一大段 |

> **要做得更好的方向**：把「转写的分段」和「对话的轮次」再分开一层 —— 生成期间的新一轮**单独入队**而不是拼进当前暂存区，生成完之后由用户决定是追加还是新开一轮。

## 六、生成阶段的两个设计

**只带最近 4 条历史**（`copilot.ts:86,99`）：省 token 也省首字时间（prompt 越短，模型第一个字出来越快）。**代价是二十分钟前的上下文丢了** —— 面试官问「你刚才提到的那个项目」，模型看不到。

**`startTransition` 是干嘛的**（`CopilotSection.tsx:260`）：模型的字是一个一个回来的，每秒几十个，每个都触发一次界面更新就是**每秒几十次重新渲染**。`startTransition` 是 React 的一个 API，意思是「**这个更新不着急，可以被打断**」—— React 会把它们合并，并且在用户点击这类更急的事情发生时先处理那个。

> **不加会怎样**：答案越长，每次重渲染越贵，到后面输入框可能开始卡 —— **因为渲染答案在和用户交互抢主线程**。

## 七、其余三个小追问

| 问题 | 答法 |
|---|---|
| **`filler_words: false` 是什么** | 滤掉 uh / um / 呃 这类填充词。收益：屏幕上的字干净，**喂给模型的内容噪声也少**。代价：**做不了口头禅分析**，那些词在识别阶段就丢了 |
| **流式回答怎么保证顺序** | 服务端和客户端**两边都是 `for await` 逐个消费一个有序序列**，前一块处理完才轮到下一块，**这里根本没有并发**。真正的并发被四态机挡掉了（见 [② 四态机](/docs?section=beyz&item=d3-statemachine)） |
| **为什么发空包会断连** | Deepgram 把 0 字节的音频包当作「客户端结束了」，会直接关连接。所以发之前必须检查 `e.data.size > 0` |

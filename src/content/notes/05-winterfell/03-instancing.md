# ③ 合批渲染与它的代价

> **简历原句**
>
> **Cut draw calls from 129 to 76** by collapsing each obstacle field into **two instanced meshes**, **measured frame by frame in a headless Chromium harness**: **the cost is that off-screen obstacles can no longer be skipped one by one**.
>
> ---
>
> 把每一段障碍阵合并成两个实例化 mesh，draw call 从 129 降到 76 —— 由一个无头 Chromium 测量装置逐帧测得；代价是屏幕外的障碍不能再逐个跳过。

「提交的三角形涨了 2.6 倍」这个数不在简历上，代价那半句写成了大白话。但 2.6 倍仍要会答——它是「为什么绘制命令少了反而要交代代价」的关键一环。

## 这条要讲清什么

整份简历二十个数字，十九个是变好了，这条里有一个是变差了——而它恰恰最能加分，因为它证明你在报代价，不只是报收益。

这条 bullet 自己就把取舍写在句子里了。面试官读到这一句会认真起来，因为绝大多数简历只报收益。

## 什么是绘制命令，为什么它是瓶颈

绘制命令就是 CPU 对 GPU 说一次「画这个东西」。

关键在于它的成本主要在 CPU 那一侧，不在 GPU。每发一次命令，图形驱动要做状态校验、可能要切换着色器和贴图和顶点缓冲、把命令打包送进队列。

典型的瓶颈长这样：场景里五百个方块，每个一次命令，每帧五百次 CPU 到 GPU 的提交，CPU 忙不过来，GPU 反而在等，帧率被 CPU 卡住而 GPU 占用率很低。

这种情况有个名字叫受绘制命令限制。它的特征很好认：你把模型面数砍一半，帧率纹丝不动——因为瓶颈根本不在 GPU 算不算得过来。

## 实例化渲染：一次命令画一万个

如果五百个方块用的是同一个几何体和同一个材质，只是位置、旋转、缩放不同，那完全没必要发五百次命令。可以把几何体传一次给 GPU，把五百个变换矩阵打包成一个数组传过去，然后发一次命令告诉 GPU 用这个几何体画五百遍，第几遍用数组里第几个矩阵。

three.js 里这个东西叫实例化网格。

简历那句「把每个障碍区合并成两个实例化网格」的意思是：每个区段原本几十个独立物体，合并成两个。为什么是两个不是一个——因为实例化要求同几何体、同材质，两个大概对应两类外观，面试时要能说出这两类分别是什么。两个网格共用同一份变换数据，同一批障碍物的位置只算一次、只上传一次。

## 测量的坑：两个后端的计数含义不一样

这是这条最有含金量的地方。

WebGL 渲染器里那个计数字段是「这一帧的绘制命令数」。而 WebGPU 渲染器里同名的字段却是「从启动到现在，渲染函数被调用了多少次」——一个单调递增的累计值；它的每帧绘制命令数在另一个字段里。而且 WebGPU 是异步渲染的，它自动的每帧清零不一定在你读取之前完成。

三个坑叠在一起。解法是三步：关掉自动清零，读取时优先读 WebGPU 那个字段并回退到 WebGL 的字段，采样完自己手动清零。这样每次读到的都恰好是一帧的量，两个后端才可比。

不知道这个坑的话，你在 WebGPU 下量出来的绘制命令数会是一个从零一路涨到几万的数字，而且你可能还会信它。

能讲出「我发现两个后端的同名字段含义不同」，是「真的量过」和「抄了段代码」的分水岭。这句话本身就值得在面试里说出来。

## 实验是怎么设计的

一共四个场景，是个二乘二的受控实验：渲染后端乘以实例化开关。WebGPU 开实例化、WebGPU 关实例化、WebGL 开实例化、WebGL 关实例化。

三个开关各有用途，都值得讲。第一个开关挂载性能探针，只在带这个参数时挂载，正常访问零开销。第二个开关让飞行器不死——否则采样窗口会因为撞毁而中断，每次采样的时长和场景都不一样。第三个开关关掉实例化，走对照组。

不死那个开关是关键设计：它把采样窗口这个变量固定住了。没有它，两组数据采集的赛道段落都不一样，比出来的差异就混进了场景差异。

采样方式是用 playwright 启动一个无界面浏览器，每个场景采样固定秒数，探针每帧记一条，最后取统计量。一百二十九到七十六报的是每帧绘制命令数在采样窗口内的平均值。

## 为什么报绘制命令数而不是帧率

测量脚本里有一个判断：如果一个场景的帧率中位数超过一百一十五，就在报告里加一条警告，说这些场景顶在了显示合成器大约一百二十帧的上限上，帧率区分不了它们，请改看绘制命令数和三角形数。

这不是在过滤数据，是在给报告加警告。逻辑是：帧率这个指标已经饱和了，优化前后都是一百二十，看不出任何差别；但这不代表没有差别，只代表 GPU 还有富余、瓶颈还没到。

这正是为什么这条 bullet 报的是绘制命令数而不是帧率。被问「为什么不报帧率提升」，答案就在这里——报一个已经饱和的指标是自欺欺人。

还有一条相关的警告：无界面浏览器里 WebGL 常常退化成软件渲染，也就是用 CPU 模拟 GPU。所以在这个环境里，绘制命令数和三角形数是可信的，因为它们是 CPU 侧的计数，渲染器记录自己提交了多少，跟有没有真 GPU 无关；而帧时间和帧率是不可信的。

主动说出这一条非常加分：它说明你清楚自己的测量环境边界在哪，只在有效范围内下结论。

## 按「审什么」逐条

探针是自己写的组件，每帧采样一次，只在带性能参数时挂载。同一台机器、同一个无界面浏览器、同一分辨率，不死开关固定采样窗口，四个场景只差开关。报的是采样窗口内的每帧平均值。复现方式是起开发服务器再跑那个 bench 脚本，需要 playwright。归因是自己写的探针、自己搭的实验、自己跑的。

跑之前把具体命令、分辨率、采样秒数记下来——这三个参数会影响结果，尤其是分辨率，它决定 GPU 是不是真的被压满。

## 先说什么是视锥剔除

视锥是相机能看到的那个截头金字塔形的空间，近平面到远平面之间。视锥剔除就是渲染前先判断这个物体在不在视锥里，不在就直接跳过，连提交都不提交。

three.js 默认对每个物体做这件事：每帧遍历场景，拿每个物体的包围体——一个能装下它的球或盒子，用来做廉价的粗略判断——和视锥求交，不相交就跳过。

这是个非常划算的优化，一次廉价的球体求交就省掉了整个物体的顶点处理。在这个游戏里尤其划算：赛道很长，视野受雾限制大约六百个单位，任何时刻绝大多数障碍物都在视野外。

## 实例化为什么会杀掉视锥剔除

这就是那个取舍的核心。

优化前，场景里是 N 个独立物体，剔除是逐个判断的，视野外的一个都不提交。优化后，场景里只有两个实例化网格，整个区段共用一个包围体，只要有一个实例在视野里，整批全部提交。

关键一句话：剔除是按场景对象做的，而实例化把 N 个对象合成了一个。

于是一个区段里八十个方块、玩家只看得到最前面十个的时候，优化前剔掉七十个只提交十个的三角形，优化后包围体和视锥相交，八十个全部提交。GPU 会为那七十个不可见的实例跑完顶点着色器，然后在裁剪阶段把它们丢掉——工作做了，画面上什么都没多。

这就是提交的三角形涨到 2.6 倍的原因，绝对数是从两万六千多涨到六万九千多。报比值的时候要能一并报出绝对值，被问「涨到多少」答不上来会显得只背了个倍数。

注意「提交」这个词用得很准：涨的是提交给 GPU 的三角形数，不是画面上多了三角形，画面完全一样。面试时要强调这一点，否则听起来像是画质变了。

## 那为什么这笔交易还是划算

这是必答题：绘制命令降了四成，三角形涨了一倍半，凭什么说这是优化？

答案在于两种成本的性质完全不同。绘制命令的成本花在 CPU 上——驱动状态校验、命令打包、提交，基本串行，受驱动开销限制，成为瓶颈时的表现是 CPU 满 GPU 闲。顶点处理的成本花在 GPU 上——顶点着色器，极度并行，几千个核同时算，成为瓶颈时的表现是 GPU 满 CPU 闲。

如果瓶颈在 CPU，那么少发五十三次绘制命令是直接省下 CPU 时间，多提交一点六倍三角形花的是 GPU 的富余产能。

用一个瓶颈资源换一个非瓶颈资源——这就是这笔交易划算的全部理由。而前面那条帧率饱和的提示正好佐证了 GPU 有富余：四个场景的帧率都顶在合成器上限上，测量脚本自己就说了在这个分辨率下 GPU 还有余量。

## 但这个结论有前提，必须主动说

如果换个场景——更高分辨率、更复杂的着色器、更重的后处理——GPU 变成瓶颈，这笔交易就反过来亏了。

那时候正确的做法是分块实例化：不是整个区段一个实例化网格，而是按空间切成若干块、每块一个，换回一部分剔除粒度。

能说出「什么情况下我这个优化是错的」，比说出它为什么对更有说服力。这句话适用于任何一条性能优化的 bullet。

## 实际帧率影响：诚实答案

在这次测量里看不出来，因为帧率饱和了。四个场景的帧率中位数都超过一百一十五、顶在合成器约一百二十的上限，帧率区分不了它们。

正确的说法是：这次测量没能显示帧率提升，因为那个分辨率下四个场景都顶在合成器帧率上限。要看到绘制命令下降转化成帧率，得把分辨率调高、把 GPU 压到成为瓶颈之前；测量脚本里那条提示也建议了用更大的窗口重跑。

别硬说帧率提升了。数据不支持，而且测量脚本自己把这件事写在报告里了——面试官只要打开代码就能看到那行提示。

## 这条 bullet 最大的价值

收益是绘制命令从一百二十九降到七十六，代价是提交的三角形涨了 2.6 倍，机制是每个网格只有一个包围体，代价来自失去逐实例的视锥剔除。

面试官读到这一句会认真起来，因为绝大多数简历只报收益。一个把取舍两边都量出来、还说清了机制的候选人，可信度和其他所有数字一起上升。

讲的时候可以直接点出来：这条我特意把代价也写上了，因为只报绘制命令下降是不完整的——它是用三角形数换来的。

## 英文怎么说

三句最容易说错的。「用瓶颈资源换非瓶颈资源」说 we spent GPU headroom to buy back CPU time，这是这笔交易划算的全部理由。「提交的三角形涨了」一定要用 submitted 这个词，并补一句 the image is identical，否则听起来像画质变了。「帧率区分不了这四个场景」说 FPS is saturated at the compositor cap, so it can't separate them。

其他常用词：绘制命令是 draw call，受绘制命令限制是 draw-call bound，对应的还有 GPU-bound 和 CPU-bound，实例化是 instancing，变换矩阵是 transform matrix，合批是 batching，视锥是 frustum，视锥剔除是 frustum culling，包围体是 bounding volume，剔除粒度是 culling granularity，顶点着色器是 vertex shader，裁剪阶段是 clipping，富余产能是 headroom，帧率上限是 frame cap，饱和是 saturated，软件光栅化是 software rasterisation，无头测量装置是 headless harness，受控实验是 controlled experiment，采样窗口是 sampling window，分块实例化是 chunked instancing。

## 自检

1. 能否说清绘制命令的成本主要在 CPU，并说出受绘制命令限制的特征？
2. 能否解释实例化为什么要求同几何体同材质，以及为什么是两个网格？
3. 能否讲出两个后端计数字段含义不同这个坑，以及三步解法？
4. 能否说明不死开关固定了哪个变量？
5. 能否解释为什么报绘制命令数而不是帧率？
6. 能否讲清实例化为什么杀掉逐实例剔除，并同时报出比值和绝对值？
7. 能否说出这笔交易在什么情况下会反过来亏，以及分块实例化这个补救？

# 三期/四期高阶实战 —— 今日知识点整理知识点梳理与讲解今日知识点整理

> 说明：原笔记是跟课时随手记的，比较碎片化，很多地方是当时的口语速记。这份整理按主题重新分类，把每个知识点用完整的逻辑讲清楚，方便你现在直接看懂，不用再回想当时的上下文。

## 一、Serverless 架构（BFF/SFF、Cloudflare vs AWS、IPFS）

### 1. BFF 和 SFF 是什么关系

**BFF**（Backend For Frontend）：给前端专门定制的一层后端，作用是把后面几个微服务的数据聚合、裁剪成前端刚好需要的形状，减少前端自己拼接多个接口的麻烦。

**SFF**（Serverless For Frontend）：思路和BFF一样（都是"专门为前端服务的一层后端"），区别只是这一层不再是你自己搭一个Node服务器（Express/Koa那种常驻进程），而是用云厂商的Serverless函数（比如AWS Lambda、Cloudflare Workers）来承载——用的时候才启动，不用不占资源，按调用次数计费。

为什么面试会考：因为"简历上要有Node相关项目"，而SFF正好是"前端人写Node"最自然的场景——你写的是Node代码，但目的是服务自己的前端项目，不需要你去搞复杂的后端架构。

### 2. 三大云厂商 Serverless 的部署方式区别

- **AWS Lambda**：功能最完善，几乎所有类型的node_modules依赖都支持。部署时会给你的Lambda一个隔离沙箱——哪怕你装了有问题的第三方包，也不会影响到宿主机器，因为AWS专门做了隔离层。
- 单纯的Lambda只会部署在你选的某一个区域（比如美国或者澳洲），不是全球分布的。想要做到全球就近访问，需要额外配合 **Lambda@Edge**（部署到全球边缘节点）+ **Lambda Shield**（DDoS防护）一起组成完整方案。
- **Cloudflare Workers**：写法上很像前端的Service Worker（都是拦截请求、返回响应的编程模型）。天然全球部署、自带DDoS防护，不需要像AWS那样再单独拼凑Edge和Shield。
- Cloudflare的缺点：①部分依赖它不支持（尤其是一些封装了系统底层API的包，比如涉及OpenGL这种），因为Workers运行环境比Node精简；②冷启动这块虽然做得不错，但和AWS各有取舍。
- Cloudflare部署代码的方式比较特殊：因为它自己也有打包（build）的概念，所以是把你的JS代码和node_modules依赖一起打包成一个文件上传，而不是像AWS那样直接把整个zip包（含依赖目录）传上去，或者用Nest.js/Koa模板部署。
- **Cloudflare Workers Pages**：专门用来部署前端静态站点的服务，自带一套CI/CD（拿到Git仓库授权后自动构建部署，不需要你自己配流水线）。所以一个常见组合是：前端用 Workers Pages 部署，接口用 Cloudflare Workers 部署，两者是同一家的生态，配合起来很顺。

### 3. IPFS 和去中心化部署

IPFS（InterPlanetary File System）本质是一个"去中心化的世界硬盘"——文件存储在全球分布的节点上，不依赖某一台中心服务器，理论上抗攻击性很强（打掉一个节点，其他节点还在）。

很多Web3项目会把前端部署到IPFS上。但这样做有两个现实问题：①IPFS给你的访问地址是一长串哈希值，很不友好，用户没法记；②IPFS本身的寻址协议（如何根据这个哈希找到对应内容存在哪个节点上）比较慢。

Cloudflare在这里的作用：它把全球的IPFS节点信息同步到自己的服务器，帮你做"反向解析加速"——你访问"Cloudflare域名+哈希"这种地址时，Cloudflare能更快地帮你找到并返回对应的IPFS内容，等于是在IPFS原生慢速寻址上面，加了一层CDN式的加速缓存。

### 4. Service Worker 和 PWA

PWA（Progressive Web App）：让网页做出接近原生App体验的一套技术标准（可以添加到主屏幕、离线可用、推送通知等）。这个概念现在已经不算热门了（"已经凉了"），但它留下了一个很有用的遗产——Service Worker。

**Service Worker**：运行在浏览器后台的一个独立线程，可以拦截网络请求、做离线缓存。即使PWA这个整体概念不火了，Service Worker本身依然被广泛用来做"离线缓存"这件具体的事。

**Workbox**：Google出的、目前最主流的"基于Service Worker做离线缓存"的工具库，帮你屏蔽了手写Service Worker缓存逻辑的复杂度。

Cloudflare Workers这个名字，就是想向Service Worker的开发体验看齐（写法、拦截请求处理响应的模式都类似），只是运行在服务端而不是浏览器里。

### 5. 缓存体系的整体理解（笔记里布置的思考题）

- **HTTP强缓存**：浏览器根据响应头（如 Cache-Control）判断，命中的话直接用本地副本，连请求都不发。
- **本地缓存（localStorage等）**：手动用JS存取的数据，跨页面刷新依然在，但需要自己写读写逻辑，不像HTTP缓存是浏览器自动处理的。
- **Workbox/Service Worker缓存**：介于两者之间——它能拦截网络请求本身，让你精细控制"这个请求要不要走缓存、走什么缓存策略"，甚至可以做到完全离线也能访问（网络请求失败时返回缓存的内容）。
- 三者的核心区别在于"谁来决定要不要缓存、缓存的粒度和控制精细度"：HTTP缓存是最省心但最不灵活的；localStorage是最灵活但要全手写的；Service Worker介于中间，能精细控制但需要写拦截逻辑。

## 二、Monorepo 工具链（pnpm + lerna/nx/rush + 私仓verdaccio）

### 1. 为什么需要 Monorepo

场景：公司里项目A要用项目B（比如一个组件库/工具库）。如果A和B是两个完全独立的仓库，B更新了，A要等B走完"发布新版本到npm/私仓"这一整套流程，再重新npm install，才能用到B的最新代码——这个过程慢，且沟通协调成本高。

**Monorepo**（单一仓库）的做法：把A和B放进同一个代码仓库管理，A可以直接"软链接"到本地的B，不需要真的发布到任何仓库、不需要等待，改了B，A立刻就能感知到最新代码——这就是Monorepo解决的核心痛点。

### 2. pnpm 的核心优势

- **速度快**：通过内容寻址+硬链接复用已下载过的包，不需要每个项目都重新下载一份相同版本的依赖（对比npm/yarn，同一个lodash在100个项目里可能被物理复制100份，pnpm只存一份，其他都是链接过去的）。
- **硬链接 vs 软链接的区别**（笔记里反复出现的概念）：硬链接相当于给硬盘上同一份数据开了多个"入口"，删掉一个入口不影响其他入口继续访问这份数据；软链接则是"指向另一个链接的快捷方式"，如果它指向的硬链接失效了，软链接也跟着失效。pnpm正是利用硬链接的特性，实现"物理只存一份、但多处都能用"。
- **安全性**：pnpm有严格的依赖访问控制。比如A依赖B，B依赖C，如果A的代码里直接import了C（C并没有在A的package.json里正式声明依赖），pnpm会认为这是"非法访问"——因为C是通过B间接带进来的，B的版本一旦变化，C可能也跟着变或者消失，A这样直接用不安全。pnpm会把这种"未被正式声明、只是被动带进来"的包放到一个叫`.pnpm`的"孤儿院"目录里，不让你的代码正常访问到，倒逼你必须显式声明依赖。
- **支持workspace**（多包管理）：npm完全没有这个概念，yarn有但体验一般，pnpm的workspace做得比较完善，能管理一个仓库里的多个子项目/子包。

### 3. pnpm workspace 常用操作

- `pnpm add -w <包名>`：在根目录装一个所有子项目都共用的包（比如babel、eslint这种整个仓库统一版本的工具）。
- `pnpm add <包名> --filter "<子项目名>" --workspace`：给某个特定的子项目添加一个仓库内部的另一个包作为依赖（不发布也能用，直接软链接过去）。
- `link-workspace-packages=true`：开启后，workspace内的各个子包之间能互相识别、连接。
- `shared-workspace-lockfile=false`：默认情况下整个workspace共用一份lockfile，好处是所有包版本统一；但项目规模变大后，这一份lockfile会变得巨大，导致pnpm每次分析依赖关系耗时暴涨（甚至几分钟装不上一个包）。关掉这个配置后，每个子包可以有自己独立的lockfile，能提速，但代价是各个子包之间的版本可能不完全一致，需要人工留意同步。

### 4. lerna / nx / rush 分别是干嘛的

这几个工具和pnpm不是替代关系，而是配合关系——pnpm负责"依赖怎么装、怎么共享"，lerna/nx/rush负责"怎么管理多个包的版本、怎么统一发布"。

- **lerna**：老牌的Monorepo管理工具，主要负责"批量给多个包打版本号、按依赖关系顺序发布"这件事（比如`lerna publish`会自动处理包之间的依赖顺序）。3.0版本之后不再支持"只发布某一个指定包"这种精细化操作，笔记里提到这种场景建议改用npm自带的发包方式。
- **nx**：和lerna是配合关系，最大的特点是能生成项目/包之间依赖关系的可视化图（`nx graph`），方便你直观看清楚整个Monorepo里谁依赖谁。
- **rush.js**：微软出的，工程化程度更重，笔记里提到"最后集成到工程化发包时要用rush.js"——意思是当workspace这套体系要真正落地成公司级的标准流程时，rush提供的能力更完整。

### 5. verdaccio 私仓

**私仓**：公司内部自己搭的、外部访问不到的npm包仓库，用来存放公司内部才用的工具库（不适合/不想发到公开npm上的包）。

**verdaccio**：一个基于Node.js的开源私有npm仓库代理工具，装好后能在内网起一个服务（默认地址 http://localhost:4873），配置`.npmrc`的registry指向它，团队内部就能像用npm官方仓库一样，从这个私仓下载/发布内部包。

实际部署时的坑：私仓要装在真正的服务器（比如ECS）上长期运行（用pm2这类进程管理工具保活），如果私仓所在网络访问不了外网（"出不了墙"），会导致内部安装依赖时既要连私仓、又要连外网公共源，速度会成为大问题。

随着私仓里的包越来越多（几千个包规模），pnpm在分析依赖关系时会显著变慢，可能几分钟都装不上一个包，这也是为什么前面提到"规模大了要考虑拆分lockfile"这个优化。

## 三、React 状态管理库全景对比

### 1. 先分清两类状态：组件内状态 vs 组件外状态

**组件内状态**：就是最常见的useState/useReducer，状态存在于React组件树内部，参与React的渲染调度（reconciliation）。

**组件外状态**：状态存在于React组件树之外的一个普通JS对象里（说白了就是一个游离在React管理范围外的对象），要通过特定机制（比如Provider、或者订阅函数）才能和React组件"连接"上。Redux、Zustand、Recoil都属于这一类。

为什么要用组件外状态：①React的hooks有很多使用限制（不能写在if里、不能写在普通函数里），组件外状态没有这些限制；②可以实现更简洁的全局共享，不用无限层层传props或者套一层层Context；③组件卸载后状态依然保留（对"记住用户上次填的表单内容"这种场景很有用）；④能做到"细粒度订阅"——只有真正用到某个状态片段的组件才会重新渲染，不像Context那样容易导致整棵子树跟着重渲染。

### 2. 各个状态管理库逐个讲

- **Redux**：结构清晰，能撑住大项目，但写法偏重（reducer、action、dispatch一套流程走下来比较啰嗦），且状态管理方式比较"中心化"（所有状态挤在一个大store里）。需要配合react-redux这个桥接库才能和React组件连接起来。
- **Mobx**：用Proxy做响应式监听，写法比Redux简单（不需要写reducer）。但笔记里评价比较负面——因为它的响应式更新思路和React"单向数据流"的设计理念有冲突，数据变化不够透明、难追踪，而且所有用到它的函数组件都要包一层`@observer`装饰器，写法上比较"闭包缠绕"，跟hooks时代的写法不太搭。曾经出过mobx-state-tree（想做更好用的树形状态管理），但因为用了generator函数（yield），在V8引擎里有性能问题，作者又不愿意改，最终没有成为主流。
- **Recoil**：React官方团队出的，核心思路是"原子化状态管理"——把状态拆成一个个独立的最小单元（atom），组件只订阅自己需要的那个atom，从而解决传统Context嵌套多层Provider的问题。
- **Jotai**：定位是"更简化版的Recoil"，语法更精简，从Recoil迁移过来几乎没有学习成本。它的野心比Recoil更大——即使项目里已经在用Redux/Mobx，也可以让Jotai和它们共存、二次集成，不需要推倒重来。Jotai底层实现依赖`useState`，所以完全绑定在React的hooks体系里（这也是它的局限——只能用在React组件/hook内部）。
- **Zustand**：和Jotai是同一个作者做的，体积极小（1kb级别），核心思路完全脱离hooks——它创建出来的store就是一个普通的JS对象，可以在任何地方使用，甚至在非React环境（比如一个Three.js/Babylon.js的3D场景逻辑里）也能直接读写状态，这是它和Jotai最大的区别。
- **Valtio**：语法风格跟Vue的响应式很像（用过Vue的人上手Valtio会觉得很顺手），提供了不错的"派生状态"（derive）能力，以及对redo/undo（撤销重做）操作的良好支持——特别适合输入框、富文本编辑器这类需要撤销重做功能的场景（配套还有canRedo/canUndo这种判断能不能撤销/重做的辅助方法，方便控制按钮的可用状态）。
- **xState**：基于"有限状态机"（Finite State Machine）模型，适合状态流程本身很复杂的场景（游戏逻辑、审批流程、用户认证流程、下单结账全流程、订单跟踪状态等），能把这些复杂的状态流转关系用状态机的方式清晰表达出来，而不是用一堆零散的if/else去处理各种状态跳转。它还有配套的可视化工具——装个VSCode插件，能把代码里声明的状态机直接生成流程图，也能反过来通过拖拽流程图自动生成状态机代码。

### 3. 一个简单的选型思路总结

- 简单React项目、不追求太复杂的状态流转 → **Jotai**（轻量、原子化、够用）
- 需要在非React环境（比如3D/游戏引擎场景）里管理状态 → **Zustand**（因为它不依赖hooks，能脱离React单独使用）
- 项目里有大量"输入撤销重做"的交互（富文本编辑器） → **Valtio**
- 状态流转本身极其复杂（多阶段审批、订单状态机） → **xState**
- 网络请求相关的异步状态（loading/成功/失败/缓存） → **React Query**（不是严格意义上的"状态管理库"，专门用于把"异步网络状态"和"组件内部状态"解耦，见后面章节）
- Redux适合"项目规模巨大、团队协作规范要求高"的老派场景；Mobx笔记里评价较低，新项目不建议选。

### 4. 状态撕裂（State Tearing）问题

背景：React 18引入了并发渲染（Concurrent Rendering），渲染过程可以被打断、之后再继续（比如渲染到一半，有更紧急的更新插进来，React可以先处理紧急的，稍后再回来继续渲染没做完的部分）。

问题：如果状态存在"React组件树之外"（也就是前面说的组件外状态，比如Redux/Zustand/Jotai这类），在渲染被打断、之后恢复继续渲染的这段时间里，这个外部状态可能已经被别的地方改变了——导致同一次渲染过程里，前半段用的是"旧值"，后半段用的是"新值"，页面上出现数据不一致的撕裂现象。

这是所有"组件外状态管理库"都要面对的共性问题，官方给出的解决方案是`useSyncExternalStore`这个API——它的作用就是"安全地从外部数据源读取状态，专门用来避免并发渲染下的状态撕裂"。Jotai内部据说是用了"双重渲染"的方式，把出问题的那一次渲染结果直接覆盖掉，来规避这个问题。

## 四、Webpack 性能优化与拆包（重点章节）

### 1. 为什么要拆包（SplitChunksPlugin）

如果完全不配置任何拆包策略，Webpack默认会把所有代码都塞进一个`main.js`里，项目稍微大一点，这个文件轻松涨到4MB以上——这种情况下再去谈"性能优化"是没有意义的，因为最基本的"别把所有代码堆一个文件里"这一步都没做。笔记里说得比较直白："如果你没配置过SplitChunkPlugin，说明你从来没关心过项目性能"。

### 2. Webpack Runtime 是什么，为什么要单独抽出来

Webpack打包后的代码，实际上是被塞进一个叫`__webpack_modules__`的对象里（key是模块路径，value是这个模块对应的函数），外部再通过类似`__webpack_modules__['./src/index.js']`这种方式去调用。

Webpack Runtime就是Webpack自己注入的一层"胶水代码"，负责模块的加载、解析、执行调度——包括记录"chunk id 对应哪个文件名"这份映射表。（这部分逻辑详细原理：拆分runtime主要是为了让其他chunk的hash不会因为任何chunk的增删而被连带改变，从而保护浏览器缓存命中率。）

单入口(SPA)应用一般没必要特意拆runtime，除非打包出来的总体积已经比较大（比如超过100kb+），拆出来才有实际收益；多入口(MPA)应用则一定要拆，因为多个入口之间会共享同一份runtime代码，不拆的话每个入口文件里都会重复一份。

抽离出来的runtime文件本身很小——笔记里提到没压缩前大概23kb，gzip压缩后大概7kb左右，所以拆出来的额外请求成本很低，收益（保护其他大文件的缓存）远大于这点开销。

### 3. cacheGroups —— 拆包配置的核心

cacheGroups是splitChunks配置里最核心的部分，你想让Webpack按什么规则去分包（比如"把所有node_modules里的代码单独打一个vendor包""把多个入口共用的工具函数单独打一个common包"），基本都是通过配置cacheGroups的正则匹配规则来实现的。

- **minSize / maxSize**：控制"小于多大就不拆""大于多大就强制拆开"。这两个属于比较"暴力"的拆分手段，不建议轻易调整默认值。
- **enforce**：强制执行某条cacheGroups规则，忽略其他优先级判断。使用场景举例：比如要求"只清除.tsx文件里的console.log，.ts文件里的要保留"，如果直接用统一的压缩插件配置，会不分青红皂白全部清掉——这时就需要用enforce结合loader规则做精细拦截。要注意enforce一旦用了，别的优先级配置可能会跟着失效，所以要谨慎、优先处理它。
- **chunks: 'all'**：告诉Webpack不仅要处理"同步引入"的代码，异步（动态import）引入的代码也要一并纳入拆包分析范围。
- **priority**：当一个模块同时匹配多条cacheGroups规则时，用来决定优先按哪条规则打包，避免规则冲突。同时要注意chunk输出的先后顺序——如果输出顺序反了，可能导致页面里script标签插入顺序不对，进而引发JS执行报错（比如依赖的代码还没加载，就先执行了用到它的代码）。
- **maxInitialRequests**：入口文件加载时，最多能同时并行加载几个JS文件（含入口本身），默认值是4。
- **maxAsyncRequests**：最多允许拆出几个"按需异步加载"的包，默认值是6。

### 4. 单入口 vs 多入口，拆包效果完全不同

这是笔记里反复强调、也是最容易理解错的一个点：SplitChunksPlugin这套机制，是针对"多个chunk之间有没有共享代码"来判断要不要拆的。

如果是单入口(SPA)项目，哪怕代码里两个不同地方都引用了同一个utils工具函数，只要它们最终都落在同一个主chunk里（没有被拆成独立的异步chunk），Webpack是不会主动把这个utils拆出来的——因为对Webpack来说，"大家本来就在同一个包里"，谈不上"共享"这个概念。

只有当这个utils被两个不同的"异步chunk"（比如两个不同的路由懒加载模块）分别引用时，Webpack才会识别出"这是被多处共享的代码"，从而把它提取成一个独立的公共chunk。

实操结论：如果想让某段公共代码被正确拆分出来，必须先通过lazy/动态import的方式，把用到它的地方拆成独立的异步chunk，拆包才有意义——不然minChunks配置得再对，Webpack也无法识别出"共享关系"。

### 5. 如何判断一个包的体积算不算"太大"

参考Google的性能白皮书标准（笔记里给出的经验值）：

- gzip压缩后 30kb～120kb 之间：合格范围。
- gzip压缩后小于30kb：Webpack默认不会主动帮你拆分，因为拆开反而会多发一次没必要的请求，得不偿失。
- gzip压缩后刚好略大于30kb：体验最佳的一个区间。
- gzip压缩后接近120kb：Webpack会给出警告，并倾向于把它拆成两个独立的包。
- main.js 到 8MB 级别：已经算是严重超标了。

补充：包体积只是影响页面加载速度的一个维度，JS/CSS资源的加载本身也会阻塞（pending）页面渲染，所以"体积合格"不代表"加载体验就一定好"，还要结合其他指标一起看。视频这类大文件资源建议做成流式传输（分段加载），而不是等整个文件下载完才能播放。

## 五、React 18 并发渲染相关特性

### 1. 紧急状态 vs 非紧急状态

普通的useState/setState，触发的更新属于"紧急状态"——立刻执行、立刻反映到页面上。

用`useTransition`包裹的状态更新，会被标记为"非紧急状态"——React会优先处理其他更紧急的更新（比如用户当前正在做的输入操作），把这个非紧急更新的实际渲染工作延后处理，避免阻塞用户当前的交互。

### 2. 典型应用场景1：Tab栏切换

场景：点击左侧某个Tab，每次切换都要加载一批新的数据/资源，如果不做处理，加载过程可能会让界面卡住，用户这时候想点别的Tab却点不动。

解法：把"加载新Tab内容"这个更新过程放进`startTransition`里执行。这样即使这次切换要处理很多东西，用户依然可以流畅地点击其他Tab（因为React会把这个渲染工作标记为可被打断的低优先级任务），还可以配合`useTransition`解构出的`isLoading`值，来控制过渡期间要不要展示loading效果。

### 3. 典型应用场景2：本地大数据量的实时筛选（filter）

场景：一个表格类页面，用户一边输入筛选关键字，一边实时展示筛选结果，本地数据量是几百条这种级别。低端设备上，每敲一个字就重新筛选渲染一遍，容易卡顿。

- **解法一**：把"根据输入内容去筛选/查询数据"这部分逻辑放进`startTransition`。效果是：输入框本身的显示（用户打的字）依然是高优先级、立刻响应的，但筛选计算和渲染结果这部分工作变成低优先级，如果用户输入很快，React甚至可以跳过中间几次不必要的筛选渲染，只计算并展示最终稳定下来的那次结果，减少无意义的重复计算。
- **解法二**：`useDeferredValue`。这个hook会给你一个原值的"延迟副本"——当其他所有紧急更新都处理完了，这个延迟副本才会更新为最新值。效果和startTransition类似，只是用法不同（一个是包裹"更新动作"，一个是包裹"某个值"）。

### 4. React 18 相关 Hooks 速查

- `useTransition()` / `startTransition()`：把某次状态更新标记为非紧急，可被打断、延后处理。
- `useDeferredValue()`：得到某个值的"延迟版本"，紧急更新处理完才会同步最新值。
- `useId()`：生成一个当前组件唯一的ID，常用来避免表单里多个字段的name/id冲突（配合UI库自动生成的id用）。
- `useInsertionEffect`：给css-in-js这类库在底层用的（要在浏览器插入样式规则的时机做一些操作），日常开发很少直接用到，属于"造轮子"用的hook。
- `useSyncExternalStore`：安全地从"组件外部数据源"（前面提到的组件外状态库）读取状态，专门用来避免并发渲染模式下的状态撕裂问题。

### 5. RSC（React Server Components）简单理解

给客户端发送的是一份"已经在服务端计算好的、可直接渲染的DOM描述"（序列化后的结果），客户端不需要再重新计算这部分逻辑，直接渲染即可——这是和传统"客户端拿到数据自己算怎么渲染"不同的地方，能减少客户端的计算量和最终传输的JS体积。

### 6. 其他细节

- React 18严格模式（StrictMode）下，useEffect在开发环境会执行两次——这是React官方故意设计的，目的是帮你提前暴露"副作用清理不干净"这类潜在bug（比如忘记在useEffect的return里清理定时器/订阅）。
- **why-did-you-render**：一个专门用来调试"这个组件为什么会重新渲染"的库，排查不必要的re-render问题很有用。

## 六、组件库开发体验（Storybook、Tailwind CSS）

### 1. Storybook 是什么

一个专门用来"隔离开发和展示UI组件"的工具——你可以脱离实际业务页面，单独给每个组件写一个"故事（story）"，在一个独立的playground里预览这个组件在不同props/状态下的样子，方便组件库的开发、调试和对外文档展示。

如果只是一个项目内部用的组件，不需要跨团队共享，可以直接在项目里建个stories文件夹，用Storybook做本地预览就行，不需要专门发布成一个独立的包；如果要给多个团队公用，就要单独起一个项目、发布成包。

`npx storybook init` 会自动装好相关依赖，并生成两个命令：一个是本地预览模式，另一个是把组件文档编译成静态产物，方便部署上线当文档站点用。

**MDX**：一种"Markdown里能直接嵌入React组件"的文件格式，Storybook用它来写文档，可以做到"文字说明+组件实际渲染效果"混排在一起。

Storybook配合Webpack5的"懒编译"（lazy compilation）实验特性，能显著提升本地开发时的编译速度，适合组件较多、项目较大的场景。

### 2. Tailwind CSS 原理

Tailwind是"原子化CSS"的代表——每个样式属性（比如padding、颜色）都对应一个独立的、可复用的类名（比如`p-4`、`text-red-500`），项目里不同组件复用同一批类名，最终打包出来的CSS体积会大幅减小（官方数据：能减少约70%的CSS体积）。

常见误解："Tailwind减小了CSS体积，但增大了HTML体积"——笔记里纠正说，更准确地讲，增大的其实是JS体积，而不是HTML体积。因为现代前端项目大多是SPA+虚拟DOM，页面上看到的标签本质上是JS渲染出来的，这些长长的类名字符串是被打包进JS文件里的，不是写在静态HTML里的。

进一步的优化思路：可以写一个postcss插件，把这些冗长的原子类名编译替换成更短的单字母/双字母类名（用一个hashMap做映射），这样能进一步压缩JS体积（可以减少60%左右），对SSR场景效果尤其明显。不过笔记里提到市面上目前没有现成的这类插件，需要自己写。

Tailwind适配情况：移动端场景很适合直接手写Tailwind（页面通常不复杂），PC端如果需要复杂组件库（类似antd那种），Tailwind自己也有官方组件库（付费），或者可以配合headlessUI（免费但组件较少）、Material UI/antd这类更成熟的组件库使用。

**Tailwind的JIT（Just-In-Time）模式**：旧版Tailwind只能用预定义好的几个尺寸类名（比如`w-4`、`w-64`），JIT模式下可以直接写任意值（比如`w-[1200px]`），也是使用calc()这类动态计算样式的前提。

## 七、数据请求（React Query）与 SSR/Next.js

### 1. React Query 解决什么问题

核心思路：把"异步的网络请求状态"（loading、成功、失败、缓存的数据）和"组件自身的普通状态"分开管理，不要把请求逻辑和loading/error这些状态混在一堆useState里手写。

- `useQuery`：发起单个查询请求；`useQueries`：同时控制多个并行请求。
- `useInfiniteQuery`：专门用于"无限滚动/分页加载"场景（这个正好呼应你之前学的虚拟列表+无限滚动的知识点）。
- 对SSR的"注水/脱水"（hydration/dehydration）支持很好——意思是服务端先把数据请求好、渲染成HTML发给客户端，客户端接管后可以"继承"服务端已经请求过的数据，不需要重新请求一遍。

适用场景：偏"展示型、查询多、提交少"的网站（比如博客、内容网站）比较适合；如果是toB场景、有大量表单提交（POST请求）的后台系统，React Query不是特别对口（它的强项在"管理查询缓存"，不是"管理复杂表单提交流程"）。

### 2. Next.js 的优缺点（笔记里评价比较直接）

优点：编译工具链做得好（融合了SWC），本地开发体验流畅。

缺点：框架本身束缚比较多——比如数据预获取被强制要求走它自己那套约定的API（如getServerSideProps这类）；它的中间件被封装在"Edge Runtime"（一个比完整Node.js环境更轻量的执行环境）里运行，导致想用一些Node原生能力（比如文件系统fs、操作系统os模块）时会直接报错，因为Edge Runtime根本没有实现这些API。

Next.js比较适合初创团队快速起步，尤其是配合它自家的Vercel生态（一键部署、RSC等新特性支持最好）。如果部署在阿里云这类非Vercel环境，要考虑和处理的细节会明显变多，束缚感也更强；纯粹为了用SSR而选它，不一定划算，需要衡量清楚。

国内业务不太适合直接用Vercel（它只有全球8个边缘节点，国内访问速度和合规性都不理想）。

### 3. Remix（另一个全栈React框架）

核心特点是"无感知加载"（导航切换页面时不需要刷新、不需要明显的loading等待），适合做电商、博客这类需要"页面切换快、且要兼顾SEO"的静态类网站。

### 4. 路由预加载优化（preload）

目标：让用户点击某个链接/切换某个模块时，几乎感觉不到加载过程（不需要骨架屏、不需要loading转圈）。

和"懒加载"的区别：懒加载是等用户真正点击/路由命中了，才开始加载对应资源；preload则是提前预判用户"大概率要去哪"，在用户还没真正点击前就开始悄悄加载，等真正点击时资源已经准备好了。

- 预加载时机1：`onMouseOver`（鼠标悬停在某个模块上）时，就开始预先加载这个模块对应的资源。
- 预加载时机2：`requestIdleCallback`（浏览器主线程空闲的时候），趁机悄悄预加载一些大概率会用到的资源，不占用当前紧要的渲染时间。

常用的库是**loadable-components**（虽然已经不太维护了，但目前还没有更合适的替代品）。这两种预加载时机，底层调用的都是它提供的preload方法。

配合**webpack-stats-plugin**：这个插件能读取webpack打包后生成的stats文件（里面记录了每个路由分别对应哪些chunk文件），从而在页面初始加载时，就提前用`<script>`标签+defer的方式把这些chunk预先加载好，效果上更准确地说是"预加载"而不是"懒加载"，但前提是你已经用了lazy做了按路由的代码拆分。

## 八、其他杂项知识点

- **Mock Service Worker (MSW)**：目前各大厂做接口mock数据的首选库，底层原理是调用浏览器的Service Worker去拦截真实的网络请求，返回你预设的mock数据，这样调试代码时不需要真的连后端接口。
- **GraphQL**：一般用在BFF这一层，作用是"削减接口数量"——前端不用为了拼一个页面而调好几个REST接口，一次GraphQL查询就能按需拿到所有需要的字段。ApolloGraphQL是配合React/Vue使用GraphQL的常用客户端库。
- **Emotion CSS**：MUI（Material UI）内部封装使用的一个"css-in-js"方案，可以通过styled函数或者高阶组件（HOC）的形式动态改变组件样式。
- **PixiJS**：一个基于WebGL的2D渲染库，适合做精美的封面/海报/运营页这类需要复杂图形效果的场景（类似"凡科网"这种在线设计工具背后可能用到的技术）。
- **react-helmet-async**：SSR场景下专门用来管理HTML的`<head>`标签内容（title、meta、link等），对SEO优化很关键。CSR（纯客户端渲染）可以用普通版react-helmet，但SSR场景必须用async版本，否则会有内存泄漏问题（社区和官方issue都有记录这个坑）。
- **class component（类组件）**：笔记里提到未来可能会被React官方逐渐淘汰，新项目建议直接用函数组件+hooks，不要再选类组件的写法。
- 为什么TS里函数组件不用再写`React.FC`类型：现在的React类型定义已经默认把函数组件当成FC来处理，显式声明FC反而是多此一举，直接写普通函数+参数类型标注就够了。
- **推荐的学习/资讯渠道**：dev.to、bestofjs、Twitter（获取前端生态最新动态）；ts-challenges（GitHub上的TS类型体操练习仓库）；bigfrontend.dev（前端手写题练习网站）；web.dev（Google官方的性能优化系列文章，前面提到的LCP等性能指标建议都通读一遍）。
- **推荐书单**：《非暴力沟通》《疯狂的程序员》《编程之美》《编程珠玑》《自制编译器》——其中《编程之美》讲的是场景式面试题，适合面试准备阶段翻一翻。
- **现代JS引擎的编译流程核心三阶段**：Ignition（字节码解释器）、Sparkplug（快速的基线编译器）、TurboFan（深度优化编译器）——各大云厂商在拼Serverless冷启动速度时，底层比拼的正是JS引擎这几个阶段的效率。
- **单元测试相关**：项目里如果有意为之地打印console.error（比如测试异常分支），但单测跑在Node环境里，遇到console.error单测框架可能会直接判定失败——可以用Jest的配置提前mock/拦截所有console.error，避免这种误判。给别人用的工具类库，测试覆盖率要求接近100%，因为一旦出bug会直接影响所有下游使用者的信任度，这也是写单测的核心意义之一。
- **Atomics**：JS里线程锁相关的API，用于配合SharedArrayBuffer实现多线程间的同步（笔记标注"需要去了解一下"，可以理解为JS在多线程编程场景下的一个底层同步机制）。
- **webAI / TensorFlow.js**：把别人已经训练好的机器学习模型，直接在浏览器端用JS加载运行的技术方向。
- **RxJS**：专门用来处理复杂异步编程和事件流的库（基于"响应式编程"思想，把事件、请求都当成一个个可以组合、变换的数据流来处理）。
- **YJS**：用于实现多人协同编辑、实时数据同步的库，核心解决的问题是"多个用户同时编辑同一份文档时如何不产生冲突"（比如多人同时编辑一个文档，怎么合并大家的修改）。
- **conclave**：基于WebRTC实现的多人协作库（点对点连接，不一定需要经过中心服务器转发）。

## 一、这条 bullet 在解决什么问题

**server state（服务端状态）和 client state（客户端状态）是两种东西。**

client state 是纯本地的：弹窗开没开、表单填了什么、当前选中哪个 tab。它归你管，你说了算。

server state 不是：它的真身在服务器上，你手里只有一份**可能已经过期的副本**。所以它天然带着一堆问题——什么时候重新拉、拉的时候要不要显示旧数据、多个组件同时要同一份数据要不要发两次请求、改完之后哪些副本该作废。

**用 `useState` + `useEffect` 手写这套，就是在重新发明一个缓存系统**，而且每个组件发明一遍。TanStack Query 就是把这套抽出来的库。

但光引入库还不够。**引进来之后怎么组织代码，才是这条 bullet 在说的事。**

## 二、三层到底是哪三层

参照实现在 `~/Desktop/projects/github/Prometheus`，`src/features/blog/api/get-posts.ts` 一个文件里就是完整的三层：

**第 1 层 —— 纯 API 函数**（`:50-54`）

```ts
export const getPosts = (options: GetPostsOptions = {}): Promise<PostsResponse> => {
  return api.get('/api/posts', { params: options });
};
```

只管发请求。**不依赖 React**，可以单独测试。

**第 2 层 —— queryOptions 工厂**（`:72-77`）

```ts
export const getPostsQueryOptions = (options: GetPostsOptions = {}) => {
  return queryOptions({
    queryKey: ['posts', options],
    queryFn: () => getPosts(options),
  });
};
```

**这一层是整个设计的枢纽。** 它把「这份数据叫什么名字（queryKey）」和「怎么拿到它（queryFn）」绑成一个对象。

**第 3 层 —— 类型化 Hook**（`:96-104`）

```ts
export const usePosts = ({ options = {}, queryConfig }: UsePostsOptions = {}) => {
  return useQuery({
    ...getPostsQueryOptions(options),
    ...queryConfig,
  });
};
```

组件只碰这一层。

**为什么不能少一层？** 常见的疑问是「第 2 层能不能省掉，直接在 Hook 里写 queryKey」。答案在下一节——**省掉第 2 层，这条 bullet 后半句的性能数字就没了。**

## 三、三层和 LCP 之间的桥（这一节是核心）

**三层结构本身不会让页面变快。** 它是个架构收益，不是性能收益。把这两件事直接划等号，面试官一问就穿。

真正的因果链是这样的：

```
queryOptions 独立成一层
   ↓
同一个配置对象能被三个入口复用：useQuery / prefetchQuery / ensureQueryData
   ↓
于是「预取」和「读取」用的是同一个 queryKey
   ↓
预取写进缓存的数据，详情页能原样命中
   ↓
详情页挂载时不发请求 → 直接渲染 → LCP 压下来
```

**关键在倒数第三步：`single-source cache keys`（缓存键单一来源）。**

假设 queryKey 写在两个地方——列表页预取时写 `['post', slug]`，详情页读取时写 `['posts', slug]`（多了个 s）。结果是：预取照样发请求、照样写缓存，**但详情页一个字都读不到**，还得自己再发一次。用户看不出区别，你还白白多打了一倍请求。

**这就是为什么 queryKey 必须只在 queryOptions 里定义一次。** 它不是代码整洁问题，是**预取到底生不生效**的问题。

代码里怎么强制的？`src/lib/react-query.ts:98-101`：

```ts
export type QueryConfig<T extends (...args: never[]) => unknown> = Omit<
  ReturnType<T>,
  'queryKey' | 'queryFn'
>;
```

调用方能覆盖 `enabled`、`staleTime` 这些配置，但 **`queryKey` 和 `queryFn` 在类型层面被 `Omit` 掉了，传进去直接编译报错**。

> **一句话答法**：三层结构不是为了好看。把 queryOptions 独立成一层，才能让预取和读取共用同一个 queryKey；共用了 key，预取的数据才能被详情页命中；命中了才谈得上 LCP。中间任何一环断了，前面的功夫全白费。

## 四、预取具体怎么做的

**Hover Prefetch**（`src/features/blog/components/post-card.tsx:84-85, :97`）

```ts
const prefetchPost = () => {
  queryClient.prefetchQuery(getPostQueryOptions(post.slug));
};
// ...
<motion.article onMouseEnter={prefetchPost} onClick={() => navigate(...)}>
```

**为什么 hover 是个好时机？** 因为它是**意图信号**：鼠标停到卡片上，到真正点下去，通常还有 200–500 ms。这段时间白白浪费掉了，用来提前拉数据正好。

两个实现细节值得说：

- **不 `await`**（`:80-83` 的注释写明了）：预取失败不该阻塞任何 UI。用户真进详情页时 `useQuery` 会正常走 loading / error 流程。
- **用 `prefetchQuery` 而不是自己 `fetch`**：`prefetchQuery` 把结果按 queryOptions 的 queryKey 写进 React Query 缓存，详情页用同一个 key 直接命中。自己 fetch 存到 state 或 localStorage，就得重新对接缓存，繁琐且易错。

**分页预取**（`src/features/blog/components/posts-list.tsx:59-63`）：悬停「下一页」时预取下一页数据，同样的套路。

**Mutation 驱动失效**（`src/features/comments/api/create-comment.ts:96-98`）：

```ts
onSuccess: () => {
  queryClient.invalidateQueries({ queryKey: ['comments', postId] });
}
```

评论发布成功 → 把评论列表缓存标记为过时 → 正在用这份缓存的组件自动重新请求。**这也依赖 queryKey 单一来源**：key 对不上，失效就失效了个寂寞。

## 五、LCP 是什么

**Largest Contentful Paint** —— Core Web Vitals 之一，测的是**视口内最大的那块内容元素完成渲染的时刻**，从导航开始计时。

「最大内容元素」通常是 `<img>`、`<video>` 的封面帧、带 `url()` 背景图的元素，或者**包含文本的块级元素**。详情页的话，一般就是标题或正文首屏那块。

官方阈值（取 75 分位）：

| 评级 | LCP |
|---|---|
| Good | ≤ 2.5 s |
| Needs improvement | 2.5 – 4.0 s |
| Poor | > 4.0 s |

**所以 500 ms 是「非常快」**——只有 good 门槛的五分之一。这是个好数字，但**正因为它好，被追问的概率也高**。

## 六、按「审什么」逐条过

审计表要你答的是：**工具、环境、样本、优化前基线、lab 还是 field**。逐条过一遍，你会发现这条目前一条都答不上——**这就是今天要产出的东西**。

### ① 工具

必须能报出具体的名字，二选一：

- **Lab（实验室）数据**：Lighthouse、Chrome DevTools 的 Performance 面板、PageSpeed Insights 的 lab 部分。特点是**可复现**，同样的配置跑出同样的数。
- **Field（真实用户）数据**：`web-vitals` 这个库上报、CrUX（Chrome 用户体验报告）、或者你们自己的 RUM。特点是**真实但不可控**，反映的是真用户在各种设备网络下的分布。

**「lab 还是 field」这个区分是这条审计的核心**，因为它决定了后面所有问题的答法。

### ② 环境

lab 数据必须交代：什么机器、什么网络节流档位（Lighthouse 默认对移动端做 4x CPU 降速 + Slow 4G 模拟）、桌面还是移动端配置、有没有开缓存。

**同一个页面，Lighthouse 移动端和桌面端的 LCP 能差三倍以上。** 只说「500 ms」不说档位，等于没说。

### ③ 样本

- lab：跑了几次？取的是中位数还是最好的一次？（Lighthouse 单次跑波动很大，一般至少跑 5 次取中位数）
- field：多少次页面加载？取的是 p75 还是平均值？**Core Web Vitals 的官方口径是 p75，不是平均值**——如果你报的是平均值，那和「LCP 达标」不是一个口径。

### ④ 优化前基线

**这条最重要，也最容易被问死。**

「LCP under 500 ms」只是个绝对值，它没有回答**「你做了什么让它变成这样」**。要能说出：优化前是多少？做了 hover prefetch 之后变成多少？

没有基线，这个数字就只是「这个页面本来就快」，跟你的三层架构一点关系都没有。**有基线，它才是你的成果。**

### ⑤ lab 还是 field

见 ①。答不上来就说明这个数根本没被正经测过。

## 七、最致命的一个追问：SPA 里详情页到底有没有 LCP

**这是这条 bullet 结构上的硬伤，必须自己先想清楚。**

LCP 是按**页面导航**计算的。而 hover prefetch 优化的路径是：

```
用户在列表页 → 悬停卡片（预取）→ 点击 → 前端路由切换 → 详情页组件挂载
```

这整个过程里**没有发生页面导航**。SPA 的路由切换属于 soft navigation（软导航），标准的 LCP 测量**不会为它产生新的 LCP 值**。（Chrome 有个实验性的 Soft Navigations API 能做这件事，但那不是默认行为，Lighthouse 和 `web-vitals` 默认也不按它报。）

**于是就出现一个矛盾：**

| 进入详情页的方式 | 有没有 LCP | hover prefetch 有没有用 |
|---|---|---|
| 直接输入 URL / 外部链接进来（硬导航） | ✅ 有 | ❌ 没用——用户根本没经过列表页 |
| 从列表页点进去（软导航） | ❌ 标准口径下不产生新 LCP | ✅ 有用 |

**hover prefetch 优化的恰恰是那条不产生 LCP 的路径。**

所以「detail pages open instantly, with no request at all」这句话，要么测的是硬导航（那 prefetch 没帮上忙，快是别的原因），要么测的其实不是标准 LCP（可能是自己用 `performance.mark` 量的组件渲染耗时，被叫成了 LCP）。

**这不代表这条 bullet 是假的**——数据预取确实让详情页秒开，用户体感是真的。**问题出在把这个体感套用了「LCP」这个有严格定义的指标名。**

**两条出路，今天选一条：**

1. **补测**：真去测硬导航下详情页的 LCP（Lighthouse 直接跑详情页 URL），拿到真实数字和基线，那这句话就站得住。
2. **改措辞**：把 `detail pages open instantly, with no request at all` 换成不占用标准指标名的说法，比如 `detail view renders from cache with no network round-trip`。**丢掉一个数字，换掉一个必输的追问。**

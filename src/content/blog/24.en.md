# Notes on useLayoutEffect

## What it is, in one sentence

**`useLayoutEffect` is the last chance to change the DOM before the page is painted.**

## Where it sits in the pipeline

```
render phase (the diff is done; what changes is locked in)
        ↓
commitBeforeMutationEffects
    getSnapshotBeforeUpdate runs — it can read the old DOM, not change it
        ↓
commitMutationEffects
    the real DOM is mutated; React has done its DOM work
    ★ the previous useLayoutEffect's cleanup runs here, synchronously ★
    the current pointer switches
        ↓
commitLayoutEffects (the layout phase)
    ★ useLayoutEffect runs here ★
    at this moment: the DOM is updated, but the browser has not painted yet
        ↓
    [the browser paints]
        ↓
useEffect runs — the user has already seen the frame
```

## Why it is synchronous

It **blocks painting**. The browser waits for it to finish before drawing this update to the screen.

That blocking is exactly what makes it useful: you can measure the DOM inside it and adjust the layout by hand, and the user never sees the "before" frame, because the browser has not drawn anything yet.

Compare `useEffect`: it does not block painting. It is scheduled asynchronously after the commit is finished, by which point the frame is usually already on screen. (The exception: for updates triggered by a discrete event such as a click, React 18+ flushes passive effects synchronously before paint.)

**The cleanup is synchronous too, and it does not only run on unmount.** From the docs on the `setup` parameter:

> After every commit with changed dependencies, React will first run the cleanup function (if you provided it) with the old values, and then run your setup function with the new values.

So when a dependency changes, last time's cleanup runs first and this time's setup runs second — both before the browser paints. They do not even sit in the same place: **the cleanup runs in the mutation phase** (right after the DOM is mutated, before the `current` pointer switches), **the setup runs in the layout phase.** React's own DOM work happens in between, but as far as the user is concerned it is all one frame — no intermediate state is ever visible.

## The common question: "does changing the DOM in here re-run the diff?"

It depends on what you do:

- **Touching the real DOM directly (a ref plus native APIs)**: no diff, nothing to do with the reconciler. It is the same as changing the page with jQuery or plain JavaScript.
- **Calling `setState` inside it**: that triggers a **completely new, independent** update (diff plus commit). React guarantees the new pass finishes before the browser paints — so several small cycles may run back to back underneath, but the user only ever sees the final version, never anything half-finished.

## The one you will definitely hit: it does not run during SSR

`useLayoutEffect` **only runs on the client. It does not run during server rendering.** In React 18 and earlier, hitting it makes React warn you directly (React 19 removed the warning, but the server still does not run it):

> useLayoutEffect does nothing on the server

The reason is blunt: on the server a component is only rendered to an HTML string. **There is no layout phase at all**, and nothing with a size or a position to measure. The tooltip that measures its own height to decide whether to sit above or below has no way to decide on the server — and even if you rendered it anyway, its position would "jump" once the client JavaScript loads and measures for real.

The official ways out:

- **Use `useEffect` instead.** Enough in most cases; the cost is that the user may see the un-adjusted frame.
- **Mark the component client-only**, so server rendering falls back to the nearest `<Suspense>` boundary.
- **Render it only after hydration**: keep an `isMounted` state initialised to `false`, set it to `true` inside a `useEffect`, then `return isMounted ? <RealContent /> : <FallbackContent />`. On the server and during hydration the user sees the fallback, which never calls `useLayoutEffect`.
- If you are using it **to sync with an external store rather than to measure layout**, you wanted `useSyncExternalStore` all along — it supports server rendering natively.

A component that genuinely needs layout information to decide what to render usually has no business rendering on the server anyway: a tooltip is triggered by a client interaction in the first place.

## Compared with getSnapshotBeforeUpdate

The two sit at two different moments in the DOM's lifecycle:

| | getSnapshotBeforeUpdate | useLayoutEffect |
|---|---|---|
| When | **Before** the DOM changes | **After** the DOM changes, **before** it is painted |
| What you can do | Read only — writing is pointless, the new DOM overwrites it immediately | Write, and the user sees no seam |
| In a sentence | A last look at the old DOM before it dies | The new DOM is born but not yet visible — reshape it while you can |

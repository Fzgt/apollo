title: Promise Odds and Ends
---

### `async` always returns a promise, so these two are near-equivalent:

```js
// one
async function f() { return 5; }

// two (wrap it by hand, no async)
function f() { return Promise.resolve(5); }
```

### `.catch(() => {})` launders a rejected promise into a resolved one

### An error thrown in a `.then` callback (or a rejected promise returned from it) **sinks** to the next rejection handler further down the chain — the next `.catch`

### The second argument to `.then(onOk, onErr)` cannot catch what the first argument throws

Why: `onErr` only handles rejections coming from upstream, and `onOk` and `onErr` are two siblings passed to the same `.then`. An error thrown by `onOk` looks for the *next* link's handler, not its neighbour. Hence the common advice: prefer `.then().catch()` and use the two-argument `.then(onOk, onErr)` sparingly, because it is easy to miss errors thrown in the success callback.

One more: an error thrown inside a `.catch` keeps sinking to the next `.catch`.

```js
Promise.reject(new Error("a"))
  .catch(() => { throw new Error("b"); })   // threw b while handling a
  .catch(err => console.log(err.message));  // b
```

And if a `.catch` returns normally without throwing, the chain is "restored" to fulfilled — which is exactly the mechanism behind `.catch(() => {})` laundering a rejection into a resolution.

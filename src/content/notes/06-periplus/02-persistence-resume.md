# ② 持久化与断点续跑

> **简历原句**
>
> **Six-stage LLM pipeline behind typed Pydantic stage contracts** filled by **schema-constrained JSON output**, with **run state and stage artifacts in PostgreSQL**: **a run that dies mid-pipeline resumes from the last completed stage**.
>
> ---
>
> 六阶段 LLM 流水线，阶段之间只认带类型的 Pydantic 契约，由受 schema 约束的 JSON 输出填充；运行状态与阶段产物都落在 PostgreSQL 里：流水线中途挂掉的运行可以从最后一个已完成阶段续跑。

本篇和[① 六阶段与类型化契约](/docs?section=periplus&item=typed-contract)共用简历上的第一条。「每次运行的 token 和时间预算」不在简历上，但预算续跑那一节仍是这篇最值钱的部分。

## 这条要讲清什么

表面是「我做了断点续传」。但真正值钱的是三个边界判断：什么样的产物才算合法的续跑起点，预算续跑时为什么不能重置，以及无从恢复和重新开始为什么是两回事。

## 要解决什么

这个流水线跑一次要几分钟、要花钱，每个阶段都在调模型、抓网页。如果进程挂在第四阶段，重跑意味着前三阶段的钱和时间全部白花。

所以运行状态、每个阶段的产物、还有检索到的证据全部存进 PostgreSQL，进程重启时把没跑完的捡起来接着跑。

## 续跑边界必须是通过了关卡的产物

先说关卡是什么：每个阶段跑完会有一道检查，看产物结构是否合法、内容是不是空的，不合格就算这个阶段没过。

产物模块的文件头写得很清楚：每一次阶段尝试产出的东西都保留下来，不管它有没有通过这个阶段的关卡；被拒绝或被取代的尝试仍然可以取出来检查，它只是永远不能作为重放的起点。

保留失败产物是为了排查，允许从它续跑是另一回事。这两件事分开，是这个设计最容易被忽略的一半，也是被问到时最能拉开差距的一句。

## 预算续跑时不重置，这条最值钱

先说预算是什么：一次运行有四个上限——最多发多少次检索、最多抓多少个网页、最多花多少 token、最多跑多少秒。

预算模块的文件头是这样写的：预算是整个运行的天花板，包括重放在内；为重放建的计数器会把这次运行已经花掉的量作为起点，而不是清零；反复续跑一个运行，不能被用来一个阶段一个阶段地突破配额上限。

这是个真正的安全性质：如果续跑时预算归零，那「反复让它崩」就变成了绕过配额的手段。

能主动指出这一点，说明你想过这个机制会怎么被滥用——这比讲清楚它怎么工作高一个层次。这句话适用于任何一条讲机制的 bullet。

检查的时机也讲究。预算检查发生在一个阶段跑完之后、下一个阶段开始之前，从不在阶段内部打断它。所以它不能抢占正在飞的阶段，只能让它不算通过，或者不让下一次尝试开始。

## 崩在哪里，决定了怎么恢复

三个分支，每个都有理由。

一个关卡都没过就死了，标成失败，不重跑。注释的理由是：重新开始等于静默地假装这次尝试从未发生过。

所有阶段都过了、死在记录成功的路上，直接标成成功，而不是重放一条已经跑完的流水线。

中间某个阶段之后崩的，从下一个阶段续跑，这是正常路径。

第一种最值得讲：无从恢复和重新开始是两回事。直接重跑会让这次失败的尝试在记录里凭空消失，而那正是你排查问题时需要的东西。

## 第四阶段挂了怎么从第三阶段之后接着跑

进程启动时扫数据库里所有还标着运行中的运行——这个状态本身就是信号，因为正常结束一定会写一次已完成。然后沿着阶段顺序走一遍，找最靠后的、有通过关卡的产物的阶段，从它的下一个开始。

有个位置问题答错很难看：续跑逻辑不在编排器里，在 API 层的运行存储里。编排器只管在给定的起点上跑流水线，上次跑到哪、该不该续，是持久化层的职责。

## 运行状态为什么不能只放在内存

三条。进程会挂，这就是整个机制的前提。要能水平扩容，另一个实例得看得到状态。用户要能刷新页面看进度，前端轮询的是数据库，不是某个进程的内存。

## 续跑的那个阶段怎么保证幂等

靠的不是让阶段本身幂等，是让边界干净。只从通过关卡的产物续跑，所以续跑的输入是确定的；重跑的那个阶段会产生新的尝试编号，不覆盖旧的。

有个很细的坑值得讲：崩溃可能发生在某个阶段中途，所以要续跑的那个阶段可能已经有过没通过关卡的尝试记录了。代码会先填充占位的历史，让编排器的尝试计数器接着往下走，而不是撞上一个产物库里已经存在的编号。

能讲出这个细节，说明你真的处理过崩在半路，而不只是崩在阶段之间。

## 向量缓存里存的是什么，怎么失效

存的是抓取到的证据段落和它的向量，目的是同一段证据不重复抓、不重复算向量。

向量的意思是把一段文字转换成一串数字，意思相近的文字数字也相近，这样就能问「有没有和这段话意思差不多的、我已经抓过的内容」。

失效靠的是[新鲜度窗口](/docs?section=periplus&item=evidence-judgment)那一套：缓存本身不设过期时间，是消费它的时候按日期判断过没过期。

这个区分值得主动说：缓存不负责判断新不新鲜，只负责别重复干活。新鲜度是业务语义，归判断过期的那个函数管。

## 向量缓存不在这一条里

pgvector、余弦索引和本地向量模型是独立的一条 bullet，细节全部在[③ pgvector 证据缓存与本地向量](/docs?section=periplus&item=pgvector-embeddings)。

这一条只需要记住它和持久化的关系：运行状态和阶段产物走运行持久化那个类，证据缓存走证据缓存那个类，是另一个类、另一张表、另一套生命周期。两者共用 PostgreSQL，但失败语义完全不同——续跑数据丢了这次运行就废了，证据缓存丢了只是多抓一次页面。

## 英文怎么说

三句最容易说错的。「预算不重置而是带入已花的量」说 the tracker is seeded with what the run already spent, not reset to zero——这是这条最值钱的一句。「无从恢复不等于重新开始」说 restarting would silently pretend the failed attempt never happened。「不能抢占正在飞的阶段」说 it cannot preempt a stage in flight; it can only refuse to pass it or refuse to start the next attempt。

其他常用词：一次运行是 a run，持久化是 persist，阶段产物是 stage artifacts，续跑是 resume，重放是 replay，续跑边界是 replay boundary，关卡是 gate，尝试是 attempt，预算和上限是 budget 和 ceiling，计数器带入初值是 seeded，幂等是 idempotent，占位历史是 placeholder history。

## 30 秒回答

> 这个流水线跑一次要几分钟、要花钱。进程挂在第四阶段，重跑意味着前三阶段全部白花。所以运行状态、每个阶段的产物、还有检索到的证据全部落在 PostgreSQL 里。进程重启时会扫出所有还标着运行中的运行，从它最后一个通过了关卡的阶段之后接着跑。关键在「通过了关卡」这个限定：失败的产物我们也留着，供事后检查，但它永远不是合法的续跑边界。另外预算是整个运行的天花板，续跑时不会重置，而是把已经花掉的量带进来——否则反复重启就能一次一个阶段地把配额刷穿。

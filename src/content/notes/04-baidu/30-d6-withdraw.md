# 提现：前端能保证什么，不能保证什么

> 🔴 **必看**。数字口径见 [#7 · 2,000+ peak QPS](/docs?section=baidu&item=n07-qps) · [#8 · 零资损](/docs?section=baidu&item=n08-zero-loss)。**这里只讲前端那一层。**

## 30 秒口播稿（改一改就能用）

> 这是个活动期间的提现入口，峰值时整条链路到过两千多 QPS。**前端在这里的职责很窄但很明确：把无效的重复请求挡在发出之前，并且在结果不确定时永远往「失败」那边说。**
>
> 具体三件事：请求发出到响应回来这段窗口里锁住同一笔提现，不让用户狂点产生第二个请求；幂等 key 在前端生成并存进 sessionStorage，**这样用户刷新页面重试，后端还能认出这是同一笔**；超时和网络中断一律按失败提示、引导去查提现记录，绝不显示成功。
>
> **但我很清楚前端锁挡不住跨设备、跨标签页和刷新重试——真正的正确性来自后端的幂等键和数据库约束。前端减少的是无效负载，不是提供保证。**

## 一、先定义「幂等」，这个词后面到处要用

> ⭐ **幂等（idempotent）= 同一个操作执行一次和执行 N 次，系统最终状态一样。**

- `把余额设为 100` → **幂等**（做几次都是 100）
- `余额减 50` → ⭐ **不幂等**（做两次就扣了 100）

**提现天然属于第二种。** 所以必须在外面套一层机制，**让「重复执行」变成「识别出是重复、不再执行」**。

## 二、防抖 vs 节流 vs 请求锁（常混，要分清）

| | 行为 | 场景 |
|---|---|---|
| **Debounce（防抖）** | 多次触发，**停下来之后 n 毫秒才执行一次** | 搜索框输入、resize |
| **Throttle（节流）** | **每 n 毫秒最多执行一次**，匀速 | scroll、mousemove |
| ⭐ **请求锁** | **第一次立即执行，之后到响应回来为止全部拦掉** | 提交类操作 |

⭐ **提现按钮为什么不能用 debounce**：「停下来才生效」意味着用户点了 100 次，只有最后一次在 300ms 后发请求。**用户点第一下时什么都没发生，他会觉得「没反应」，于是点更多次**——体验和意图完全相反。

> **提交类操作要的是「首次立即执行 + 锁住后续」（leading edge + lock），不是防抖的「最后一次才执行」（trailing edge）。**

## 三、请求锁的两个版本，逐行读

**朴素版**：

```js
let inFlight = false;                    // 「有没有一个请求正在飞」
async function withdraw() {
  if (inFlight) return;                  // 正在飞 → 直接不做事
  inFlight = true;                       // 上锁
  try { ... } finally { inFlight = false; }   // ⭐ finally：成功失败都要解锁
}
```

> ⭐ **`finally` 那一句是重点**：如果只在成功分支里解锁，**一次失败之后按钮就永久锁死了**，用户再也提不了现。

**按参数去重版**（更完整——**同一笔锁住，不同笔可以并发**）：

```js
const inFlightMap = new Map();           // key = 这一笔的单号，value = 正在飞的那个 Promise
async function withdraw(orderId) {
  if (inFlightMap.has(orderId))
    return inFlightMap.get(orderId);     // ⭐ 不是「拒绝」，是把同一个 Promise 还给他
  const promise = api.withdraw(orderId);
  inFlightMap.set(orderId, promise);
  try { return await promise; }
  finally { inFlightMap.delete(orderId); }
}
```

**逐行说明**

- `Map` 而不是布尔量 → **锁的粒度从「整个按钮」细化到「每一笔单」**，用户同时提两笔不同的不会互相挡
- ⭐ `return inFlightMap.get(orderId)` → 第二次调用**拿到的是第一次那个 Promise**。所以调用方 `await` 之后照样能拿到结果，**它不知道自己被去重了**，代码不用写任何特判
- `finally { delete }` → 请求结束就把锁拿掉，下次点击是一次全新的请求

> ⭐ **这个模式叫「请求去重」（request deduplication），React Query / SWR 内部就是这么做的。** 能点出这一句，说明你知道自己在复现一个通用模式，而不是随手写的。

## 四、幂等 key：前端能做的最有价值的一件事

**前端锁挡不住三件事**（因为那个 `Map` 只活在当前这个页面的内存里）：

1. 网络超时后的**自动重试**
2. 用户在**不同设备 / 不同标签页**同时操作
3. ⭐ **页面刷新后再点**——刷新等于整块内存清零，锁没了

**所以真正的保证必须来自后端幂等**：每个提现请求带一个**幂等 key**（一个这笔操作专属的随机串），后端把已处理过的 key 存下来，**同 key 再来就直接返回上次的结果，不再执行扣款**。

**前端的配合是关键的一半：**

| 做法 | 为什么 |
|---|---|
| **提前生成 key**（进页面就生成，不是点击时生成） | 点击时生成的话，**用户点两次就是两个不同的 key，后端看到的就是两笔不同的提现** |
| ⭐ **存 sessionStorage** | **刷新页面后还是同一个 key**——否则刷新重试在后端看来是一笔新提现 |
| 每次调用都带上它 | |

> **后端拿这个 key 建唯一索引兜底**：第二次插入直接违反唯一约束，数据库层面就失败了。
>
> ⭐ **这和 [Stripe webhook](/docs?section=beyz&item=n02-stripe-events)、[Beyz 的 cron 去重](/docs?section=beyz&item=d4-service) 是完全同一个模式：把不变量放在数据层。** 应用层的判断会因为并发、重启、多实例失效，**数据库的唯一索引不会。**

## 五、defensive fallback：金融场景的错误处理原则

> ⭐ **默认失败，只有明确成功才展示成功。**

| 结果 | 怎么处理 |
|---|---|
| **明确失败**（4xx/5xx、业务错误码） | 显示错误 + 可重试 |
| ⭐ **不确定**（超时、网络中断、发出去没响应） | **按失败处理**，但措辞是「网络异常，请稍后查看提现记录」——**不要直接说「失败了」**（后端可能已经处理了） |
| **明确成功**（2xx + 业务成功码） | 展示成功 |

⭐ **为什么「不确定」要往失败那边倒——因为两种错法的代价不对称：**

- **错误地显示失败** → 用户去重试 → **重试有幂等 key 兜底，不会真的扣两次** → 代价只是一次白跑
- **错误地显示成功** → 实际没到账 → **用户以为提了但钱没来** → 客诉、投诉、事故

> **这句「代价不对称」是这一节的题眼**，也是所有金融前端错误处理的通用原则。

## 六、被追问时的分工表（必须能一口气说清）

| 问题 | 答法 |
|---|---|
| **用户绕过前端锁会怎样？** | **能绕，而且很容易**——F12 直接调接口。所以前端锁只是减少无效请求，**正确性靠后端幂等键 + 唯一索引 + 数据库事务 + `WHERE balance >= ?` 的余额不变量** |
| **2000 QPS 是你测的吗？** | 不是。后端监控里的整条链路量级，**前端不「扛」QPS，前端「贡献」QPS**。详见 [#7](/docs?section=baidu&item=n07-qps) |
| **零资损怎么保证的？** | **对账的结论，不是我测的**。详见 [#8](/docs?section=baidu&item=n08-zero-loss) |
| **前端还能做什么？** | 限流（没配额时按钮 disabled）、活动开始瞬间的排队/验证码削峰、**但这些都是体验优化不是正确性保证** |

> ⭐ **一句话收尾**：**前端减少无效负载，后端提供正确性。**

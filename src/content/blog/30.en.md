## The basics

```javascript
const [isPending, startTransition] = useTransition();
//     ↑ first      ↑ second     ← the order cannot be swapped: isPending first, startTransition second
```

- `isPending`: a boolean saying whether this transition is still in flight
- `startTransition`: a function that marks a state update as low priority and interruptible

```javascript
function TabContainer() {
  const [tab, setTab] = useState('about');
  const [isPending, startTransition] = useTransition();

  function selectTab(nextTab) {
    startTransition(() => {
      setTab(nextTab); // marked as a transition; higher-priority updates can interrupt it
    });
  }

  return (
    <div>
      {isPending && <Spinner />}
      {/* ... */}
    </div>
  );
}
```

---

## ⚠️ The core rule: the function may be async, but a `set` after an `await` needs another wrap

In React 19 the function you pass to `startTransition` has a name: an **Action**. Straight from the docs, on the `action` parameter:

> React calls `action` immediately with no parameters and marks all state updates **scheduled synchronously** during the `action` function call as Transitions. **Any async calls that are awaited in the `action` will be included in the Transition**, but currently require wrapping any `set` functions after the `await` in an additional `startTransition`.

Four things fall out of that:

1. **The function is called immediately**, not deferred like a `setTimeout`. `console.log(1); startTransition(() => console.log(2)); console.log(3);` prints 1, 2, 3.
2. Every state update scheduled **synchronously** during that call is marked as a transition.
3. **The function itself may be `async`.** Async calls awaited inside the action are included in the transition — `isPending` flips to `true` at the first `startTransition` call and stays `true` until every Action finishes and the final state is on screen.
4. The one restriction: the `set` functions **after** an `await` need another `startTransition` around them.

> **Stop repeating "the function you pass must be synchronous".** That is React 18 wording. It survives in today's docs only in the troubleshooting section about `setTimeout`, where it contradicts the parameter description above — the docs never cleaned it up. The real line is not "sync function vs async function", it is **whether React can still see this `set` on the chain it is tracking**: the synchronous execution counts, an awaited chain counts, a `setTimeout` callback does not, and a bare `set` after an `await` does not.

---

## ❌ Two things that still do not work

### 1. Setting state after leaving the call stack

```javascript
// wrong
startTransition(() => {
  setTimeout(() => {
    setPage('/about'); // not marked as a transition
  }, 1000);
});
```

The `setTimeout` callback is a brand-new macrotask with no link back to that `startTransition` call. Dropping a `.then()` callback in has the same problem:

```javascript
// wrong
startTransition(() => {
  fetchData().then(result => setData(result)); // the promise is never awaited, so React cannot track it
});
```

The fix is to move `startTransition` inward, so it wraps the moment the state is actually set:

```javascript
setTimeout(() => {
  startTransition(() => {
    setPage('/about'); // ✅
  });
}, 1000);
```

### 2. Setting state right after an `await` inside an async action

```javascript
// wrong
startTransition(async () => {
  await someAsyncFunction();
  setPage('/about'); // ❌ no second startTransition after the await
});
```

React documents this as a **known limitation** ("React doesn't treat my state update after await as a Transition"). The cause is not React but JavaScript: the async context is lost across the `await`, so React has no way to know this `set` still belongs to that transition. Once TC39's [AsyncContext](https://github.com/tc39/proposal-async-context) lands, the limitation goes away.

---

## ✅ The right way: wrap again after the await

```javascript
const loadData = () => {
  startTransition(async () => {
    const result = await fetchData();
    startTransition(() => {  // ← the point: wrap again after the await
      setData(result);
    });
  });
};
```

The outer `startTransition` is not decoration: because it receives the promise this async function returns, `isPending` stays `true` for the whole `await fetchData()` wait. The inner one puts the post-`await` `setData` back inside the transition.

## While we are here: three loading mechanisms, do not blur them

- **`isPending`**: the flag returned by `useTransition`, **maintained by React itself**. You never call `setLoading(true)` / `setLoading(false)` — it opens and closes with the transition's own lifecycle.
- **A hand-rolled `useState` loading flag**: you call `setIsPending(true/false)` around the request yourself. This is an *alternative* to `isPending`, not a partner to it. The difference that matters: the manual version cannot stop out-of-order responses, while Actions keep the results in order.
- **`Suspense`**: catches a **promise thrown** during a child's render. Unrelated to either of the above.

If a component manages its loading state manually with `useState` and never throws a promise while rendering, wrapping it in `<Suspense fallback="...">` will never trigger — unless the component genuinely uses something that throws a promise, such as `React.lazy` or a Suspense-aware data-fetching library.

---

## In one sentence

> `useTransition` returns `[isPending, startTransition]` in that order. The function you pass — the Action — **may be async**: awaited calls inside it are part of the transition and `isPending` stays `true` throughout. But a `set` after an `await` needs another `startTransition` to count, and a `set` that has left the call stack (`setTimeout`, an un-awaited `.then()`) never counts. `isPending`, a manual `useState` flag, and `Suspense` are three separate loading mechanisms that do not link up on their own.

title: Why Did You Render

## What it solves

`React.memo` and `PureComponent` decide whether to skip a render by shallow-comparing props and state. There is a quiet trap in that: **if you pass an object, array, or function, an identical value with a different reference still compares as changed, and the component re-renders anyway.**

```javascript
<BigList style={{ paddingTop: 350 }} /> {/* a brand new object on every parent render */}
```

The contents of `style` never change, but because it is a new object each time, `memo` decides it changed and re-renders for nothing. This kind of bug logs no error, looks fine on screen, and is very hard to spot by eye.

**why-did-you-render finds these invisible wasted renders and prints them to the console.**

---

## How to use it, in three steps

### Step 1: install

```bash
npm install @welldone-software/why-did-you-render --save-dev
```

### Step 2: create a dedicated init file, development only

```javascript
// wdyr.js
import React from 'react';

if (process.env.NODE_ENV === 'development') {
  const whyDidYouRender = require('@welldone-software/why-did-you-render');
  whyDidYouRender(React, {
    trackAllPureComponents: true, // track every component using memo/PureComponent
  });
}
```

**⚠️ The docs are explicit: never use it in production.** It monkey-patches React's internals to record comparisons, which costs performance. It is purely a development tool.

### Step 3: make it the very first import in the app

```javascript
// index.js
import './wdyr'; // ← must come first
import React from 'react';
import ReactDOM from 'react-dom';
```

---

## Two ways to track specific components

**Option 1 (recommended)**: `trackAllPureComponents: true` tracks everything using `memo` or `PureComponent`, with nothing to mark by hand.

**Option 2**: mark the suspects yourself

```javascript
class BigList extends React.PureComponent {
  static whyDidYouRender = true;
  render() { ... }
}

// same for function components
const BigListPureComponent = (props) => <div>...</div>;
BigListPureComponent.whyDidYouRender = true;
```

---

## What you get

When it detects a render that could have been avoided, the console prints something like:

```
Main was "re-rendered because of props changes"
    style has received different objects that are equal by value:
    {paddingTop: 350} !== {paddingTop: 350}
```

It tells you **which component and which prop**, and that the values are equal but the references are not — at which point whether to wrap it in `useMemo` or hoist the object out of the component is obvious.

---

## In one sentence

> It is not a tool for *avoiding* re-renders — that is what `memo`, `useMemo`, and `useCallback` are for. It is a development-only detective that finds the cases where `memo` or `PureComponent` was applied but a fresh reference threw the optimisation away, and points at the exact prop, so you do not have to hunt.

## Addendum: React's own three gates — bailout at the source level

Everything above is about diagnosing "it should have skipped and didn't". Looking the other way — from an update being dispatched to it being rendered — React has **three gates** that can stop it, and `memo` is only one of them. "Why did `setState` not re-render?" and "why is `memo` not working?" are both answered here.

### Gate 1: eagerState — the value didn't change, so no render is even scheduled

When you call `setCount(1)`, if this hook's update queue is **currently empty**, React **computes the next state immediately** and compares it with the old one. If they match, it returns without scheduling a render at all.

```js
// ReactFiberHooks.js, inside dispatchSetState
const currentState = queue.lastRenderedState;
const eagerState = lastRenderedReducer(currentState, action);
update.hasEagerState = true;
update.eagerState = eagerState;
if (is(eagerState, currentState)) {
  // Fast path. We can bail out without scheduling React to re-render.
  enqueueConcurrentHookUpdateAndEagerlyBailout(fiber, queue, update);
  return false;
}
```

The comparison is `Object.is`, so:

- `setCount(1)` when it is already 1 → no render
- `setUser({...user})` with identical contents → **renders anyway**, because the object is a new reference

A commonly asked symptom: you click twice, the first click changed nothing, yet the console still logs a render. The reason is that this fast path **only applies while the queue is empty** (`fiber.lanes === NoLanes`); with another update already queued, the value can only be computed during the render phase.

### Gate 2: memo / PureComponent — a shallow props comparison

The gate this post is about. In the source it is `shallowEqual(prevProps, nextProps)` — one level deep, and passing it means bailing out. Passing a new object or a new function is what fails at this gate.

### Gate 3: bailoutOnAlreadyFinishedWork — skipping an entire subtree

The first two stop *this component*; the third stops *everything below it*.

```js
// ReactFiberBeginWork.js
function bailoutOnAlreadyFinishedWork(current, workInProgress, renderLanes) {
  // Check if the children have any pending work.
  if (!includesSomeLane(renderLanes, workInProgress.childLanes)) {
    // The children don't have any work either. We can skip them.
    ...
    return null;   // returning null = the whole subtree skips beginWork
  }
  // otherwise reuse this node and keep walking down
}
```

The key is `childLanes`: every fiber records whether its subtree has pending work. A component with an update **bubbles its lane all the way up to the root**, so on the way down React only needs to glance at `childLanes` to know whether a branch is worth walking.

**This explains a counter-intuitive observation**: a parent re-renders, a `memo`'d child's props are unchanged, and yet some component deeper down renders anyway — because that deep component called `setState` itself, bubbled its lane upward, `childLanes` matched, and React had to walk through.

### One more: context bypasses the first two gates

`memo` cannot stop a context update. When a Provider's value changes, React takes a different path — walking down from the Provider to **hunt for consumers specifically** (`propagateContextChange`) and marking them directly, no matter how many layers of `memo` sit in between. The bailout source above leaves that door open explicitly:

```js
// Before bailing out, check if there are any context changes in the children.
lazilyPropagateParentContextChanges(current, workInProgress, renderLanes);
```

So when "it's memo'd and still re-rendering" survives the reference check, context is the next thing to look at — particularly a Provider written as `value={{ state, dispatch }}`, which mints a new object on every render and drags the whole consumer tree with it.

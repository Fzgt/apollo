# ② 合批渲染与它的代价

> **简历原句**
>
> Collapsed each obstacle section into **two InstancedMeshes sharing one matrix set**: a **headless Chromium harness sampling renderer stats every frame** put **draw calls down from 129 to 76** and **triangles submitted up 2.6×**, **one bounding volume per mesh being the price of losing per-instance frustum culling**.
>
> ---
>
> 把每一段障碍物合并成两个共享同一套矩阵的 InstancedMesh：一个逐帧采样渲染器统计数据的无头 Chromium 测量装置显示，draw call 从 129 降到 76，提交的三角形数上升 2.6 倍 —— 每个 mesh 只剩一个包围盒，这是失去逐实例视锥剔除的代价。

## 这条 bullet 在讲什么

⭐ **整份简历二十个数字，十九个是「变好了」，这条里有一个是「变差了」—— 而它恰恰最能加分，因为它证明你在报代价，不只是报收益。**

**这条 bullet 自己就把取舍的机制写在句子里了**（`one bounding volume per mesh being the price of...`）。**面试官读到这一句会认真起来，因为绝大多数简历只报收益。**

## 一、什么是 draw call，为什么它是瓶颈

**draw call（绘制调用）= CPU 对 GPU 说一次「画这个东西」。**

**关键在于：它的成本主要在 CPU 那一侧，不在 GPU。** 每发一次绘制命令，图形驱动要做状态校验、可能要切换着色器/贴图/顶点缓冲、把命令打包送进队列。

**典型的瓶颈长这样：**

```
场景里 500 个方块，每个一次绘制命令
  → 每帧 500 次 CPU → GPU 的命令提交
    → CPU 忙不过来，GPU 反而在等
      → 帧率被 CPU 卡住，而 GPU 占用率很低
```

> **这种情况有个名字叫「受绘制命令限制」（draw-call bound）。特征是：你把模型面数砍一半，帧率纹丝不动** —— 因为瓶颈根本不在 GPU 算不算得过来。

## 二、实例化渲染：一次命令画一万个

**如果 500 个方块用的是同一个几何体和同一个材质，只是位置/旋转/缩放不同，那完全没必要发 500 次命令。** 可以：

1. 把几何体传一次给 GPU
2. 把 500 个**变换矩阵**打包成一个数组传过去
3. **发一次**绘制命令，告诉 GPU「用这个几何体画 500 遍，第 i 遍用数组里第 i 个矩阵」

**three.js 里这个东西叫 `InstancedMesh`（实例化网格）。**

**简历那句「把每个障碍区合并成两个实例化网格，共用一套矩阵」的意思是：**

- 每个区段原本几十个独立物体 → 合并成 **2 个**
- **为什么是 2 个不是 1 个**：实例化要求**同几何体、同材质**。两个大概对应两类外观 —— **面试时要能说出这两个分别是什么**
- **共用一套矩阵**：两个网格用同一份变换数据，同一批障碍物的位置**只算一次、只上传一次**

## 三、⚠️ 测量的坑：两个后端的计数含义不一样

**这是这条最有含金量的地方。**

`PerfProbe.tsx:11-21` 的注释：

> - **WebGL 渲染器的 `info.render.calls` 是「这一帧的绘制命令数」**
> - **WebGPU 渲染器的同名字段却是「从启动到现在，渲染函数被调用了多少次」** —— 一个单调递增的累计值；它的每帧绘制命令数在**另一个字段** `drawCalls` 里
> - **而且 WebGPU 是异步渲染的**，它自动的每帧清零**不一定在你读取之前完成**

**三个坑叠在一起。解法（`:37-44` 和 `:74`）：**

```js
info.autoReset = false;                              // ① 关掉自动清零
// ...读取...
drawCalls: render.drawCalls ?? render.calls ?? 0,    // ② 优先读 WebGPU 那个字段
// ...
info.reset?.();                                      // ③ 采样完自己手动清零
```

> ⭐ **关掉自动清零、采样后自己清零** —— 这样每次读到的都恰好是一帧的量，**两个后端才可比**。
>
> **不知道这个坑的话，你在 WebGPU 下量出来的「绘制命令数」会是一个从 0 一路涨到几万的数字，而且你可能还会信它。**
>
> **能讲出「我发现两个后端的同名字段含义不同」，是「真的量过」和「抄了段代码」的分水岭。**

## 四、实验是怎么设计的

`bench/run.mjs:32-40` 定义了**四个场景**：

```js
{ name: 'WebGPU + instancing',    flags: 'perf=1&immortal=1' },
{ name: 'WebGPU, no instancing',  flags: 'perf=1&immortal=1&instancing=off' },
{ name: 'WebGL + instancing',     flags: 'perf=1&immortal=1&renderer=webgl' },
{ name: 'WebGL, no instancing',   flags: 'perf=1&immortal=1&renderer=webgl&instancing=off' },
```

**这是个 2×2 的受控实验**：渲染后端 × 实例化开关。

**三个开关各有用途，都值得讲：**

| 开关 | 作用 |
|---|---|
| `perf=1` | 挂载性能探针。**只在带这个参数时挂载，正常访问零开销** |
| ⭐ `immortal=1` | **飞行器不死** —— 否则采样窗口会因为撞毁而中断，**每次采样的时长和场景都不一样** |
| `instancing=off` | 关掉实例化，走对照组 |

> ⭐ **`immortal=1` 这个设计很关键**：它把「采样窗口」这个变量固定住了。**没有它，两组数据采集的赛道段落都不一样，比出来的差异就混进了场景差异。**

**采样方式**：用 playwright 启动一个无界面的浏览器，每个场景采样固定秒数，探针**每帧**记一条，最后取统计量。

**129 → 76 报的是每帧绘制命令数在采样窗口内的平均值。**

## 五、`fps.p50 > 115` 那个条件是干什么的

```js
// bench/run.mjs:123-131
const capped = ok.filter(r => r.report.fps.p50 > 115);
if (capped.length) {
  console.log(`> Note: ${capped.length}/${ok.length} scenarios sit at the compositor's
    frame cap (~120 fps), so FPS does not separate them — the GPU still has headroom
    at this resolution. Compare draw calls and triangles instead...`);
}
```

**这不是在过滤数据，是在给报告加一条警告。**

**逻辑**：如果一个场景的**帧率中位数超过 115**，说明它**顶在了显示合成器的 120 帧上限**上。**这时候帧率这个指标已经饱和了** —— 优化前后都是 120，看不出任何差别，**但这不代表没有差别，只代表 GPU 还有富余、瓶颈还没到。**

> ⭐ **所以这行代码是在说：「在这个分辨率下帧率已经区分不了这四个场景了，请改看绘制命令数和三角形数。」**
>
> **这正是为什么这条 bullet 报的是绘制命令数而不是帧率。** 被问「为什么不报帧率提升」，答案就在这里 —— **报一个已经饱和的指标是自欺欺人。**

**还有一条相关的警告**（`:146-153`）：无界面浏览器里 WebGL 常常退化成**软件渲染**（用 CPU 模拟 GPU）。这条警告划清了界限：

| 指标 | 在无界面环境里可不可信 |
|---|---|
| **绘制命令数 / 三角形数** | ✅ **可信** —— **它们是 CPU 侧的计数**（渲染器记录自己提交了多少），跟有没有真 GPU 无关 |
| **帧时间 / 帧率** | ❌ **不可信** |

> **这一条能主动说出来非常加分**：它说明你清楚**自己的测量环境边界在哪**，只在有效范围内下结论。

## 六、按「审什么」逐条

| 问 | 答 |
|---|---|
| **哪个探针** | `src/utils/PerfProbe.tsx`，每帧采样一次，**只在 `?perf=1` 时挂载** |
| **同场景同设备吗** | ✅ 同一台机器、同一个无界面浏览器、同一分辨率、**`immortal=1` 固定采样窗口**，四个场景只差开关 |
| **报的是什么统计量** | 采样窗口内的**每帧平均值** |
| **能否复现** | ✅ 起开发服务器 + 跑 `node bench/run.mjs`，需要 playwright |
| **归因** | **你自己写的探针、自己搭的实验、自己跑的** |

⚠️ **一个建议**：跑之前把**具体命令、分辨率、采样秒数**记下来 —— 这三个参数会影响结果，**尤其分辨率**（它决定 GPU 是不是真的被压满）。

## 七、先说什么是「视锥剔除」

**视锥（frustum）= 相机能看到的那个截头金字塔形的空间。**

```
        相机
         /\
        /  \        ← 视锥：近平面到远平面之间
       /____\          这个范围里的东西才会出现在画面上
```

**视锥剔除（frustum culling）= 渲染前先判断「这个物体在不在视锥里」，不在就直接跳过，连提交都不提交。**

**three.js 默认对每个物体做这件事**：每帧遍历场景，拿每个物体的**包围体**（一个能装下它的球或盒子，用来做廉价的粗略判断）和视锥求交，**不相交就跳过**。

> **这是个非常划算的优化**：一次廉价的球体求交测试，就省掉了整个物体的顶点处理。
>
> **在这个游戏里尤其划算** —— 赛道很长，视野受雾限制大约六百个单位，**任何时刻绝大多数障碍物都在视野外**。

## 八、⭐ 实例化为什么会杀掉视锥剔除

**这就是那个取舍的核心。**

| | 场景里的对象数 | 剔除粒度 |
|---|---|---|
| **优化前**：N 个独立物体 | N 个 | ✅ **每个方块单独判断** —— 视野外的一个都不提交 |
| **优化后**：2 个实例化网格 | 2 个 | ⚠️ **整个区段共用一个包围体** —— 只要有一个实例在视野里，**整批全部提交** |

> ⭐ **关键：剔除是按「场景对象」做的，而实例化把 N 个对象合成了 1 个。**

**于是：**

```
一个区段里 80 个方块，玩家只看得到最前面 10 个
  优化前：剔掉 70 个，只提交 10 个的三角形
  优化后：包围体和视锥相交 → 80 个全部提交
```

**GPU 会为那 70 个不可见的实例跑完顶点着色器，然后在裁剪阶段把它们丢掉。工作做了，画面上什么都没多。**

**这就是提交的三角形涨 2.6 倍的原因。**

> ⭐ **注意 `submitted`（提交的）这个词用得很准** —— 涨的是**提交给 GPU 的三角形数**，**不是画面上多了三角形。画面完全一样。** 面试时要强调这一点，否则听起来像是画质变了。

**绝对数字**：**26,230 → 69,112**（69112 ÷ 26230 = 2.635，即 2.6×）。**报比值时要能一并报出绝对值** —— 被问「涨到多少」答不上来会显得只背了个倍数。

## 九、那为什么这笔交易还是划算

**这是必答题：绘制命令降了 41%，三角形涨了 160%，凭什么说这是优化？**

**答案在于两种成本的性质完全不同：**

| | 绘制命令 | 顶点处理 |
|---|---|---|
| **成本花在哪** | **CPU** —— 驱动状态校验、命令打包、提交 | **GPU** —— 顶点着色器，高度并行 |
| **能不能并行** | 基本串行，受驱动开销限制 | **极度并行**，几千个核同时算 |
| **成为瓶颈时的表现** | CPU 满、GPU 闲 | GPU 满、CPU 闲 |

**如果瓶颈在 CPU：**

- 少发 53 次绘制命令 = **直接省下 CPU 时间**
- 多提交 1.6 倍三角形 = **花的是 GPU 的富余产能**

> ⭐ **用一个瓶颈资源，换一个非瓶颈资源 —— 这就是这笔交易划算的全部理由。**

**而 第五节 里那条 `fps.p50 > 115` 的提示正好佐证了「GPU 有富余」**：四个场景的帧率都顶在合成器 120 的上限上，**测量脚本自己就说了「在这个分辨率下 GPU 还有余量」**。

## 十、⚠️ 但这个结论有前提，必须主动说

> **如果换个场景 —— 更高分辨率、更复杂的着色器、更重的后处理 —— GPU 变成瓶颈，这笔交易就反过来亏了。**
>
> **那时候正确的做法是「分块实例化」**：不是整个区段一个实例化网格，而是**按空间切成若干块，每块一个** —— **换回一部分剔除粒度**。

> ⭐ **能说出「什么情况下我这个优化是错的」，比说出它为什么对更有说服力。**

## 十一、实际帧率影响 —— 诚实答案

**在这次测量里看不出来，因为帧率饱和了。**

四个场景的帧率中位数都超过 115、顶在合成器约 120 的上限，**帧率区分不了它们**。

**所以正确的说法是：**

> 「这次测量没能显示帧率提升，**因为那个分辨率下四个场景都顶在合成器帧率上限**。要看到绘制命令下降转化成帧率，得把分辨率调高、把 GPU 压到成为瓶颈之前 —— 测量脚本里那条提示也建议了用更大的窗口重跑。」

> ⚠️ **别硬说帧率提升了。** 数据不支持，**而且测量脚本自己把这件事写在报告里了** —— 面试官只要打开代码就能看到那行提示。

## 十二、这条 bullet 最大的价值

```
draw calls down from 129 to 76        ← 收益
triangles submitted up 2.6×            ← 代价
one bounding volume per mesh being     ← 代价的机制
the price of losing per-instance
frustum culling
```

> ⭐ **面试官读到这一句会认真起来**，因为绝大多数简历只报收益。**一个把取舍的两边都量出来、还说清了机制的候选人，可信度和其他所有数字一起上升。**
>
> **讲的时候可以直接点出来**：「这条我特意把代价也写上了，因为只报绘制命令下降是不完整的 —— **它是用三角形数换来的。**」

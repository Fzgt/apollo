# 传输层：为什么是 WebSocket，断了会怎样

> ⚪ **速查**。被追问选型、断线、背压时翻这里。

## 一、先看清需求

```
浏览器 ──每 250ms 一块音频，持续几十分钟──→ Deepgram      上行，高频
浏览器 ←──识别结果，什么时候来不确定────── Deepgram      下行，高频
```

**两个方向都是持续的、高频的、时机不确定的。** 记住这一条，下面的排除就都是它推出来的。

## 二、三个方案的能力

| | 数据能往哪走 | 连接 | 谁能主动发 |
|---|---|---|---|
| **轮询** | 客户端问一次、服务端答一次 | **每次都是一条新的 HTTP 请求** | 只有客户端能发起 |
| **SSE**（Server-Sent Events） | **只能服务端 → 客户端** | 一条长连接 | 只有服务端 |
| **WebSocket** | **双向** | 一条长连接 | **两边随时都能发** |

> **SSE 是什么**：浏览器发一个普通 HTTP 请求，服务端**不关闭这个响应**，而是持续往里写数据。它是**单向**的 —— 客户端开了这条通道之后就只能听，不能往里说话。

## 三、逐个排除

**SSE 出局** —— 它**只能服务端往客户端推**。而这里**音频必须持续上行**。用 SSE 的话上行还得另开一条 HTTP 通道，**等于用两套机制维护一个逻辑上的单一数据流**。

**轮询出局** —— 两个理由：

1. **上行做不了流**：每 250 毫秒发一个 HTTP 请求，就是每秒 4 次完整的请求-响应往返。**每次都要带完整的 HTTP header（常常上 KB），而一块音频可能才几 KB** —— 协议开销和数据本身一个量级
2. **下行拿不到实时性**：识别结果什么时候出来是不确定的。轮询间隔短就是空转浪费，间隔长就是延迟 —— **而临时结果的全部价值恰恰在于「立刻」**

**WebSocket 留下** —— 一次握手（就是建立连接时的那次协商），之后两边随时发，**每条消息只有 2–14 字节的帧头**。对一条要跑几十分钟、每秒来回十几条消息的通道，这是唯一合理的选择。

## 四、那 WebRTC 呢（面试官很可能追这一句）

**因为实时音频的「标准答案」往往是 WebRTC。**

| | 为什么存在 |
|---|---|
| **WebRTC** | 为**人对人通话**优化：走 UDP、**允许丢包**换极低延迟、内建回声消除和抖动缓冲 |
| **WebSocket** | 把数据**可靠地**送到对端：走 TCP、不丢包、保证顺序 |

**这里选 WebSocket 是对的**：

- 目标是**转写**不是通话 —— **一个丢失的音频包 = 一段听不见的话 = 一段错的转写**。**可靠性优先于极致低延迟**
- 250 毫秒的延迟预算下，TCP 偶尔重传的代价完全可以接受
- Deepgram 的实时接口本身就是 WebSocket

## 五、连接的生命周期

```
connectToDeepgram()                        useDeepgram.ts:30
  ├── getApiKey()          现取一把临时凭证    :32
  ├── deepgram.listen.live()  ← 这里握手      :35
  ├── 监听 Open  → 状态改成「已连接」          :37
  └── 监听 Close → 状态改成「已断开」          :42
```

> ⭐ **一个有意的顺序**：`useAudioToText.ts:133-140` 里，**先确认 socket 打开了，才启动麦克风**。
>
> **反过来的话**，麦克风在连接建立之前就开始吐音频块，**那些块无处可发只能丢掉** —— 开头几百毫秒的话就丢了。

## 六、断了会怎样

```js
// useDeepgram.ts:42-45
newConnection.addListener(Close, () => {
  setConnectionState(SOCKET_STATES.closed);   // 就这一行
});
```

**就这些。** 状态改成「已断开」，然后：

1. 那个「连接是开着的吗」的判断不再成立，**所有事件监听被摘掉**
2. 保活心跳的定时器被清掉
3. **麦克风还在录，但音频已经没人接了，直接进虚空**

> ⚠️ **没有自动重连、没有重试、没有给用户的任何提示。** 用户得自己发现「怎么不出字了」然后手动点重启。

### 主动交代 + 给方案

> 「现在的行为是：连接关闭事件只把状态改掉，**没有自动重连**。面试中途网络抖一下，用户得自己点重启。**这是我会优先补的地方，因为面试场景断一次的代价很高** —— 用户可能过几十秒才发现屏幕不出字了。」

**该怎么补（四条）：**

| 做法 | 说明 |
|---|---|
| **指数退避重连** | 断开 → 等 1 秒重试 → 失败 → 等 2 秒 → 4 秒 → 8 秒 → 封顶 30 秒。**再加一点随机抖动**，避免很多客户端同时重连打爆服务端 |
| **重连要重新铸凭证** | 那把临时钥匙只有 60 秒有效期，**不能复用**（见 [② 60 秒临时凭证](/docs?section=beyz&item=n01-ephemeral-keys)） |
| **断开期间的音频怎么办** | 三选一：**丢掉**（转写出现空洞）/ **本地缓冲重连后补发**（要限制上限，否则断久了内存爆）/ **暂停录制并明确提示「连接中断」**。**面试场景第三个最诚实** —— 与其给一段有空洞的转写让用户以为面试官没说话，不如明说断了 |
| **区分「用户主动停」和「意外断开」** | 现在两者都走同一个关闭事件。要做重连就必须能分辨，**否则用户点了停止，代码还在勤勤恳恳地重连** |

### 顺带：重连之后转录会乱吗

**不会丢** —— 「已确认」那部分存在客户端的一个 ref 里，连接断了它还在，重连后新来的字接着往上拼。

⚠️ **但有个真实的坑**：如果断在**一句话说到一半**，那半句会留着，**和重连后的下半句拼成一句语义断裂的话**。

## 七、背压（backpressure）

**先定义**：背压指的是「**生产的速度超过了消费的速度，数据在中间堆积**」。

这条链路上，**生产者**是录音器（每秒 4 块音频），**消费者**是 WebSocket 发送。

```js
// useAudioToText.ts:111-113
if (e.data.size > 0) connection.send(e.data);   // 直接发，不检查缓冲区
```

**代码没有检查发送缓冲区** —— 浏览器的 WebSocket 有个 `bufferedAmount` 属性，表示「已经调用 send 但还没真正发出去的字节数」，这里没看它。

**为什么现在问题不大**：音频码率不高（每块几 KB）、频率很低（每秒 4 个）、正常网络下发送速度远快于生产速度。

⚠️ **什么时候会变成问题**：网络严重降级时缓冲区会涨，**而且这里有个恶性循环** —— 缓冲堆积 → 发出去的音频越来越滞后 → 识别结果延迟越来越大 → **屏幕上的字比实际说话慢好几秒**，用户会以为系统卡死了。

**正确做法：**

```js
if (ws.bufferedAmount < 阈值) {
  connection.send(e.data);
} else {
  // 丢掉最旧的一块，而不是排队
}
```

> ⭐ **对实时音频，丢掉旧数据比排队更好** —— 一段五秒前的音频现在才发过去，转写出来也已经没有价值了。**「实时系统里，过期的数据不如没有数据。」**

## 1. getDerivedStateFromProps

**What it is**: a class-only **static lifecycle method** that decides whether the newest props should update state.

```javascript
class MyComponent extends React.Component {
  static getDerivedStateFromProps(props, state) {
    if (props.value !== state.prevValue) {
      return { prevValue: props.value, displayValue: props.value * 2 };
    }
    return null; // no update
  }
}
```

**The things that matter**:

- It is static, so there is no `this` and no `this.setState`. You update state by returning an object, or return `null` for no update.
- **It runs on every render**, not only when props change — unlike `componentWillReceiveProps`, which only fired on prop changes.
- It replaces the unsafe `componentWillReceiveProps`, which concurrent mode could call unexpectedly more than once.

**Where it is used**: when state has to be force-synced to a particular prop — a list component that something outside can reset, for example.

**In practice**: rarely. ① Class components are already uncommon in new projects. ② Even at their peak, the React team said this API is seldom needed and wrote a post arguing against overusing it — most cases are better handled another way, such as forcing a remount with `key`. Know what it is, be ready for the interview question, and leave it there.

## 2. Concurrent mode

**The common misunderstanding**: it is not multithreading, and nothing runs simultaneously. The JS engine is still single-threaded.

**What it actually means**: the render phase (`beginWork` / `completeWork`) **can be paused, abandoned, or restarted at any time**, without the user ever seeing a half-finished frame. That is the opposite of the traditional synchronous mode, where once rendering starts it has to run to the end.

**An intuitive example**: typing in a search box.

- Without concurrent mode: if the render triggered by the first character is expensive, it **blocks** the page and the second keystroke is stuck behind it.
- With concurrent mode: on the second keystroke React **throws away** the unfinished work for the first, handles the higher-priority input first, and the box stays smooth.

**The APIs**: `useTransition` and `useDeferredValue`, which let you mark an update as non-urgent and interruptible.

```javascript
const [isPending, startTransition] = useTransition();
function handleChange(e) {
  setInputValue(e.target.value);         // high priority, update now
  startTransition(() => {
    setSearchResults(computeResults(e.target.value)); // low priority, interruptible
  });
}
```

## 3. "Jotai is fully concurrent-friendly" — a claim that needs qualifying

**The PDF's phrasing is misleading.** The truth is a trade-off between two technical routes, not "Jotai is good and the others are not".

**Background — tearing**: during concurrent rendering React may pause and hand control back to the browser. If a data source that lives *outside* React (a Redux store, a Zustand store, a global variable) happens to change during that pause, **different components in the same render read the source at different moments** and the screen shows information that contradicts itself.

**React's official answer**: `useSyncExternalStore`, introduced in React 18. Redux (react-redux v8+) and Zustand both use it, and both **avoid tearing** — so "only Jotai does not tear" is simply not accurate.

**The real comparison**:

| | Redux/Zustand (via useSyncExternalStore) | Jotai (via useState/useReducer) |
|---|---|---|
| Can it tear? | Never | Briefly, and it self-heals |
| Smoothness with `useTransition` | De-optimised; some concurrency is given up (Zustand plus `useTransition` cannot show the pending state) | Fully smooth; real concurrent rendering |

**Conclusion**: not black and white. It is "zero tearing" versus "fully smooth concurrency", and Jotai chose the second.

## 4. Portals

**What they solve**: they decouple a component's **logical position** (its parent-child relationship) from its **physical DOM position**. It stays a child logically — props, context, and event bubbling all behave normally — while its DOM can be rendered anywhere on the page.

**Where it matters**: when an ancestor has `overflow: hidden` or a CSS property that creates a new stacking context, a child modal or tooltip gets clipped or cannot sit above the page. Portalling it to `<body>` escapes those constraints.

```javascript
function Modal({ children }) {
  return ReactDOM.createPortal(children, document.body);
}
```

**How often you write one**: not very. But the modals, tooltips, and select dropdowns in the mainstream UI libraries (Ant Design, MUI) are built on portals internally; it is just wrapped away.

**The part most people miss**: the DOM moves, but **event bubbling still follows the React component tree, not the physical DOM** — because it goes through React's own synthetic event system.

## 5. What `react.d.ts` is

The TypeScript declaration file at `node_modules/@types/react/index.d.ts`.

**The key fact**: React does **not** maintain its own TypeScript types. They come from `DefinitelyTyped`, a community repository (`types/react/index.d.ts`) — a separate package, a different team, its own release cadence.

**What it is for**: when you hit a type error or are unsure how to type an API, this file is the authority — more reliable than any blog post. `Cmd`/`Ctrl`-click any React API name in VS Code jumps straight to it.

**Watch out**: because they are maintained separately, `react` and `@types/react` versions can drift. If something runs fine but TypeScript complains, or the reverse, suspect a version mismatch.

## 6. FID has been replaced by INP (since March 2024)

**Update**: on 12 March 2024 Google removed `FID` (First Input Delay) from Core Web Vitals and replaced it with `INP` (Interaction to Next Paint).

**Why**: FID only measured the delay on the user's **first** interaction. INP measures responsiveness across **every interaction in the page's lifetime**, taking the worst.

**How that relates to React's concurrency**: the reasoning in the PDF — that concurrent mode lets the main thread respond to input sooner — is correct, but:

1. It should say "improves INP", not FID. FID is retired, and INP's whole-session measurement matches concurrency's goals better.
2. "Brings it earlier" is the wrong phrasing. FID and INP are durations; the goal is a smaller number, not an earlier one.

# Notes on closures and the captured-value trap

## 1. The strict definition (from MDN)

> A closure is the combination of a function bundled together with references to its surrounding state (the lexical environment). **In JavaScript, closures are created every time a function is created, at function creation time.**

So: a closure is the function plus the scope it can reach, bundled together. **Creating a function creates a closure. There are no additional conditions.**

---

## 2. The "three conditions" people quote are not the definition — they describe when the effect becomes visible

The three conditions you usually hear:

1. Nested functions
2. The inner function references an outer variable
3. The inner function is returned or passed out (it escapes)

**These are not requirements for a closure to exist** — by MDN's definition, every function forms one. What they describe is when closures become *noticeable* and start causing real bugs. The third one matters most: if a closure is created and used on the spot, you never see that it captured an old value. Only when it is handed to some mechanism that **calls it later** does "it captured the old value" become observable.

---

## 3. Captured values — one specific symptom of closures

**Not a separate concept.** It is the informal name for the bug closures produce in the specific case of "escaping function plus reference to an outer variable".

```
closures (the mechanism)
    │
    └─ when the closure escapes (outlives the execution that created it)
              │
              └─ you observe captured values (it holds an old value and never updates)
```

### The classic example

```javascript
function Timer() {
  const [count, setCount] = useState(0);
  const handleClick = () => setCount(count + 1);

  useEffect(() => {
    const id = setInterval(() => {
      console.log(count); // always the value from the effect's first run; clicks never update it
    }, 1000);
    return () => clearInterval(id);
  }, []); // empty deps → this callback is created exactly once

  return (
    <div>
      <p>{count}</p>
      <button onClick={handleClick}>+1</button>
    </div>
  );
}
```

What you see: clicking the button really does change `count` on the page, but the `count` printed inside `setInterval` is stuck at the value from the moment the effect first ran.

### Which closure is the culprit

```javascript
useEffect(() => {                    // ① outer: the useEffect callback. Runs once and is done — no escape
  const id = setInterval(() => {
    console.log(count);              // ② inner: the real culprit — it references count, is held by setInterval, and runs repeatedly in the future
  }, 1000);
  return () => clearInterval(id);
}, []);
```

① is technically a closure too, but it finishes and is never called again, so nothing shows. ② is the one that satisfies both "references an outer variable" and "escapes", and it is what produces the captured-value problem.

> ① (the useEffect callback) and ② (the interval callback) are both closures, nested, sharing the same frozen lexical environment. That is fine in itself. Calling ② the culprit does not mean only ② is a closure — it means only ② gets called repeatedly in the future, which is what makes the inherent "captured an old value" property observable and turns it into a real bug. ① is a closure as well, but since it runs once and never again, you never get the chance to check whether the value it holds is stale, so it is not the one producing a visible bug.

---

## 4. The root cause is not "useEffect is asynchronous", it is the empty dependency array

- Whether `useEffect` is asynchronous or synchronous (`useLayoutEffect` is synchronous) **has nothing to do with captured values.** Swap `useEffect` for `useLayoutEffect` and the same bug appears.
- The real cause: **an empty dependency array `[]` means the effect creates its callback — its closure — once, on the first render.** However many times the component re-renders afterwards, and however many new `count` values there are, that callback never gets recreated.
- Think of it this way: each render builds a separate house (a variable environment) furnished with that render's own `count`. The effect callback was handed a key when it was born, and that key only opens the first house.

---

## 5. `setInterval` is not required — it is just the easiest demonstration

**What is actually required**: a gap in time between when the closure is created and when it is called, during which the outer variable changes.

Plenty of mechanisms create that gap:

- `setTimeout`
- Event listeners (`addEventListener` — `resize`, `scroll`)
- `Promise.then()` and async request callbacks
- `WebSocket.onmessage`

Code that runs synchronously and reads its value on the spot never has this problem: creation and invocation are the same moment, and the variable has no chance to change in between.

---

## 6. Fixing it with a ref

```javascript
function Timer() {
  const [count, setCount] = useState(0);
  const countRef = useRef(count);
  countRef.current = count; // kept in sync on every render

  useEffect(() => {
    const id = setInterval(() => {
      console.log(countRef.current); // read through the ref — always current
    }, 1000);
    return () => clearInterval(id);
  }, []);

  return <div>{count}</div>;
}
```

**Why it works**: `countRef` is a box (`{current: xxx}`), and there is exactly one of it for the component's whole life — it is never recreated. The interval callback is still the old closure, but what it captured is not the value, it is a reference to the box. The box's contents are refreshed on every render, so what you read through it is always current.

---

## The whole thing in one sentence

> Closures are a language mechanism and every function creates one. "Captured values" is the specific bug closures produce when a function escapes while referencing an outer variable. The root cause is an empty dependency array creating the closure only once, and it has nothing to do with whether the effect is synchronous. `setInterval` is just one of many ways to delay a call. The fix is a ref: a box whose contents are refreshed every render but whose reference never changes, so the closure can reach the latest value through it.

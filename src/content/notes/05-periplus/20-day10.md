# Day 10 · Periplus ③ 持久化与 resume + ④ scripted seam

> **详解**：[必看 · 持久化与 resume](/docs?section=periplus&item=d10-resume)

## 🔴 今天必看

⚠️ **④ scripted seam 那半边 Day 1 已经学透**：[#14](/docs?section=numbers&item=n14-server-tests)（四个 seam、三种注入手法、为什么注入时钟）· [#15](/docs?section=numbers&item=n15-end-to-end)。**今天只补 ③ 持久化与 resume。**

**六个核心点：**

| # | 要点 |
|---|---|
| 1 | ⭐ **replay 边界必须是「过了 gate 的产物」**——失败的产物也留着（供排查），**但它永远不是合法的续跑边界** |
| 2 | ⭐ **预算续跑时不重置，而是把已花掉的量带进来**——否则「反复让它崩」就成了绕过配额的手段 |
| 3 | 预算检查在**阶段之间**做，**从不打断正在飞的阶段**——只能让它不算通过、或不让下一次开始 |
| 4 | ⭐ **一个 gate 都没过就死掉的 run 不重跑，标成 FAILED**——重跑会「让这次尝试凭空消失」，而那正是排查要用的 |
| 5 | ⚠️ **resume 逻辑不在 orchestrator 里，在 API 层的 `RunStore`**——Hermes 只管「在给定起点上跑」，答错位置很难看 |
| 6 | 崩溃**可能落在阶段中途**，所以续跑前要**填充占位历史**，让 attempt 计数器不撞上产物库里已有的编号 |

> 第 2 点和第 4 点最能体现深度——一个是「这机制会怎么被滥用」，一个是「无从恢复和重新开始是两回事」。

## Two completely different kinds of "pause" in React

| | Interruptible render phase | Commit-phase pause (View Transitions) |
|---|---|---|
| Why it stops | Pre-empted by higher-priority work | Waiting for the browser to finish a transition animation |
| What stops | Building the work-in-progress tree (`beginWork` / `completeWork`) | Wall-clock time after the real DOM operations are done |
| Purpose | Keep interaction responsive | Work with the browser's View Transition API for smooth animation |
| Core mechanism? | Yes — Fiber has had this since the beginning | No — added in a recent version to support view transitions |

**The rule has not changed**: the DOM operations themselves — the actual commit to the page — still cannot be interrupted arbitrarily. Getting interrupted halfway would show the user a half-finished screen, which is never acceptable. What is new is only "once the DOM is updated, we can wait out an animation before continuing".

---

## 1. What the reconciler is

**In one sentence**: it decides whether anything needs to change and where, but it does not touch the DOM.

Every update — `setState`, `ReactDOM.render` — has to answer: the UI looked like this, the data has changed, what should it look like now, and what actually needs to move?

The reconciler answers that question. It compares the old and new trees, finds the differences, and tags the places that need to change (insert, delete, update props). It does not touch the real DOM itself; it draws the blueprint.

<img width="350" height="200" alt="Image" src="https://github.com/user-attachments/assets/1e7bcd19-ad72-4cbe-bc9e-f843af827d36" />

> On *finding* which components changed, Vue is faster: its reactivity targets a specific component, so it can just collect the updates into a queue. React has to walk down from the fiber root to see what changed.

> That is why Vue and React look similar at first and diverge later: React invests in runtime optimisation, Vue in compile-time optimisation plus runtime.

## 2. Double buffering

<img width="230" height="260" alt="Image" src="https://github.com/user-attachments/assets/d795ad87-e80c-42a9-afc6-19100f6114df" />

**In one sentence**: always keep one verified tree on screen, build the new one separately, and switch across in a single step so the user never sees a construction site.

- **The current tree**: what is on screen now. Stable, untouched.
- **The work-in-progress tree**: the new tree being built in memory. Building it can be interrupted — that is the interruptible render phase above.
- Once it is built and verified, the `current` pointer flips to the new tree in one instant. There is no intermediate state.

**Reuse**: the new tree is not built from nothing. **Nodes whose data has not changed are borrowed from the old tree**, which saves memory and computation. That is why it is called reuse, not rebuild.

**An analogy**: an offscreen canvas. You do not draw on the visible canvas; you draw a full frame where nobody can see it and swap it in at once, so nobody sees a half-drawn image. React adds two things: ① construction can be interrupted (an offscreen canvas generally cannot); ② unchanged nodes are reused piecemeal (an offscreen canvas usually redraws everything).

## 3. Building the fiber tree (the render phase)

**In one sentence**: walk down from the root deciding whether and how each node changes, then walk back up collecting the results.

Two directions of traversal:

- **Downwards (`beginWork`)**: from the root, level by level into the children. At each node, decide whether it changed since last time and what should be done about it, work out how its children should be handled, and keep going deeper.
- **Upwards (`completeWork`)**: at the bottom, with no children left, start returning. Each node's "what has to happen" tag is rolled up level by level to the root, producing one complete list of the DOM operations this update needs.

Together, those two directions are how a work-in-progress tree gets built from nothing.

## 3b. The two `workLoop`s of the render phase — "interruptible" is not "will be interrupted"

**Why Fiber can be interrupted at all**: the traversal is a **loop, not recursion**, and the progress marker lives on a module-level variable, `workInProgress` — so it can stop and it can resume. A recursive call stack cannot be stopped, which is exactly why the Stack Reconciler was replaced. (Asked "why can Fiber be interrupted?", answering "because it's a linked list" is only half of it.)

But *being capable of interruption* and *this particular render actually being interrupted* are two different things, and the lane decides:

```js
// react-reconciler/src/ReactFiberWorkLoop.js
// We disable time-slicing in some cases: if the work has been CPU-bound
// for too long ("expired" work, to prevent starvation), or we're in
// sync-updates-by-default mode.
const shouldTimeSlice =
  (!forceSync &&
    !includesBlockingLane(lanes) &&
    !includesExpiredLane(root, lanes)) ||
  checkIfRootIsPrerendering(root, lanes);

const exitStatus = shouldTimeSlice
  ? renderRootConcurrent(root, lanes)   // → concurrent loop, shouldYield() checked per fiber
  : renderRootSync(root, lanes, true);  // → workLoopSync, rendered in one go
```

```js
// react-reconciler/src/ReactFiberLane.js
export function includesBlockingLane(lanes) {
  const SyncDefaultLanes =
    SyncHydrationLane | SyncLane |
    InputContinuousHydrationLane | InputContinuousLane |
    DefaultHydrationLane | DefaultLane | GestureLane;
  return (lanes & SyncDefaultLanes) !== NoLanes;
}
```

**`DefaultLane` is on the blocking list** — `setState` inside `setTimeout`, inside `.then()`, or outside any React context is that lane; all of it takes `workLoopSync`, and that loop condition has no `shouldYield()` in it. `setState` from a click or a keystroke sits even further up: those discrete events get `SyncLane`, are flushed synchronously in a microtask, and never enter the Scheduler at all (`getEventPriority` returns `DiscreteEventPriority` for `click` / `keydown` / `input`). The comment in the source, `sync-updates-by-default mode`, means exactly what it says.

**Only two lanes actually take the concurrent loop:**

| Lane | Where it comes from |
|---|---|
| `TransitionLane` | `startTransition` / `useDeferredValue`; also what Next.js App Router navigations and React Router 6.4+ navigations wrap internally |
| `RetryLane` | The re-render after Suspense data arrives |

**There is also starvation protection**: when a transition is repeatedly interrupted by higher-priority updates and passes its deadline, `includesExpiredLane` matches, React stops being polite and forces it through `workLoopSync`. So even "transitions always take the concurrent loop" is not absolute.

### While we are here: concurrent rendering ≠ time slicing

Concurrent rendering means **different versions of the UI can exist on screen and in memory at the same time, with their progress interleaved** — on a single thread, hence concurrent, not parallel.

There are two reasons a render might stop:

- **It has held the CPU too long** → time slicing, yield the main thread
- **The data has not arrived** → Suspense suspends; the new tree stays in memory uncommitted while the screen keeps showing the old version

The second involves no slicing whatsoever and still produces "paused, with two versions coexisting". So **time slicing is one implementation of concurrent rendering, not the thing itself**.

Three further things come for free from the concurrent architecture without writing a single transition: automatic batching (from 18, multiple `setState` calls inside `setTimeout` / `.then()` are merged too), Suspense streaming SSR with selective hydration, and `useSyncExternalStore` tearing protection — which external store libraries must use unconditionally, since a library cannot know whether its caller will wrap things in a transition.

### Version history

The 2019 design was called **Concurrent Mode**: turn on `createRoot` and the entire application became interruptible by default. That direction was abandoned in 2021, and what shipped in React 18 was **concurrent features** — the architecture is on by default, slicing is enabled per lane. Most Chinese-language write-ups stopped at the earlier version, which is where "the diff can be interrupted at any time" comes from.

## 4. The React diff algorithm

**In one sentence**: skip the exhaustive comparison — too slow — and take shortcuts based on a few assumptions, trading a little space (extra tags) for time.

Three core assumptions:

1. **Only compare nodes at the same level.** It never compares A's child against B's grandchild. Cross-level comparison is abandoned outright, which cuts out an enormous amount of pointless work.
2. **If the node type changed, do not try to reuse — delete and rebuild.** A `<div>` becoming a `<span>` is treated as a completely different thing; no guessing about a relationship.
3. **Use `key` to recognise "is this still the same thing".** Especially in lists. Without a key, position is all you have to go on, and it gets it wrong — reorder a list and every item looks changed when it only moved. With a key, React can tell "this moved, its content did not" and reuse it.

Those assumptions trade the theoretically optimal result for something fast enough in almost every real situation — which is why it is called reconciliation, not a perfect diff.

## Tying it together

> The reconciler draws the blueprint (does anything change, and where). Double buffering keeps the construction hidden from the user. Building the fiber tree is how the blueprint gets drawn, step by step — **decide on the way down, collect on the way up**. And the diff algorithm is the set of shortcuts used while drawing it, to decide quickly whether a given piece needs touching.

## getSnapshotBeforeUpdate and componentDidUpdate

The last chance to read information from the old DOM before it is replaced, and hand it to `componentDidUpdate`.

> By the time `getSnapshotBeforeUpdate` runs, what this update will produce is already fixed. The render phase (`beginWork` / `completeWork`) has finished, the work-in-progress tree is built, and every tag has been applied. Nothing you do in this function can change what is about to be committed.

```js
getSnapshotBeforeUpdate(prevProps, prevState) {
  // the DOM is still "old" here — the new message has not been inserted yet
  // so record how far the scrollbar is from the bottom, right now
  const list = this.listRef.current;
  return list.scrollHeight - list.scrollTop;
}

componentDidUpdate(prevProps, prevState, snapshot) {
  // the DOM is "new" now — the message is in
  // use the snapshot to restore the same relative scroll position
  const list = this.listRef.current;
  list.scrollTop = list.scrollHeight - snapshot;
}
```

Without that last glance, `scrollHeight` changes the instant the new message enters the DOM and the pre-insert scroll position is gone forever. That is the whole point of it: grab data that is about to disappear, at the exact moment before the old DOM is replaced.

## The commit phase

> The commit phase renders the changed components to the page, in three parts.

### commitBeforeMutationEffects (before any DOM operation)

1. Call `getSnapshotBeforeUpdate` — read information from the old DOM before it disappears
2. Schedule `useEffect` (asynchronous and non-blocking — this only books it; it runs later)

### commitMutationEffects (the DOM operations)

1. Walk `finishedWork` and perform the DOM operations (insert, delete, update)
2. ★ point `current` at the work-in-progress tree ★
   (this is exactly where it sits: the DOM is updated, but the layout-phase lifecycle has not run yet)

### commitLayoutEffects (after the DOM operations; formerly `recursivelyCommitLayoutEffects`)

1. Run `componentDidMount` / `componentDidUpdate`
2. Run `useLayoutEffect` — the genuine last chance to touch the DOM before the page is painted
3. Assign refs
   (`current` has already switched, so refs here point at the new DOM)

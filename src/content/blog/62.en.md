title: 'A Front-End Performance Toolchain: Lighthouse, web-vitals, Flame Charts, React Profiler, Coverage'
---

> Five panels, five different questions: is there a problem, which layer is slow, which line of code. Mix them up and you reach for the wrong tool and look in the wrong direction.
>
> Every screenshot is from the Chrome DevTools / React DevTools docs, except the Lighthouse one — that is a real run against this site.

The order matters, and each section below is one step:

| Step | Tool | The question it answers |
| --- | --- | --- |
| 1 | Lighthouse | Is there a problem, and roughly what kind |
| 2 | web-vitals / Live metrics | Are real users seeing it too |
| 3 | Performance flame chart | Which call stack is eating the main thread |
| 4 | Long-task markers | Which stretch is blocking interaction |
| 5 | Layout shifts track | Which element is jumping |
| 6 | React Profiler | Which component renders too often, or too long |
| 7 | Coverage | How much code was downloaded but never ran |

Doing it in reverse is the most common way to waste a day: wrapping components in `memo` one by one before anyone has confirmed there is a problem.

---

## 1. Lighthouse — a check-up, not a diagnosis

One run gives you four category scores and a list of concrete suggestions. Its value is in **pointing a direction**, not in reaching a conclusion — what it measures is one simulated load, not your users.

![Lighthouse report](https://raw.githubusercontent.com/Fzgt/Blog/main/assets/perf-tools/05-lighthouse-apollo.png)

This is a real run against this site (apollo), 2026-09-05, mobile with simulated throttling:

- Performance **75**, Accessibility 98, Best Practices 100, SEO 66
- LCP **6.8 s** (red), FCP 2.1 s, Speed Index 2.1 s
- CLS **0.001**, TBT **30 ms** (both excellent)
- Top suggestion: render-blocking resources, est. saving **470 ms**

Those numbers are themselves the lesson. CLS and TBT are near perfect, which says **runtime is fine and the layout does not jump** — the whole problem is a handful of render-blocking resources on first load. Look only at "75" without the breakdown and it is easy to dive straight into component optimisation, which is the wrong direction entirely.

One thing that trips people up: Lighthouse scores against **a mobile device on a slow network** by default. Your site opening instantly on a MacBook and Lighthouse giving it a 75 are both true — they are simply not answering the same question.

## 2. `web-vitals` and Live metrics — the number from real users

The `web-vitals` npm package has no UI. All it does is collect LCP / INP / CLS in real users' browsers and hand them to you to report:

```js
import { onLCP, onINP, onCLS } from 'web-vitals';

onLCP(send);
onINP(send);
onCLS(send);

function send(metric) {
  navigator.sendBeacon('/analytics', JSON.stringify(metric));
}
```

The clearest picture of what that data looks like is the DevTools **Live metrics** panel — your local run on the left, the 75th percentile of real users on the right:

![Live metrics panel](https://raw.githubusercontent.com/Fzgt/Blog/main/assets/perf-tools/06-live-metrics.png)

These are web.dev's own numbers (collection period 2025-10-22 to 2025-11-18):

- LCP: local **0.47 s**, real users at p75 **3.26 s**
- INP: local **48 ms**, real users **304 ms**
- CLS: zero on both sides

Nearly seven times apart. **This chart is the entire origin of "works fine on my machine"** — your hardware and your network are not in your users' distribution. So what you watch in production is the percentile from field data; the local number is only for locating the cause.

Worth keeping straight what each metric covers: LCP is how long the largest above-the-fold content takes to appear, INP is the delay from an interaction to the next painted frame (it replaced FID), CLS is layout jumping around.

## 3. Performance flame chart — where the main thread went

Time on the x-axis, call depth on the y-axis: the function above called the function below, and the wider the bar the longer it took.

![Performance flame chart](https://raw.githubusercontent.com/Fzgt/Blog/main/assets/perf-tools/02-flame-chart.png)

Here a single `Event: click` has a dozen frames stacked under it — `Function Call → onEndpointClick_ → handleClick_ → dispatchEvent → resolveCommand …`. There are only two rules for reading it:

1. **Look for the widest bar, not the deepest one.** Depth only tells you the call chain is long; width is time.
2. Once you have the widest bar, look at the **layer below it**, and keep going down until no single child dominates the width. That is the function actually spending the time.

Three tabs — Summary / Bottom-Up / Call Tree. Use the flame chart to trace one specific call; use Bottom-Up to ask "across this whole recording, which function was most expensive in total".

## 4. Long tasks — the direct cause of janky interactions

In the same panel, a Task bar with **a red corner and red stripes** is a long task. Select it and the Summary spells it out:

![Long task marker](https://raw.githubusercontent.com/Fzgt/Blog/main/assets/perf-tools/03-long-task.png)

> Warning: Long task took **400.84 ms**.

The definition is **any main-thread task over 50 ms**. For those 400 ms JavaScript owns the main thread and a click does nothing at all — the click event sits in the queue until the task finishes. That is where the overwhelming majority of bad INP comes from.

Note the `Self Time` in the screenshot: **77 μs**. The task itself does almost nothing; all 400 ms is in its children (Evaluate Script / Compile Script). So do not stop at this level when you see a long task — drill down.

The fix is to break it up rather than speed it up: split one long task into several short ones (`scheduler.yield()`, yielding via `setTimeout`, or moving the work to a Web Worker) so the browser gets a chance to respond to input in between.

## 5. Layout shifts track — which element is jumping

The hard part about CLS is that it is over the moment it happens, which makes it almost impossible to catch by eye. The Performance panel has a dedicated `Layout shifts` track where every purple diamond is one shift:

![Layout shifts track](https://raw.githubusercontent.com/Fzgt/Blog/main/assets/perf-tools/04-layout-shifts.png)

Hover or select one and the Summary gives you three things:

- Start time: 344 ms
- Shift score: 0.0268
- **Elements shifted: `mat-sidenav-content.mat-drawer-conte…`**

The third is the one that matters — it names the DOM element that moved, so there is nothing to guess. It also shows the parent cluster (`@ 311.01 ms`), because CLS is scored by grouping shifts into 500 ms windows; the score of a single shift on its own means nothing.

The usual causes are a short list: images and videos without width and height, font swapping (FOUT), an ad or banner injected at the top, async content inserted above existing content.

## 6. React DevTools Profiler — which component renders too much

Everything above is the browser's point of view, and the browser cannot see components. The Profiler fills in that layer: record an interaction and it slices the recording by **commit**, one flame chart per commit.

![React Profiler](https://raw.githubusercontent.com/Fzgt/Blog/main/assets/perf-tools/08-react-profiler-flame.png)

This is commit 4 of 12, render duration **18.4 ms** on the right. Each bar on the left is a component and how long it took this time: `Router (18.4ms)`, `Nav (8.4ms)`, `Route (7.9ms)`, `SubMenu (5.1ms)`. Grey means it did not re-render.

The genuinely useful parts are the Ranked view and the render count: **a component that rendered ten times during one interaction** is almost always a context or a prop whose reference changes every time. In the browser's flame chart that problem shows up as a pile of identical `Function Call` frames with no way to tell which component they belong to.

(This screenshot is from the docs, so the UI is a little older than the current version; the layout and how you read it have not changed.)

## 7. Coverage — code that was downloaded but never ran

It lives in the drawer at the bottom of the Sources panel. Record a session and it lists, per file, how many bytes were downloaded and how many of them never executed — green is executed, grey is not.

![Coverage panel](https://raw.githubusercontent.com/Fzgt/Blog/main/assets/perf-tools/07-coverage.png)

This is google.com's home page: **2.8 MB of 5.1 MB (56%) used so far, 2.3 MB unused**. The per-file column is more telling — the second row has **72.9%** of its 526 KB unexecuted.

### Those two buttons are not "pause / play"

The red dot and the reload arrow in the top-left are **two ways to start**, not a pause-and-resume pair:

| Button | What it does |
|---|---|
| ● Red dot (record) | Starts recording **from the current state**, **without reloading** |
| ⟳ Reload arrow | Reloads the page and records — this is the only one that refreshes |

Which one you press after stopping depends on whether you want to start over from a fresh load.

### It is byte-level, not file-level

"I don't use this vendor bundle" is not something Coverage can tell you. What it says is **"26% of the bytes in `vendor-react.js` never executed"**, not "you don't use this file" — **a file that was never downloaded and executed at all does not appear in the list in the first place**.

So its real use is **finding a large block of code inside a file that is not needed for the first screen**. If `vendor-framer-motion` is 46% unused, that may mean half the animation library is irrelevant to this page — which is not a reason to delete it, only a hint that it may belong behind a lazy import.

### The recording window decides the result, so measure twice

What it reports is coverage **for this one session**, not dead code. A dialog you never opened and a route you never visited obviously did not run. The reverse holds too: click through every feature after hitting record and the unused percentage drops a long way.

So the standard approach is two separate runs:

| How to record | What that data is for |
|---|---|
| **First screen only**: start with reload, stop the moment the page has loaded | Finding **code-splitting** opportunities — big modules off the critical path go behind `import()` |
| **Full sweep**: with recording on, walk through the main features | Whatever is *still* 100% unused here is a real **dead code** candidate |

Running only the first and concluding "this code is unused" is mistaking "not reached on first load" for "never reached".

---

## In one paragraph

Use Lighthouse and field data first to establish **whether there is a problem and whether it is loading or interaction**. Slow loading points at Coverage and render-blocking resources; janky interaction points at long tasks and the flame chart; a React app then goes one layer deeper with the Profiler. Skip that first step and you are probably optimising a problem that does not exist.

# ① 虚拟列表信息流

> **简历原句**
>
> Built a **virtualized React feed** serving **5M+ daily page views** on a custom **useVirtualList** hook over **IntersectionObserver**: **live DOM nodes stay near 100 at any scroll depth**, scroll **from 30 to a stable 60 FPS**.
>
> ---
>
> 基于自研 useVirtualList hook（底层用 IntersectionObserver）实现承载日均 500 万+ PV 的 React 虚拟列表信息流：任意滚动深度下存活 DOM 节点都稳定在 100 上下，滚动帧率从 30 回到稳定 60。

## 这条 bullet 在讲什么

**一句话：无限滚动的信息流，DOM 会一直涨，涨到几百个节点就掉帧。**

⭐ **但这条 bullet 真正的价值不在「我做了个虚拟列表」——那是个有现成库的东西。它在于三个数字每一个的口径你都说得清：5M PV 不是你的成果是你的环境，100 个节点是你自己量的，60 FPS 是三项优化叠出来的。**

**三个数字性质完全不同，混着讲会被问穿：**

| 数字 | 性质 | 谁测的 |
|---|---|---|
| **5M+ daily PV** | **规模背书** | 埋点系统，**你只是读报表** |
| **DOM 节点 ~100** | **优化成果** | **你自己**用 DevTools 量的 |
| **30 → 60 FPS** | **优化成果** | **你自己**用 DevTools 量的 |

## 30 秒口播稿

> 这是个信息流页面，日均五百万 PV 量级。**问题是无限滚动会让 DOM 一直涨** —— 用户滚十屏就是两百多条，滚久了五百条以上，滚动直接掉到三十帧。
>
> 关键认知是：**用户在视口里同时能看到的其实就十来条，其余的「假装存在」就够了**。所以我写了个 `useVirtualList`，只渲染可视区加上下各几条缓冲，外层用一个撑满总高度的容器保住滚动条，每一条用 `transform: translateY` 定位。
>
> ⭐ **真正的收益不是「少了多少个节点」，是复杂度的量级变了** —— 优化前 DOM 数随已加载条数增长，是 O(n)；优化后只随视口高度增长，跟数据量无关，**用户滚一万条 DOM 里还是那二十来个**。滚动回到稳定 60 帧。

## 一、⭐ 先讲通「为什么节点多了会卡」

**浏览器每渲染一帧要走五步** —— 这条流水线是所有前端性能问题的地基：

| 步骤 | 干什么 | 成本随什么涨 |
|---|---|---|
| **JS** | 跑你的代码，改 DOM | 代码量 |
| **Style** | 算每个节点最终应用哪些 CSS 规则 | ⭐ **节点数** |
| **Layout**（重排 / reflow） | 算每个节点的**位置和尺寸** | ⭐ **节点数**（最贵的一步） |
| **Paint**（重绘 / repaint） | 把每个节点画成像素 | 像素面积 |
| **Composite**（合成 / compositing） | 把画好的图层拼起来交给 GPU | 图层数 |

**「重排」（reflow）= 重新计算所有节点的几何位置。** 它贵，是因为⭐ **一个节点的位置会影响它后面所有节点的位置**，所以成本随节点总数线性涨。

⭐ **这就是 500 个节点会掉帧的原因**：不是「节点占内存」，是**每一帧的 Layout 都要把这 500 个都算一遍**。

## 二、⭐ 为什么恰好掉到「30」（这个数不是随手写的）

**讲出来会显著提高可信度。**

显示器按固定节奏刷新（vsync，60Hz 就是每 16.67ms 一次）。浏览器必须**赶在下一次 vsync 之前**把这一帧交出去。

⭐ **一旦某帧超时，它不会「晚一点点交」，而是直接等下一个 vsync。** 于是实际帧间隔从 16.67ms 跳到 **33.3ms** —— 正好是 **30 FPS**。

```
每帧耗时 < 16.67ms          → 60 FPS
每帧耗时 16.67 ~ 33.3ms     → 掉到 30 FPS（不是 45，也不是 50）
每帧耗时 33.3 ~ 50ms        → 掉到 20 FPS
```

⭐ **所以「30 FPS」是 60 的谐波，是掉帧时的典型稳态值。** 它说明当时每帧耗时落在 16.67–33.3ms 之间 —— 超了预算，但没超太多。

**这也顺带回答了「为什么优化后正好回到 60」：把每帧压回 16.67ms 以内就自动回到 60，中间没有过渡态。**

> **60 FPS = 每帧 16.67ms 的预算，而浏览器自己要用掉一部分，真正留给你 JS 的大概只有 10ms。**

## 三、虚拟列表的两个结构（spacer 是题眼）

**天真的想法「只渲染可见的十条」有个直接问题：滚动条会消失** —— 页面里只有十条的高度，浏览器认为内容就那么高。

**所以要拆成两层：**

```
外层容器（撑满总高度：总条数 × 每条高度）  ← ⭐ 只为骗住滚动条，叫 spacer
  └── 内层每一条（position: absolute + transform: translateY(该条的偏移量)）
```

⭐ **外层负责「假装有一万条那么高」，内层负责「只画看得见的那十条」。**

### 为什么用 `transform` 而不是 `top`（必背）

| 改什么 | 触发哪几步 |
|---|---|
| `top` / `left` / `width` / `height` | ⚠️ **Layout → Paint → Composite**（全走一遍，最贵） |
| `background-color` / `box-shadow` | Paint → Composite |
| ⭐ `transform` / `opacity` | **只走 Composite**（GPU 直接搬图层，CPU 几乎不参与） |

**原因**：改 `top` 是在改「这个元素在文档流里的位置」，**会影响别人** → 必须重排。⭐ **改 `transform` 是在「把已经画好的那张图搬个位置」，文档流里它没动过** → 不影响任何人，浏览器可以直接交给 GPU 平移。

## 四、「~100」是算出来的，不是拍脑袋

**渲染多少条是一个确定的公式：**

```
渲染条数 = ceil(视口高度 / item 高度) + overscan × 2 + 1
```

代入移动端典型值（视口 600、item 高 80、overscan 3）：`ceil(600/80) = 8`，`8 + 3×2 + 1 = 15` —— **十四五行**。

⭐ **注意这是行数，不是节点数。** 再乘以每张卡的节点数才是简历上那个 100：一张 feed 卡片（外层 div + 图容器 + `img` + 时长角标 + 右栏 + 标题 + 底栏 + 作者 + 播放量）**八九个元素起**，`14 × 8 ≈ 110`。

### overscan 是个取舍，不是越小越好

`overscan`（**缓冲区**，也叫 overscan）是在可视区上下**多渲染**几条作为缓冲：

| overscan | DOM 数 | 快速滚动时 |
|---|---|---|
| 小（0–1） | 更少 | ⚠️ **白闪** —— 新条目还没挂载，用户先看到空白 |
| 大（5–10） | 更多 | 平滑，但 DOM 和内存回去了 |

⭐ **所以「一百上下」这个数本身就是这个取舍的产物。** 被问「为什么不把 overscan 调到 0 让节点更少」，答案就是白闪。

## 五、这三个数怎么测（这一节是重点）

### DOM 节点数

| 方法 | 说明 |
|---|---|
| `document.querySelectorAll('*').length` | 最快但最糙 —— **数的是整页**，还**只含 Element 不含文本节点** |
| `document.querySelector('#feed-list').children.length` | 只数列表容器里的项，**准** |
| ⭐ **DevTools → Performance Monitor** | 有一条实时曲线就叫 **DOM Nodes**。**一边滚一边看那条线：优化前单调上升，优化后一条平线** |
| Memory 面板 heap snapshot | 验证**回收有没有泄漏** —— 搜 `Detached` 看滚过去的条目有没有真被移除 |

⭐ **「一条平的曲线」比任何数字都直观。要给面试官现场演示就用 Performance Monitor。**

> ⚠️ **两个工具口径不一样，报数前必须说清**：`querySelectorAll('*')` **只数 Element**；DevTools 的 `DOM Nodes` **数所有 Node，含文本节点和注释**。**同一个页面这两种量法能差近一倍。** 简历上那个 100 是**列表容器内的 Element 计数**。

### FPS

| 工具 | 用途 |
|---|---|
| **Rendering → Frame Rendering Stats** | 页面左上角实时浮层，**三十秒就能做完的定性验证** |
| ⭐ **Performance 面板录制** | **最有说服力的证据** —— 顶部 FPS 条带（红色=掉帧）、Frames 轨道（每帧实际时长）、Main 轨道（掉帧那几帧主线程在干什么） |
| **Performance Monitor** | `CPU usage` / `Layouts per sec` / `Style recalcs per sec` —— **直接证明是布局阶段被打爆了** |
| `requestAnimationFrame` 自己数帧 | 能在**真机真实环境**下跑。⚠️ **但它自己也在主线程上，主线程被打爆时它也被推迟，所以重负载下这个数偏乐观** |
| `PerformanceObserver` 监听 long task | **单个任务占用主线程超过 50ms 就是 long task，一个就意味着连掉 3 帧**。这个视角比 FPS 更有用 —— **它直接指出是哪段代码卡住了** |

⭐ **DOM 节点数、Layout 耗时、帧率应该出现在同一段 Performance 录制里 —— 那才是完整的因果链条，而不是三个孤立数字。**

### ⚠️ FPS 必须交代设备和场景，否则这个数没有意义

| 要交代 | 为什么 |
|---|---|
| ⭐ **在什么机器上测的** | 同一个页面旗舰机稳 60、千元机连 30 都够呛。**如果用了 DevTools 的 CPU throttling（4x/6x slowdown）模拟低端机，一定要说** —— 这是 lab 里的标准手段，说出来直接加分 |
| **匀速慢滚还是快速甩动** | **快速滚动才是压力测试**，慢滚可能根本不掉帧 |
| ⭐ **滚到第几屏时测的** | **优化前那个 30 FPS 一定是列表已经累积到几百条之后测的** —— 刚打开只有二三十条，全量渲染也不卡 |

### ⭐ `stable` 这个词怎么撑住

`a stable 60 FPS` 是**比「60 FPS」更强的声明**，它承诺没有波动。而 ⭐ **FPS 是个不能简单取平均的指标**：

| | 用户感知 |
|---|---|
| 稳定在 30 | 有点钝，但**均匀** |
| 在 10 和 60 之间反复跳，平均 30 | ⚠️ **明显卡顿** |

⭐ **用户感知到的「卡」来自帧时间的方差，不是平均帧率。** 所以现代性能工作看的是**帧时长分位数（p95/p99）、long task 数量、掉帧数**，线上看 **INP**。

> ⭐ **答法**：「stable 的意思是滚动过程中 Performance 录制里没有出现红色掉帧标记、Frames 轨道里没有超过 16.67ms 的长帧 —— **不是指平均值到了 60**。」**把 `stable` 定义成「没有长帧」而不是「平均值高」，既准确又显得专业。**

## 六、⭐ 量化归因：具体是哪几步让帧率上去的

**这是这条 bullet 最硬的部分 —— 每条都能在 DevTools 里找到对应证据：**

| # | 做了什么 | 为什么快了 | 在 DevTools 里看哪 |
|---|---|---|---|
| 1 | **DOM 五百多 → 恒定一百上下** | Layout 时间从 ~10ms 降到 ~0.5ms | Performance Monitor 的 `Layouts/sec` |
| 2 | **`transform` 替代 `top`** | 只走 Composite，GPU 做，主线程无压力 | 录制里 Paint 事件明显减少 |
| 3 | **scroll 加 `passive: true`** | 告诉浏览器「我不会 `preventDefault()`」，**浏览器可以立即开始滚动而不等 JS 跑完** | 录制里 scroll handler 不再阻塞合成 |
| 4 | ⭐ **IntersectionObserver 替代 scroll + `getBoundingClientRect()`** | 后者每次滚动都**强制同步布局** | ⭐ **DevTools 会直接标出来** —— Main 轨道黄色三角 + `Forced reflow is a likely performance bottleneck` |

**第 4 条值得单独讲**：⭐ **「强制同步布局」（forced synchronous layout，也叫 layout thrashing）是指你在 JS 里读一个几何属性（比如 `getBoundingClientRect()`），浏览器为了给你准确答案，被迫立刻把 Layout 同步跑一遍。** `IntersectionObserver` 由浏览器在自己的时机异步算好再通知你，**绕开了这一步**。

⭐ **而且那个警告不是你推断出来的，是浏览器自己报的** —— 「优化前 DevTools 一直在报 forced reflow，改用 IntersectionObserver 之后警告消失了」，这是能拿出来的具体证据。

## 七、5M PV：它是环境，不是成果

⭐ **这个数字不是你的成果，是你的工作环境。** 同样一个虚拟列表，写在个人博客上和写在日均 500 万 PV 的信息流上，工程含义完全不一样。

**简历里 `serving` 这个词用对了** —— 它描述的是「承载」，不声称「带来」。⚠️ **口头讲的时候也别说成 brought 或 grew。**

### PV 的口径，先分清几个量

| 指标 | 同一个人刷 10 次算几次 |
|---|---|
| **PV**（页面浏览量） | **10 次** |
| **UV**（独立访客） | 1 次 |
| **DAU**（日活跃用户） | 1 次 |
| **曝光量**（impression） | ⚠️ 一次页面加载可能产生**几十次** |

⭐ **最容易被问穿的地方**：信息流一次加载会滚出几十条内容，**所以 PV 500 万时曝光量可能是 5000 万甚至上亿**。如果你记忆里那个数其实是曝光量，**`page views` 这个词就用错了口径，数字还虚高十倍**。

### 它是怎么来的：不是「测」出来的，是「埋」出来的

⭐ **前端没有任何 API 能告诉你「这个页面今天被打开了多少次」。** 唯一的办法是每次被打开时往服务器发一条记录，后端累加：

```
用户打开页面 → 埋点 SDK 上报 → 日志服务器 → 数仓/流处理聚合 → BI 报表按天出 PV
```

⭐ **你（前端）只负责第一段。5M 是从报表里读的，不是你算的 —— 这一点必须说清楚，因为它直接决定归因怎么写。**

**内部产品走的是内部埋点 + BI 看板，不是对外的百度统计。** ⚠️ **如果记不清内部平台叫什么，就说「内部埋点和 BI 看板」—— 千万别硬编一个系统名字，编错比说不知道难看得多。**

**为什么 PV 天然被低估**：广告拦截插件会拦掉统计域名、用户秒退时 SDK 还没加载完、网络失败。⭐ **所以真实访问量一般 ≥ 报表里的 PV —— 简历写 `5M+` 带个加号是合理的。**

### 归属怎么说

- ✅ 「我负责的这个 feed **承载** 5M+ 日均 PV」
- ❌ 「我**带来了** 5M+ PV」

⭐ **更好的答法是把规模翻译成工程约束**：「这个量级意味着一次掉帧影响的是百万级用户，所以改动必须灰度、必须有性能监控。**这也是为什么我们没有直接引一个第三方虚拟列表库，而是自己写了个可控的 hook。**」—— **这样这个数字就从「吹牛」变成了「技术决策的依据」。**

## 八、为什么自己写而不用现成库（预期追问）

> 「诚实说：**当时更多是团队约束而不是技术判断** —— 引三方库要走评估流程，而这个需求边界很清楚、item 结构也固定。**自己写的代价是动态高度、键盘导航、无障碍这些边角要自己补，而成熟库已经处理过。** 现在做的话我会先用 TanStack Virtual，除非它的 API 拦住了某个必须的定制。」

⭐ **主动说「现在会选库」比硬撑「自己写更好」可信得多。**

**顺带一个诚实的补充**：这个 feed 的卡片**高度本来就不一致**（有的带封面图有的不带），所以 `visibleCount` 本身随滚动位置浮动 —— ⭐ **这是 `near 100` 里那个 `near` 的第二个来源**。动态高度的标准处理是「预估高度 + `ResizeObserver` 测量修正」或者「偏移量表 + 二分查找」。

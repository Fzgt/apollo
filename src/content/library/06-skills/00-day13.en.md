## 1. concept-tracker — the 90-second version

> A concept card tracker: manages the terms I need to revise for interviews, with CRUD, filtering, pagination and per-module statistics.

**Tell it in this order, not by directory:**

1. **What it solves**: while revising I had a pile of concept cards to manage, so I turned it into something genuinely usable — I use it myself, it is not a demo written and abandoned.
2. **Three backend layers, dependencies one-way**: `model` (what the data looks like, what counts as valid) → `store` (persistence) → `httpapi` (the HTTP translation layer). `httpapi` uses `store`, `store` uses `model`, and never the other way round. ## 2. Go — questions and answers

**"What does `var _ Repository = (*SQLiteRepo)(nil)` do?"** (`store/sqlite.go:29`)
Go interfaces are implemented implicitly; there is no `implements` keyword. This line assigns a nil pointer to an anonymous variable of the interface type. It does nothing at runtime, but it **forces a compile-time check** that the method set is complete. Miss a method and compilation fails right there, instead of somewhere else at the call site.

**"How do Go interfaces differ from TypeScript's or Java's?"**
Implicit implementation, which means an interface can be **defined by the consumer** rather than the implementer. The `rowScanner` at `sqlite.go:314` is the example — the standard library's `*sql.Row` and `*sql.Rows` share no interface but both have a `Scan` method, so I define an interface with only `Scan` and both types immediately "implement" it without touching a line of the standard library. You cannot do that in Java.

**"How do you handle errors?"**
Three things: `%w` wrapping preserves the error chain; the sentinel error `ErrNotFound` (`store.go:23`) lets callers use `errors.Is` instead of comparing strings; and **errors are translated at boundaries** — `sqlite.go:195` turns the database's `sql.ErrNoRows` into my own `ErrNotFound` so database concepts never leak into the HTTP layer. Using `%v` instead of `%w` flattens the error into a string and breaks the chain.

**"Why Ping after `sql.Open`?"** (`sqlite.go:81`)
`sql.Open` does not actually connect; it only prepares the pool, and the first use establishes a connection. To find out at startup that the database is unreachable, you have to Ping once yourself.

**"Why `SetMaxOpenConns(1)`?"** (`sqlite.go:88`)
SQLite's writes lock the whole database file, so raising the connection count just makes connections fight over the lock and report `database is locked`. **With Postgres it is exactly the opposite** and this value should go up. It is an example of configuration following the storage engine, not a universal best practice.

**"What happens if you skip `rows.Err()`?"** (`sqlite.go:179`)
`rows.Next()` returning false means one of two things: you read everything, or something failed part-way. Skip this check and a failure looks like a normal end of results — **silently losing data**, the hardest class of bug to track down.

**"Why is `pageArgs := append(append([]any{}, args...), …)` nested twice?"** (`sqlite.go:152`)
`append` may rewrite the underlying array in place, so `append(args, …)` directly would corrupt the caller's `args`. Slices sharing a backing array is the classic Go trap; copying into a fresh slice before appending is the least error-prone way to write it.

**"And if you leave out `defer rows.Close()`?"**
The connection never returns to the pool, and eventually the pool is exhausted. This is the most common resource leak in Go backends.

**"Why `make([]model.Card, 0, …)` for items instead of leaving it nil?"** (`sqlite.go:168`)
A nil slice marshals to `null`; only an empty slice marshals to `[]`. The frontend calling `.map` on null blows up.

**"What is middleware, and why this order?"** (`httpapi/middleware.go`, `router.go:38`)
There is no framework magic in Go: middleware is just `func(http.Handler) http.Handler`. The order is CORS → request ID → logging → recover → handler:
- CORS outermost, so OPTIONS preflight short-circuits as early as possible;
- request ID next, because the logging and errors after it both need it;
- **logging must sit outside recover** — that way, after a handler panics and recover has written the 500, the logging layer still records the request and its status code. The other way round, the panicking request vanishes from the access log entirely.

The `chain` loop runs **backwards** (`middleware.go:28`), because the outermost middleware has to be wrapped on last.

**"Why must `recover` be inside a `defer`?"**
It is a language rule: recover only works when called from a deferred function. A Go panic unwinds the whole call stack, and if nobody recovers, the process exits — one nil pointer can disconnect every user. That makes this middleware mandatory in an HTTP service. Note too that `middleware.go:143` returns only "internal server error" and **never sends the panic content to the client**, which would leak file paths and possibly connection strings.

**"How do you record the status code?"** (`middleware.go:84`)
`http.ResponseWriter` is write-only; once written, you cannot ask it what you wrote. So a `statusRecorder` wraps it and intercepts on the way out. Note that when a handler calls `Write` without `WriteHeader`, the standard library implicitly sends 200, which you have to fill in or the log records 0.

**"What is context for?"**
Every store method takes `context.Context` first. When the user closes the page or the request times out, the ctx is cancelled and the SQL query underneath is interrupted rather than tying up a connection to no purpose. The context key is also a custom type, `ctxKey` (`middleware.go:42`) — using a plain string as the key lets two packages overwrite each other, which the context guidelines explicitly warn about.

**"How is it concurrency-safe?"**
The request-ID counter uses `atomic.Int64` (`middleware.go:49`). Each request runs in its own goroutine, so an ordinary `counter++` is a data race — and **`go test -race` catches it directly**, which is how my tests are run.

**"Talk me through graceful shutdown."** (`cmd/api/main.go:74-119`)
The problem: Ctrl+C kills the process outright, in-flight requests are cut off, and every rolling update hits it.
The solution: `signal.NotifyContext` catches SIGINT/SIGTERM (the latter is what `docker stop` and a k8s pod deletion send) → `ListenAndServe` goes into a goroutine (it blocks) → the main goroutine `select`s on both "the server failed" and "a signal arrived" → on a signal, `srv.Shutdown(ctx with a 10 second timeout)` stops accepting new connections and waits for the in-flight ones.
Two details: the error channel is buffered to 1 so the goroutine does not block forever with nobody reading; and on a clean shutdown `ListenAndServe` returns `ErrServerClosed`, which is not an error and has to be excluded explicitly.

**"What are the three Server timeouts for?"** (`main.go:69-71`)
`ReadTimeout` / `WriteTimeout` / `IdleTimeout` default to **never timing out**. Leave them unset and a client that connects and says nothing holds a connection and a goroutine indefinitely; a few thousand of those can take the service down (Slowloris). Mandatory in production.

**"Do you still need chi or gorilla after Go 1.22?"** (`router.go:18`)
The standard library `ServeMux` now supports patterns like `"GET /api/cards/{id}"` with a method and path parameters, and this project uses nothing else. Needing a third-party router used to be exactly because it could not do that. **Where you still want one**: route groups with group-level middleware, regex constraints, and performance with a large number of routes. For a small project the standard library means one fewer dependency to upgrade and audit.

**"How do you choose between panic and error?"**
An error is an expected failure (not found, invalid input); a panic means the program itself is wrong. `main.go:48` exits a failed startup with `os.Exit(1)` rather than a panic — a configuration mistake is not a bug, a page of stack trace tells you nothing, and one clear error line plus a non-zero exit code is what CI and operations actually need.

## 3. Angular — questions and answers

Both projects' frontends are Angular 22 (`@angular/core: ^22.1.0`, TypeScript 6.0); the line numbers below refer to `concept-tracker/web`.

**"What is zoneless, and what does it mean for how you write code?"** (`app.config.ts:15`)
**Angular 22 ships without zone.js by default**, and neither project's package.json has the dependency. Change detection used to rely on zone.js monkey-patching `setTimeout`, events and XHR, then dirty-checking the whole tree from the root component. Now signal changes notify precisely, and only the DOM that reads them re-renders.
**The cost**: changing an ordinary class field does not refresh the view, so state has to live in signals. Copying a tutorial from a few years ago is exactly where this goes wrong. That sentence is itself the proof that "I'm using today's Angular, not the Angular I remember".

**"How do signal, computed and effect divide the work?"** (`cards-page.ts:60-119`)
- signal = source state (`cards`, `page`, the four filter conditions)
- computed = **derived** state (`totalPages`, `hasPrev/hasNext`). The test in one sentence: **can this value be derived from other state? If yes, it must be a computed.** Store the page count as a signal and sync it by hand, and sooner or later the two disagree.
- effect = side effects. The effect at `cards-page.ts:109` reads page and the four filters, so changing any of them refetches automatically, with no manual reload in every `(change)` callback.

**"Can an effect write to a signal?"**
Don't. It is easy to end up in a loop. My effect does `set(cards)` via `load()`, but that happens in an **async callback**, outside the effect's synchronous dependency tracking, so there is no cycle. An effect must also be created in an injection context (the constructor counts), and it cleans itself up when the component is destroyed — no manual unsubscribe.

**"I changed an array in a signal and nothing happened. Why?"**
Signals compare with `Object.is` by default. After `arr.push(x)` the reference is unchanged, so the view does not update. You need `set([...arr, x])` or `update(a => [...a, x])`.

**"What goes wrong if `@for`'s `track` is wrong?"**
`track` is how Angular decides whether a row is still the same row. With an index, deleting a middle row shifts the identity of everything after it — DOM gets reused against the wrong data, which shows up as input contents shifting to the wrong rows and animations jumping. Use a stable `item.id`. `@for` is compiler-built-in control flow rather than a structural directive like `*ngFor`, and `track` went from optional to **required**.

**"Reactive forms or template-driven?"** (`card-form-page.ts:66`)
Reactive: the form model lives in TS, is created synchronously, can be unit tested directly, and validation is centralized and composable. Complex forms (interdependent fields, dynamically added and removed fields) leave no other option. Template-driven: the structure lives in the template and is created asynchronously, which is convenient for simple forms and unmanageable as soon as they are not.
Why `fb.nonNullable.group` matters: after `reset()` fields return to their initial values rather than null, and the types stop needing `| null` everywhere.

**"What is the difference between `patchValue` and `setValue`?"**
`setValue` requires **every** field and errors if one is missing; `patchValue` only updates the fields you pass. Use patchValue to populate an edit form, but be aware it will not tell you about a field you forgot.

**"Once the interceptor has caught the error, why re-throw with `throwError`?"** (`error.interceptor.ts:34`)
If it swallowed the error with `return of(null)`, the caller would believe it succeeded, blow up somewhere else on the null, and leave a stack trace with no trace of the real cause. **An interceptor is responsible for a consistent notification, not for deciding on the caller's behalf whether the error matters.**
One more: `inject()` can only be called in the interceptor function body, never moved into the `catchError` callback — the injection context is gone by then and it throws.

**"What does `err.status === 0` mean?"** (`error.interceptor.ts:47`)
Not "the server returned 0" but **no response arrived at all**: the backend is down, the network dropped, or CORS blocked it. All three possibilities have to be in the message, or the investigation heads the wrong way.

**"What is a cold Observable, and why was my endpoint called twice?"** (`card.service.ts:94-99`)
`HttpClient` returns a cold Observable: **no request is actually sent until something subscribes**, and two subscriptions mean two requests. So the counter in `track()` cannot live in the method body; it belongs in `tap`'s `subscribe` callback, which is the moment the request really starts.

**"Which subscriptions must be unsubscribed by hand?"** (`cards-page.ts:128`)
An HttpClient stream completes when the response arrives and the subscription ends with it, so no. **Only streams that never complete** must be: `interval`, `fromEvent`, route parameter streams. Use `takeUntilDestroyed` or the `async` pipe. **Do not answer "all of them"** — that shows you have not made the distinction.

**"What is the difference between `inject()` and constructor injection?"** (`card.service.ts:29`)
Two things: with inheritance, a subclass does not have to redeclare all the parent's dependencies; and you can use it in field initializers and functions, free of the constructor signature.

**"What does `providedIn: 'root'` buy you?"**
An application-wide singleton, and it is **tree-shakable** — if no component ever injects it, it is dropped entirely. Listing it in an NgModule's providers does not get that treatment.

**"Why is `HttpParams` written as `params = params.set(...)`?"** (`card.service.ts:52`)
It is immutable and every `set` returns a new object. Calling it without taking the return value does nothing. `HttpHeaders` behaves the same way.

**"Any traps in the routing?"** (`app.routes.ts`)
Three, all of them hit in this file:
1. `{ path: '', redirectTo: 'cards', pathMatch: 'full' }` — **without `pathMatch: 'full'` the empty path prefix-matches every URL**, so everything redirects and the whole app collapses into one page.
2. `'cards/new'` must come before `'cards/:id'`. Routes match top-down and the first match wins; reversed, `new` is taken as an id and `Number('new')` gives NaN.
3. The wildcard `**` must come last, because it matches everything.

**"How finely do you split lazy loading?"**
`loadComponent` per route is the safest default. Do not overdo it — a component of a few dozen lines in its own chunk costs an extra round trip and ends up slower.

**"`snapshot` or subscribing to `paramMap`?"** (`card-form-page.ts:85`)
When two routes never navigate to each other (there is no "same component reused, only the parameter changed"), snapshot is enough. **When that case does exist you must subscribe** — reading only the snapshot means the component does not reload on a parameter change and the page sits on stale data. The classic case is a details page with a "next" button. This is the most common routing bug there is.

**"Why does a `<select>` with async options lose its selection?"** (there is a full comment block in `job-tracker`'s `list-page.html`)
The options arrive asynchronously, the bound value exists before them, and Angular finds no matching option so it clears the selection. Fix it by setting the value after the options land, or by giving `[compareWith]` a comparison function.

**"How do you compare Angular and React?"**
Angular gives you the whole set (DI, routing, forms and HttpClient are all in the framework): strong conventions, a steep start, but a large team never argues about tooling choices. React is a library with a pick-your-own ecosystem: flexible, but every team's stack is different. **Change detection has actually converged** — Angular went to signals, React is pushing a compiler, and both are moving toward knowing precisely what changed.

## 5. Django / DRF — questions and answers

**"How do you choose between an ORM and hand-written SQL?"** (this is the entire reason both projects exist, so answer it more thoroughly than anyone else)
- Hand-written SQL: every query is right there in front of you and performance is controllable; the price is repetitive code, schema changes that must be mirrored by hand in several places, and no migrations.
- ORM: fast to develop, migrations automated, portable across databases; the price is that **it writes inefficient queries you never see**, N+1 being the most common.
The one-line version: **Go makes you look at every SQL statement, Django means you don't have to.** Which you want depends on whether the team's time or the machine's time is the expensive one.
And one more turn of the knife: it is not that an ORM cannot express complex queries, it is that **past a certain complexity the ORM expression is harder to read than the SQL**, and at that point you should reach for raw SQL or a view.

**"A QuerySet is lazy — when is the SQL actually sent?"**
On iteration, on slicing to a concrete value, and on `len()`, `bool()` or `list()`. So `qs = Model.objects.filter(...)` issues no query and you can keep chaining conditions. That is also why `get_queryset` is a **method** rather than a class attribute (`views.py:67`) — a class attribute is evaluated once at import time and every request then shares one QuerySet object, which lands you on cached results that never refresh.

**"What is N+1, and how do you choose between the three tools?"** (`views.py:79-95`)
The list returns 20 rows and each one queries its related data again: 1 + 20 statements.
- `select_related` — one-to-one and many-to-one, uses a JOIN, one statement fetches the related object
- `prefetch_related` — one-to-many and many-to-many, issues a second statement and joins in Python
- `annotate` — when what you want is an **aggregate** (count, sum) and not the related objects themselves
Here I only want "how many events does this application have", so annotate is the cheapest. There is a comment in `serializers.py` about exactly this: switch to calling `obj.events.count()` in a `SerializerMethodField` and 20 records become 20 COUNT queries — the textbook way to write an N+1.

**"How do you stop the N+1 coming back?"**
`assertNumQueries`. Assert that this endpoint may issue N statements and no more, and the day somebody adds a `SerializerMethodField` **the test goes red**. It is the most effective defence there is, and more reliable than code review.

**"Why `order_by` again after `annotate`?"** (`views.py:95`)
An annotate aggregation adds a `GROUP BY`, and when Django decides whether a QuerySet is ordered it treats a query with group_by as **no longer inheriting `Meta.ordering`**. Without that call the paginator raises `UnorderedObjectListWarning`, and paging really can skip or duplicate rows. **After annotate, put the ordering back yourself.**

**"Why `.order_by()` with no arguments before an aggregation?"** (`views.py:206`)
The mirror-image trap. The default `Meta.ordering` is carried into the GROUP BY statement and becomes `GROUP BY status ORDER BY created_at`, where `created_at` is not in the grouping, so the database either errors or produces spurious groups. **Clear the ordering before aggregating** — a classic, and very well hidden.

**"Why does `Meta.ordering` include `id`?"** (`models.py:109`)
Order by time alone and two records created in the same second can land on page 1 one moment and page 2 the next, so paging loses rows. **Pagination ordering must include a unique field as a tiebreaker** — a general rule, not a Django one, and true of any paginated endpoint.

**"What is the difference between `null=True` and `blank=True`?"** (`models.py:81-87`)
`null` allows NULL at the database level, `blank` allows an empty value at the form and validation level. Numbers and dates get both; **string fields get only `blank=True`**, because if both "empty string" and "NULL" exist as empty values, every query has to test for two things.

**"Why is `on_delete` required?"**
Because there is no safe default. `CASCADE` deletes along with the parent, `PROTECT` blocks the delete, `SET_NULL` nulls it, `SET_DEFAULT` substitutes a default. Django forces you to decide what happens to the child when the parent goes — the field used to have a default, and it became mandatory precisely because the default CASCADE had deleted too much data.

**"Why have both a `CheckConstraint` and validation in code?"** (`models.py:116`)
A database constraint is enforced by the database and **cannot be broken even by SQL that bypasses the ORM**; code validation gives the user a friendly error. The first keeps the data clean forever, the second keeps the experience good. With only the first, the user sees a 500; with only the second, dirty data eventually arrives through some other entry point.

**"Does `Model.save()` call `clean()`?"**
**No.** `full_clean()` does, and `save()` does not call it automatically. This is one of Django's counter-intuitive corners — plenty of people assume validation on the model is airtight. DRF validates through serializers and does not rely on `clean()`.

**"What are the traps with `auto_now`?"** (`models.py:95-100`)
`auto_now_add` writes only on INSERT and `auto_now` refreshes on every `save()`, but **both assign the value in Python**, so a direct UPDATE such as `QuerySet.update()` never triggers them. To refresh the timestamp on a bulk update you have to pass `updated_at=timezone.now()` yourself.
A related one: with `save(update_fields=[...])` you must list `updated_at` explicitly (`views.py:168`), or auto_now is filtered out.

**"What order does serializer validation run in?"**
Field level → `validate_<field name>` → object level `validate(self, attrs)`. **On a PATCH, `attrs` only contains the fields the client sent**, so cross-field validation that reads `attrs["x"]` directly raises KeyError; take the old value from `self.instance` or use `.get()`. This is one of the most common sources of DRF production incidents.

**"What is the difference between PUT and PATCH?"** (`views.py:49`)
PUT semantically means "replace the whole thing with this data", and fields you omit should return to their defaults; PATCH means "change only what I sent". DRF implements it by having `partial_update` set the serializer's `partial=True`, which makes every field optional.

**"Why does 'change status' get its own endpoint instead of a PATCH?"** (`views.py:135`)
Changing the status is an **action** with business meaning: it writes a timeline entry and may trigger a notification. A separate endpoint says that clearly and makes it easy to add permissions on its own. It is the resource-versus-action trade-off in REST — expressing this kind of operation in pure resource style is contorted.

**"Where do you use transactions?"** (`views.py:107`)
Saving the application and writing the first timeline entry must both succeed or both fail. Without `transaction.atomic`, an exception in the second step leaves an application with no initial event — **half-succeeded data is the hardest class of bug to track down**.

**"Why read the old value before `save()` in `perform_update`?"** (`views.py:124`)
Before `save()`, `serializer.instance` is still the old object from the database; afterwards it has been **mutated in place** to the new values. Read it after save and the event's from and to are identical.

**"Does middleware order matter?"** (`config/settings.py:73`)
It is the same onion model as on the Go side. `CorsMiddleware` must be **first** — it has to add the CORS headers before any other middleware, especially anything that might return a response early, or error responses come back without them and the browser reports only a CORS error while the real message is invisible.

**"How are CORS and CSRF related?"**
**They are not, and they point in opposite directions.** CORS is the browser's same-origin policy limiting whether your page may read another origin's response; CSRF protects against someone else's page borrowing your cookie to send a request. One restricts reads, the other guards writes. And note CORS is a **browser** restriction, not a server one — curl against the same endpoint sees none of it. Both projects give you code to point at for this.

**"What happens if `DEBUG=True` reaches production?"**
The exception page hands the visitor the full traceback, the settings variables and the SQL queries, including SECRET_KEY and the database connection details. `ALLOWED_HOSTS` also has no effect under DEBUG.

**"Why is `USE_TZ=True` the only correct choice?"**
Store UTC uniformly in the database and convert to the user's timezone for display. Store local time and you are waiting for supernatural bugs across timezones and daylight saving changes. The same rule holds in concept-tracker's hand-written SQL (`sqlite.go:206` uses `time.Now().UTC()` throughout) — **this is not a framework matter, it is a data matter**.

**"What would you change to move to Postgres?"**
The `DATABASES` block in `settings.py`, and not one line of business code — the most tangible benefit an ORM gives you. Know SQLite's limits: writes are serialized database-wide, there is no `ALTER COLUMN`, and concurrent writes hit `database is locked`.

## 6. The comparison table — say this out loud when asked about stack choices

| | concept-tracker (Go) | job-tracker (Django) |
| --- | --- | --- |
| Data access | hand-written SQL + `database/sql` | ORM, SQL generated by the framework |
| Schema changes | inline CREATE TABLE, no migrations | `makemigrations` / `migrate`, versioned |
| Validation | hand-written `Validate()`, returns every error | derived from field declarations + three serializer layers |
| Routing | Go 1.22 `ServeMux`, registered one by one | Router generated from the ViewSet |
| Admin back office | none, write it yourself | thirty lines of `admin.py` |
| Typical performance trap | forgetting `rows.Err()`, slices sharing a backing array | N+1, forgetting to clear ordering before aggregating |
| Startup | a single binary, milliseconds | needs a Python runtime |
| When to pick it | high concurrency, control over every query, single-file deployment | many business tables, an admin UI, shipping fast |

**This table is the one thing from Day 13 that has to be memorized.** Fumbling the other follow-ups is survivable; fumbling this comparison means both projects were written for nothing.

## 8. Limitations to raise yourself

When asked "what is wrong with this project", work through these. Volunteering them scores; having them extracted costs:

- **No authentication**. A real system needs middleware to validate a token and filtering by `request.user` in `get_queryset()` — that second part is the easiest thing to miss.
- **The search box has no debounce**, so every keystroke sends a request.
- **The frontend types are hand-written** and kept in sync with the backend by hand. At any scale that should become `drf-spectacular` + `openapi-typescript` generation — **Periplus got this right, so it is a natural place to steer the conversation**.
- **No optimistic locking**. Two people editing at once, and the later save overwrites the earlier one. The fix is a version field or `If-Match` with an ETag.
- **Deletes are hard deletes**, with no `deleted_at`.
- **concept-tracker has no migrations**, only inline CREATE TABLE; any team work would need golang-migrate.
- **SQLite**, where writes serialize database-wide.
- **No frontend unit tests**, only "it compiles" plus one manual pass through the flow.

## 9. The framing for the other four words in the skills row (settled 2026-08-18: they stay)

`MongoDB`, `Jenkins`, `AWS`, `Cloudflare` — zero code on this machine, and **the decision is to keep them on the resume**. Since they stay, a question about them has to be answered at the concept level. The minimum:

- **MongoDB**: the document model vs the relational one; when to choose it (a schema that changes often, naturally nested structures, write-heavy log-like data); aggregation pipelines; indexes; multi-document transactions exist after 4.0 but cost. **The honest version**: the project I actually used was PostgreSQL, Mongo I know at the concept level.
- **Jenkins**: pipeline as code (a Jenkinsfile), agents and nodes, stages; the difference from GitHub Actions is **self-hosted vs managed** — Jenkins has a huge plugin ecosystem and can run inside a private network, at the cost of maintaining the machines and plugin upgrades yourself. **The CI I have actually built was GitHub Actions** (the Beyz bullet), so say so.
- **AWS**: the basic EC2/S3/IAM model; the Beyz email service was deployed on EC2, kept alive by PM2 and pushed by GitHub Actions — **there is real provenance here, so do not answer as if there were none**.
- **Cloudflare**: CDN, DNS, Workers (an edge runtime), cache rules. **The honest version**: concept level.

**The rule**: answer these four as far as "I know what problem it solves, when you would choose it, and how it differs from what I have used", and **never pretend to have used them**. Pushed on the detail, say "this one I know at the concept level; what I have actually done is X" — that costs nothing, and being caught pretending costs a great deal.

## Question: explain the HTTP caching strategies — how do they differ, and what does each one solve?

**Answer:**

HTTP caching is a technique for making web applications faster. The point is to stop transferring the same data twice, take load off the server, and get the client rendering sooner. Each strategy has its own characteristics and its own place:

1. Strong caching
2. Negotiated (revalidated) caching
3. No caching

---

## 1. Strong caching

**How it works**: the `Expires` and `Cache-Control` headers.

**The difference between them**:

- **`Expires`** sets an absolute expiry time (`Thu, 01 Dec 2022 16:00:00 GMT`). It depends on the client's local clock, so it can be wrong.

- **`Cache-Control`** is more flexible. `max-age` sets a relative lifetime (3600 seconds, say), and it supports more directives: `no-cache`, `no-store`, `must-revalidate`, and others.

**What it solves**: it removes unnecessary requests entirely — while the resource is fresh, the browser reads it straight from the local cache.

---

## 2. Negotiated caching

**How it works**: `Last-Modified` / `If-Modified-Since` and `ETag` / `If-None-Match`.

**The difference between them**:

- **`Last-Modified` / `If-Modified-Since`**: the server returns the resource's last modification time, and the client sends it back as `If-Modified-Since` next time. If nothing changed, the server answers 304 and the client uses its cache.

- **`ETag` / `If-None-Match`**: more precise. The server generates a unique identifier for the resource, and the client sends it as `If-None-Match`. If it matches, the server answers 304 and the cache is used.

**What it solves**: finer control over caching. It suits resources that are re-saved often but whose content does not always actually change.

---

## 3. No caching

**How it works**: `Cache-Control: no-store` or `Cache-Control: no-cache`.

**What it solves**: it guarantees the client always gets the newest version from the server. For highly dynamic content — live news, stock prices.

---

## Choosing between them

| Situation | Example | Recommended |
|---|---|---|
| Rarely changes | Site logo, CSS files | **Strong caching** |
| Updated often, but not changed every time | News summaries, avatars | **Negotiated caching** |
| Must be current | Stock prices, live news | **No caching** |

> The right caching strategy noticeably improves the experience while cutting server load and network latency.

---

## The three side by side

| Strategy | Key header | Sends a request? | Precision | Typical use |
|---|---|---|---|---|
| Strong | `Expires` / `Cache-Control: max-age` | No — nothing is sent at all while the resource is fresh | Coarse (time-based) | Logos, static CSS/JS |
| Negotiated | `Last-Modified` / `ETag` | Yes — but the response may be a 304 with no body | ETag is precise (compares content) | Avatars, news summaries |
| None | `Cache-Control: no-store` / `no-cache` | Yes — the real data is fetched every time | Most precise (always live) | Stock prices, live news |

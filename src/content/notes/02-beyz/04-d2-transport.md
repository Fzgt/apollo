# 传输层（速查）

> ⚪ 被追问 WebSocket 选型、断线、backpressure 时翻这里。

## 为什么是 WebSocket

**需求：两个方向都是持续、高频、不定时的。** 音频每 250ms 一块要一直**上行**，识别结果要随时**下行**。

| 方案 | 为什么不行 |
|---|---|
| **SSE** | **只能服务端 → 客户端**。上行没法走，得另开通道维护两套机制 |
| **轮询** | 上行每秒 4 次完整 HTTP 往返，**header 和音频数据一个量级**；下行拿不到实时性（间隔短是空转，长就是延迟） |
| **WebRTC** | 为**人对人通话**优化：UDP、可丢包换极低延迟。**这里要的是可靠送达做转写——丢一个包就是一段错的转写** |
| **WebSocket** ✅ | 一次握手，双向随时发，每帧只有 2–14 字节帧头 |

## 连接生命周期

```
connectToDeepgram()              useDeepgram.ts:30
  ├── getApiKey()                :32   ← 现取临时凭证
  ├── deepgram.listen.live()     :35   ← 握手
  ├── on(Open)  → state=open     :37
  └── on(Close) → state=closed   :42
```

> **顺序很关键**：`useAudioToText.ts:133-140` 里 **socket 先开、麦克风后开**。反过来的话，麦克风在连接建立前就吐数据，**开头几百毫秒的话直接丢了**。

## 追问速查

| 问题 | 答法 |
|---|---|
| **断了会怎样？** | ⚠️ **只把状态改成 closed，没有自动重连、没有退避、没有提示**（`useDeepgram.ts:42-45`）。麦克风还在录，`onData` 已被摘掉，音频进虚空。**主动承认，然后给方案** |
| **该怎么补？** | ①**指数退避 + 抖动** ②重连要**重新铸 key**（60 秒 TTL 不能复用）③**断开期音频**：丢弃 / 本地缓冲补发 / 暂停录制并提示——**面试场景选第三个最诚实**，有空洞的转写比明确报错更坑用户 ④**区分主动停和意外断**，否则用户点了停还在勤奋重连 |
| **重连后转录会重复吗？** | 不会，`confirmedTranscriptRef` 是客户端 ref，连接断了它还在。**但有个真坑**：断在一句话中间，那半句会和重连后的下半句拼成语义断裂的一句 |
| **backpressure 怎么处理？** | ⚠️ **没处理**——`connection.send()` 不检查 `bufferedAmount`。正常网络下不成问题（每秒 4 个包、每块几 KB），**弱网下会形成恶性循环**：缓冲堆积 → 音频越来越滞后 → 字比说话慢好几秒 |
| **正确做法？** | 检查 `bufferedAmount`，超阈值就**丢最旧的而不是排队**——**实时系统里，过期的数据不如没有数据** |

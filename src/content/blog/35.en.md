## 1. What hydration is actually for

The HTML a server renders is just static markup that *looks* right. **It has no event listeners attached. Clicking a button does nothing, because the interaction logic is JavaScript and the server only produced HTML text — it never ran anything that binds events.**

Once the browser has downloaded that HTML, it still has to download and run the bundled React JavaScript. At that point React rebuilds the corresponding fiber tree in memory against the HTML that already exists, and reinstalls the dynamic parts — event listeners, state — onto those existing DOM nodes. That process is **hydration**.

## 2. Why this step can never be skipped

Whatever version of React you use, SSR-generated HTML is inert. **It has to be hydrated before it comes alive.** That is inherent to SSR and no version upgrade removes it.

**Clearing up a common misconception**: there is no version that "does not need hydration". What changes is never *whether* you hydrate, only the granularity and the manner.

## 3. React 18's improvement: selective hydration

The old hydration was all-at-once, over the whole tree. **The user could not interact with any part of the page until every component had hydrated** — wanting to click a button at the top still meant waiting for a complicated comment section at the bottom.

React 18's change: **hydration order can follow what the user is actually interacting with.** Click the button at the top and React can hydrate that part **first** so it responds, while the rest continues in the background.

**This did not remove hydration.** It turned "the whole tree at once" into "in batches, by priority, as needed".

## 4. Hydration and dehydration — the metaphor

**Dehydration**: the server compresses a live, stateful React tree into two things — plain HTML text, and a serialised copy of the **application data** (a Redux preloadedState, the result of React Query's `dehydrate()`, Next's RSC payload — usually stuffed into a `<script>` tag in the HTML). Note that it is the data layer that gets serialised, not component state — React never writes `useState` values into the HTML. Like turning a living plant into a dried specimen: the shape survives, but the water — interactivity, dynamism — is gone.

**Rehydration**: when the browser runs the React JavaScript, the framework first restores the store / query cache from that serialised data, then `hydrateRoot` **runs the component tree again from scratch** (`useState` takes its initial values), matches the resulting fiber tree against the existing DOM, and reattaches event listeners to those nodes. Because this is a re-execution rather than a snapshot read, the server and client first renders must produce the same output — otherwise you get a hydration mismatch. Water goes back into the specimen and it is alive and interactive again.

The two words map exactly onto their literal meanings, which is where the naming came from.

## 5. Qwik — a completely different approach

### 5.1 No reconciliation — its headline claim

Qwik's core idea is radical: **hydration should not need to exist at all.** Hydration is fundamentally a recomputation of "what events should this HTML have, and what is the state". If **the server can serialise "this button is bound to this handler" straight into the HTML** — into HTML attributes — the browser does not have to compute anything. It reads what is already written there and lazily loads the small piece of JavaScript it needs.

React's hydration still builds a fiber tree in memory and does comparison work. Qwik encodes that information into the HTML and skips the rebuild and the comparison entirely, wiring things up on demand. That is "no reconciliation".

### 5.2 It is not only about reconciliation — the bigger ambition is resumability plus extreme lazy loading

**How far the lazy loading goes**: however much traditional frameworks (React included) optimise, the browser still ends up downloading and executing the JavaScript for every component the page uses. Interact with one button and the other components' code has almost certainly been downloaded and run anyway — it just may not have re-rendered.

Qwik wants: **if the user never interacts with a component, its JavaScript is never downloaded at all.** Only when the user actually clicks a specific button does Qwik go and fetch the small handler for it and run it. So even a logically complex page can need close to zero JavaScript on first load, with code trickling in as the user does things.

**Resumability and no-reconciliation are two faces of the same design.** Because "which function this button binds to" is written into the HTML, the browser neither has to recompute it (no reconciliation) nor download the code before it is clicked (lazy loading / resumability). They are not two separate features.

### 5.3 The cost, and where it fits

It requires a framework designed from the ground up around "everything must be serialisable". The migration cost and the range of suitable projects are fundamentally different from React's; this is not an optimisation you get by installing a library. Complex interaction state is hard to serialise into HTML attributes, so **it may not suit a complex SPA or an app that updates state constantly.** Learn Qwik as a different technical route, not as a more advanced replacement for React — the problems it targets do not fully overlap.

---

## Everything in one sentence

> Hydration is inherent to SSR — it is what gives inert HTML its interactivity back — and every version needs it. React 18's advance is doing it in prioritised batches, not abolishing it. "Dehydrate and rehydrate" is the specimen metaphor. Qwik's ambition goes beyond removing reconciliation: by writing event bindings into the HTML it gets both "nothing to recompute" and "no download until you click", at the cost of a framework paradigm completely unlike React's and a narrower range of suitable projects.

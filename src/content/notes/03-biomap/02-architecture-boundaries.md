# ② 架构边界：把约定变成约束

> **简历原句**
>
> Led the **React 18 and TypeScript architecture** for Digital OS, the team's core consumer-facing product, **enforcing feature boundaries with custom ESLint rules**.

## ⭐ 这条 bullet 的统领句

> **「文档是约定，ESLint 是约束。」**
>
> **约定靠人记得住，约束靠工具挡得住。团队一大、人一换，约定就会漂 —— 唯一不会漂的是「做不到」。**

**面试里先抛这句话，再用例子落地。** 这比逐条介绍 ESLint 规则高一个层次 —— ⭐ **展示的是判断力，不是工具熟练度。**

> **顺带**：这句话同时也解释了 [④ 设计系统与 MSW](/docs?section=biomap&item=design-system-msw) 那条 —— **那两条表面上没关系，其实是同一个思想的两次应用，合起来讲比分开讲各强一倍。**

## 30 秒口播稿

> Digital OS 是团队的核心对客产品，我负责它的 React 18 + TypeScript 架构。**架构工作里真正值钱的不是画了什么分层图，是那张图能不能被强制执行。**
>
> 我们的分层是 **`app` → `features` → 通用层**，依赖只能往一个方向流。**但这种规矩写在 README 里是没用的** —— 赶工期的时候没人会去查文档，一个跨功能的 import 就进来了，等发现的时候两个功能已经焊死了。
>
> 所以我把它写成了 **ESLint 规则**：五条路径限制加一条禁止循环引用。**违规不是「code review 时可能被指出」，是直接编译报错、CI 直接红。** 从「靠自觉」变成了「做不到」。

## 一、要解决的是什么：大泥球

**大项目里最常见的腐化叫「大泥球」（big ball of mud）**：模块之间随便互相引用，**最后谁也删不掉、谁也读不懂**。

**解法是规定依赖只能往一个方向流：**

```
app/ ──→ features/ ──→ components/ hooks/ lib/ types/ utils/

箭头方向是允许的依赖方向，反向一律禁止。
```

| 层 | 装什么 |
|---|---|
| **`app/`** | 页面和路由的**组装层** |
| **`features/`** | 一个个**业务功能**（blog、comments、theme……） |
| **底下那一排** | **通用的东西**：组件、hook、工具函数、类型 |

⭐ **这个方向不是随便定的：越往下越通用、越稳定；越往上越具体、越易变。让稳定的东西不依赖易变的东西，改动的影响面才收得住。**

## 二、用什么规则强制

**`import/no-restricted-paths` 这条 ESLint 规则**的作用是：**「在某个目录里，不许 import 另一个目录的东西」**。代码里定了五条：

| 规则 | 挡住什么 |
|---|---|
| **1–3** | `features/blog` 不能引用 `features/` 下的其他功能（除了它自己）—— ⭐ **功能之间互相引用** |
| **4** | `features/` 不能引用 `app/` —— **下层反向依赖上层** |
| **5** | 通用层不能引用 `features/` 和 `app/` —— **通用层被业务污染** |

**外加一条 `import/no-cycle`（禁止循环引用）。**

## 三、这三条各自防的是什么（这一节是答题的肉）

### ① 功能隔离防的是「焊死」

```
blog 引了 comments 的一个工具函数
  → comments 又引了 blog 的一个类型
    → 两个功能焊死了
      → 想删掉 comments？删不掉
      → 想让新人只改 blog？他得先读懂 comments
```

**要通信只能通过上层组装，或者把公共部分下沉到通用层。** ⭐ **这样每个功能才是可以独立删除、可以独立理解的单元** —— 而「能不能独立删掉」是判断模块边界是否成立的最好标准。

### ② 通用层不能反向引用

`components/Button` 一旦引了 `features/blog` 的东西，⭐ **它就不再通用了** —— 别的项目、别的功能都用不了它。**通用层的价值完全建立在「它不知道业务存在」这件事上。**

### ③ 禁止循环引用防的是真实的运行时 bug

**循环引用**就是 A 引 B、B 又引 A（或者绕一圈回来）。它的后果有三条，**第二条是真的会炸的**：

1. 模块初始化顺序变得不确定
2. ⭐ **可能拿到 `undefined`** —— 因为你引用它的时候，那个模块还没初始化完
3. 难以维护，重构时牵一发动全身

> **这一条值得单独讲**，因为它不是「代码整洁」问题，**是一类极难排查的线上 bug** —— 报错发生在使用处，而原因在模块图的形状里。

## 四、⭐ 为什么这件事值得写进简历

**「我搭了个 React 架构」是句空话，任何人都能说。** 这条 bullet 之所以立得住，是因为它回答了一个更难的问题：**架构决定怎么才能不腐化？**

| | 约定（会漂） | 约束（挡得住） |
|---|---|---|
| **架构边界** | README 里画一张依赖方向图 | ⭐ **一条 ESLint 规则 —— 违规直接编译报错** |
| **代码风格** | 「大家注意一下命名」 | 格式化工具 + lint 规则 |
| **前后端解耦** | 「接口先约定好，后端慢慢写」 | **MSW 拦在网络层**（见 [④](/docs?section=biomap&item=design-system-msw)） |

> ⭐ **和 [Beyz 的四态机](/docs?section=beyz&item=credential-quota)、[Stripe 的终身档保护](/docs?section=beyz&item=stripe-billing)、[TanStack Query 的 `Omit`](/docs?section=biomap&item=tanstack-query) 是同一个思想：把「不该发生的事」从「靠自觉」变成「做不到」。**
>
> **四个例子来自三个项目，串起来讲就是[跨项目追问](/docs?section=cheatsheet&item=crosscut)的现成答案。**

## 五、生产级 / 会被追问的三点

| 做法 | 说明 |
|---|---|
| ⭐ **规则必须进 CI** | **规则不进持续集成等于没有** —— 本地能跳过、能加忽略注释。和 [Beyz 那道 CI gate](/docs?section=beyz&item=service-cicd) 是同一个道理 |
| **规模大了上专门的工具** | `dependency-cruiser` 能生成依赖图、定义更复杂的架构规则、输出可视化 —— **ESLint 规则的表达能力是有上限的** |
| ⚠️ **规则要和目录结构一起演进** | 加了新功能就要加规则，**否则它会慢慢变成摆设** —— 这是这套做法真正的维护成本，主动说出来 |

### 预期追问：barrel export 要不要用

**「barrel export」是指在一个目录下放一个 `index.ts`，把这个目录里的东西统一再导出一遍**，让外面 `import { A, B } from '@/features/blog'` 而不是逐个写路径。

| 好处 | 代价 |
|---|---|
| 外部只认一个入口，**内部文件怎么挪都不影响调用方** —— 这正好配合上面的边界规则：**一个功能对外只有一个门** | ⚠️ **容易制造循环引用**（A 引 barrel，barrel 又引 B，B 又引 A）；**对打包工具的摇树优化不友好**，可能把整个目录拉进产物 |

> **答法**：「用，但只在功能目录的对外边界上用，**内部文件之间直接引具体路径**。滥用 barrel 是循环引用最常见的来源 —— 而循环引用正是我们用规则禁掉的东西，**所以这两件事必须一起想。**」

# 双后端的 bloom，和一次精确到帧的排查

> 🔴 **必看**。第 ② ③ 条（合批渲染、关卡扫描）的测量方法在另外四篇。**这一篇补 ① ④ 两条**，外加四条各自的口播稿。

## 四条各 30 秒（改一改就能用）

**① bloom 与双后端**

> 这是个霓虹风格的跑酷游戏，**发光材质本身是平的，真正让它「亮」起来的是光晕**。问题在于常用的后处理库**只支持 WebGL**，而我们整个游戏是走 WebGPU 渲染的。
>
> 所以光晕是用 three.js 的**节点管线**写的 —— **同一套节点在 WebGPU 和它自带的 WebGL2 回退上都能跑**。这样没有 WebGPU 的机器拿到的是同一个画面，**而不是悄悄丢掉这个效果**。

**② 合批渲染**（细节见 [② 129 → 76 draw calls](/docs?section=winterfell&item=n18-draw-calls) / [② 2.6× 三角形](/docs?section=winterfell&item=n19-triangles)）

> 每个障碍区原本是几十个独立的物体，合并成两个「实例化网格」共用一套变换矩阵，**每帧的绘制命令从 129 条降到 76 条**。代价我也量了：**提交的三角形涨了 2.6 倍** —— 因为「看不见就不画」这个优化是按物体算的，合并之后粒度从「每个方块」退化成「整个区段」。**这笔交易划算是因为省的是 CPU、花的是 GPU 的富余产能。**

**③ 关卡可通过性**（细节见 [③ 1,020 layouts](/docs?section=winterfell&item=n17-layouts) / [③ gap ≥ 15](/docs?section=winterfell&item=n20-gap)）

> 障碍是程序生成的，每局都不一样，**所以「这关能不能过」没法靠试玩验证**。关键是意识到可通过性是**布局的几何性质**，不是运行结果 —— 所以我直接算几何：从整条赛道宽度出发，每前进十个单位按飞行器**在那一关速度下**的横向能力扩张一次可达范围，再减掉障碍物的碰撞半径，**范围变空就说明这个布局必死**。扫了一千多个布局，全部有连续通路。

**④ 那次冻结**（下面详讲）

> 有个卡顿**每次都精确地落在关卡换色那一刻**。追下去发现是雾：它当时是写成 JSX 标签的，**换色时整个雾对象被重建**，而**雾属于材质的「程序标识」的一部分** —— 换掉它等于让场景里每一个材质同时失效，渲染器在一帧之内把它们全部重新编译了一遍。**我写了个探针数每帧编译了多少条渲染管线，确认了慢帧就是编译帧。**

## ⭐ 第 ④ 条讲透：一次完整的排查

**这条 bullet 的价值在于它是完整的 观察 → 假设 → 验证 → 修复 链条**，而且每一环都有东西可指。**3 分钟版建议主讲这条。**

### 现象（`Game.tsx:99-111` 的注释原话）

> *"That was the freeze that landed **exactly on a sector change**, with **the last drawn frame stuck on the previous palette while the HUD had already moved on**."*
>
> （那个冻结**精确地落在换关那一刻**，**最后画出来的那一帧还停在旧配色上，而 HUD 已经更新了**。）

> ⭐ **最后半句是最好的线索**：画面卡在旧配色，**而界面上的血条分数已经更新了** —— 说明**游戏逻辑在正常跑，堵住的是渲染这一侧**。
>
> **能讲出这个观察，说明你是从症状往回推的，不是猜的。**

### 根因链条（三层，缺一层都讲不通）

```
① 雾是写成 JSX 标签的：<fog args={[palette.fog, ...]} />
     → 关卡换色时参数变了，React 认为要换一个新对象，于是重建了一个雾
         ↓
② 雾属于材质的「程序标识」
     → 换了雾对象 = 场景里每一个材质的程序标识都变了
         ↓
③ 渲染器必须为每个材质重新编译着色器
     → 全场景的编译挤在同一帧里 → 冻结
```

### ⭐ 第 ② 层是技术核心，展开讲

**先说什么是「着色器」**：GPU 上实际跑的小程序，决定每个像素最终什么颜色。**它需要先编译成 GPU 能执行的指令**，这个编译是有成本的。

**「程序标识」（program key）是什么**：渲染器不会为每个物体单独编译一份着色器 —— 它会把**需要同一份着色器的材质归成一类**，这个分类的依据就是程序标识。

**关键在于：哪些东西会进这个标识？**

| 进标识的（改了要重编译） | 不进标识的（改了只是换个数值） |
|---|---|
| **有没有雾** | 材质的颜色 |
| 光源的数量和类型 | 透明度 |
| 用了几张贴图 | 位置、旋转 |

> ⭐ **判据是：它改变的是着色器的代码本身，还是只是传给着色器的一个参数？**
>
> **雾会改变着色器代码** —— 有雾的时候，着色器末尾要多一段「根据距离把颜色混向雾色」的计算。所以**「有雾」和「没雾」需要两份不同的编译产物**。
>
> **而换掉雾对象，渲染器认为「这是一个不同的雾配置」，于是场景里每个材质的标识全变了 —— 全部要重编译。**

**换 uniform 便宜，换程序标识要重编译。** 这句话是这一段的题眼。

### 验证：数一数每帧编译了多少

**探针的文件头说明了方法**（`bench/pipelines.mjs`）：

> *"WebGPU compiles a render pipeline **the first time a material/geometry combination is drawn**, and that compile happens on the frame that needs it... **If the slow frames are the frames that compiled, the hitch is shader compilation.**"*
>
> （WebGPU 在**某个材质/几何组合第一次被绘制时**编译渲染管线，而这个编译就发生在需要它的那一帧……**如果慢帧正好就是编译帧，那这个卡顿就是着色器编译。**）

**做法**：**包住设备创建渲染管线的那个接口**，按帧记录「这一帧编译了几条管线」和「这一帧耗时多少」。两条曲线对上，猜想就变成了结论。

> ⭐ **这一步是这条 bullet 最值钱的地方：不是「我觉得是着色器编译」，是「我数了」。** 面试时强调这个转变 —— **从猜测到证据。**

### 修法（`Game.tsx:112-129`）

```tsx
const LevelFog = ({ color }) => {
  const fog = useRef<Fog | null>(null);
  useEffect(() => {
    if (!fog.current) fog.current = new Fog(color, 300, 1000);  // ⭐ 只创建一次
    scene.fog = fog.current;
    return () => { if (scene.fog === fog.current) scene.fog = null; };
  }, [scene, color]);
  useEffect(() => { fog.current?.color.set(color); }, [color]);  // ⭐ 之后只改颜色
};
```

**用一个 ref 把雾对象存住，第一次才 `new`，之后只调 `color.set()` 改颜色。**

> ⭐ **对象的身份不变 → 程序标识不变 → 不重编译 → 冻结消失。**

### 一句话答法

> 「症状是卡顿精确落在换色那一刻，而且卡住的那帧画面是旧配色但 HUD 已经更新了 —— **说明逻辑在跑，堵的是渲染侧**。根因是雾当时写成了 JSX 标签，换色时 React 重建了雾对象；**而雾会改变着色器代码本身，它属于材质的程序标识**，换掉它等于让全场景材质同时失效，渲染器在一帧里重编译了所有材质。我写了个探针包住管线创建接口、按帧统计编译数量，**确认慢帧就是编译帧**。修法是把雾提到 ref 里只创建一次、之后只改颜色 —— **对象身份不变，程序标识就不变。**」

## ⭐ 第 ① 条讲透：为什么不用现成的后处理库

**这是「为什么不用现成方案」的最好例子，因为理由是硬的。**

### 先说什么是 bloom

**bloom（辉光）是一种后处理效果**：把画面里特别亮的像素「晕开」，模拟人眼看强光时的光晕。

**为什么这个游戏离不开它**：霓虹风格的世界里，**发光材质本身渲染出来是平的一块亮色**，看不出「在发光」。**周围那圈光晕才是「发光」的视觉信号。**

### 硬理由

| | |
|---|---|
| **常用的 `postprocessing` 包** | **只支持 WebGL**。而这个游戏是用 WebGPU 渲染器渲染的 |
| **three.js 的 TSL 节点管线** | 同一套节点**在 WebGPU 后端和这个渲染器自带的 WebGL2 回退上都能跑** |

**「TSL 节点管线」是什么**：three.js 新的着色器写法 —— **你用 JavaScript 把效果描述成一张节点图，three.js 再把它编译成对应后端的着色器代码**（WebGPU 用 WGSL，WebGL 用 GLSL）。**所以同一份描述能跑在两个后端上。**

### 一个渲染器，两个后端

```ts
// Game.tsx:216-219
const renderer = new WebGPURenderer({ ..., forceWebGL: !isWebGPUSupported });
```

> ⭐ **不是「WebGPU 一套代码、WebGL 另一套代码」，是同一个渲染器内部切后端。** 检测到浏览器不支持 WebGPU，就让它走自带的 WebGL2 实现。

> ⭐ **简历那句 `the look survives the fallback instead of quietly degrading` 是这条的题眼**：
>
> **常见的做法是「检测不到 WebGPU 就退回一个简化版」，结果是一部分用户看到的其实是另一个游戏。** 这套的做法是 —— **让回退路径拿到同一个画面。**

### 顺带一个细节

**后处理组件把渲染优先级设成大于 0，就把渲染权接管过来了**（`PostFX.tsx` 的注释）—— react-three-fiber 不再自己调渲染，**最终上屏的是合成后的画面**。

**这是「后处理为什么要设优先级」的答案**：因为后处理必须是最后一步，它要拿到已经渲染好的画面再加工。

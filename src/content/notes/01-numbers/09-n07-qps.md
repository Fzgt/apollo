# #7 · `sustained 2,000+ peak QPS`

> **材料说明**：百度代码不在本机，材料是 `LEARNING_NOTES_BAIDU.md` + 回忆。
>
> 但这条和前面所有条都不一样：**它根本不是前端能测的数。** 前端拿不到全站每秒请求数——那是网关和后端监控里的东西。所以这条要答的不是「我怎么测的」，而是**「这个数从哪来、后端做了什么才有这个数、我在里面负责哪一段」**。

## 对应简历原句

Baidu 第 3 条 bullet（v40）：

> Delivered a withdrawal flow that **sustained 2,000+ peak QPS** through request locking and defensive fallbacks, without a single dollar of financial loss.

同一条 bullet 里有两个高危数字：`2,000+ peak QPS`（本篇）和 `without a single dollar of financial loss`（审计表第 8 项，**全份简历最难自证的一句**）。

---

## 一、先把归属摆正：这个数字不属于前端

笔记里已经写得很直白（第 ⑤ 点）：

> QPS 通常是**后端指标**，不是前端。**前端不「扛」QPS，前端「贡献」QPS**——每个用户点一下就贡献 1 QPS。

**从后端同事那里知道这个数完全合理**，这是团队里正常的信息流动。但你必须能说清楚**你知道的是什么、你做的是什么**，这两件事不能混。

**这里有个措辞风险，今天必须自己看清楚。** 简历原句的语法结构是：

```
Delivered a withdrawal flow that sustained 2,000+ peak QPS
                                              ↑
                          through request locking and defensive fallbacks
```

**语法上，「扛住 2000 QPS」被归因给了「请求锁和错误兜底」——而这两样都是前端的东西。**

但笔记第 ③ 点自己就说了：前端锁只能防「同一个 tab 快速点击」，**防不了**网络超时重试、跨设备/跨 tab 同时操作、刷新后再点。**真正让系统扛住 2000 QPS 的，是后端那一整套。**

**两条出路：**

1. **改措辞**（推荐）：把因果拆开，比如 `Built the withdrawal flow's client layer — request locking, idempotency keys and defensive fallbacks — on a path that peaked above 2,000 QPS`。**规模还在，但不再声称是你的锁扛住的。**
2. **不改，但讲的时候主动拆**：*「2000 QPS 是整条链路的量，扛住它的是后端的限流、分库和幂等；我负责的是客户端这一层，把无效的重复请求挡在发出之前。」*

**主动拆比被拆穿好得多。**

---

## 二、QPS 是什么，以及「峰值」和「持续」的区别

**QPS = Queries Per Second**，每秒请求数。

但这里有个关键认知：**QPS 不是一个被直接测量的量，它是「计数器在一个时间窗口上的斜率」。**

监控系统实际存的是一个只增不减的计数器（累计请求数），QPS 是算出来的：

```
QPS = (窗口结束时的计数 - 窗口开始时的计数) / 窗口长度
```

**于是窗口大小直接决定了你看到的数字。** 这是这条最容易被问穿的地方：

| 统计窗口 | 同一段流量算出来的「峰值 QPS」 |
|---|---|
| 1 秒 | 可能 2000 |
| 1 分钟 | 可能只有 600 |
| 5 分钟 | 可能只有 300 |

**窗口越大，峰值被抹得越平。** 所以「峰值 2000 QPS」这句话不说窗口，等于没说。

### `sustained` 和 `peak` 放在一起是有张力的

- **peak（峰值）**：某个瞬间的最高值，可能只持续几秒
- **sustained（持续）**：在一段时间里稳定维持

简历写的是 `sustained 2,000+ peak QPS`，勉强能读成「在峰值时段持续扛住 2000+」，但**面试官很可能就问这一句**：「到底是持续 2000，还是峰值摸到过 2000？」

**这两个的工程难度差很远**——峰值 2000 持续 3 秒，和持续 2000 跑 30 分钟，对数据库的压力完全不是一回事。**你得知道自己说的是哪个。**

## 三、后端是怎么得到这个数的（重点）

**有两条完全不同的来源，对应审计表那句「监控还是压测」。这两个的含义天差地别。**

### 路径 A：线上监控 —— 「真实发生过」

这是**事后观测**：活动真的跑了，监控记录下了当时的流量。

```
请求进来
  → 网关 / 接入层（Nginx、BFE 之类）记 access log，或应用暴露 metrics
    → 采集 agent 拉取（pull）或推送（push）
      → 时序数据库存起来
        → 看板按时间轴画出 QPS 曲线
```

**典型工具链**（业界通用，面试官都认）：

| 环节 | 常见方案 |
|---|---|
| 指标暴露 | 应用埋 counter，暴露 `/metrics` |
| 采集 | **Prometheus**（拉模型）、StatsD / Telegraf（推模型） |
| 存储 | Prometheus TSDB、InfluxDB |
| 展示 | **Grafana** |
| 查询写法 | `rate(http_requests_total{api="withdraw"}[1m])` |

**注意最后那个 `[1m]`——它就是上面说的窗口。改成 `[5m]` 数字立刻变小。**

**百度内部走的是自研监控平台**，不是开源这套。**如果记不清内部平台叫什么，就说「内部监控看板」**——千万别硬编一个系统名字，编错比说不清难看得多。

### 路径 B：压测 —— 「验证过能扛」

这是**事前验证**：活动上线前，用工具造流量打系统，看能扛到多少。

**典型工具**：JMeter、wrk、ab、Locust、k6、Gatling；国内还有阿里云 PTS；大厂一般有内部的全链路压测平台。

**压测的几个关键概念（能说出来就说明你真见过）：**

- **梯度加压**：从低 QPS 一档档往上加，不是一上来就打满
- **拐点 / 容量水位**：QPS 还在涨、但 **P99 延迟开始飙升、错误率开始上升**的那个点，就是系统真实容量。**容量不是「打得进去多少」，是「打进去还不崩的最大值」**
- **完整的压测结论长什么样**：不是「能扛 2000 QPS」，而是**「压到 2000 QPS 时 P99 延迟 120ms、错误率 0，继续加到 2600 时 P99 涨到 800ms」**。光一个 QPS 数字是不完整的
- **单接口压测 vs 全链路压测**：单接口能压很高（下游都 mock 了），加上真实数据库和下游依赖之后往往掉一大截。**真实容量看全链路**
- **影子库 / 压测标记**：线上压测必须把压测流量和真实流量隔开，写到影子表里。**金融场景尤其不能污染真实资金数据**——能提这一点很加分

### 这两条路径给出的是不同性质的数字

| | 监控 | 压测 |
|---|---|---|
| 含义 | **真实发生过** | **验证过能承受** |
| 说明什么 | 业务量级真的到了这个水位 | 系统容量上限在这里 |
| 正确表述 | 「活动峰值时段监控看到 2000+」 | 「压测验证能扛 2000+」 |

**绝对不能混说。** 说成监控数据但其实是压测结论，是在虚报业务体量；反过来则是低估了自己的工作。

**今天要定的就是这一条：你听到的那个 2000，是监控看板上的，还是压测报告里的？** 记不清就用一个安全说法：*「这是后端给的口径，我记得是活动期间的峰值量级，具体是监控还是压测报告我需要确认。」*——**「我需要确认」永远比编一个答案安全。**

## 四、后端做了什么才扛得住（你要的这部分）

**能把这段讲出来，就从「我听后端说的」升级成「我知道整条链路怎么工作」——这是这条 bullet 真正的价值。**

### ① 接入层：把洪峰削平

- **限流**：网关按令牌桶/漏桶算法限制入口速率，超出的直接拒绝或排队。**保护的是后面的系统，宁可拒绝一部分，也不能全崩**
- **排队 / 验证码 / 答题**：活动场景的经典手段，把「一万人同一秒点」摊成「一万人在两分钟内陆续进来」
- **熔断降级**：下游超时就快速失败，不要让请求堆在那里拖垮整条链路

### ② 应用层：无状态 + 水平扩容

应用服务器不存会话状态 → **加机器就能线性扩容**。

**这一点特别重要，因为它能让 2000 QPS 这个数字变得不吓人**：如果集群有 20 台机器，单机只承担 100 QPS，那压根不算高负载。

> **QPS 是集群指标，不是单机指标。** 被问到「2000 QPS 很高吗」，正确答法是：「取决于分摊到多少实例，以及每个请求背后要做多少数据库写入——纯读的接口 2000 QPS 很轻松，涉及资金写入的就完全是另一回事。」

### ③ 数据层：这才是真正的瓶颈

**提现是写操作，写扛不住就是扛不住——缓存救不了写。**

单个 MySQL 实例的写入能力大概在几千 QPS 量级（还要看事务复杂度）。所以：

- **分库分表**：按用户 ID 哈希，把写入打散到多个库，单库压力降下来
- **读写分离**：查询走从库，主库只承担写
- **热点账户问题**（这个细节很能体现深度）：如果所有提现都从**同一个资金池账户**扣钱，那所有事务都在抢同一行的行锁，**分库分表也救不了**。解法是把这个账户拆成多个「子账户/分桶」，扣款时随机落到某个桶上，把行锁竞争打散

### ④ 一致性：幂等 + 事务 + 不变量

**这部分是「零资损」的地基**（第 8 项会细讲），这里只说和 QPS 相关的：

**幂等键靠唯一索引兜底。** 这是最可靠的实现方式：

```sql
-- 幂等 key 上建唯一索引
INSERT INTO withdraw_order (idempotency_key, user_id, amount, ...) VALUES (...);
-- 重复请求 → 违反唯一约束 → 直接失败 → 返回上次的结果
```

**为什么不能「先查再写」？** 因为「查」和「写」之间有时间窗口，2000 QPS 下两个并发请求可能同时查到「不存在」，然后都写进去。**唯一索引是数据库层面的原子保证，没有这个窗口。**

**业务不变量写在 SQL 里，不写在 if 里：**

```sql
UPDATE account SET balance = balance - ?
WHERE user_id = ? AND balance >= ?;
```

那个 `AND balance >= ?` 保证**余额永远不会被扣成负数**，不管并发多少。**受影响行数为 0 就说明余额不足，业务层据此判断。**

> 这和 [#2 补充](/docs?section=numbers&item=n02b-convergence) 里 Stripe 那个 `ne(subscribedPlan, Lifetime)` **是完全同一个模式**：把不变量放在数据层，而不是应用层的 if 判断。**能把这两个场景串起来讲，是跨项目追问里的加分项**（复习计划 Day 14 Round 3 就要考这个）。

### ⑤ 异步化：把重活挪出请求链路

**这一点会改变 QPS 这个数字的含义，必须知道。**

提现通常不是同步完成的：

```
用户点提现
  → 后端校验 + 落一条「处理中」的订单（快，能扛高 QPS）
    → 返回「提现申请已提交」
      → 真正的打款走异步队列，慢慢处理
        → 完成后推送/用户自己去记录页看
```

**所以如果是这个架构，2000 QPS 指的是「提交申请」的 QPS，不是「实际打款」的 QPS。** 这两个数可以差很远。**被问到时能区分，说明你真的理解这条链路。**

### ⑥ 对账：零资损的最后一道

T+1 和支付渠道核对流水，发现差异走修补流程。

**这也正是为什么「零资损」是财务对账的结论，前端测不出来**——第 8 项就卡在这。

## 五、按「审什么」逐条过

### ① 峰值还是持续

见第二节。**必须能区分，并且说清统计窗口。**

推荐答法：

> 「是活动期间的峰值量级，不是全天持续的水位。QPS 本身是按时间窗口算出来的，窗口越大峰值越平——所以说峰值的时候得配上窗口才有意义。」

### ② 监控还是压测

见第三节。**今天要确认的核心问题。** 记不清就说「需要确认」，别编。

### ③ 系统规模 vs 个人实现

**这是这条最需要小心的一问。** 三句话划清界限：

- ✅ **系统规模**：「这条提现链路在活动峰值时到过 2000+ QPS」
- ✅ **我的部分**：「我做的是客户端这一层——请求锁把 in-flight 期间的重复点击拦下来、幂等 key 提前生成并存 sessionStorage 保证刷新后一致、错误兜底按『不确定即失败』处理」
- ❌ **不能说**：「我的请求锁让系统扛住了 2000 QPS」

**再往上一层的答法**（把规模转成设计约束，和 [#4](/docs?section=numbers&item=n04-daily-pv) 同一个套路）：

> 「这个量级意味着任何一个重复请求都会被放大两千倍，所以客户端必须在请求发出之前就把重复挡掉——但我也很清楚前端锁挡不住跨设备和刷新重试，真正的保证是后端的幂等键加唯一索引。前端做的是减少无效负载，不是提供正确性。」

**「前端减少无效负载，后端提供正确性」——这一句话就能把整条 bullet 的分工讲干净。**

## 六、一句话答法

> 2000+ QPS 是整条提现链路的峰值量级，从后端的监控看板上来的，不是我测的——前端也测不到全站每秒请求数。扛住它的是后端那一套：网关限流削峰、应用无状态水平扩容、写入按用户维度分库分表、幂等 key 建唯一索引防重复扣款、余额约束直接写在 UPDATE 的 WHERE 里，再加上打款异步化，所以那个 QPS 其实是「提交申请」的量而不是「实际打款」的量。我负责的是客户端这一层：请求锁挡住 in-flight 期间的重复点击、幂等 key 提前生成存 sessionStorage 让刷新后也一致、不确定的结果一律按失败提示。**前端减少的是无效负载，正确性是后端给的。**

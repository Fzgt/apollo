## Why hooks exist, and what they fixed

Some history. Before hooks, the accepted pattern was class components as containers and function components for UI, because a function component could not hold state — everything came in through props, which made it very thin.

**Pain point 1: state logic was hard to share between components.** Your only options were HOCs or render props, which produced wrapper hell: a component tree nested deep and hard to read.

**Pain point 2: lifecycle methods forced unrelated logic together.** A single `componentDidMount` might hold both a subscription and a data fetch. The code was organised by lifecycle phase, not by what it actually does.

How hooks answer that:

- `useState` and `useReducer` give function components their own state, so nothing has to be rewritten as a class
- `useEffect` splits along business logic instead: related code (subscribe and clean up) sits together, unrelated code goes in a separate effect
- There is usually less code than the class version — no constructor, no `bind(this)`, none of that boilerplate

## Why useCallback

- The problem
  - <img width="400" height="180" alt="Image" src="https://github.com/user-attachments/assets/2c49be76-c543-45ce-b784-9c02d4384fde" />

  - When a value in the parent changes, the parent re-runs, and everything defined inside it runs again — including the definition of `addCount`.

  - So the `addCount` prop passed down to `Child` is a new value, and `Child` re-renders because of it. Extending `PureComponent` (or wrapping in `React.memo`) does not help, because both do a shallow comparison and the prop really did change: it is a new function reference. (`shouldComponentUpdate` is hand-written, so it *could* skip that prop and `return false` — what cannot see through this is the shallow comparison, not sCU itself.)

- The fix
  - `useCallback` caches the function definition, and the dependency array in its second argument controls when the definition is recreated. Put every outside value the callback reads into that array, or the cached function will keep closing over stale ones.

- **The prerequisite: `useCallback` on its own buys you nothing**
  - If the child is not wrapped in `React.memo` (or, for a class, does not extend `PureComponent` and has no sCU), it re-renders unconditionally whenever the parent does — whether or not any prop reference changed.
  - So `useCallback` / `useMemo` only pay off when paired with `memo` / `PureComponent`; alone they just cache a function for nothing. Their reason to exist is not "caching a computation", it is **preserving a reference** for the shallow comparison to see.

## Understanding useState

`useState` is commonly described as sugar over `useReducer`, and behaviourally you can model it with `useReducer` plus a `basicStateReducer`:

```js
function basicStateReducer(state, action) {
  return typeof action === 'function' ? action(state) : action;
}
```

In the source, though, `mountState` / `updateState` and `mountReducer` / `updateReducer` are two separate implementations, and `useState` has one extra trick — the **eager state** optimisation. Calling `setCount(x)` runs `basicStateReducer` up front to compute the next value; if it is `Object.is`-equal to the current one, React never schedules the update at all. "Special case" is the more accurate word; "sugar" is not.

See #25, useState vs useReducer.

## Understanding useEffect

- It can stand in for three lifecycle methods. The second argument has three distinct forms — do not conflate them:
  - **An empty array `[]`**: the callback runs once, after mount — `componentDidMount`
  - **An array with dependencies `[name]`**: runs after mount, then again every time `name` changes — roughly `componentDidMount` + `componentDidUpdate` (note it is not purely `didUpdate`; the first render fires it too)
  - **No second argument at all**: the callback runs after *every* render — this is the "runs every time" form
  - Returning a function from the callback gives you the cleanup — `componentWillUnmount`. But it does **not** only run on unmount: when a dependency changes and the effect re-runs, React runs the previous cleanup first, then the new effect. Leaked subscriptions and request race conditions almost always come from ignoring that half.

- How you get an infinite loop
  - <img width="400" height="200" alt="Image" src="https://github.com/user-attachments/assets/bc61015b-ff89-4442-a7da-6e90d9a88eb7" />
  - `name` is used here, probably inside the effect as `if (name) { ... }` before firing a request. Define a `nameRef` and write the check as `if (nameRef.current === xx)` instead: changing a ref does not re-render the component, and it does not have to go in the dependency array.
  - <img width="400" height="200" alt="Image" src="https://github.com/user-attachments/assets/f2314eb7-28e6-45bf-ad8d-5764921d099b" />

- When you do not need a particular value in the dependency array

  Pass a function to `setName()` (a functional update). Its argument is always the latest `name`, so `name` does not have to go in the array. What you save is *that one dependency* — the array itself still has to be there, written as `[]`.

  - <img width="406" height="105" alt="Image" src="https://github.com/user-attachments/assets/02234713-0126-485b-b13c-47fdfa882294" />

- Batching, to avoid scheduling more than once
  - <img width="400" height="200" alt="Image" src="https://github.com/user-attachments/assets/77adc301-8e1f-4f2c-9cf3-ffeb8738e77a" />
  - `setState` in a class component batches by default. (It does not batch inside async callbacks, native events, or `.then` — there you have to call `batchedUpdates` yourself.)
  - Written this way in hooks you need `batchedUpdates` to merge them, or the scheduler runs three times and you get three separate renders.
  - React 18 batches automatically everywhere, so `unstable_batchedUpdates` is no longer needed in most cases.

## React.memo vs PureComponent vs shouldComponentUpdate

`PureComponent`: avoids re-renders in class components. Extend it and it shallow-compares props and state for you.
`React.memo`: avoids re-renders in function components. Wrap the component and it shallow-compares props for you.
`shouldComponentUpdate` is a class-only lifecycle method — the manual version of what `PureComponent` does automatically.

**Why does `PureComponent` compare state as well as props?** A class component re-renders for two reasons: new props from the parent, or its own `setState`. sCU is the single gate both paths go through, so comparing props alone misses half of them. What it compares is the component's own `this.state` against `nextState` — nothing to do with what gets passed down to children:

```js
// PureComponent is roughly equivalent to
shouldComponentUpdate(nextProps, nextState) {
  return !shallowEqual(this.props, nextProps)
      || !shallowEqual(this.state, nextState);
}
```

**Then why does `React.memo` only compare props?** It is a wrapper around the component, so props are all it can see — it has no access to `useState` inside. State in a function component is handled a layer down, by React itself (the eager state check above: if the new value is `Object.is`-equal, nothing is scheduled). Different division of labour, not a gap in `memo`.

**What a shallow comparison actually does:** `Object.is` on the objects themselves; if that fails, `Object.is` on each key of the first level. One level only, no recursion.

```js
shallowEqual({ a: 1, b: obj }, { a: 1, b: obj })  // true
shallowEqual({ a: { x: 1 } }, { a: { x: 1 } })    // false — two different references
```

The half that bites is the other direction: **a changed reference counts as changed even when the contents are identical.** In `<Child style={{color:'red'}} onClick={() => {}} />` both props are brand-new references on every render, and `memo` is defeated — which is exactly what the `useCallback` / `useMemo` section above is for.

**Use both and sCU wins.** Extend `PureComponent` and also write your own `shouldComponentUpdate`, and React only honours the one you wrote (the source checks for sCU first and falls back to `isPureReactComponent`); the shallow comparison never runs, and development mode warns you about it.

## What `useState` really looks like — the hook linked list

The two problems with the minimal implementation above (only one piece of state, and separate components clobbering each other) are solved in React's actual source by **a linked list plus a pointer to "whoever is currently rendering"**.

### 1. Every hook is a node on a linked list

```js
// react-reconciler/src/ReactFiberHooks.js
function mountWorkInProgressHook() {
  const hook = {
    memoizedState: null,   // this hook's own value: state for useState, {current} for useRef, an effect object for useEffect
    baseState: null,
    baseQueue: null,
    queue: null,           // pending updates
    next: null,            // the next hook
  };

  if (workInProgressHook === null) {
    // first hook — attach it to the fiber
    currentlyRenderingFiber.memoizedState = workInProgressHook = hook;
  } else {
    // append to the tail
    workInProgressHook = workInProgressHook.next = hook;
  }
  return workInProgressHook;
}
```

Two things follow:

- **State lives on the fiber, not in the function.** `fiber.memoizedState` is the head of this list. Every time a function component finishes executing its locals are gone, but the fiber remains — which is the whole answer to "how can a function component have state".
- **Components do not bleed into each other because of the module-level `currentlyRenderingFiber` pointer.** While rendering A it points at A's fiber, while rendering B at B's. The minimal implementation has no such layer, which is exactly why two components' `name` overwrite each other there.

### 2. Why hooks cannot go inside an `if` — the list has no names

The nodes carry **no identifier at all** — not "which hook am I", not a name. On update, `updateWorkInProgressHook()` walks the old list **strictly in order**.

So if the first render runs `useState / useState / useEffect` and the second, because of an `if`, runs `useState / useEffect`, the second position picks up the node belonging to the previous `useState` and every value is off by one. React's "Rendered fewer hooks than expected" is what happens when it reaches the end of the list and finds the counts do not line up.

(What to do when the business logic genuinely needs a condition is covered in the separate post on hooks in conditionals, loops and nested functions.)

### 3. Mount and update are two different functions

The same `useState` call does **not** execute the same function on first render and on update. React swaps the dispatcher:

```js
ReactSharedInternals.H =
  current === null || current.memoizedState === null
    ? HooksDispatcherOnMount    // mountState: create the node, initialise
    : HooksDispatcherOnUpdate;  // updateState: take the node from the old list, compute the new value
```

`current === null` means "there is no old fiber", i.e. first mount. This also explains a familiar error: **calling a hook outside a component or inside an event callback throws "Invalid hook call"** — at that moment `ReactSharedInternals.H` points at `ContextOnlyDispatcher`, every method of which calls `throwInvalidHookError` straight away, because React is not rendering. "Hooks may only be called at the top level of a component" is, physically, this one line.

### 4. Updates form a circular list

`setCount(1)` does not change the value there and then; it creates an update object and queues it. That queue is a **circular linked list** — `queue.pending` points at the *last* update, and `pending.next` is the first.

```js
// react-reconciler/src/ReactFiberConcurrentUpdates.js
// finishQueueingConcurrentUpdates(): before render, splice the staged updates into the ring
const pending = queue.pending;
if (pending === null) {
  // This is the first update. Create a circular list.
  update.next = update;        // points at itself, closing the ring
} else {
  update.next = pending.next;
  pending.next = update;
}
queue.pending = update;
```

(One more layer of detail: `setState` initially only pushes the update into a `concurrentQueues` staging array; the splice above happens just before rendering actually begins, so updates arriving mid-render cannot contaminate the current pass.)

The point of the ring: **appending at the tail and finding the head are both O(1)** with a single pointer. During render React starts at `pending.next`, goes round once, and runs the reducer over each update to arrive at the final state.

Do not tie two separate things together here: calling `setCount` three times in one event **renders once because of batching**, not because of the ring. The ring is just the data structure holding those three updates. Without batching, three calls would still trigger three render passes, each settling the queue from the head — the queue structure computes *the final value*, batching decides *that it is computed only once*.

## Garbage collection

> Interview question this covers: how does garbage collection work in V8?

#### (1) Overview

Garbage collection (GC) means the runtime manages the memory used while code runs. The collector periodically finds variables that are no longer in use and frees their memory. It is not real time, because collection is expensive — but in V8 it is not on a fixed interval either. It is **triggered by allocation**: the young-generation Scavenge runs when the semi-space (From space) fills up, the old-generation Mark-Sweep runs when the heap crosses a dynamically computed threshold, and idle time slices are used for incremental and concurrent marking.

#### (2) Collection strategies

Two are common: mark-and-sweep and reference counting. Mark-and-sweep is the one you see most.

**Mark-and-sweep**

A variable is marked when it enters scope, and marked again — and collected — when it leaves. Every current JavaScript implementation (IE, Firefox, Opera, Chrome, Safari) uses mark-and-sweep or something close to it; only the collection interval differs.

When a variable enters the environment — declaring a variable inside a function, say — it is marked "in the environment". Logically, memory for such a variable can never be freed, because as long as execution is inside that environment the variable may be used. When the variable leaves the environment it is marked "out of the environment".

**Reference counting**

Reference counting tracks how many times each value is referenced. Every reference adds one; when the count reaches zero the object is a collection candidate, and the next time the collector runs, everything at zero is freed. The catch is cycles, which behave like a deadlock and leak.

In the classic example, `objA` and `objB` reference each other through their own properties, so both counts are 2. Under reference counting, both objects leave scope when the function returns, yet `objA` and `objB` live on, because their counts never reach zero. Enough of these and you leak a lot of memory.

#### (3) What causes leaks

1. Global variables
2. Closures — use them carefully
3. Listeners that were never removed when the DOM was cleared or deleted
4. Reference cycles

#### (4) Reducing the cost of collection

Each collection pass is relatively expensive, and the gaps in the mechanism can leak, so it is worth collecting less and avoiding cycles.

Set `obj = null` when you are done with an object. That breaks cycles and lets dead variables be collected promptly.
The operations that allocate in JavaScript are `new()`, `[]`, `{}`, and `function () {...}` — reuse objects as much as you can.
Be careful with closures. Normally everything a function allocated is freed when it returns, but a closure may hold references to the function's internals, and because the closure lives outside, those internals can never be destroyed.

#### (5) The weakness of garbage collection

JavaScript's GC cannot avoid the problem every other language has: while collecting, everything else stops, for safety. A pause of 100 ms or more is fine for an ordinary app, but for JS games and animation — anything that needs continuity — it is a real problem. Avoiding these long pauses is exactly what newer engines have worked on.

#### (6) Optimising GC

**Generational collection.** The same idea as Java's. Separate "temporary" objects from "long-lived" ones; collect the young generation often and the tenured generation rarely, so each pass walks fewer objects and takes less time.

**Incremental GC.** Simple idea: do a little now, a little more next time, and so on.

## The young generation

Objects in the young generation are usually short-lived, and it uses the Scavenge algorithm.

Young-generation memory is split into two halves, From-space and To-space. One is always in use and the other is always idle. New objects go into From-space, and when From-space fills up, young-generation GC kicks in. The algorithm finds the live objects in From-space and copies them into To-space, destroying anything dead. When the copy is done the two spaces swap, and that is the end of the pass.

## The old generation

Objects in the old generation tend to live longer and there are more of them. Two algorithms are used: mark-and-sweep and mark-compact.

First, what puts an object in the old generation:

- The object has already survived one round of Scavenge in the young generation, so it is promoted.
- To-space is more than 25% full. Objects are promoted so that allocation is not affected.

The old generation is split into several spaces:

Mark-and-sweep starts in the old generation when:

- a space has no free block left;
- the objects in a space pass a certain limit;
- a space can no longer guarantee that young-generation objects can be promoted into it.

The pass walks every object in the heap, marks the live ones, and destroys everything unmarked. On a large heap a single marking pass can take hundreds of milliseconds, which is a performance problem in itself. V8 moved from stop-the-world marking to incremental marking in 2011: GC breaks marking into smaller chunks and lets application code run in the gaps, so the app does not freeze. In 2018 came a bigger step — concurrent marking, which lets JavaScript keep running while the collector scans and marks. There is a [blog post](https://link.juejin.im/?target=https%3A%2F%2Fv8project.blogspot.com%2F2018%2F06%2Fconcurrent-marking.html) with the details.

Sweeping leaves the heap fragmented, and past a certain threshold the compaction algorithm runs. Compaction moves live objects toward one end until they are all packed together, then frees the memory that is no longer needed.

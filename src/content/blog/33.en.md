# How React builds its own event system

## 1. What a synthetic event is

When you write `onClick={(e) => {...}}`, that `e` is **not the browser's native event object**. It is React's own wrapper around it.

```javascript
<button onClick={(e) => {
  console.log(e);            // a SyntheticEvent — React's wrapper
  console.log(e.nativeEvent); // this is the browser's native event
}}>
  Click
</button>
```

A synthetic event is an adapter layer. It mimics the properties and methods a native DOM event has — `target`, `preventDefault()`, `stopPropagation()` — but the implementation underneath is React's own.

---

## 2. Why build this layer at all — three reasons

### Reason 1: smoothing over browser differences (historical, and less important every year)

Native event behaviour used to differ a lot between browsers, especially IE. Synthetic events made behaviour consistent so you did not have to write compatibility code.

### Reason 2: event delegation, for performance

React does not attach a native listener at each DOM node for each `onClick`. It attaches **one listener in one place** — `document` before React 17, the root DOM container of that tree from 17 onwards — relies on native bubbling to collect everything there, and dispatches to the right component's callback. Less memory, less work.

(See the event delegation notes for how moving from `document` to the root container fixed `stopPropagation` when several Reacts coexist.)

### Reason 3: deep integration with React's update scheduling — the most overlooked and the most important

The reason React knows "we are inside React right now, so batch these updates" is that the callback was invoked through its own synthetic event system, not called directly by a native `addEventListener`. Before running your callback, React sets a flag saying "this is a React execution context", and every `setState` inside is merged and batched because of it.

**Bind a handler with a raw `addEventListener` and you bypass the synthetic system**, and before React 18 the `setState` calls inside it were not batched automatically. This is the root of all those questions about whether `setState` is synchronous or asynchronous, and whether you are "inside React".

---

## 3. How it actually works

### Layer one: a single native listener

```
React 16 and earlier: attached to document
React 17 onwards:     attached to the root DOM container of that tree
```

### Layer two: what React does when an event fires

1. The native event bubbles up to the node where React's listener sits
2. React uses `e.target` to work out which React component and which JSX element produced it
3. React builds a **synthetic event object**, wrapping the native one
4. **It sets the execution context** — the flag that says "we are inside React, batch the `setState` calls"
5. It calls your callback with the synthetic event
6. When the callback returns, it clears the flag

---

## 4. History: event pooling, removed in React 17

In React 16 and earlier, synthetic event objects were **reused** to save memory: once an event was handled, all of the object's properties were **cleared** so the next event could reuse it. The classic trap:

```javascript
// React 16 and earlier
function handleClick(e) {
  setTimeout(() => {
    console.log(e.target); // throws, or null — React already cleared and reused e
  }, 1000);
}
```

To use the event object in async code you had to call `e.persist()` first, to keep it from being recycled.

**React 17 removed pooling entirely.** Synthetic event objects can now be read normally in async callbacks, and `persist()` is no longer needed.

---

## In one sentence

> A synthetic event is React's own wrapper around a native event, not the native event itself. The layer exists for three reasons: ① smooth over browser differences; ② save performance through event delegation; ③ **most importantly, let React know it is inside its own execution context, so `setState` can be batched.** Cross-browser compatibility, delegation, and batching are three faces of the same system design.

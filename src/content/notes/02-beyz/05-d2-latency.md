# 端到端延迟（速查）

> ⚪ 一句话记住就够：**用户感知的延迟里有个 2 秒的固定底座，那是设计不是性能。**

## 先反问口径

**起点终点各有两种选法，报出来的数完全不同：**

| 口径 | 量的是什么 |
|---|---|
| **说完最后一个字 → 屏幕出现第一个字** | ✅ **用户真实等待**（含 2 秒静默窗口） |
| **UtteranceEnd 事件到达 → 首 token** | ✅ 系统内部耗时（工程调优用） |

> **报「1.5 秒」和报「3.5 秒」说的是同一个系统。** 被问到先反问是哪个口径。

## 链路分段

| # | 段 | 量级 | 能不能优化 |
|---|---|---|---|
| ① | **静默检测窗口** `utterance_end_ms` | **2000 ms** | ⚠️ 能动但有代价——调小会把句中停顿误判成说完 |
| ② | 事件下行 | 几十 ms | ❌ |
| ③ | Server Action 往返 | 几十~百 ms | 🔸 可考虑 edge runtime |
| ④ | 鉴权 + 组装 history | 几~几十 ms | 🔸 `getAuthUser` 已有 `cache()` |
| ⑤ | **GPT-4o 首 token（TTFT）** | **几百 ms ~ 1s+** | ✅ **最大的一段**：换模型、缩 system prompt、减历史条数 |
| ⑥ | 流回传 | 几十 ms | ❌ |
| ⑦ | React 提交绘制 | 几 ms | ❌ 已用 `startTransition` |

> **两个大头是 ① 和 ⑤，而它们性质完全不同**：① 是**产品决策**（2 秒换的是不误判），⑤ 是**模型/成本决策**。**都不在「代码写得慢」上。**
>
> `MaxHistoryLength = 4` 同时在优化成本和 TTFT——prompt 越短首 token 越快。

## ⚠️ 没有埋点

**全仓库没有任何延迟测量**——`onFinish` 里只记了 token 用量，没记耗时。

**答法**：「链路我能拆开讲，但**当时没埋端到端的点，所以给不了 P95**，只能说体感是一两秒内开始出字。要测的话我会在四个位置打点：UtteranceEnd 到达、Server Action 返回、**首 delta 到达（关键指标）**、流结束；上报 `t2-t0`（用户等待）和 `t2-t1`（模型 TTFT），把慢归因到具体某一段。」

## 1. What "isomorphic" actually means

Normally React only runs in the browser: the user opens the page, downloads a near-empty HTML file, downloads the JavaScript, and only once that JavaScript has executed does any content appear. **Between the HTML arriving and the JavaScript finishing, the user is looking at a blank screen.**

Isomorphic means **the same React code runs once on a Node server to produce complete HTML, and once in the browser to take that HTML over and make it interactive**. The server renders the content into the HTML and sends it straight down, so the user sees a full page without waiting for JavaScript. That is the core of SSR; "isomorphic" is the part that stresses that the rendering logic is written once and runs on both sides.

## 2. What the two deployment paths really differ on

**With Next.js**: how React runs on the server, how the result reaches the browser, how routes map to files, when data is fetched ahead of time — all of it is handled. You write page components. This is what almost every company chooses; building SSR infrastructure from scratch has a poor return.

**Rolling your own (Express + `react-dom/server`)**: you handle route matching, when data is prefetched, and getting the client to take over the bundled JavaScript correctly. It works in theory, but it is reinventing what Next.js already packages. Not worth it unless you have an unusual requirement.

## 3. Streaming SSR, in detail

### The problem it solves

The old, non-streaming way: **render the entire component tree, assemble one complete HTML string, and send it all at once.** If one part of the page depends on a slow request — a module that takes three seconds — **the entire page waits those three seconds**, even though the other 90% was ready immediately.

Streaming: **the HTML goes out in chunks as it is generated.** What is ready goes first and the browser starts parsing and displaying it right away; the slow module is sent later, once its data arrives, and slotted into the right place.

### Underneath: HTTP chunked transfer encoding

This has been in HTTP for a long time; React did not invent it. An ordinary HTTP response needs to know its total length up front (`Content-Length`) and is sent in one piece. **Chunked transfer lets the server send piece by piece without knowing the total, and the browser processes each piece as it arrives** instead of waiting for the server to finish.

### How React uses it

`react-dom/server` provides APIs like `renderToPipeableStream` (for Node). Rather than rendering the whole tree to a string and returning it, it **pipes rendered output into the response stream as it goes**. When it hits a component whose data is not ready — something wrapped in `Suspense` — it skips it and sends the `fallback` first. When the data arrives, that content is appended as a **later chunk**, along with a small inline script telling the browser where on the page to put it.

### This only exists with SSR

Streaming depends on the server continuously generating and pushing content, and that only holds for server rendering. Pure CSR sends a near-empty shell up front and everything after that is fetched and computed by the browser — there is no "the server is still generating, in batches" to speak of.

### In practice this means Next.js

`renderToPipeableStream` is a low-level `react-dom` API, and in principle you can call it from your own Express server. But deciding what belongs inside `Suspense`, coordinating data fetching with rendering, handling errors, and getting the client to receive these chunks and hydrate correctly are all fiddly, and Next.js has handled them — you wrap the slow part in `Suspense` and that is it. So "I want streaming SSR" is in practice "I want Next.js" (or Remix, or something similar). Building it by hand is possible and rarely worth it.

## 4. Which performance metrics isomorphic rendering helps

### Why SSR naturally helps some of them

Pure client-side rendering is a long serial chain: **download the (nearly empty) HTML → download the JavaScript → execute it → request data → content appears.** SSR moves "content appears" up to the server: the HTML that comes back already has content, so the browser can display it by parsing HTML, with no JavaScript execution and no data request in between.

### Metric by metric

**LCP (Largest Contentful Paint)** measures when the largest piece of content — the hero image, a big block of text — actually shows. With SSR that content is already in the HTML, needing neither JavaScript nor a client request, so it **appears materially earlier**. LCP benefits clearly.

**CLS (Cumulative Layout Shift)** measures unexpected movement during load. It is not especially tied to SSR — it depends more on reserving space for images and ad slots. But in a CSR app, a skeleton being swapped for real content easily causes shift, and SSR returns the final content the first time, removing that intermediate state. So it helps indirectly.

**INP (which replaced FID in March 2024)** measures interaction responsiveness, and is mostly about JavaScript efficiency and long tasks blocking the main thread. **SSR does little for it directly** — and because SSR adds hydration, a heavy hydration pass (especially the old all-at-once kind) can make interaction stutter briefly while it runs. That is exactly why React 18 introduced selective hydration.

### What bites you in practice

**Data prefetching**: the data a page needs has to be ready before the server renders it. You cannot render a skeleton first and let the data trickle in as you would on the client, so you need a mechanism for "which component fetches what during server rendering".

**Lifecycle limitations**: methods like `componentDidMount` only mean something in a browser and are never called during server rendering — there is no real DOM there. Logic that depends on them is skipped in the SSR pass, which is an easy source of bugs.

**Server cost**: the server now has to render React components and build HTML strings, which it never did in a pure CSR setup. That is real CPU. Streaming and a sensible caching strategy are the usual mitigations.

## 5. What changes on serverless

Running React SSR on serverless functions (Cloudflare Workers, AWS Lambda) differs from a traditional always-on Node server in one big way: **serverless functions start on demand, and any request may hit a brand new, cold execution environment.** A traditional Node process stays resident and can reuse whatever is in memory.

Three things have to change:

1. **Do not rely on process-level global caches.** The next request may well be served by a fresh instance that cannot see anything the previous one accumulated in memory. Use an external cache (Redis) rather than a module-level variable.
2. **Keep the bundle small.** Cold start time is directly tied to how much code has to load. A traditional Node server barely cares; on serverless, a leaner bundle starts faster.
3. **Adapt to the platform's runtime.** Cloudflare Workers run in a V8 isolate, not a full Node environment, and some Node-only APIs — certain filesystem operations, for instance — may simply not exist. The code has to be written for the target.

---

## Everything in one sentence

> Isomorphic means one codebase running on both sides. Streaming is built on HTTP chunked transfer and in practice means Next.js or Remix, and it only exists with SSR. SSR mainly helps LCP, does little for INP, and can even hurt it through hydration. In practice, watch out for when data is prefetched, which lifecycle methods do not run, and the extra server cost. On serverless the difference is that a cold start can happen at any time, which rules out resident in-memory caches and forces you to keep the bundle small and write for the platform's runtime.

## 6. RSC (React Server Components) is not SSR

The confusion worth clearing up first: **SSR ships HTML; RSC ships "this component's code is never sent at all".**

| | SSR | RSC |
|---|---|---|
| What the server produces | An HTML string | A stream of data describing the UI (not HTML) |
| Does the component's code enter the bundle | **Yes** — the client needs the same JS to hydrate | **No** — a Server Component's code is never shipped |
| What it solves | Blank first paint, SEO | Bundle size, data-fetching round trips |
| Can components hold state | Yes | Server Components cannot |

The two do not conflict, and real projects usually run both: RSC decides *which components' code reaches the browser*, SSR decides *whether the first paint arrives as HTML*.

### How you write it

In the Next.js App Router **every component is a Server Component by default**; becoming a client component requires declaring it:

```jsx
// a Server Component by default: can be async, can read the database directly
async function ProductList() {
  const products = await db.query('SELECT * FROM products');  // no useEffect, no loading state
  return <ul>{products.map(p => <Item key={p.id} product={p} />)}</ul>;
}
```

```jsx
'use client';   // ← a boundary declaration: everything from here down is a client component
import { useState } from 'react';

function Counter() {
  const [n, setN] = useState(0);           // state, events and browser APIs all require this side
  return <button onClick={() => setN(n + 1)}>{n}</button>;
}
```

Three constraints cover most of it:

1. **No `useState` / `useEffect` / event handlers in a Server Component** — it finishes on the server and there is no "afterwards".
2. **`'use client'` is a boundary, not a label** — once a file declares it, everything that file imports becomes a client component too. So push the boundary downward; putting it at the root is equivalent to not using RSC at all.
3. **Props crossing the boundary must be serialisable** — strings, numbers, objects and arrays are fine; functions, class instances and complex objects beyond `Date` are not (Server Actions being a specially handled exception). Passing a Server Component **as `children`** into a Client Component is the usual way around the constraint.

### Roughly how it works

A Server Component renders on the server (at build time or per request) and outputs, instead of HTML, a serialised "UI description" — the RSC payload — saying "here is a div, here insert the client component called Counter with these props". React in the browser receives that stream, slots the client components in, and assembles the full tree.

**That is where the smaller bundle comes from**: libraries such as `marked` or `sanitize-html`, used only inside Server Components, never send a single byte to the browser.

## 1. The conclusion first: what actually changed

|  | Old architecture (the diagram in #75) | RenderingNG |
|---|---|---|
| Where layerization happens | **Before** paint (`Update Layer Tree`) | **After** paint (`layerize`) |
| Which thread it runs on | Main thread | **Compositor thread** |
| What paint produces | One set of paint instructions per layer | **One** display list for the whole document |
| What layerization is based on | DOM and style — you have to **guess up front** which elements deserve a layer | The display list paint has already produced |

The change is called **CompositeAfterPaint**, which is exactly what the name says: the compositing decision moved to after paint.

**Why it was changed.** In the old architecture, layers had to be decided before painting — you had to guess which content was worth its own layer before anything had been drawn. Guess too generously and you waste GPU memory; guess too conservatively and animations force a repaint. On top of that, the work ran on the main thread, so a busy main thread could not even work out whether an element was independently compositable.

The new architecture inverts it: paint the whole document into a single display list, hand that to the compositor thread, and let it decide how many layers to cut **based on what has already been drawn**. The decision is now made from facts instead of guesses, and it no longer costs main-thread time.

## 2. How to read the diagram

There are three dimensions in it:

- **The vertical spine is stage order**, running from `animate` down to `draw`
- **Colour is thread/process ownership**: green = renderer main thread, yellow = renderer compositor thread, orange = the Viz process
- **The pale blue blocks on both sides are data structures** — the inputs and outputs of each stage

Slice it horizontally by colour and you get the single most important sentence about this architecture: **the main thread's work ends at `commit`; everything after that belongs to somebody else.**

| Thread / process | Stages it owns |
|---|---|
| Renderer main thread (green) | animate, style, layout, pre-paint, paint, **commit** |
| Renderer compositor thread (yellow) | scroll, **layerize**, raster / decode, activate |
| Viz process (orange) | aggregate, draw |

`animate`, `scroll` and `raster` are two-toned in the diagram — they can run on either thread. **That two-tone is exactly why scrolling and transform animations do not disturb the main thread.**

## 3. The twelve stages

Following the official list, top to bottom along the spine:

| # | Stage | What it does |
|---|---|---|
| 1 | **animate** | Advances computed styles and property trees along declarative timelines |
| 2 | **style** | Applies CSS to the DOM, producing computed styles |
| 3 | **layout** | Works out the size and position of every element, producing an **immutable fragment tree** |
| 4 | **pre-paint** | Computes **property trees** and invalidates stale display lists and GPU textures |
| 5 | **scroll** | Updates the scroll offset — really just changing one transform in the property trees |
| 6 | **paint** | Produces a **display list** describing how to rasterize the DOM into GPU textures |
| 7 | **commit** | Copies the property trees and the display list over to the compositor thread |
| 8 | **layerize** | Cuts the display list into a **composited layer list** so layers can be rasterized and animated independently |
| 9 | **raster / decode / paint worklets** | Turns paint instructions, encoded images and worklet code into **GPU textures (tiles)** |
| 10 | **activate** | Builds a **compositor frame**: how to draw, where the tiles go, which visual effects to apply |
| 11 | **aggregate** | Viz merges every visible compositor frame into one global frame |
| 12 | **draw** | Executes on the GPU and produces pixels |

**Stages can be skipped** — the official docs say so outright: animations of visual effects, and scrolling, can skip layout, pre-paint and paint. And once those three are skipped, the whole update can **run entirely on the compositor thread**.

That line from #75 — "the main thread is pegged by JS and scrolling still holds 60fps" — is something you can now read straight off the colours.

## 4. The four property trees — the real foundation

Every document has four independent property trees:

| Tree | What it holds |
|---|---|
| **transform** | CSS transforms, plus scrolling (a scroll is expressed as a 2D transform matrix) |
| **clip** | Overflow clips |
| **effect** | Everything else visual: opacity, filter, mask, blend modes, `clip-path` |
| **scroll** | Scroll chains and related data, which the compositor thread needs to scroll on its own |

Every DOM element holds a **property tree state** — a `(transform, clip, effect, scroll)` tuple pointing at its nearest ancestor node in each tree. The topology is a **sparse representation** of the DOM: three overflow clips on the page means three nodes in the clip tree.

One entry in the official list of use cases maps directly onto this post: **"decoupling compositing from paint, and compositing from the main thread."** CompositeAfterPaint only works because property trees came first — pulling "how visual effects apply to an element" out of the tangle of DOM and CSS and into a standalone structure is what makes it copyable to another thread and processable there.

It also explains, in passing, why transforms are cheap: **a transform's value lives in the property trees, and changing it produces no new display list.**

## 5. The production chain: how a div becomes pixels

```
display item → display list → paint chunk → composited layer list
  → tile (GPU texture) → draw quad → render pass → compositor frame → pixels
```

- **display item** — one low-level drawing command (draw a border, a background, a run of text) that Skia can rasterize. A single DOM element may produce several: the background of `#green` is one item, the text inside it is another
- **display list** — the list of display items produced by walking the layout tree **in CSS paint order**, sorted **back to front**. That is why a negative `z-index` element sits early in the list even if it comes late in the DOM
- **paint chunk** — adjacent display items that share the same property tree state, grouped together. **This, not the raw list, is what layerize actually consumes**
- **composited layer list** — layerize's output, deciding which chunks are worth their own layer
- **tile** — the viewport is cut into tiles, each backed by a GPU texture. While scrolling, most tiles are just repositioned; only the newly exposed strip needs rasterizing. **The white blocks you see when scrolling too fast in #75 are tiles that have not finished rasterizing**
- **draw quad** — a texture plus a transform plus the visual effects to apply. It **contains no pixels itself**; it is only an instruction about where and how to draw
- **compositor frame** — a series of draw quads packed into render passes and submitted to Viz

One optimization deserves its own note: **display lists get reused.** If a layout object has not changed during the paint walk, its display items are copied straight from the previous list. Better still — the CSS spec guarantees that **a stacking context paints atomically**, so when nothing inside one has changed, that entire stretch of display items is copied in one go and skipped wholesale.

## 6. Change one property — where does the work start?

| What you change | Where it starts | Cost |
|---|---|---|
| Anything affecting size (`width`, `font-size`) | style → layout → pre-paint → paint → commit → … | The whole pipeline; the most expensive |
| `color` / `background` / `box-shadow` | style → paint → … (layout skipped) | Moderate |
| `transform` / `opacity` on an **already promoted** element | Property trees only; layout / pre-paint / paint all skipped | Cheapest, and can bypass the main thread entirely |
| Scrolling | Same as above — it changes the scroll transform in the property trees | Same as above |

Two statements here are sharper than the ones in #75:

1. **The reason it is cheap is not "it only runs composite" — it is that changing one property tree node means layout and paint never re-run.** Same conclusion, different mechanism, and the difference matters a lot under follow-up questioning.
2. **It only holds if the element is already on its own composited layer.** Change opacity on an unpromoted element and it still has to be repainted. Giving that promotion reason up front is exactly what `will-change: transform` is for.

## Summary

- **The old diagram is not wrong** — it depicts the architecture before CompositeAfterPaint. In the new one, layerization happens **after** paint and runs on the **compositor thread**
- **The main thread's work ends at `commit`**: layerize / raster / activate run on the compositor thread, aggregate / draw in the Viz process
- **Property trees are the foundation** (transform / clip / effect / scroll). Decoupling compositing from paint, and from the main thread, rests entirely on them
- **Paint produces a display list, not pixels**; raster is what produces pixels. Text rasterization, shadows and rounded corners are slow in raster, not in paint
- **Stages can be skipped**: an update that skips layout / pre-paint / paint can run entirely on the compositor thread — which is why transform animations do not care how busy the main thread is

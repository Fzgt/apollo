# ① 虚拟列表信息流

> **简历原句**
>
> Built a **virtualized React feed** serving **5M+ daily page views** on a custom **useVirtualList** hook over **IntersectionObserver**: **live DOM nodes stay near 100 at any scroll depth**, scroll **from 30 to a stable 60 FPS**.
>
> ---
>
> 基于自研 useVirtualList hook（底层用 IntersectionObserver）实现承载日均 500 万+ PV 的 React 虚拟列表信息流：任意滚动深度下存活 DOM 节点都稳定在 100 上下，滚动帧率从 30 回到稳定 60。

## 先把词说清

**虚拟列表（virtualized list / windowing）**：只渲染视口里看得见的那些条目，其余的用占位高度假装存在。

**PV（Page View，页面浏览量）**：页面被打开的次数，**同一个人刷十次算十次**。对照：**UV**（Unique Visitor，独立访客）、**DAU**（Daily Active User，日活）、**impressions（曝光量）**。**这四个数字差一个数量级，混用会被问穿。**

**重排 / 布局（reflow / layout）**：浏览器重新计算每个节点的位置和尺寸。**成本随节点数线性增长，是最贵的一步。**

**绘制（paint）**：**不画像素**，产出的是一份**绘制指令列表**（display list）——「这里画个圆角矩形、这里画一行文字」。

**栅格化（raster）**：把绘制指令真正跑成**位图图块（tile）**，在 raster 线程或 GPU 上做。**文字栅格化、阴影、圆角慢在这一步。**

**分层（layerize）**：决定切成几个合成层。**层不是 paint 生成的，是单独一步**——Chromium 从 90 前后的 CompositeAfterPaint 起，先 paint 出整份指令列表、再据此分层。

**合成（composite）**：合成线程把栅格化好的图块生成 draw quads、拼成一帧交给 GPU 上屏。**最便宜的一步。**

**强制同步布局（forced synchronous layout / layout thrashing）**：JS 里读一个几何属性（`offsetTop`、`getBoundingClientRect`），浏览器为了给准确答案**被迫立刻同步跑一遍布局**。

**IntersectionObserver**：浏览器 API，元素进出视口时**异步**通知你，**不需要读几何属性**。

**overscan（缓冲条数）**：视口上下各多渲染几条，防止快速滚动时来不及挂载。

**长任务（long task）**：单个任务占用主线程**超过 50 毫秒**。**一个长任务 = 至少连掉三帧。**

**passive 事件监听**：告诉浏览器「我不会调 `preventDefault`」，**浏览器可以不等 JS 跑完就开始滚动**。

## 这条要讲清什么

虚拟列表本身是有现成库的东西，**讲「我做了个虚拟列表」不值钱**。这条 bullet 真正的价值在于**三个数字的口径你每一个都说得清，而且它们的性质完全不同**：

- **500 万 PV 是我的工作环境，不是我的成果**，数字来自埋点报表。
- **100 个节点是优化成果**，是我自己用 DevTools 量的。
- **30 → 60 帧同样是优化成果**，同样是我自己量的。

**三个数字混着讲一定会被问穿。先把归属分清，再讲技术。**

## 先讲通为什么节点多了会卡

浏览器渲染一帧的流水线，**这条是所有前端性能问题的地基**：

1. **JS** —— 成本随代码量涨。
2. **Style（算样式）** —— 每个节点最终应用哪些 CSS 规则，**成本随节点数涨**。
3. **Layout（布局 / 重排）** —— 算位置和尺寸，**成本随节点数涨，而且这一步最贵**。
4. **Paint（绘制）** —— 记录绘制指令，成本随绘制项的数量和复杂度涨。
5. **Layerize（分层）** —— 决定切几个合成层。
6. **Raster（栅格化）** —— 把指令跑成位图图块，成本随像素面积涨。
7. **Composite（合成）** —— 合成线程拼帧交给 GPU，成本随图层数涨。

**面试里说「五步」也没人挑，但被追问 Paint 和 Composite 之间发生了什么，答不出 Raster 就露怯。**

**重排之所以贵，是因为一个节点的位置会影响它后面所有节点的位置**，所以成本随节点总数线性增长。

**这就是 500 个节点会掉帧的原因：不是节点占内存，是每一帧的布局都要把这 500 个重算一遍。**

## 为什么恰好掉到 30

**这个数不是随手写的，能讲出来会显著提高可信度。**

显示器按固定节奏刷新，60Hz 就是每 **16.67 毫秒**一次。浏览器必须赶在下一次刷新之前把这一帧交出去。**一旦某帧超时，它不会晚一点点交，而是直接等下一个刷新信号。**于是实际帧间隔从 16.67ms 跳到 **33.3ms——正好是 30 帧**。

**所以掉帧不是线性变慢，是踩台阶：要么 60，要么 30，中间那段是抖动。**

## 虚拟列表的两层结构

天真的想法是只渲染看得见的那十条，但这么做**滚动条会消失**——页面里只有十条的高度，浏览器认为内容就那么高。

所以要拆成两层：

```jsx
// 外层 spacer：唯一作用是骗住滚动条
<div style={{ height: total * ITEM_HEIGHT, position: 'relative' }}>
  {visible.map(item => (
    <div
      key={item.id}
      style={{
        position: 'absolute',
        top: 0,
        // ↓ 用 transform 位移，不用 top —— 只走合成，不触发布局
        transform: `translateY(${item.index * ITEM_HEIGHT}px)`,
      }}
    >
      <FeedCard {...item} />
    </div>
  ))}
</div>
```

**一句话记法：外层负责假装有一万条那么高，内层负责只画看得见的那十几条。**

## 为什么用 transform 而不是 top

**这是必背的一条。**

- 改 `top` / `left` / `width` / `height` → **布局 + 绘制 + 合成**，整条流水线走一遍，**最贵**。
- 改背景色、阴影 → **绘制 + 合成**。
- 改 **`transform` 和 `opacity`** → **只走合成**，GPU 直接搬图层，**CPU 几乎不参与**。

原因在于：改 `top` 是在改这个元素**在文档流里的位置，会影响别人，所以必须重排**；改 `transform` 是**把已经栅格化好的那张图搬个位置**，文档流里它根本没动过，不影响任何人，浏览器只需改这层的变换矩阵重新拼帧。

**加分的半句**：transform 的变化可以**完全跑在合成线程上，不需要主线程参与**——主线程被长任务卡住时，合成层上的 transform 动画照样流畅。

## 100 这个数是算出来的

```
渲染条数 = ceil(视口高度 / 单条高度) + overscan × 2 + 1
```

代入移动端典型值——视口 600、单条 80、overscan 3——是 **8 + 6 + 1 = 15 行左右**。

**注意这是行数不是节点数。**一张信息流卡片：外层容器、图片容器、图片本身、时长角标、右栏、标题、底栏、作者、播放量，**八九个元素起步**。15 行 × 8~9 个元素 ≈ **110 上下**，这才是简历上那个 100。

**overscan 是个取舍，不是越小越好。**调到 0 或 1，节点更少，但快速滚动时新条目还没挂载，**用户先看到空白，也就是白闪（blank flash）**。调到 5~10，滚动平滑，但 DOM 数和内存又回去了。

**所以「100 上下」这个数本身就是这个取舍的产物**——被问「为什么不把 overscan 调到 0 让节点更少」，**答案就是白闪**。

## 三个数怎么测

**DOM 节点数。** 最糙的办法是 `document.querySelectorAll('*').length`，但它数的是整页，**而且只含元素不含文本节点**。准一点的办法是只数列表容器的直接子节点。**最好的办法是 DevTools → Performance Monitor，那里有一条实时曲线就叫 DOM Nodes**：一边滚一边看那条线，**优化前是单调上升，优化后是一条平线**。一条平的曲线比任何数字都直观，**要给面试官现场演示就用这个**。另外可以在 Memory 面板抓堆快照搜 **detached DOM nodes（分离节点）**，验证滚过去的条目有没有真被回收。

**这里有个必须主动说清的口径差**：`querySelectorAll('*')` 只数元素节点，而 **DevTools 的 DOM Nodes 数所有节点，包含文本节点和注释**。**同一个页面这两种量法能差近一倍。**简历上那个 100 是列表容器内的元素计数。

**帧率。** 定性验证用 Rendering 面板的实时 FPS 浮层，30 秒就能做完。**最有说服力的证据是 Performance 面板录制**：顶部的帧率条带会标红掉帧，Frames 轨道显示每帧的实际时长，Main 轨道能看到掉帧那几帧主线程在干什么。**Performance Monitor 里的每秒布局次数和样式重算次数可以直接证明是布局阶段被打爆了。**

也可以用 `requestAnimationFrame` 自己数帧，好处是能在**真机真实环境**下跑，但**它自己也在主线程上，主线程被打爆时它同样被推迟，所以重负载下这个数偏乐观**。

**比帧率更有用的一个视角是用 `PerformanceObserver` 监听长任务**：超过 50ms 就是长任务，一个就意味着连掉三帧，**而且它直接指出是哪段代码卡住了**。

**最理想的证据是让 DOM 节点数、布局耗时和帧率出现在同一段 Performance 录制里**，那才是完整的因果链条，而不是三个孤立的数字。

**帧率必须交代设备和场景，否则这个数没有意义。**

- **在什么机器上测的**——同一个页面旗舰机稳 60、低端机连 30 都够呛；**如果用了 DevTools 的 CPU throttling 模拟低端机，一定要说出来**，那是实验室里的标准手段，说出来直接加分。
- **匀速慢滚还是快速甩动（fling scroll）**——**快速滚动才是压力测试**，慢滚可能根本不掉帧。
- **滚到第几屏时测的**——**优化前那个 30 帧一定是列表已经累积到几百条之后测的**，刚打开只有二三十条，全量渲染也不卡。

## stable 这个词怎么撑住

**`a stable 60 FPS` 是比 `60 FPS` 更强的声明，它承诺没有波动。**

而帧率是个**不能简单取平均**的指标：稳定在 30 帧是有点钝但均匀；在 10 和 60 之间反复跳、平均也是 30，**用户感受到的是明显卡顿**。

**用户感知到的卡来自帧时间的方差，不是平均帧率。**所以现代性能工作看的是**帧时长的分位数、长任务数量和掉帧数**，线上看 **INP（Interaction to Next Paint）**。

**所以 stable 的答法是**：滚动过程中 Performance 录制里**没有出现红色掉帧标记**，Frames 轨道里**没有超过 16.67ms 的长帧**——**不是指平均值到了 60**。把 stable 定义成「没有长帧」而不是「平均值高」，**既准确又显得专业**。

## 帧率具体是哪几步提上去的

**第一**，DOM 从 500 多降到恒定 100 上下，**布局时间从 10ms 量级降到 0.5ms 量级**，证据在 Performance Monitor 的每秒布局次数上。

**第二**，用 `transform` 替代 `top`，**只走合成**，GPU 做，主线程无压力，录制里绘制事件明显减少。

**第三**，滚动监听加 **`{ passive: true }`**，等于告诉浏览器我不会阻止默认行为，**浏览器可以立即开始滚动而不等 JS 跑完**，录制里滚动处理不再阻塞合成。

**第四**，用 `IntersectionObserver` 替代「滚动事件 + 读取元素位置」。后者**每次滚动都会强制同步布局**：你在 JS 里读一个几何属性，浏览器为了给你准确答案，**被迫立刻把布局同步跑一遍**。`IntersectionObserver` 由浏览器在自己的时机**异步**算好再通知你，绕开了这一步。

**第四条值得单独强调，因为那个警告不是你推断出来的，是浏览器自己报的**：DevTools 会在主线程轨道上标黄色三角，写着 **Forced reflow is a likely performance bottleneck**。

**「优化前 DevTools 一直在报强制重排，改用 IntersectionObserver 之后警告消失了」——这是能拿出来的具体证据。**

## 500 万 PV 是环境不是成果

同样一个虚拟列表，写在个人博客上和写在日均 500 万 PV 的信息流上，**工程含义完全不一样**。**这个数字是我的工作环境，不是我的成果。**

**简历里 `serving` 这个词用对了**，它描述的是承载，不声称是我带来的；**口头讲的时候也别说成 brought 或 grew**。

**最容易被问穿的地方在这里**：信息流一次加载会滚出几十条内容，所以 **PV 500 万的时候 impressions 可能是 5000 万甚至上亿**。如果记忆里那个数其实是曝光量，**那 page views 这个词就用错了口径，数字还虚高十倍**。

**这个数也不是测出来的，是埋出来的。**前端没有任何接口能告诉你这个页面今天被打开了多少次，**唯一的办法是每次被打开时往服务器发一条记录，日志进数仓聚合，BI 报表按天出 PV**。前端只负责第一段，**500 万是从报表里读的，不是我算的**——这一点必须说清楚，因为它直接决定归因怎么写。

内部产品走的是**内部埋点和 BI 看板**，不是对外的百度统计；**如果记不清内部平台叫什么，就说「内部埋点和 BI 看板」，千万别硬编一个系统名字**，编错比说不知道难看得多。

**顺带一个知识点：PV 天然被低估。**广告拦截插件会拦掉统计域名，用户秒退时 SDK 还没加载完，网络也会失败。**所以真实访问量一般 ≥ 报表里的 PV，简历写 5M+ 带个加号是合理的。**

**归属的正确说法**是「我负责的这个 feed **承载** 500 万以上日均 PV」，不是「我带来了 500 万 PV」。**更好的答法是把规模翻译成工程约束**：这个量级意味着**一次掉帧影响的是百万级用户**，所以改动必须灰度、必须有性能监控，**这也是为什么我们没有直接引一个第三方虚拟列表库，而是自己写了个可控的 hook**。这样这个数字就从吹牛变成了技术决策的依据。

## 为什么自己写而不用现成库

**诚实说：当时更多是团队约束而不是技术判断。**引三方库要走评估流程，而这个需求边界很清楚、卡片结构也固定。自己写的代价是**动态高度、键盘导航、无障碍这些边角要自己补**，而成熟库已经处理过。**现在做的话我会先用 TanStack Virtual，除非它的接口拦住了某个必须的定制。**

**主动说「现在会选库」比硬撑「自己写更好」可信得多。**

顺带一个诚实的补充：这个信息流的**卡片高度本来就不一致**，有的带封面图有的不带，所以可见条数本身随滚动位置浮动——**这是 `near 100` 里那个 `near` 的第二个来源**。动态高度的标准处理是**预估高度 + `ResizeObserver` 测量修正**，或者维护一张偏移量表再二分查找。

## 30 秒回答

> 这是个信息流页面，日均五百万 PV 量级。问题是无限滚动会让 DOM 一直涨，用户滚十屏就是两百多条，滚久了五百条以上，滚动直接掉到三十帧。关键认知是：用户在视口里同时能看到的其实就十来条，其余的假装存在就够了。所以我写了个 useVirtualList，只渲染可视区加上下各几条缓冲，外层用一个撑满总高度的 spacer 保住滚动条，每一条用 transform 的纵向位移定位。真正的收益不是少了多少个节点，是复杂度的量级变了：优化前 DOM 数随已加载条数增长，优化后只随视口高度增长，跟数据量无关，用户滚一万条 DOM 里还是那十几行、一百个节点上下。滚动回到稳定六十帧。

## 英文怎么说

**「复杂度的量级变了」不要说 O(n) to O(1)**，说 **DOM count stopped growing with the data and became a function of viewport height**，更让人信服。**「稳定 60 帧」的定义说 no frame over 16.67 ms**，不要说 the average was 60。**「承载 500 万 PV」用 serving，绝不能说 brought 或 grew。**

**术语对照**：虚拟列表 a virtualized feed ／ 重排 layout、reflow ／ 强制同步布局 forced synchronous layout、layout thrashing ／ 掉帧 dropped frames ／ 长帧 long frame ／ 帧预算 frame budget ／ 长任务 long task ／ 缓冲条数 overscan ／ 白闪 blank flash ／ 占位容器 spacer ／ 分离节点 detached DOM nodes ／ 降速模拟 CPU throttling ／ 快速甩动 fling scroll ／ 卡顿 jank ／ 曝光量 impressions（**注意别和 page views 混**）。

**node 和 element 在英文里也是两个词**，node 含文本节点，两者能差近一倍。

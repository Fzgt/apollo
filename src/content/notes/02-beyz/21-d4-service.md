# Day 4 · 必看 · 定时任务这条怎么答赢

> 🔴 **必看**。这一篇按**面试官会问什么**组织，不按代码文件组织。
>
> 每个问题三段式：**① 我当时怎么做的（诚实、简短）→ ② 背后的通用原理 → ③ 规模上去了我会怎么做**。
> **第 ③ 段是赢面试的地方**——面试官在评估的是你能不能在他那儿做这件事，不是你当年做的东西多大。

## Q：为什么要单独一个服务

### ① 事实

主应用是 Next.js，部署在无状态平台上。**定时任务需要一个常驻进程**——一个每分钟自己醒一次、决定该给谁发邮件的东西。无状态平台上没有这个语义：serverless 函数是被请求唤醒的，不会自己醒。

### ② 原理

这是**「按运行模型拆服务」**，不是按业务域拆。

| 运行模型 | 适合放哪 |
|---|---|
| 请求驱动、短生命周期 | serverless / 无状态实例 |
| **常驻、自己触发** | **长跑进程 / 专门的 worker** |
| 长连接 | 专门的网关 |

**拆的收益**：独立发版（改邮件模板不用重新部署前端）、独立重启、独立扩容——**它的负载曲线和主站完全不同**。

**代价也要说**：多一套部署和监控、数据库连接多一个来源、**两边 schema 要保持同步**。

### ③ 生产级会怎么做

**402 行的规模下，单独一个 NestJS 服务是合理的。但如果这类任务变多，我会换成托管的调度层：**

- **云原生的调度**：EventBridge Scheduler / Cloud Scheduler 触发一个函数，**不用自己养常驻进程**
- **任务队列**：BullMQ / Temporal —— 有重试、退避、死信队列、可观测性，**这些我现在全是手写或者没有**
- **关键的架构升级：从轮询改成事件驱动**。用户注册的那一刻就排一个 24 小时后执行的延时任务，**根本不用每分钟扫库**

> **最后这条是这一问的加分项**：它说明你知道**轮询是这类需求的下策**——我当时用的就是下策，因为最简单。

## Q：怎么保证同一封邮件不会发两遍（最值钱的一问）

### ① 事实

幂等靠**一张表**，不靠调度频率：

```ts
// email.job.ts:24-37
.leftJoin(upgradeReminders, eq(users.id, upgradeReminders.userId))
.where(and(
  eq(users.subscribedPlan, 'Free'),
  lt(users.createdAt, twentyFourHoursAgo),
  isNull(upgradeReminders.id)        // ⭐ 只挑「还没发过」的
))
```

发完写一条记录。**「已发过」是数据库里的一行，不是内存里的标志位、不是「上次跑到哪」的游标。**

`leftJoin` + `isNull` 是 SQL 里的 **anti-join**：左表里那些在右表中没有对应行的记录。

> **所以服务重启、换机器、跑几次都不影响正确性——判据是持久化的事实，不是进程状态。**

### ② 原理：至少一次 vs 至多一次

**这是分布式系统的核心取舍，答这一问必须上到这个层次。**

发邮件涉及**两个系统**（邮件服务商 + 你的数据库），跨系统的操作**没有原子性**。于是只有两种排法：

| 排法 | 崩在中间会怎样 | 语义 |
|---|---|---|
| **先发后记**（我当时这样） | 邮件发了，记录没写 → **重发** | **at-least-once（至少一次）** |
| **先记后发** | 记了已发送，邮件失败 → **永远收不到** | **at-most-once（至多一次）** |

**没有第三种，除非引入分布式事务——而那个代价通常不值得。**

**所以真正的问题不是「怎么做到恰好一次」，是「这个业务宁可重复还是宁可丢失」。**

- **营销邮件 → 宁可重复**：多收一封升级提醒是骚扰，收不到是一次转化机会没了 ✅ 我当时选的
- **付款通知 / 密码重置 → 宁可丢失**：重复发付款成功通知会让用户以为被扣了两次

> **「exactly-once 在跨系统场景下不存在，能做到的是 at-least-once 加上幂等消费」**——这句话说出来，这一问就满分了。

### ③ 生产级会怎么做

**当时的实现有两个我知道的洞：**

1. **`select` 和 `insert` 之间没有锁** —— 两个实例并发会各发一封
2. **崩在发信和记账之间会重发**

**生产级的四层做法：**

| 做法 | 解决什么 |
|---|---|
| **`userId` 上建唯一索引** | 第二次 insert 直接违反唯一约束，**数据库层面挡住并发重复**。这是最便宜也最可靠的一层 |
| **先插「处理中」再发信** | 插入成功才拿到发送权（等于抢锁），发完更新状态。**把二选一变成三态**，可以重试也可以对账 |
| **给邮件服务商传幂等 key** | 多数服务商支持 `Idempotency-Key`，**把去重推到最后一层** |
| **调度层保证单实例** | 分布式锁或者用支持 singleton 的调度器 |

> **「唯一索引兜底」这一招和 [Stripe webhook 的幂等](/docs?section=numbers&item=n02-stripe-events)、[百度提现的幂等键](/docs?section=numbers&item=n07-qps) 是完全同一个模式：把不变量放在数据层，不放在应用层的 if 里。**
>
> **能把三个项目串起来讲这一点，是 Day 14 Round 3 那道跨项目题的现成答案。**

## Q：为什么 cron 定成每分钟

### ① 事实

```ts
// @Cron(CronExpression.EVERY_DAY_AT_9AM)     ← 注释掉的
// @Cron(CronExpression.EVERY_10_MINUTES)     ← 注释掉的
@Cron(CronExpression.EVERY_MINUTE)
```

**幂等靠表不靠频率，所以频率不影响正确性，只影响触达延迟**——用户注册满 24 小时后，最多一分钟收到提醒。

**但诚实地说：对一个「24 小时后才发」的提醒，每分钟的精度是过剩的。** 注释里从每天降到每分钟的痕迹，说明这是调试时调下来忘了改回去的。

### ② 原理

**调度频率和正确性正交** —— 这是「幂等做在数据层」买到的自由：做对了，频率就变成纯粹的产品参数（延迟 vs 成本），而不是正确性参数。

**如果幂等靠的是「记住上次跑到哪」，频率一变就可能漏或者重。**

### ③ 生产级会怎么做

**改成事件驱动，根本不轮询**：用户注册时就排一个 24 小时后执行的延时任务（BullMQ 的 delayed job / EventBridge 的 one-time schedule）。

- 精确在 24 小时那一刻触发，不多不少
- 不用每分钟扫库
- **用户量涨了也不会变慢**——轮询的代价随用户数线性增长，延时任务是 O(1)

> **这一段是这一问真正的价值**：把一个「我当时随手设的值」变成「我知道这个方案的天花板在哪」。

## Q：为什么 Fastify 不是 Express

### ① 事实

```ts
// main.ts:3,6
new FastifyAdapter()  →  NestFactory.create<NestFastifyApplication>(...)
```

**NestJS 把 HTTP 层抽象成了可替换的 adapter**，换 Fastify 只改这一行加一个依赖，controller / service / DI 全都不动。

### ② 原理

Fastify 的实际差异：路由用**基数树**匹配、序列化走**预编译的 JSON schema**（不是通用 `JSON.stringify`）、schema 校验是一等公民、插件有**显式的封装边界**（不像 Express 中间件全局叠加）。

### ③ 怎么答才不翻车

> ⚠️ **别吹性能。** 这个服务的负载是「每分钟查一次库、发几封邮件」——**吞吐差异在这里根本体现不出来。**

**赢的答法是主动否认自己本可以吹的点：**

> 「这是选型题不是性能题。Nest 的 adapter 让切换成本几乎为零，Fastify 在 schema 和 swagger 集成上更顺手，就选了它。**这个服务的量级完全用不到它的吞吐优势，说它解决了性能瓶颈是不诚实的。** 真要吞吐成为瓶颈，那时候该考虑的是水平扩容和把同步逻辑挪出请求路径，不是换个 HTTP 框架。」

**主动否认一个能吹的点，比多吹一个点更能建立可信度。**

### 顺带：NestJS 的 DI 要能讲清

```ts
constructor(
  private mailerService: MailerService,              // 按类型注入
  @Inject('DATABASE_CONNECTION') private db: any     // 按 token 注入
) { }
```

**两种注入方式都在这一段里**：`MailerService` 是**按类型**（Nest 从 TS 元数据读参数类型）；`db` 是**按字符串 token**——因为数据库连接不是一个类、是工厂 provider 造出来的对象，**没有类型可以匹配**。

| 概念 | 一句话 |
|---|---|
| **Module** | 组织单元：声明有哪些 provider、导出什么、依赖谁 |
| **Controller** | 只管 HTTP：路由、参数、返回值。**不放业务逻辑** |
| **Provider** | 可被注入的东西，`@Injectable()` 标记 |
| **DI 容器** | 启动时按类型或 token 解析依赖，自己构造并缓存 |

## 一个该主动交代的疤

```ts
// app.controller.ts:17-28
@Get('trigger-cron')
async triggerCronManually() {
  await this.mailerService.sendEmail('fzgt320@gmail.com', ...)   // 写死的邮箱
}
```

**三个问题：它并不真的触发 cron（只给固定邮箱发测试邮件）、没有任何鉴权、用 GET 做有副作用的操作**（HTTP 语义里 GET 应该安全且幂等，浏览器预取和链接预览都可能意外触发它）。

**答法**：「这是当时留的调试口子，名字起得比它做的事大。**上生产前应该删掉，或者至少加鉴权并改成 POST。**」

> **主动指出自己代码里的疤，收益比看起来大**：它证明你现在的标准高于当时的产出——**而面试官招的是现在的你。**

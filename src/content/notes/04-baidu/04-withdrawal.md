# ④ 提现客户端

> **简历原句**
>
> Built the **withdrawal client** on a path **peaking above 2,000 QPS**: **request locking** drops in-flight duplicates, **client-generated idempotency keys survive reloads**, and **uncertain outcomes surface as failures, never successes**.
>
> ---
>
> 在峰值超过 2,000 QPS 的链路上实现提现客户端：请求锁丢弃在途的重复请求，前端生成的幂等键在页面刷新后依然有效，结果不确定时一律按失败提示，绝不显示成功。

## 这条要讲清什么

一句话：前端在金融链路里能保证什么，不能保证什么。

这条 bullet 最容易翻车的方式，是把它讲成「我用前端的锁扛住了两千 QPS」。那句话经不起一层追问——打开开发者工具直接调接口就绕过去了。

它真正的价值在于你能主动划清界限：前端减少无效负载，后端提供正确性。说不出这句，这条 bullet 就是负资产。

## 先定义幂等

幂等的意思是同一个操作执行一次和执行 N 次，系统最终状态一样。「把余额设为一百」是幂等的，做几次都是一百；「余额减五十」不是幂等的，做两次就扣了一百。

提现天然属于第二种。所以必须在外面套一层机制，让重复执行变成识别出是重复、不再执行。

## 防抖、节流、请求锁，别混

防抖是多次触发之后停下来若干毫秒才执行一次，适合搜索框输入和窗口尺寸变化。节流是每若干毫秒最多执行一次，匀速，适合滚动和鼠标移动。请求锁是第一次立即执行，之后到响应回来为止全部拦掉，适合提交类操作。

提现按钮为什么不能用防抖：停下来才生效意味着用户点了一百次，只有最后一次在几百毫秒后发请求。用户点第一下时什么都没发生，他会觉得没反应，于是点得更多——体验和意图完全相反。

提交类操作要的是首次立即执行加锁住后续，不是防抖的最后一次才执行。

## 请求锁的两个版本

朴素版是一个布尔量：有请求在飞就直接返回不做事，没有就上锁、发请求，最后在 finally 里解锁。

finally 那一句是重点。如果只在成功分支里解锁，一次失败之后按钮就永久锁死了，用户再也提不了现——这是这个模式最常见的一个 bug。

按参数去重的版本用一个 Map，键是这一笔的单号，值是正在飞的那个 Promise。第二次调用时不是拒绝，而是把第一次那个 Promise 原样还给他；调用方 await 之后照样拿到结果，它根本不知道自己被去重了，所以调用端一行特判都不用写。请求结束后把这一项删掉，下次点击是一次全新请求。

用 Map 而不是布尔量，锁的粒度就从整个按钮细化到了每一笔单，用户同时提两笔不同的不会互相挡。

这个模式叫请求去重，React Query 和 SWR 内部就是这么做的。能点出这一句，说明你知道自己在复现一个通用模式，而不是随手写的。

## 幂等键：前端能做的最有价值的一件事

前端锁挡不住三件事，因为那个 Map 只活在当前页面的内存里：网络超时后的自动重试、用户在不同设备或不同标签页同时操作、页面刷新之后再点——刷新等于整块内存清零，锁没了。

所以真正的保证必须来自后端幂等：每个提现请求带一个这笔操作专属的随机串，后端把处理过的串存下来，同一个串再来就直接返回上次的结果，不再执行扣款。

前端的配合是关键的一半，三点。第一，key 要提前生成，进页面就生成而不是点击时生成——点击时生成的话，用户点两次就是两个不同的 key，后端看到的是两笔不同的提现。第二，存进 sessionStorage，这样刷新页面之后还是同一个 key，否则刷新重试在后端看来是一笔新提现，简历里 survive reloads 就是这个。第三，每次调用都带上它。

## 结果不确定时一律往失败那边说

默认失败，只有明确成功才展示成功，这套做法叫防御式兜底。

明确失败的时候——业务错误码或者 4xx、5xx——显示错误并允许重试。明确成功的时候展示成功。而结果不确定的时候，也就是超时、网络中断、请求发出去没有响应，按失败处理，但措辞要谨慎：说「网络异常，请稍后查看提现记录」，不要直接说「失败了」，因为后端可能已经处理了。

为什么不确定要往失败那边倒？因为两种错法的代价不对称。错误地显示失败，用户会去重试，而重试有幂等键兜底不会真的扣两次，代价只是一次白跑。错误地显示成功，实际没到账，用户以为提了但钱没来，那是客诉、投诉和事故。

代价不对称是这一节的题眼，也是所有金融前端错误处理的通用原则。

## 两千 QPS 是什么、谁测的

**归属：这个数字不属于前端。** QPS 是后端指标。前端不扛 QPS，前端贡献 QPS——每个用户点一下就贡献一次。前端拿不到全站每秒请求数，那是网关和后端监控里的东西。

从后端同事那里知道这个数完全合理，这是团队里正常的信息流动。但你必须能说清楚你知道的是什么、你做的是什么，这两件事不能混。

简历现在的写法是安全的：说的是链路的量级，而锁和幂等键各自写成自己的动作，规模还在，但不声称是你的锁扛住的。

**QPS 是算出来的，不是测出来的。** 监控系统实际存的是一个只增不减的计数器，QPS 是这个计数器在一个时间窗口上的斜率：窗口结束时的计数减去开始时的计数，除以窗口长度。

于是窗口大小直接决定了你看到的数字。同一段流量，用一秒的窗口算出来可能是两千，用一分钟的窗口可能只有六百，用五分钟可能只有三百。窗口越大峰值被抹得越平，所以「峰值两千 QPS」不说窗口等于没说。

峰值和持续也差很远：峰值两千持续三秒，和持续两千跑三十分钟，对数据库的压力完全不是一回事。简历现在明确只说峰值。

**监控还是压测，含义天差地别。** 监控的含义是真实发生过，来源是网关记日志、采集、进时序库、看板画曲线，正确表述是「活动峰值时段监控看到两千以上」。压测的含义是验证过能承受，来源是用工具造流量打系统、梯度加压，正确表述是「压测验证能扛两千以上」。

这两个绝对不能混说。说成监控但其实是压测，是在虚报业务体量；反过来则是低估了自己的工作。

压测的几个概念能说出来就说明你真见过。梯度加压是从低 QPS 一档档往上加，不是一上来就打满。拐点或者说容量水位，是 QPS 还在涨但 P99 延迟开始飙升、错误率开始上升的那个点，那才是真实容量——容量不是打得进去多少，是打进去还不崩的最大值。完整的压测结论长这样：不是「能扛两千 QPS」，而是「压到两千时 P99 延迟一百二十毫秒、错误率为零，继续加到两千六时 P99 涨到八百毫秒」。线上压测必须把压测流量写进影子表，金融场景尤其不能污染真实资金数据。

记不清就用安全说法：这是后端给的口径，我记得是活动期间的峰值量级，具体是监控还是压测报告我需要确认。「我需要确认」永远比编一个答案安全。

## 后端做了什么才扛得住

讲这段能把「听说」升级成「理解」。

接入层做限流，令牌桶或漏桶，宁可拒绝一部分也不能全崩；活动开始瞬间用排队或验证码削峰；异常时熔断降级。

应用层保持无状态，加机器就能线性扩容。这里有个容易忽略的点：QPS 是集群指标不是单机指标，二十台机器分摊两千 QPS，单机只有一百。

数据层才是真正的瓶颈。提现是写操作，缓存救不了写。常见手段是按用户 ID 哈希分库分表打散、读写分离。还有一个热点账户问题：如果所有提现都从同一个资金池账户扣钱，所有事务都在抢同一行的行锁，分库分表也救不了，要把账户拆成多个分桶。

一致性靠两样东西写在数据层：幂等键建唯一索引，重复请求直接违反约束；余额不变量写进 UPDATE 的 WHERE 条件里，靠影响了几行来判断成败。

为什么不能先查再写：查和写之间有时间窗口，两千 QPS 下两个并发请求可能同时查到「不存在」然后都写进去。数据库的唯一索引和单条 UPDATE 是原子的，没有这个窗口。

异步化也要提：提现通常不是同步完成的，校验后落一条处理中的订单就返回，真正打款走异步队列。所以那两千 QPS 是提交申请的量，不是实际打款的量，这两个数可以差很远。

把不变量放在数据层而不是应用层的 if 判断里——这和 Stripe 那条终身档保护、Beyz 邮件的唯一索引、BioMap 的类型约束是同一个模式，四个例子来自三个项目，串起来就是跨项目追问的现成答案。

## 零资损被问到怎么答

简历原句里曾经有「没有一分钱资金损失」，已经删了。删的原因值得知道：它是个否定性断言，要证明从来没有发生过任何一次资金损失，而你没法穷举所有没发生的事。

唯一能支撑它的是对账，而对账在财务侧，不在任何技术监控看板里：业务库的提现流水和支付渠道次日下发的对账文件按渠道流水号逐笔比对，差异进差错处理流程，补单、退款或者追回。所以零资损的准确含义是对账差异全部平掉、最终没有净损失。

资损防线是分层的，讲出来很加分。第一层是前端：请求锁、幂等键、错误兜底，作用是减少无效重复。第二层是网关和应用：限流、参数校验、风控，挡住异常流量。第三层是数据库：幂等键唯一索引、余额不变量、事务，这才是正确性的真正来源。第四层是异步状态机：订单只允许合法的状态转移，防乱序和重放。第五层是对账：逐笔核对，差异进差错流程，作用是发现并修补。

关键洞察是：前四层是让它不发生，第五层是发生了也能发现并补回来。真正的零资损靠的是第五层兜底，不是前四层做到完美——任何做支付的人都知道前四层不可能完美，网络会抖、渠道会超时、人会写 bug。

承认自己只是第一层，反而比声称做到了第五层更可信。

## 被追问时的分工

用户能绕过前端锁吗？能，而且很容易，打开开发者工具直接调接口就行。所以前端锁只减少无效请求，正确性靠后端幂等键、唯一索引、数据库事务和余额不变量。

两千 QPS 是你测的吗？不是，是后端监控里整条链路的量级；前端不扛 QPS，前端贡献 QPS。

零资损怎么保证的？那是对账的结论，不是我测的；防线分五层，前端只在第一层。

前端还能做什么？没配额时把按钮置灰、活动开始瞬间排队或验证码削峰——但这些都是体验优化，不是正确性保证。

一句话收尾：前端减少无效负载，后端提供正确性。

## 英文怎么说

三句必须背下来。整条 bullet 的收尾句是 the client reduces useless load; correctness comes from the backend。「前端不扛 QPS，前端贡献 QPS」说 the client doesn't absorb QPS, it contributes to it。「零资损是对账的结论」说 that's a reconciliation result, not something I measured。

其他常用词：提现是 withdrawal，在途请求是 in-flight request，请求锁是 request locking，请求去重是 request deduplication，首次立即执行是 leading edge 相对 trailing edge，幂等键是 idempotency key，刷新后仍有效就是简历原句 survive reloads，防御式兜底是 defensive fallback，结果不确定是 uncertain outcome，代价不对称是 asymmetric cost，唯一索引是 unique index，业务不变量是 business invariant，限流是 rate limiting，令牌桶是 token bucket，熔断是 circuit breaker，水平扩容是 scale horizontally，分库分表是 sharding，热点账户是 hot account，行锁竞争是 row-lock contention，峰值和持续是 peak 和 sustained，压测是 load testing，梯度加压是 ramp up，影子库是 shadow table，对账是 reconciliation，差异是 discrepancy，资损是 financial loss。

## 30 秒回答

> 这是个活动期间的提现入口，峰值时整条链路到过两千多 QPS。前端在这里的职责很窄但很明确：把无效的重复请求挡在发出之前，并且在结果不确定时永远往失败那边说。具体三件事：请求发出到响应回来这段窗口里锁住同一笔提现，不让用户狂点产生第二个请求；幂等键在前端生成并存进 sessionStorage，这样用户刷新页面重试，后端还能认出这是同一笔；超时和网络中断一律按失败提示，引导去查提现记录，绝不显示成功。但我很清楚前端锁挡不住跨设备、跨标签页和刷新重试，真正的正确性来自后端的幂等键和数据库约束——前端减少的是无效负载，不是提供保证。

## The basics

```javascript
const [isPending, startTransition] = useTransition();
//     ↑ first      ↑ second     ← the order cannot be swapped: isPending first, startTransition second
```

- `isPending`: a boolean saying whether this transition is still in flight
- `startTransition`: a function that marks a state update as low priority and interruptible

```javascript
function TabContainer() {
  const [tab, setTab] = useState('about');
  const [isPending, startTransition] = useTransition();

  function selectTab(nextTab) {
    startTransition(() => {
      setTab(nextTab); // marked as a transition; higher-priority updates can interrupt it
    });
  }

  return (
    <div>
      {isPending && <Spinner />}
      {/* ... */}
    </div>
  );
}
```

---

## ⚠️ The core rule: the function you pass must be synchronous

Straight from the React docs:

> The function you pass to startTransition must be synchronous. React immediately executes this function, marking all state updates that happen while it executes as Transitions. **If you try to perform state updates in a setTimeout, for example, they won't be marked as Transitions.**

**React runs the function immediately and synchronously, and only the state updates that happen during that synchronous run are marked as transitions.**

---

## ❌ The common mistake: putting an async `.then()` callback inside

```javascript
// wrong
startTransition(() => {
  fetchData().then(result => setData(result)); // setData is in .then() — it is NOT marked as a transition
});
```

**Why it does nothing**: `fetchData()` is async, and the `.then()` callback does not run until the promise resolves — long after `startTransition`'s synchronous tracking window has closed. `setData(result)` is an ordinary, normal-priority update, and the `startTransition` wrapper achieved nothing.

React documents this explicitly as a known limitation, with a section titled "React doesn't treat my state update after await as a transition".

---

## ✅ The right way: wrap again after the await

```javascript
const loadData = () => {
  startTransition(async () => {
    const result = await fetchData();
    startTransition(() => {  // ← the point: wrap again after the await
      setData(result);
    });
  });
};
```

(React 19 improved `startTransition`'s handling of async functions, but the rule that state updates after an `await` need another `startTransition` still holds. The docs confirmed it repeatedly through 2024–2025; it is not fully solved.)

---

## While we are here: isPending and Suspense are two separate loading mechanisms

- **`isPending`**: a loading state you manage yourself alongside `useState`, controlled by the component.
- **`Suspense`**: catches a **promise thrown** during a child's render. It has nothing to do with `isPending`.

If a component manages its loading state manually with `useState` and `isPending` and never throws a promise while rendering, wrapping it in `<Suspense fallback="...">` will never trigger. The two do not cooperate automatically unless the component genuinely uses something that throws a promise — `React.lazy`, or a Suspense-aware data-fetching library.

---

## In one sentence

> `useTransition` returns `[isPending, startTransition]` in that order. `startTransition` only counts the code that runs **synchronously** inside the function it wraps; a state update after an `await` or `.then()` needs another `startTransition` to count. And `isPending` and `Suspense` are separate loading mechanisms that do not link up on their own.

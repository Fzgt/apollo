## 1. concept-tracker —— 90 秒讲法

> 概念卡片追踪器：管理面试要复习的名词，增删改查 + 筛选 + 分页 + 按模块统计。

**按这个顺序讲，不要按目录讲：**

1. **它解决什么**：我复习的时候要管一堆概念卡片，顺手把它做成了真能用的东西——所以我自己在用，不是写完就扔的 demo。
2. **后端分三层，依赖单向**：`model`（数据长什么样、什么算合法）→ `store`（存取）→ `httpapi`（HTTP 翻译层）。`httpapi` 用 `store`，`store` 用 `model`，反过来一律不行。业务规则不进 handler，SQL 不进 handler。
3. **存储层先定接口再写实现**：`store/store.go` 只有一个 `Repository` 接口，`sqlite.go` 是它的一个实现。好处是上层只依赖接口，测试可以塞假实现，换库不动上层。
4. **SQL 是手写的**：条件动态拼、值永远走 `?` 占位符。防注入不是靠过滤引号，是靠让驱动把值当数据发过去。
5. **前端 Angular 22，standalone + zoneless**：状态全在 signal 里，派生值用 computed，拉数据用 effect 自动触发。
6. **测过**：16 个 Go 测试，`-race` 竞态检测打开跑，全绿。

## 2. Go —— 追问与答案

**「`var _ Repository = (*SQLiteRepo)(nil)` 这行在干什么？」**（`store/sqlite.go:29`）
Go 的接口是隐式实现的，没有 `implements` 关键字。这行把一个 nil 指针赋给接口类型的匿名变量，运行时什么都不做，但**编译期强制检查**方法集是否完整。少写一个方法，编译当场失败，而不是等到别处调用时才报。

**「Go 的接口和 TypeScript / Java 的接口有什么不同？」**
隐式实现，所以接口可以**定义在使用方**而不是实现方。`sqlite.go:314` 那个 `rowScanner` 就是例子——标准库的 `*sql.Row` 和 `*sql.Rows` 没有共同接口，但都有 `Scan` 方法，我自己定义一个只有 `Scan` 的接口，那两个类型立刻就"实现"了它，不用改标准库一行。这在 Java 里做不到。

**「错误处理你怎么做的？」**
三件事：`%w` 包装保留错误链；哨兵错误 `ErrNotFound`（`store.go:23`）让上层用 `errors.Is` 判断而不是比字符串；**在边界上翻译错误**——`sqlite.go:195` 把数据库的 `sql.ErrNoRows` 翻成自己的 `ErrNotFound`，不让数据库概念泄漏到 HTTP 层。用 `%v` 而不是 `%w` 会把错误压成一句字符串，链子就断了。

**「`sql.Open` 之后为什么还要 Ping？」**（`sqlite.go:81`）
`sql.Open` 不会真的连库，它只准备连接池，第一次用才建连接。想在启动阶段就发现"连不上"，必须手动 Ping 一次。

**「为什么 `SetMaxOpenConns(1)`？」**（`sqlite.go:88`）
SQLite 的写会锁整个库文件，放开连接数反而互相抢锁报 `database is locked`。**换成 Postgres 就完全反过来**，那时候要把这个值调大。这是"配置跟着存储引擎走"的例子，不是通用最佳实践。

**「`rows.Err()` 不查会怎样？」**（`sqlite.go:179`）
`rows.Next()` 返回 false 有两种可能：读完了，或者中途出错。不查这一下，出错会被当成正常读完——**静默丢数据**，最难查的一类 bug。

**「`pageArgs := append(append([]any{}, args...), …)` 为什么要套两层？」**（`sqlite.go:152`）
`append` 可能就地改写底层数组，直接 `append(args, …)` 会把外面的 `args` 弄脏。切片共享底层数组是 Go 的经典坑，先拷进一个新切片再追加是最省心的写法。

**「`defer rows.Close()` 不写呢？」**
连接不还回池里，最终把连接池耗干。这是 Go 后端最常见的资源泄漏。

**「为什么 items 要 `make([]model.Card, 0, …)` 而不是留 nil？」**（`sqlite.go:168`）
nil 切片 `json.Marshal` 出来是 `null`，空切片才是 `[]`。前端拿到 null 再 `.map` 就炸了。

**「中间件是什么？顺序为什么这么排？」**（`httpapi/middleware.go`、`router.go:38`）
Go 里没有框架魔法，中间件就是 `func(http.Handler) http.Handler`。顺序是 CORS → 请求ID → 日志 → recover → 业务：
- CORS 最外，OPTIONS 预检要尽早短路；
- 请求 ID 次外，后面的日志和错误都要用它；
- **日志必须在 recover 外面**——这样 handler panic 之后，recover 写完 500，日志层依然记得下这条请求和它的状态码。反过来的话 panic 那条请求在访问日志里会彻底消失。

`chain` 的循环是**倒着走**的（`middleware.go:28`），因为最外层的必须最后一个被套上去。

**「`recover` 为什么必须在 `defer` 里？」**
语言规定：只有在 defer 的函数里调用 recover 才有效。Go 的 panic 会一路炸穿调用栈，没人 recover 整个进程就退出——一个空指针能让所有用户断线。所以 HTTP 服务这个中间件是必备的。另外 `middleware.go:143` 对外只回"服务器内部错误"，**不把 panic 内容返回给客户端**，那会泄漏文件路径甚至连接串。

**「怎么记状态码？」**（`middleware.go:84`）
`http.ResponseWriter` 是只写接口，写完没法问它"刚才写的是多少"。所以包一层 `statusRecorder` 在写的路上截一刀。注意 handler 不调 `WriteHeader` 直接 `Write` 时标准库会隐式发 200，要补上，否则日志记成 0。

**「context 用来干什么？」**
每个 store 方法第一个参数都是 `context.Context`。用户关掉页面或请求超时，ctx 被 cancel，底层 SQL 查询跟着中断，不会白占连接跑完。另外 context key 用了自定义类型 `ctxKey`（`middleware.go:42`）——直接用字符串当 key，两个包会互相覆盖，这是 context 规范明确要求的。

**「并发安全怎么保证的？」**
请求 ID 的计数器用 `atomic.Int64`（`middleware.go:49`）。每个请求跑在独立 goroutine 里，普通 `counter++` 有数据竞争，**`go test -race` 能直接测出来**——我的测试就是带 `-race` 跑的。

**「优雅关闭讲一下。」**（`cmd/api/main.go:74-119`）
问题：Ctrl+C 直接杀进程，处理中的请求被硬截断，滚动更新每次都踩。
解法：`signal.NotifyContext` 捕获 SIGINT/SIGTERM（后者是 `docker stop` / k8s 删 Pod 发的）→ `ListenAndServe` 放进 goroutine（它是阻塞的）→ 主 goroutine 用 `select` 同时等"服务出错"和"收到信号" → 收到信号就 `srv.Shutdown(带 10 秒超时的 ctx)`，停止接受新连接、等已有请求做完。
两个细节：错误 channel 缓冲为 1，避免没人读时 goroutine 永远卡住；正常关闭时 `ListenAndServe` 返回 `ErrServerClosed`，那不算错误要专门排除。

**「三个 Server 超时是干什么的？」**（`main.go:69-71`）
`ReadTimeout` / `WriteTimeout` / `IdleTimeout` 的默认值是**永不超时**。不设的话，一个连上来不说话的客户端能一直占着连接和 goroutine，几千个就能拖垮服务（Slowloris）。生产必设。

**「Go 1.22 之后还需要 chi / gorilla 吗？」**（`router.go:18`）
标准库 `ServeMux` 现在支持 `"GET /api/cards/{id}"` 这种带方法和路径参数的模式，这个项目全部用标准库。以前要装第三方就是因为它做不到。**还需要第三方的场景**：路由分组 + 组级中间件、正则约束、大量路由时的性能。小项目用标准库就是少一个依赖、少一份升级和安全负担。

**「panic 和 error 怎么选？」**
error 是预期内的失败（查不到、参数不合法），panic 是程序自己写错了。`main.go:48` 启动失败用 `os.Exit(1)` 而不是 panic——配置错误不是 bug，打一整页调用栈没意义，一行清楚的错误加非零退出码才是给 CI 和运维看的。

## 3. Angular —— 追问与答案

两个项目的前端都是 Angular 22（`@angular/core: ^22.1.0`，TypeScript 6.0），下面的行号按 `concept-tracker/web` 给。

**「zoneless 是什么？对写法意味着什么？」**（`app.config.ts:15`）
**Angular 22 默认不带 zone.js**，两个项目的 package.json 里都没有这个依赖。以前的变更检测靠 zone.js 猴子补丁拦截 `setTimeout`、事件、XHR，然后从根组件开始脏检查整棵树；现在靠 signal 变更精确通知，只刷用到它的那块 DOM。
**代价**：普通类字段改了视图不会刷新，状态必须放进 signal。照抄几年前的教程最容易在这里翻车。这句话本身就是"我用的是现在的 Angular，不是记忆里的 Angular"的证明。

**「signal / computed / effect 怎么分工？」**（`cards-page.ts:60-119`）
- signal = 源状态（`cards`、`page`、四个筛选条件）
- computed = **派生**状态（`totalPages`、`hasPrev/hasNext`）。判断标准一句话：**这个值能不能从别的状态推出来？能就必须用 computed。** 把总页数也存成 signal 再手动同步，迟早出现两个状态对不上。
- effect = 副作用。`cards-page.ts:109` 那个 effect 读了 page 和四个筛选条件，所以改任意一个都自动重新拉数据，不用在每个 `(change)` 回调里手写 reload。

**「effect 里能不能写 signal？」**
不要。容易绕成环。我这个 effect 内部 `load()` 确实会 `set(cards)`，但那是在**异步回调**里，不在 effect 的同步依赖追踪范围内，所以不成环。另外 effect 必须在注入上下文里创建（构造函数里就是），组件销毁时自动清理，不用手写 unsubscribe。

**「signal 改数组为什么没反应？」**
signal 默认用 `Object.is` 比较。`arr.push(x)` 之后引用没变，视图不更新。必须 `set([...arr, x])` 或者 `update(a => [...a, x])`。

**「`@for` 的 `track` 写错会怎样？」**
`track` 是 Angular 判断"这条还是不是原来那条"的依据。用 index 的话，删掉中间一条会让后面所有项的身份错位——DOM 被复用到错误的数据上，表现是输入框里的内容跟着串位、动画乱跳。用稳定的 `item.id`。`@for` 相比 `*ngFor` 是编译期内建控制流，不再是结构型指令，`track` 从可选变成**必填**。

**「响应式表单 vs 模板驱动？」**（`card-form-page.ts:66`）
响应式：表单模型写在 TS 里、同步创建、能直接单测、校验集中可组合，复杂表单（联动、动态增删字段）只能用它。模板驱动：结构写在模板里、异步创建，简单表单省事，一复杂就失控。
`fb.nonNullable.group` 的意义：`reset()` 之后字段回到初始值而不是 null，类型上也不用到处写 `| null`。

**「`patchValue` 和 `setValue` 的区别？」**
`setValue` 要求把**所有**字段都给全，少一个直接报错；`patchValue` 只更新给了的字段。回填编辑表单用 patchValue，但要清楚它不会告诉你漏了字段。

**「拦截器捕获错误后为什么还要 `throwError`？」**（`error.interceptor.ts:34`）
如果这里 `return of(null)` 把错误吞掉，调用方以为成功了、拿到 null 在别处炸，堆栈里完全看不出真正原因。**拦截器负责统一提示，不负责替业务决定这个错误重不重要。**
还有一条：`inject()` 只能在拦截器函数体里调，不能挪进 `catchError` 回调——那时候注入上下文已经没了，直接报错。

**「`err.status === 0` 是什么意思？」**（`error.interceptor.ts:47`）
不是"服务器返回了 0"，是**请求压根没拿到响应**：后端没起、网络断了、或者被 CORS 拦下。这三种可能必须在提示语里说出来，否则排查方向会跑偏。

**「冷 Observable 是什么？为什么我的接口被调了两遍？」**（`card.service.ts:94-99`）
`HttpClient` 返回的是冷 Observable，**没人 subscribe 就不会真的发请求**，subscribe 两次就发两次。所以 `track()` 里的计数不能写在方法体，必须写进 `tap` 的 `subscribe` 回调——那才是请求真正开始的时刻。

**「什么订阅必须手动退订？」**（`cards-page.ts:128`）
HttpClient 的流收到响应会自己 complete，订阅随之结束，不用退。**永不完结的流**才必须退：`interval`、`fromEvent`、路由参数流。用 `takeUntilDestroyed` 或 `async` 管道。**别一律回答"都要退订"**，那是没分清的表现。

**「`inject()` 和构造函数注入的区别？」**（`card.service.ts:29`）
两点：继承时子类不用重复声明父类的一堆依赖；可以在字段初始化和函数里直接用，不受构造函数签名限制。

**「`providedIn: 'root'` 有什么好处？」**
全应用单例，而且 **tree-shakable**——没有任何组件注入过它就会被整个摇掉。写在 NgModule 的 providers 里没这个待遇。

**「`HttpParams` 为什么要写成 `params = params.set(...)`？」**（`card.service.ts:52`）
它是不可变的，每次 `set` 返回新对象。直接调用不接返回值等于没做。`HttpHeaders` 一样。

**「路由这块有什么坑？」**（`app.routes.ts`）
三个，全在这个文件里踩过：
1. `{ path: '', redirectTo: 'cards', pathMatch: 'full' }` —— **漏了 `pathMatch: 'full'`，空路径会前缀匹配到所有 URL**，访问什么都被重定向，整个应用只剩一页。
2. `'cards/new'` 必须排在 `'cards/:id'` 前面。路由从上往下第一个匹配的赢，反过来 `new` 会被当成 id，`Number('new')` 得到 NaN。
3. 通配符 `**` 必须最后，它匹配一切。

**「懒加载拆到什么粒度？」**
`loadComponent` 按路由拆是最稳的默认策略。别过度拆——几十行的组件单独成 chunk，多一次网络往返反而更慢。

**「`snapshot` 和订阅 `paramMap` 怎么选？」**（`card-form-page.ts:85`）
两个路由之间不会互跳（不存在"组件复用、只有参数变了"）时用 snapshot 就够。**存在那种情况必须订阅**——只读 snapshot 的话参数变了组件不重新加载，页面停在旧数据上。典型场景：详情页点"下一条"。这是路由相关最常见的 bug。

**「`<select>` 配异步选项，选中态为什么会丢？」**（`job-tracker` 的 `list-page.html` 有整段注释）
选项是异步拉回来的，绑定值先于选项存在，Angular 找不到匹配的 option 就把选中态清成空。修法是选项到位后再设值，或者用 `[compareWith]` 指定比较函数。

**「Angular 和 React 你怎么看？」**
Angular 给的是一整套（DI、路由、表单、HttpClient 全在框架里），约定强、上手陡，但团队大了不用为选型吵架；React 是库，生态自选，灵活但每个团队的技术栈都不一样。**变更检测这一层现在反而收敛了**——Angular 走 signal，React 在推 compiler，两边都在往"精确知道什么变了"走。

## 4. job-tracker —— 90 秒讲法

> 求职申请追踪器：管我投出去的每份申请，增删改查 + 筛选 + 搜索 + 分页 + 状态时间线 + 按状态聚合。

2. **为什么再写一个**：它和 concept-tracker 是**成对**的——同一类问题、两套后端。一套手写 SQL，一套 ORM。被问"你怎么选技术栈"，我有两个亲手写过的实现可以对着说。
3. **Django 的核心是 `models.py` 那一份声明**：表结构、迁移脚本、校验规则、admin 界面、序列化器全从它长出来。`admin.py` 三十行换来一个能用的后台——这是 Django 最直观的价值。
4. **DRF 三种视图写法都用了**：标准 CRUD 用 `ModelViewSet`（一个类换六个接口），统计和健康检查用 `@api_view` 函数视图。判断标准：**接口形状是标准 CRUD 就用 ViewSet，不是就别用**，把报表塞进 ViewSet 会拧巴。
5. **性能上做了两件具体的事**：列表用 `annotate` 把事件计数压进同一条 SQL 消灭 N+1；统计接口一条 SQL 出全部结果。
6. **测过**：27 个 Django 测试，全绿，其中用 `assertNumQueries` 把 N+1 变成会失败的测试。

## 5. Django / DRF —— 追问与答案

**「ORM 和手写 SQL 你怎么选？」**（这是这两个项目存在的全部理由，必须答得比别人厚）
- 手写 SQL：每条 SQL 长什么样一目了然，性能可控；代价是重复代码多、改表要手动同步好几处、没有迁移。
- ORM：开发快、迁移自动化、跨数据库；代价是**会写出人看不见的低效查询**，N+1 是最常见的。
一句话版本：**Go 让你看得见每一条 SQL，Django 让你不用看。** 选哪个取决于团队的时间贵还是机器的时间贵。
再补一刀：ORM 不是"不能写复杂查询"，是**复杂到一定程度后 ORM 表达式比 SQL 还难读**，那时候就该用 raw SQL 或者视图。

**「QuerySet 是惰性的，什么时候才发 SQL？」**
迭代、切片取具体值、`len()`、`bool()`、`list()` 的时候。所以 `qs = Model.objects.filter(...)` 这一行不发查询，可以继续链式加条件。这也是 `get_queryset` 写成**方法**而不是类属性的原因（`views.py:67`）——类属性在模块导入时求值一次，之后所有请求共用同一个 QuerySet 对象，会踩到结果被缓存住不刷新的坑。

**「N+1 是什么？三个工具怎么选？」**（`views.py:79-95`）
列表返回 20 条，每条再查一次关联数据 = 1 + 20 条 SQL。
- `select_related` —— 一对一 / 多对一，用 JOIN，一条 SQL 拿回关联对象
- `prefetch_related` —— 一对多 / 多对多，发第二条 SQL 再在 Python 里拼
- `annotate` —— 要的是**聚合值**（计数、求和），不需要关联对象本身
我这里只要"每条申请有几个事件"这个数字，所以用 annotate 最省。`serializers.py` 里专门写了注释：如果改成 `SerializerMethodField` 里调 `obj.events.count()`，20 条记录就是 20 条 COUNT 查询——那就是 N+1 的教科书写法。

**「你怎么保证 N+1 不会回来？」**
`assertNumQueries`。把"这个接口只能发 N 条 SQL"写成断言，有人后来加了一个 `SerializerMethodField` 就会**测试变红**。这是防 N+1 最有效的手段，比 code review 靠谱。

**「`annotate` 之后为什么还要 `order_by`？」**（`views.py:95`）
annotate 聚合会给查询加 `GROUP BY`，而 Django 判断"这个 QuerySet 有没有排序"时认为带 group_by 的查询**不再继承 `Meta.ordering`**。少了这句，分页器抛 `UnorderedObjectListWarning`，翻页真的可能漏数据或重复。**annotate 之后要自己把排序写回去。**

**「聚合前为什么要 `.order_by()`（空参数）？」**（`views.py:206`）
反过来的坑。`Meta.ordering` 的默认排序会被带进 GROUP BY 语句，变成 `GROUP BY status ORDER BY created_at`，而 `created_at` 不在分组里，数据库要么报错要么给出多余的分组。**聚合前先清排序**——非常经典也非常隐蔽。

**「`Meta.ordering` 为什么要带上 `id`？」**（`models.py:109`）
只按时间排，同一秒创建的两条记录在分页时可能一会儿第 1 页一会儿第 2 页，翻页漏数据。**分页排序必须包含一个唯一字段兜底**——这是通用规则，不限于 Django，任何分页接口都适用。

**「`null=True` 和 `blank=True` 的区别？」**（`models.py:81-87`）
`null` 是数据库层允许 NULL，`blank` 是表单/校验层允许留空。数字和日期两个都给；**字符串字段只给 `blank=True`**，因为"空字符串"和"NULL"两种空值并存的话，每次查询都要写两遍条件。

**「`on_delete` 为什么是必填的？」**
因为没有安全的默认值。`CASCADE` 跟着删、`PROTECT` 阻止删除、`SET_NULL` 置空、`SET_DEFAULT` 给默认值。Django 强制你想清楚"父没了子怎么办"——这个字段以前有默认值，后来改成必填就是因为默认 CASCADE 删掉过太多数据。

**「`CheckConstraint` 和代码校验，为什么两层都要？」**（`models.py:116`）
数据库约束由数据库保证，**绕过 ORM 直接写 SQL 也破不了**；代码校验给用户友好的错误信息。前者保证数据永远不脏，后者保证体验。只有前者用户看到的是 500，只有后者迟早会有一条脏数据从别的入口进来。

**「`Model.save()` 会调 `clean()` 吗？」**
**不会。** `full_clean()` 才会，而 `save()` 不自动调它。这是 Django 一个反直觉的地方——很多人以为 model 上写了校验就万无一失。DRF 走的是 serializer 校验，不依赖 `clean()`。

**「`auto_now` 有什么坑？」**（`models.py:95-100`）
`auto_now_add` 只在 INSERT 时写、`auto_now` 每次 `save()` 刷新，但**两个都是在 Python 层赋值的**，所以 `QuerySet.update()` 这种直接发 UPDATE 的写法不会触发。要批量更新也刷时间，得自己带上 `updated_at=timezone.now()`。
连带一条：`save(update_fields=[...])` 时必须把 `updated_at` 显式列进白名单（`views.py:168`），否则 auto_now 会被挡掉。

**「serializer 的校验顺序？」**
字段级 → `validate_<字段名>` → `validate(self, attrs)` 对象级。**PATCH 时 `attrs` 里只有客户端传了的字段**，跨字段校验直接读 `attrs["x"]` 会 KeyError，要么从 `self.instance` 取旧值，要么用 `.get()`。这条是 DRF 最常见的线上事故来源之一。

**「PUT 和 PATCH 的区别？」**（`views.py:49`）
PUT 语义上是"用这份数据整体替换"，没传的字段应当回到默认值；PATCH 是"只改我传的这几个"。DRF 的实现是 `partial_update` 把 serializer 的 `partial=True` 打开，于是所有字段变成非必填。

**「为什么"改状态"要单独一个端点，不用 PATCH？」**（`views.py:135`）
"改状态"是一个有业务含义的**动作**，附带写时间线、可能触发通知。做成独立端点语义清楚，也方便单独加权限。这是 REST 里"资源"和"动作"的取舍——纯资源风格表达这类操作会很别扭。

**「事务用在哪？」**（`views.py:107`）
"存申请"和"写第一条时间线"必须要么都成要么都不成。少了 `transaction.atomic`，第二步抛异常会留下一条没有初始事件的申请——**"一半成功"的数据是最难查的一类 bug**。

**「`perform_update` 里旧值为什么要在 `save()` 前取？」**（`views.py:124`）
`serializer.instance` 在 `save()` 之前还是数据库里的旧对象，save 之后被**就地改成新值**。写成 save 之后再读，事件里 from 和 to 会一模一样。

**「中间件顺序有讲究吗？」**（`config/settings.py:73`）
洋葱模型，和 Go 那边一个思想。`CorsMiddleware` 必须**最靠前**——它要在其他中间件（尤其是可能提前返回响应的）之前把 CORS 头加上，否则错误响应会缺头，浏览器只报一句 CORS 错误，真正的错误信息你根本看不到。

**「CORS 和 CSRF 有什么关系？」**
**没关系，方向相反。** CORS 是浏览器的同源策略，限制"你的页面能不能读别的源的响应"；CSRF 防的是"别人的页面借用你的 cookie 发请求"。一个是读的限制，一个是写的防护。顺带：CORS 是**浏览器**的限制，不是服务器的——用 curl 请求同一个接口完全没这回事。这条两个项目都能指着代码讲。

**「`DEBUG=True` 上生产会怎样？」**
异常页会把完整的 traceback、settings 变量、SQL 查询全吐给访问者，包括 SECRET_KEY 和数据库连接信息。而且 `ALLOWED_HOSTS` 在 DEBUG 下不生效。

**「`USE_TZ=True` 为什么是唯一正确的选择？」**
数据库里统一存 UTC，展示时按用户时区转。存本地时间等着跨时区和夏令时切换出灵异 bug。concept-tracker 那边我手写 SQL 也是同一条规矩（`sqlite.go:206` 统一 `time.Now().UTC()`）——**这不是框架的事，是数据的事**。

**「换 Postgres 要改什么？」**
`settings.py` 的 `DATABASES` 一段，业务代码一行不动——这是 ORM 最实在的好处。SQLite 的限制要知道：写是全库串行的、没有 `ALTER COLUMN`、并发写会 `database is locked`。

## 8. 必须主动说的局限

被问"这个项目有什么不足"时照着说，主动说是加分，被问出来是减分：

- **没有鉴权**。真实系统要加中间件校验 token，并在 `get_queryset()` 里按 `request.user` 过滤——那一处是最容易漏的地方。
- **搜索框没防抖**，每敲一个字发一次请求。
- **前端类型是手写的**，靠人肉和后端同步。规模一大就该上 `drf-spectacular` + `openapi-typescript` 自动生成——**这一点 Periplus 是做对了的，可以顺势把话题带过去**。
- **没有乐观锁**。两个人同时编辑，后提交的覆盖先提交的。正解是加 version 字段或 `If-Match` + ETag。
- **删除是硬删**，没有 `deleted_at`。
- **concept-tracker 没有迁移**，建表语句内联；多人协作必须上 golang-migrate。
- **SQLite**，写全库串行。
- **没有前端单元测试**，只验到编译通过 + 手点一遍全流程。

## 9. 技能栏其余四个词的口径（2026-08-18 已定：留着）

`MongoDB`、`Jenkins`、`AWS`、`Cloudflare` —— 本机零代码，**决定是留在简历上**。既然留着，被问到就必须用概念答住，下面是最低限度：

- **MongoDB**：文档模型 vs 关系型；什么时候选它（schema 频繁变、嵌套结构天然、写多读少的日志类）；聚合管道；索引；4.0 之后有多文档事务但成本高。**诚实版**：我实际项目用的是 PostgreSQL，Mongo 是了解层面的。
- **Jenkins**：pipeline as code（Jenkinsfile）、agent/node、stage；和 GitHub Actions 的差别是**自托管 vs 托管**——Jenkins 插件生态大、能进内网、但要自己维护机器和插件升级。**我实际做过的 CI 是 GitHub Actions**（Beyz 那条 bullet），照实说。
- **AWS**：EC2/S3/IAM 的基本模型；Beyz 那个邮件服务就是部署到 EC2 上、PM2 守护、GitHub Actions 推的——**这条其实有出处，别答成零经验**。
- **Cloudflare**：CDN、DNS、Workers（边缘运行时）、缓存规则。**诚实版**：了解层面。

**规矩**：这四个词答到"知道它解决什么问题、什么时候选它、和我用过的东西差在哪"为止，**不要装成用过**。被追问细节就说"这条我是了解层面，实际做过的是 X"——这句话不丢人，装用过被拆穿才丢人。

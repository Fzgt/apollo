# 提现：前端能保证什么，不能保证什么

> 🔴 **必看**。⚠️ 数字口径 Day 1 已审：[#7 · 2,000+ peak QPS](/docs?section=baidu&item=n07-qps)（后端怎么扛住、监控还是压测）· [#8 · 零资损](/docs?section=baidu&item=n08-zero-loss)（对账才是出处、改法三选一）。**这里只讲前端那一层。**

## 30 秒口播稿（改一改就能用）

> 这是个活动期间的提现入口，峰值时整条链路到过两千多 QPS。**前端在这里的职责很窄但很明确：把无效的重复请求挡在发出之前，并且在结果不确定时永远往「失败」那边说。**
>
> 具体三件事：请求发出到响应回来这段窗口里锁住同一笔提现，不让用户狂点产生第二个请求；幂等 key 在前端生成并存进 sessionStorage，**这样用户刷新页面重试，后端还能认出这是同一笔**；超时和网络中断一律按失败提示、引导去查提现记录，绝不显示成功。
>
> **但我很清楚前端锁挡不住跨设备、跨标签页和刷新重试——真正的正确性来自后端的幂等键和数据库约束。前端减少的是无效负载，不是提供保证。**

## 一、防抖 vs 节流 vs 请求锁（常混，要分清）

| | 行为 | 场景 |
|---|---|---|
| **Debounce** | 多次触发，**最后一次之后 n 毫秒才执行** | 搜索框输入、resize |
| **Throttle** | **每 n 毫秒最多执行一次**，匀速 | scroll、mousemove |
| **请求锁** ✅ | **第一次立即执行，之后到响应回来为止全部拦掉** | 提交类操作 |

**提现按钮为什么不用 debounce**：「最后一次才生效」意味着用户点了 100 次，只有第 100 次在 300ms 后发请求。**用户会觉得「没反应」于是点更多次**——体验和意图完全相反。

> **提交类操作要的是 leading edge（首次立即执行）+ 锁**，不是 trailing edge 的防抖。

## 二、请求锁的两个版本

**朴素版**：一个布尔量，`finally` 里解锁。

```js
let inFlight = false;
async function withdraw() {
  if (inFlight) return;
  inFlight = true;
  try { ... } finally { inFlight = false; }
}
```

**按参数去重版**（更完整——同一笔锁住，不同笔可以并发）：

```js
const inFlightMap = new Map();
async function withdraw(orderId) {
  if (inFlightMap.has(orderId)) return inFlightMap.get(orderId);   // ⭐ 复用同一个 Promise
  const promise = api.withdraw(orderId);
  inFlightMap.set(orderId, promise);
  try { return await promise; } finally { inFlightMap.delete(orderId); }
}
```

> **这个模式叫 Promise 去重（request deduplication），React Query / SWR 内部就是这么做的。** 能点出这一句，说明你知道自己在复现一个通用模式而不是随手写的。

## 三、幂等 key：前端能做的最有价值的一件事

**前端锁挡不住三件事**：网络超时后的自动重试、用户在不同设备/标签页同时操作、**页面刷新后再点**。

**所以真正的保证必须来自后端幂等**：每个提现请求带一个幂等 key，后端把已处理的 key 存起来，**同 key 重复请求返回上次结果，不再执行**。

**前端的配合是关键的一半**：

| 做法 | 为什么 |
|---|---|
| **提前生成 key**（进入页面就生成，不是点击时） | 点击时生成的话，用户点两次就是两个 key |
| **存 sessionStorage** | ⭐ **刷新页面后还是同一个 key**——否则刷新重试在后端看来是一笔新提现 |
| 每次调用都带上它 | |

> **后端拿这个 key 建唯一索引兜底**：第二次插入直接违反唯一约束。**这和 [Stripe webhook](/docs?section=beyz&item=n02-stripe-events)、[Beyz 的 cron 去重](/docs?section=beyz&item=d4-service) 是完全同一个模式：把不变量放在数据层。**

## 四、defensive fallback：金融场景的错误处理原则

> ⭐ **默认失败，只有明确成功才展示成功。**

| 结果 | 怎么处理 |
|---|---|
| **明确失败**（4xx/5xx、业务错误码） | 显示错误 + 可重试按钮 |
| **不确定**（超时、网络中断、发出去没响应） | ⭐ **按失败处理**，但措辞是「网络异常，请稍后查看提现记录」——**不要直接说「失败了」**（后端可能已经处理了） |
| **明确成功**（2xx + 业务成功码） | 展示成功 |

**为什么「不确定」要按失败处理**：

- 显示失败 → 用户会去重试 → **重试有幂等 key 兜底，不会真扣两次**
- 显示成功 → 如果实际没到账，**用户以为提了但钱没来，直接炸锅**

> **两种错法的代价不对称**——这就是为什么默认要往失败那边倒。**这句话是这一节的题眼。**

## 五、被追问时的分工表（必须能一口气说清）

| 问题 | 答法 |
|---|---|
| **用户绕过前端锁会怎样？** | **能绕，而且很容易**——F12 直接调接口。所以前端锁只是减少无效请求，**正确性靠后端幂等键 + 唯一索引 + 数据库事务 + `WHERE balance >= ?` 的余额不变量** |
| **2000 QPS 是你测的吗？** | 不是。后端监控里的整条链路量级，**前端不「扛」QPS，前端「贡献」QPS**。详见 [#7](/docs?section=baidu&item=n07-qps) |
| **零资损怎么保证的？** | **对账的结论，不是我测的**。资损防线分五层，前端只在第一层。详见 [#8](/docs?section=baidu&item=n08-zero-loss) |
| **前端还能做什么？** | 令牌桶/漏桶限流（没 token 时按钮 disabled）、活动开始瞬间的排队/验证码削峰、**但这些都是体验优化不是正确性保证** |

> **一句话收尾**：**前端减少无效负载，后端提供正确性。** 这句话把整条 bullet 的分工讲干净了。

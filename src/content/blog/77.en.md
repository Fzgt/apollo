---
title: 'The Next.js vs SPA Performance Ledger: Gains in First Paint and Bundle Size, Losses in TTFB and Server Cost, Interaction Unchanged'
---

> **Q: Everything Next.js does — is it actually faster than a regular SPA?**

Metric by metric. "Faster" is not a single answer.

## Clearly better

**Time to first paint (FCP/LCP).** The most certain win. An SPA has to go HTML → JS bundle → execute → fetch data → render: at least three serial round trips before anything shows. Next ships HTML that already has content — one round trip and there is a picture on screen.

**Bundle size.** The code for static components is never sent. Article content, sidebars, footers — all bundled in an SPA, none of it bundled with RSC. The gap widens with heavy libraries (markdown parsing, syntax highlighting, date libraries): they cost literally nothing on the client.

**Data-fetching waterfalls.** In an SPA a component only fires its request once it mounts, so nested components produce a serial waterfall. In a Server Component the data is fetched on the server, close to the database, and can run in parallel.

**SEO.** Goes without saying.

## Clearly worse

**Server cost.** An SPA is static files; put them on a CDN and they cost close to nothing. Next renders on the server for every request — Node processes to run, concurrency to absorb. That is real operational cost and complexity.

**The floor on in-app navigation.** In an SPA the page component is already in the bundle, so switching routes is a local render — zero network requests are achievable. Next has to fetch an RSC Payload on every navigation, which is always one round trip. `<Link>` prefetches to hide it, but on a bad connection the SPA is genuinely faster.

**TTFB.** The server has to finish rendering before it emits the first byte, which is slower than returning static HTML. Streaming softens it, but the baseline is slower.

## Not clear either way

**Interaction latency (INP).** Barely a framework question — it comes down to how your client code is written. RSC cuts total JS, so in theory the main thread carries less, but the things that actually stutter are those few complex interactive components, and they stay just as slow.

**Hydration got cheaper, but it did not go away.** Client Components still hydrate. If your app is interaction-heavy — a complex editor, a dashboard — Client Components dominate and RSC has little left to win.

## The trade at the bottom of it

RSC **moves work from the client to the server**. For "lots of content, little interaction" that is free money — product listings, blogs, docs sites, marketing pages: most of the content is static, so moving it is pure gain.

For interaction-heavy apps, most components have to be Client Components anyway. There is little to move, so you pay the server cost without buying much back. Figma, Notion, browser IDEs — a plain SPA is the more sensible choice.

## In one line

**Next does not make every app faster; it makes "content apps" faster, and the price is server complexity and cost.** If your app only works after login, has effectively no SEO requirement, and is mostly interaction, an SPA with good code splitting is probably the better answer.

# How scheduling works

<img width="1556" height="132" alt="Image" src="https://github.com/user-attachments/assets/349b525f-dd50-4148-aaea-cfebb5d7b077" />

> In one sentence: update tasks are sorted into two queues by whether they should be handled now (delayed vs ready); ready tasks are scheduled into the next macrotask through `MessageChannel`; execution is a loop that checks after each piece of work whether it should yield the main thread, resuming in the next macrotask if it does; and synchronous updates skip the whole apparatus and just run to completion.

## 1. A picture to start with

Think of the scheduler as a restaurant's ticket system. React keeps producing update tasks (customers wanting to order); the scheduler decides who gets served first, when, and how long the work can run before the server takes a breath — that is, before it yields so the browser can handle interaction.

---

## 2. Step one: two kinds of task

For every incoming task, the scheduler computes two things:

- **`timeout`** — how much slack the task gets. The more urgent, the shorter.
- **`startTime`** — the earliest moment the task may begin (`currentTime + delay`, i.e. now when there is no delay); "the latest it must finish" is `expirationTime = startTime + timeout`.

The split:

| Case | Where it goes |
|---|---|
| `startTime` has not arrived yet (e.g. "handle this in five minutes") | **`timerQueue`** — delayed tasks, the waiting list |
| `startTime` has arrived (it should run now) | **`taskQueue`** — ready tasks, the to-do list |

---

## 3. Step two: the ordering inside `taskQueue`

Anything in `taskQueue` also gets an **`expirationTime`** (`startTime + timeout`):

- **Smaller means more urgent.**
- `taskQueue` is sorted by it, so the most urgent sits at the front and the closest to expiring is handled first.

---

## 4. Step three: how the page stays responsive — the core mechanism

### The problem

If the scheduler ran each task synchronously the moment it arrived, the page would freeze and buttons would stop responding.

### The answer

Schedule the work into the **next macrotask** instead of running it immediately:

```javascript
// create a MessageChannel (two ports, port1 and port2)
const channel = new MessageChannel();
const port = channel.port2;
channel.port1.onmessage = performWorkUntilDeadline; // the function that does the work

// calling this fires port1.onmessage in the next macrotask
port.postMessage(null);
```

**Why `MessageChannel` and not `setTimeout`?**

- `postMessage` is inherently asynchronous and runs on the next turn of the event loop
- It is faster and more precise than `setTimeout(fn, 0)`: a single `setTimeout(fn, 0)` has no floor, but once timers nest more than 5 levels deep the browser clamps them to at least 4ms, and the Scheduler is exactly that kind of self-rescheduling loop; `MessageChannel` has no such clamp

> When the notes say "ready tasks are scheduled immediately but run in a macrotask", this is what they mean: not "run right now", but "queue it and arrange for the next macrotask to run it".

---

## 5. Step four: what workLoop actually loops over

The function attached to `port1.onmessage` (`performWorkUntilDeadline`) is a loop, and each pass does this:

1. **Check `timerQueue`**: has anything reached its `startTime` (`startTime <= currentTime`)? If so, move it into `taskQueue`. This step is `advanceTimers`.
2. **Take the most urgent task from `taskQueue`** and run its callback.
3. **Keep asking "do I still have time?"** (`shouldYieldToHost`). If not — a few milliseconds have gone by and the browser needs to handle that click — **stop**, mark the work unfinished, and continue in the next macrotask.
4. Once the tasks are done, check `timerQueue` again for the next one due to wake.

This is **time slicing**: instead of computing every update in one go, cut it into small pieces and leave the browser room to handle interaction in between.

---

## 6. What the task actually *is*

**The scheduler neither knows nor cares what a task contains.** It is a pure queue-and-timer: whoever hands it a callback gets that callback invoked when it is due.

The real rendering work — building the fiber tree, diffing — is a callback that **another React module, the reconciler**, hands to the scheduler:

| Path | Goes through the scheduler? | Function (the name changed between versions ⚠️) |
|---|---|---|
| **Concurrent / async updates** | ✅ queued by the scheduler | React 16–18: `performConcurrentWorkOnRoot`<br>React 19+ (after the refactor): `performWorkOnRootViaSchedulerTask` |
| **Sync updates** (e.g. `flushSync`) | ❌ never touches the scheduler; a dedicated sync queue | `performSyncWorkOnRoot` |

> ⚠️ **Version note**: React later did a "root scheduler" refactor, adding `ReactFiberRootScheduler.js` and renaming `performConcurrentWorkOnRoot` to `performWorkOnRootViaSchedulerTask`. The role is identical; only the name and the file moved. If you cannot find the old name in a newer source tree, search for the new one.

---

## 7. Inside the scheduler (steps ④b, ⑤, and ⑥ of the full diagram below)

```
an update task is produced
    │
    ▼
compute startTime / expirationTime
    │
    ├─ startTime not reached → timerQueue (delayed)
    │
    └─ startTime reached → taskQueue (ready, sorted by expirationTime)
                              │
                              ▼
                    fire port.postMessage(null)
                              │
                        (in the next macrotask)
                              ▼
                    run performWorkUntilDeadline
                              │
                              ▼
                          the workLoop:
                    ┌─────────────────────────────┐
                    │ 1. advanceTimers             │
                    │    (timerQueue → taskQueue)  │
                    │ 2. take the most urgent task │
                    │ 3. run its callback          │
                    │ 4. shouldYieldToHost?        │
                    │    yes → stop, resume next   │
                    │          macrotask           │
                    │    no  → on to the next task │
                    └─────────────────────────────┘

[a completely separate path]
sync updates (flushSync and friends) → skip all of the above → call performSyncWorkOnRoot directly → run to completion
```

## How lanes relate to the scheduler

> Lanes live entirely in the reconciler — specifically inside the `react-reconciler` package.
> The lane mechanism never enters the scheduler, and the scheduler knows nothing about lanes. What crosses the boundary is the *result*: the priority a lane computes is translated into an ordinary priority number the scheduler understands, and that number does affect how urgent a timeout the task is given. The scheduler only ever sees the translation, never the lane itself.

```

③ scheduleUpdateOnFiber() → ensureRootIsScheduled() — [reconciler]

        ↓

④a call performSyncWorkOnRoot directly    ④b the scheduler enters the picture for the first time:
   (the scheduler is never involved)          call scheduleCallback(priority, callback)

                                                ↓
```

## ⚠️ Addendum: this `workLoop` is not the reconciler's `workLoop`

The `workLoop` in section 5 belongs to the **Scheduler package**, and what it loops over are **tasks** in `taskQueue`.
The reconciler package has its own identically-named pair, looping over **fiber nodes**:

```js
// react-reconciler/src/ReactFiberWorkLoop.js
function workLoopSync() {
  while (workInProgress !== null) {
    performUnitOfWork(workInProgress);
  }
}

function workLoopConcurrentByScheduler() {
  while (workInProgress !== null && !shouldYield()) {
    performUnitOfWork(workInProgress);
  }
}
```

**So the line at the end of section 5 — "this is time slicing" — needs qualifying.** The Scheduler yields *between tasks*; what actually cuts **a single render** into pieces is the reconciler's `workLoopConcurrentByScheduler`, and that is only reached under particular lanes. The decision logic is in #23.

### The conclusion that matters: going through the Scheduler ≠ being time-sliced

`DefaultLane` — everyday `setState`, `setState` inside `setTimeout` or `.then()` — genuinely is an async lane and genuinely queues in the Scheduler. But once the Scheduler wakes it, the reconciler computes `shouldTimeSlice === false` and takes `renderRootSync` → `workLoopSync`: **rendered in one go, never yielding partway**.

The Scheduler only decides *when rendering is allowed to start*. Whether that render is sliced is a separate decision the reconciler makes from the lane.

# How useState and useReducer relate

## The short answer

**`useState` is a special case of `useReducer`.** Same hook list and dispatch machinery underneath; React just supplies a very simple default reducer so you do not have to write one.

```javascript
const [count, setCount] = useState(0);
// behaviourally close to:
const [count, setCount] = useReducer(basicStateReducer, 0);
```

**Do not lean too hard on the word "sugar":** in the source, `mountState` / `updateState` and `mountReducer` / `updateReducer` are two separate implementations, and `useState` has one optimisation `useReducer` does not — eager state. See the last section.

---

## React's built-in default reducer (it really is in the source)

```javascript
function basicStateReducer(state, action) {
  return typeof action === 'function' ? action(state) : action;
}
```

- `action` is not a function → return it as the new value
- `action` is a function → call it with the current `state` and use the result

That is why both `setCount(5)` and `setCount(c => c + 1)` work. The check is hiding in that ternary — React wrote it for you.

---

## The core difference: `action` means different things

| | The action behind useState | useReducer's action |
|---|---|---|
| Who decides its shape | React, hard-coded in `basicStateReducer` | You, in your own reducer |
| Typical form | A value, or a function | Usually an object, `{type: 'xxx', ...}` |
| Does React check the type? | Yes (`typeof action === 'function'`) | No — it is forwarded to your reducer untouched |
| Can you define the structure? | No, only "value" or "function" | Yes, your reducer decides how to read it |

---

## Side by side

```javascript
// useState: no reducer, just pass a value
const [count, setCount] = useState(0);
setCount(5);
setCount(c => c + 1);

// useReducer: write the reducer, dispatch "what happened"
function reducer(state, action) {
  switch (action.type) {
    case 'increment':
      return { count: state.count + 1 };
    case 'reset':
      return { count: 0 };
  }
}
const [state, dispatch] = useReducer(reducer, { count: 0 });
dispatch({ type: 'increment' });
```

---

## Which one to reach for

- **Simple, independent state with one way to change it** (a toggle, an input value) → `useState`
- **Complex state, several fields that move together, convoluted update logic** (forms, shopping carts) → `useReducer`. Separating "what happened" from "how the new state is computed" keeps the logic in one place and easier to maintain.

---

## Where they actually differ: eager state

Asked in an interview whether `useState` is sugar over `useReducer`, "yes" only gets you half the marks. The difference is here.

When you call `setCount(x)`, React runs `basicStateReducer` up front — **before scheduling the update** — to compute the next value (this is the eager state optimisation). If that value is `Object.is`-equal to the current state, the update is never scheduled at all and the component does not re-render.

```javascript
const [count, setCount] = useState(0);
setCount(0);   // unchanged → nothing is scheduled, no re-render
```

React can only do this because the reducer for `useState` is its own: guaranteed pure, and guaranteed never to change. The reducer you hand to `useReducer` is yours — React cannot assume it will be the same function on the next render, and will not run it early on your behalf, so there is no equivalent shortcut. Dispatching an action that does not change the state still goes through scheduling (React bails out a layer further down once it sees the state is unchanged, but that is already further than `useState` went).

(`mountState` and `mountReducer` are two independent functions in the source; neither calls the other.)

# ⑤ 一次精确到帧的排查

> **简历原句**
>
> **Traced a freeze on every color change to the fog**: **rebuilding it as a new object made every material in the scene recompile its shader in one frame**. **Reusing one fog object and setting its color removed it**.
>
> ---
>
> 把每次换配色时出现的卡顿定位到了雾：把它当成新对象重建，会让场景里每一个材质在同一帧内重新编译着色器。改成复用同一个雾对象、只改它的颜色，卡顿就消失了。

「雾属于材质的程序标识」和那个统计每帧新建管线数的探针都不在简历上。探针是这条唯一的证据来源，被追问「你怎么确认是重编译」时必须拿它出来。

## 这条要讲清什么

这是 WinterFell 几条里唯一一个完整的观察、假设、验证、修复链条，而且每一环都有东西可指。三分钟版建议主讲这条。

它最值钱的地方不是根因有多刁钻，是验证那一步：不是「我觉得是着色器编译」，是「我写了个探针数了一下」。

## 现象

那个冻结精确地落在换关那一刻，最后画出来的那一帧还停在旧配色上，而 HUD 已经更新了。

最后半句是最好的线索：画面卡在旧配色，而界面上的分数已经更新了，说明游戏逻辑在正常跑，堵住的是渲染这一侧。

能讲出这个观察，说明你是从症状往回推的，不是猜的。面试里讲这条一定要从这句开始。

## 根因链条

三层，缺一层都讲不通。

第一层，雾当时是写成 JSX 标签的，参数里带着调色板的颜色。关卡换色时参数变了，React 认为要换一个新对象，于是重建了一个雾。

第二层，雾属于材质的程序标识。换了雾对象，等于场景里每一个材质的程序标识都变了。

第三层，渲染器必须为每个材质重新编译着色器，全场景的编译挤在同一帧里，于是冻结。

## 第二层是技术核心

先说什么是着色器：GPU 上实际跑的小程序，决定每个像素最终什么颜色。它需要先编译成 GPU 能执行的指令，这个编译是有成本的。

再说程序标识：渲染器不会为每个物体单独编译一份着色器，它会把需要同一份着色器的材质归成一类，这个分类的依据就是程序标识。

关键在于哪些东西会进这个标识。有没有雾会进，光源的数量和类型会进，用了几张贴图会进。而材质的颜色、透明度、位置、旋转都不进——改这些只是换一个传给着色器的数值。

判据是：它改变的是着色器的代码本身，还是只是传给着色器的一个参数。

雾会改变着色器代码。有雾的时候，着色器末尾要多一段根据距离把颜色混向雾色的计算，所以有雾和没雾需要两份不同的编译产物。而换掉雾对象，渲染器认为这是一个不同的雾配置，于是场景里每个材质的标识全变了，全部要重编译。

一句话题眼：换 uniform 便宜，换程序标识要重编译。

## 验证：数一数每帧编译了多少

探针的思路写在它的文件头里：WebGPU 在某个材质和几何体的组合第一次被绘制时编译渲染管线，而这个编译就发生在需要它的那一帧；如果慢帧正好就是编译帧，那这个卡顿就是着色器编译。

做法是包住设备创建渲染管线的那个接口，按帧记录这一帧编译了几条管线、这一帧耗时多少。两条曲线对上，猜想就变成了结论。

这一步是这条 bullet 最值钱的地方：不是我觉得是着色器编译，是我数了。面试时要强调这个转变——从猜测到证据。这句话本身就是这条 bullet 的价值主张。

## 修法

把雾从 JSX 标签改成用一个 ref 存住的对象：第一次才创建，之后每次换色只调它的颜色设置方法。组件卸载时如果场景当前的雾还是这个对象就摘掉它。

对象的身份不变，程序标识就不变，不重编译，冻结消失。

## 英文怎么说

三句最容易说错的。题眼一句是 changing a uniform is cheap; changing the program key means every material recompiles。最好的那条线索说 the last drawn frame was stuck on the old palette while the HUD had already moved on — so the logic was fine and the render side was blocked。从猜测到证据说 I didn't assume it was shader compilation — I counted pipelines built per frame, and the slow frames were the compile frames。

其他常用词：卡顿是 hitch、freeze 或 jank，换配色是 palette change，距离雾是 distance fog，重建对象是 recreate the object，对象身份是 object identity，就地修改是 mutate，着色器编译是 shader compilation，渲染管线是 render pipeline，程序标识是 program key，传给着色器的参数是 uniform，重新编译是 recompile，探针是 probe，包住某个接口是 wrap，慢帧是 slow frame，归因是 attribute。

## 30 秒回答

> 有个卡顿每次都精确地落在关卡换色那一刻。追下去发现是雾：它当时是写成 JSX 标签的，换色时整个雾对象被重建，而雾属于材质的程序标识的一部分——换掉它等于让场景里每一个材质同时失效，渲染器在一帧之内把它们全部重新编译了一遍。我写了个探针数每帧编译了多少条渲染管线，确认了慢帧就是编译帧。修法是把雾提到 ref 里只创建一次、之后只改颜色。

## 一句话答法（完整版）

> 症状是卡顿精确落在换色那一刻，而且卡住的那帧画面是旧配色但 HUD 已经更新了，说明逻辑在跑、堵的是渲染侧。根因是雾当时写成了 JSX 标签，换色时 React 重建了雾对象；而雾会改变着色器代码本身，它属于材质的程序标识，换掉它等于让全场景材质同时失效，渲染器在一帧里重编译了所有材质。我写了个探针包住管线创建接口、按帧统计编译数量，确认慢帧就是编译帧。修法是把雾提到 ref 里只创建一次、之后只改颜色——对象身份不变，程序标识就不变。
